## Problem

Teammates share one working tree with the lead. Five incidents across PT-75 and PT-79
(2026-09-02 to 2026-09-04): a reviewer switched the shared tree to main mid-review (twice); a
reviewer reverted another writer's uncommitted file; a bare `git commit` swept another writer's
staged deletions into an unrelated commit; two rounds of phantom-red test results from running a
suite against a co-writer's half-written files. Every one is "someone else's uncommitted state
leaked into my view". Every fix so far has been a rule in the spawn brief, and rules decay because
each spawn relearns them.

## Ruling (team-lead with the user, 2026-09-04)

**Invariant (user, 2026-09-04): one branch per issue, `feature/<id>-<slug>`, that every agent
integrates on; it gets exactly one PR to main, at merge time.** All agent-to-agent integration
happens on that branch via origin; nothing else about an issue ever reaches origin or a PR.

**Every teammate works in its own git worktree at that branch's tip.** Git will not check the same
branch out in two worktrees, so a teammate's worktree sits at the feature tip in a detached or
throwaway local state, commits there, and pushes fast-forward to `feature/<id>` on origin. The
local scaffolding branch a worktree creates (`worktree-<name>`) is never pushed and never gets a
PR. The lead's tree stays on the feature branch and pulls. One-writer-per-file remains, because
it is what keeps the pulls conflict-free.

1. Mechanism, per the Claude Code docs (worktrees.md, sub-agents.md, agent-teams.md, checked
   2026-09-04): the Agent tool's `isolation: "worktree"` is documented for one-shot subagents only,
   not for persistent teammates. The documented in-session route for a teammate is the
   `EnterWorktree` tool (once per session; creates `.claude/worktrees/<name>/` on a new branch
   `worktree-<name>`). Worktrees branch from the repo's default branch unless the setting
   `worktree.baseRef: "head"` is set — it must be, so a teammate starts from the feature branch
   tip. Uncommitted changes are never carried into a fresh worktree. Gitignored files needed for
   builds (dashboard `node_modules`) are copied in via a `.worktreeinclude` file next to
   `.gitignore`. Hooks resolve `${CLAUDE_PROJECT_DIR}` to the main checkout; `cwd` follows the
   worktree. Whether SendMessage and the shared task list keep working from a worktree is
   undocumented (the mailbox is process-level, so expected yes) — the spike verifies it.
2. Every spawn brief's first instruction is `EnterWorktree`; the agent definitions carry it so it
   is identity, not a brief. Hand-off protocol (WORKFLOW.md → Sha-pinned hand-offs): commit by
   pathspec, `git pull --rebase origin <feature-branch>` before starting a step,
   `git push origin HEAD:<feature-branch>` fast-forward only on completion, report the sha. The
   lead's tree stays on the feature branch and pulls; the lead verifies against
   `origin/<feature-branch>`.
3. The `temp/` hand-off buffer is per-tree and gitignored, so cross-teammate hand-offs go through
   commits or messages, never temp/ files. temp/ remains a per-agent scratch area.
4. Shared-machine resources (ports, `cairn serve`, the OTel receiver) are unaffected by tree
   isolation; PT-81 owns those.

**Fallback if the spike fails:** reviewers only in worktrees, writers shared, rules baked into the
agent definitions.

3. `.claude/settings.json` sets `worktree.baseRef: "head"`; `.worktreeinclude` added **naming the
   directory** (`scripts/cairn/dashboard/node_modules/**`, not `**/node_modules/**` — a `**/`
   pattern does not reach into a wholly-ignored directory); `/start-feature`, `/finish-feature`
   and `/merge-pr` skill text updated; WORKFLOW.md → Team coordination and Sha-pinned hand-offs
   updated, including that **the lead never enters a worktree** (isolation blocks `git -C` and any
   command whose cwd resolves to the main checkout, and cannot be disabled).
3a. A teammate's `run_tests.py --gate` run is recorded in the **main checkout's**
   `test-runs.jsonl` with `who` populated, not the worktree's copy (the runner and the PostToolUse
   hook resolve different roots today).
3b. `snapshot_real_state` resolves the metrics paths from `CLAUDE_PROJECT_DIR` when set, so
   PT-100's guard still watches the main checkout's real files from inside a worktree.
4. A test asserts the shared block is present and identical across all agent files.
5. **Invariant enforced, not advised:** `/finish-feature` and `/merge-pr` check that origin holds
   exactly one branch for the issue (`feature/<id>-*`), no `worktree-*` branch, and exactly one PR
   for the issue; either skill fails loudly otherwise. Covered by a test with a fake remote.

## Interaction with the OTel receiver (PT-78), found at PT-79 review

The receiver resolves the issue from the checkout it runs in, and a detached HEAD resolves to
`main`. Under this ruling every teammate worktree is detached; the receiver is started by the
SessionStart hook from the main checkout (`${CLAUDE_PROJECT_DIR}`), which stays on the feature
branch, so attribution is unaffected — but the spike must confirm the receiver's cwd is the main
checkout and not a worktree, and TRACKER.md must say so.

### @architect — 2026-09-08

**Gate 1 ruling — PT-82.** Read today at `code.claude.com/docs/en/worktrees` (the `docs.claude.com` path 301-redirects there). Three mechanism claims in the 2026-09-04 body are stale, and one seam is broken in a way the body does not anticipate.

**(a) Corrections to the body's mechanism, each cited.**
1. **`EnterWorktree` is not once-per-session.** "Once in a worktree, Claude can switch directly to another one under `.claude/worktrees/` by calling `EnterWorktree` with the target path; the previous worktree stays on disk untouched." Entering a path *outside* `.claude/worktrees/` always prompts, and no permission rule suppresses it.
2. **`worktree.baseRef: "head"` is relative to the caller's HEAD, not the lead's.** "Inside a worktree, `head` resolves to that worktree's `HEAD`, not the main checkout's." It also cannot be set to a branch name. So a teammate's worktree is pinned to whatever HEAD was at entry; later lead commits arrive only by pull, which is what item 2 of the body already requires.
3. **`.worktreeinclude` will not deliver `node_modules` with a `**/` pattern.** Only files that match *and are gitignored* are copied, and for a wholly-ignored directory a `**/` pattern reaches inside only when the first name after `**/` is a name in that directory's path. `node_modules/` is ignored wholesale (`.gitignore:28`), so the pattern must **name the directory**: `scripts/cairn/dashboard/node_modules/**`, not `**/node_modules/**`. AC3 is amended to that literal.
4. **Confirmed as the body has it:** hooks keep `${CLAUDE_PROJECT_DIR}` at the main checkout while the hook input JSON's `cwd` follows the worktree; `.claude/worktrees/` is already gitignored (`.gitignore:10`).
5. **New, and it constrains the whole design:** isolation enforcement blocks any Bash command whose working directory resolves to the main checkout, any `git -C` / `--git-dir` / `GIT_DIR` / `cd`-then-git redirect into it, and any command whose shape it cannot parse — **"You can't turn this check off."** Consequence to state in WORKFLOW: **the lead never enters a worktree.** A lead inside one could not merge, verify against the main checkout, or run `git -C`. It also ends the reviewer habit of `git -C <main> show` — reviewers verify from `origin/<feature-branch>`, which works from a worktree because `.git` is shared.

**(c) The recording seam is broken today, measured.** `run_tests.py` derives its records path from **its own file location** (`SCRIPT_DIR.parent.parent`, deliberately, so fake-engine-root copies self-record), while `.claude/hooks/test_run_record.py` reads and patches `$CLAUDE_PROJECT_DIR / process/cairn/metrics/test-runs.jsonl` (L158–159). In a worktree those are **different files**: the runner writes a `who: null` record into the worktree's copy, the hook finds nothing to patch in the main checkout's copy and falls back to scraping — so a teammate's gate run is recorded twice, in two files, and never attributed. `cairn loop-stats` reads the main checkout's copy.
**Ruled fix, in this order.** (i) Set `CAIRN_TEST_RUNS_FILE` (the existing override, `run_tests.py:284`) in `.claude/settings.json`'s `env` block. (ii) If that value cannot be made repo-relative there, `run_tests.py` prefers `$CLAUDE_PROJECT_DIR` **only when `--gate` is present** — a fake-engine-root test copy never passes `--gate`, so that discriminator is exact and leaves the deliberate file-location default intact. Do **not** make the preference unconditional; it would redirect test-copy records into the real file.

**(c2) PT-100's guard goes vacuous in a worktree.** `helpers.py` resolves the real metrics paths from the test file's own location, so from a worktree it snapshots the *worktree's* `process/cairn/metrics/`, which the daemon never writes — the guard would pass while the main checkout's real file, the thing it exists to protect, is unwatched. Rule: `snapshot_real_state` resolves the metrics directory from `CLAUDE_PROJECT_DIR` when set, falling back to the current derivation, and qa adds a test that a worktree-shaped layout still snapshots the main checkout's paths.

**(b) Spike (AC1) — numbered, on a FRESH spawn; the three live teammates finish this milestone on the shared tree.** Lead: 1. set `worktree.baseRef: "head"` in `.claude/settings.json` and add the `.worktreeinclude` literal from (a)3. 2. commit and push the feature branch so its tip is on origin. 3. spawn one new qa teammate. Teammate, reporting each result: 4. run `EnterWorktree`; report the worktree path and branch name. 5. `git rev-parse HEAD` — must equal the feature tip from step 2. 6. `SendMessage` to the lead — confirms the mailbox works from a worktree. 7. read the shared task list — confirms task tools work. 8. `ls scripts/cairn/dashboard/node_modules | head` and build the dashboard — confirms `.worktreeinclude`. 9. `python3 scripts/cairn/run_tests.py -p "test_gate_head.py" --gate red`; report **which** `test-runs.jsonl` gained a line and whether `who` is populated — this is (c)'s go/no-go. 10. commit by pathspec, `git pull --rebase origin <feature>`, `git push origin HEAD:<feature>`, report the sha. 11. attempt `git -C <main checkout> status` and report the refusal verbatim — confirms (a)5. Lead: 12. verify the sha on `origin/<feature>` from the main checkout.
**Go/no-go:** steps 5, 6, 7, 10 and 12 must all succeed. Step 8 failing means fix the `.worktreeinclude` pattern and repeat 8 only. **Step 9 landing in the worktree's file is not a no-go** — it is (c)'s known defect and the fix ships with this feature; it is a no-go only if neither (c)(i) nor (c)(ii) makes it land in the main checkout.

**(d) Receiver cwd.** The SessionStart hook starts the receiver from the main checkout because hook commands resolve through `${CLAUDE_PROJECT_DIR}`, which does not follow the worktree. The spike confirms it by reading `--status` and checking the resolved repo root is the main checkout, not `.claude/worktrees/…`; TRACKER.md records the fact and the reason a detached worktree HEAD would otherwise attribute to `main`.

**(e) AC5 invariants** — `/finish-feature` and `/merge-pr` each fail loudly unless origin holds exactly one `feature/<id>-*` branch, **zero** `worktree-*` branches, and exactly one open PR for the issue. qa's fake-remote test covers all three, each with its own red mutation; a `worktree-*` branch reaching origin is the failure that matters, since it is the one that would produce a second PR.
