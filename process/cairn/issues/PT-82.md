## Problem

Teammates share one working tree with the lead. Five incidents across PT-75 and PT-79
(2026-09-02 to 2026-09-04): a reviewer switched the shared tree to main mid-review (twice); a
reviewer reverted another writer's uncommitted file; a bare `git commit` swept another writer's
staged deletions into an unrelated commit; two rounds of phantom-red test results from running a
suite against a co-writer's half-written files. Every one is "someone else's uncommitted state
leaked into my view". Every fix so far has been a rule in the spawn brief, and rules decay because
each spawn relearns them.

## Ruling (team-lead with the user, 2026-09-04)

**Invariant (user, 2026-09-04): one branch per issue, `feature/<id>-<slug>`, that every agent
integrates on; it gets exactly one PR to main, at merge time.** All agent-to-agent integration
happens on that branch via origin; nothing else about an issue ever reaches origin or a PR.

**Every teammate works in its own git worktree at that branch's tip.** Git will not check the same
branch out in two worktrees, so a teammate's worktree sits at the feature tip in a detached or
throwaway local state, commits there, and pushes fast-forward to `feature/<id>` on origin. The
local scaffolding branch a worktree creates (`worktree-<name>`) is never pushed and never gets a
PR. The lead's tree stays on the feature branch and pulls. One-writer-per-file remains, because
it is what keeps the pulls conflict-free.

1. Mechanism, per the Claude Code docs (worktrees.md, sub-agents.md, agent-teams.md, checked
   2026-09-04): the Agent tool's `isolation: "worktree"` is documented for one-shot subagents only,
   not for persistent teammates. The documented in-session route for a teammate is the
   `EnterWorktree` tool (once per session; creates `.claude/worktrees/<name>/` on a new branch
   `worktree-<name>`). Worktrees branch from the repo's default branch unless the setting
   `worktree.baseRef: "head"` is set — it must be, so a teammate starts from the feature branch
   tip. Uncommitted changes are never carried into a fresh worktree. Gitignored files needed for
   builds (dashboard `node_modules`) are copied in via a `.worktreeinclude` file next to
   `.gitignore`. Hooks resolve `${CLAUDE_PROJECT_DIR}` to the main checkout; `cwd` follows the
   worktree. Whether SendMessage and the shared task list keep working from a worktree is
   undocumented (the mailbox is process-level, so expected yes) — the spike verifies it.
2. Every spawn brief's first instruction is `EnterWorktree`; the agent definitions carry it so it
   is identity, not a brief. Hand-off protocol (WORKFLOW.md → Sha-pinned hand-offs): commit by
   pathspec, `git pull --rebase origin <feature-branch>` before starting a step,
   `git push origin HEAD:<feature-branch>` fast-forward only on completion, report the sha. The
   lead's tree stays on the feature branch and pulls; the lead verifies against
   `origin/<feature-branch>`.
3. The `temp/` hand-off buffer is per-tree and gitignored, so cross-teammate hand-offs go through
   commits or messages, never temp/ files. temp/ remains a per-agent scratch area.
4. Shared-machine resources (ports, `cairn serve`, the OTel receiver) are unaffected by tree
   isolation; PT-81 owns those.

**Fallback if the spike fails:** reviewers only in worktrees, writers shared, rules baked into the
agent definitions.

## Interaction with the OTel receiver (PT-78), found at PT-79 review

`main`. Under this ruling every teammate worktree is detached; the receiver is started by the

**Post-verdict delta 1 — the dist gate is unsatisfiable here, and the fix is right, but it needs three guards or it stops being a gate.** Verdict @e13553e stands; no other axis is re-reviewed.

**Verified.** `scripts/cairn/dashboard/package.json` was last committed at **037e6aa** (02:54:30) and `dist/` at **b08a572** (01:17:12), so ancestry says stale and `check_dist_freshness.py` exits 1. The package.json change is **`"build": "vite build"` → `"build": "node ./node_modules/vite/bin/vite.js build"`** — the build's *invocation*, which cannot alter its output, and the spike measured the rebuild byte-identical @156993b.

**The root cause is sharper than "false-stale".** The script's own design note calls false-stale "safe, visible, self-correcting: rebuild, commit". That self-correction assumes **a rebuild always produces a commit**. A no-op rebuild produces nothing to commit, so ancestry never advances and no honest commit satisfies the gate. This is the first source change that touches how the build is *invoked* rather than what it *emits*, and it is the case the design did not anticipate.

**The fix is the right shape:** ancestry is a proxy for "does the committed dist match what this source builds"; rebuilding and comparing is that predicate directly. Adopt it, with three guards.

1. **A differing rebuild fails, and names the differing files.** Never fall back to pass on any comparison outcome other than byte-identical.
2. **An absent or failing toolchain fails, it does not skip.** If `node`/`npm` is missing or the build exits non-zero, the result is `stale` with a reason saying the gate could not verify — not a pass. A hard gate that silently evaporates on a machine without node is PT-24's defect exactly: the chain that never ran and never blocked.
3. **The rebuild goes to a temp dir outside the repository** and is removed afterwards. Building anywhere inside the tree would dirty it, and could trip both this gate and PT-100's real-state guards.

**Determinism is the assumption, and it fails safe.** The fix rests on vite emitting reproducible output for this project; the spike observed that once, which is not proof. It does not need to be: a non-deterministic rebuild produces a *difference*, and by guard 1 a difference fails. So non-determinism costs a false-stale — the direction the script already chose as safe — never a false-pass.

**Rejected alternative, stated so it is not re-proposed:** narrowing the source pathspec so `package.json` no longer counts. It is hand-maintained, and `package.json`'s **dependencies** genuinely do change build output — an exclusion that is right for `scripts.build` is wrong for the file, and the next dependency bump would pass a stale dist silently. Rebuild-and-compare has no such split.

**Cost is bounded:** the rebuild runs only when ancestry already says stale, so the common path is unchanged.
