## Problem

Flagged in PT-35's design ruling (architect, 2026-08-23): `DEFAULT_COLUMNS` (cairn.py:57) and `BOARD_COLUMNS` (board-logic.js:466) are the same list maintained in two languages, and PT-35 duplicates the `+ ["cancelled"]` append rule across both. Drift is silent.

## Acceptance criteria

- [x] A guard that fails loudly on drift (e.g. a test comparing the JS export to the Python list via the fixture/API), or a single-source derivation — architect ruling picks
- [ ] Zero behavior change

### 0. Ground truth — the duplication is differently shaped than the issue says

Correcting my own PT-35 flag, which is what filed this issue:

- **The base list has exactly two canonical copies**, as filed:
  `DEFAULT_COLUMNS` (cairn.py:57) and `BOARD_COLUMNS` (board-logic.js:466).
- **The append rule has THREE copies, not two:** `cairn.py:1277`
  (`list(DEFAULT_COLUMNS) + ["cancelled"]`), `tests/test_snapshot.py:33`
  (the same expression, re-typed), and `boardColumns` in board-logic.js. Two
  of those three are in the *same language*, which means part of this problem
  needs no cross-language machinery at all (§ 2, Part A).
- **`cairn.py:644` is NOT a third copy** — `board.setdefault("columns",
  list(DEFAULT_COLUMNS))` is *derived* from `DEFAULT_COLUMNS`, so it cannot
  drift. I nearly wrote it up as one; it isn't. It is, however, dead — see
  § 5.
- **`board.js:1006`'s `listColumns` is unrelated** — it builds the *list
  view's table* columns (`id`/`repo`/`title`/…), not board statuses. Not a
  drift surface.

**Test-gate topology, which decides where the guard lives:**

- `finish-feature/SKILL.md` runs the **Python suite unconditionally** and the
  JS suite only `if command -v node`. `TEMPLATE_DECISIONS.md` (2026-08-20)
  states it outright: *"Node is a soft prerequisite for the JS test suite
  only… the Python suite stays the hard gate."*
- Python tests run from `scripts/cairn`, and `tests/helpers.py` already
  exposes `CAIRN_DIR`/`CAIRN_PY` path constants, so a test can resolve
  `board/board-logic.js` without any cwd assumption.
- A convenient accident: `["backlog", "todo", …]` is **valid JSON in both
  languages**, so a source-text extraction can be `json.loads`-ed exactly
  rather than hand-split on commas.

### 1. Rejected: a single-source derivation. This has to be a guard.

Three variants, each rejected on a measured constraint rather than taste:

- **Codegen / build step** (Python generates the JS list). The "no build step"
  contract is explicit in board-logic.js's own header comment and in
  `TEMPLATE_DECISIONS.md`. Introducing one to deduplicate five strings is the
  tail wagging the dog.
- **Serve the list at runtime and have the client consume it.** This is the
  tempting option, because `cairn.py:644` *looks* like the server already
  ships it. It does not: `config["board"]` is assembled at :646 and **read
  nowhere** — `build_board_payload` (:1318) doesn't carry it, and board.js
  never reads `state.board.columns` (grepped both, at this sha). Wiring it
  would be a **behaviour change**, which AC2 forbids: any project whose
  `config.yml` customizes `board.columns` is ignored today and would start
  rendering differently. It also drags in a second defect — `board.js:622`
  renders `STATUS_LABELS[status]` with **no fallback**, so an arbitrary
  configured status would print `undefined` as a column header (the collapsed
  chip at :762 *does* have a fallback; the header doesn't).
- **A shared JSON file both sides read.** A third artifact, and the browser
  would need a fetch to read it — reintroducing the network dependency under a
  function that is deliberately synchronous and offline-capable.

**Ruling: a guard across the language boundary; genuine single-sourcing
*within* each language.** Cross-language single-sourcing costs a build step
this project has refused on the record. Intra-language duplication has no such
excuse and should simply be removed.

### 2. The two-part ruling

**Part A — collapse the Python-side duplication (a real derivation, not a guard).**

Add next to `DEFAULT_COLUMNS` in cairn.py:

```python
STATUS_ORDER = DEFAULT_COLUMNS + ["cancelled"]   # fresh list, evaluated at import
```

Then `cairn.py:1277` becomes `status_order = STATUS_ORDER`, and
`test_snapshot.py:33` becomes `STATUS_ORDER = cairn.STATUS_ORDER`. Three
Python-side copies of the append rule collapse to one. Values are identical, so
AC2 holds trivially. (`DEFAULT_COLUMNS + [...]` builds a new list, so
`STATUS_ORDER` is not an alias of `DEFAULT_COLUMNS` and mutating one can't
touch the other.)

**Part B — one cross-language guard, in the Python suite, reading the JS as text.**

New `scripts/cairn/tests/test_column_parity.py`. It reads
`board/board-logic.js` as a **file**, extracts the two literals, and compares
them against `cairn.DEFAULT_COLUMNS` / `cairn.STATUS_ORDER`.

> **Judgment call (JC1) — the guard lives in Python, and there is only one of
> it.** Python is the hard gate: it runs in every environment, so a
> Python-side edit by someone without Node still trips the guard, and so does
> a JS-side edit. Putting it in the JS suite instead would leave the most
> likely drift direction uncovered. **Reading the JS as text rather than
> executing it via `node` is the load-bearing half of this call** — shelling
> out to `node` would make Node a hard prerequisite of the Python suite and
> silently reverse a recorded 2026-08-20 decision. Cost: the guard compares
> *source literals*, not *evaluated values*, so it cannot see through a
> future dynamic construction of the list — which is exactly what § 3.3
> exists to catch. Reversal: mirror the same assertions in the JS suite as
> well; I'd accept both, I just don't think a second copy of a guard earns
> its maintenance when the first one's coverage is already total.

### 3. What the guard asserts — and the requirement that makes it a guard rather than decoration

1. The `BOARD_COLUMNS` literal extracted from board-logic.js equals
   `cairn.DEFAULT_COLUMNS`.
2. The literal appended inside `boardColumns` (`…concat(["cancelled"])`),
   composed onto the base, equals `cairn.STATUS_ORDER` — so the **append rule**
   is covered, not just the base list. A guard on the base list alone leaves
   the thing PT-35 actually duplicated free to drift.
3. **If either pattern fails to match, the test FAILS**, with a message naming
   what it looked for and where. Never `skip`, never silently pass, never
   fall back to a default. A guard that stops guarding when the code is
   refactored is worse than no guard, because the green tick now asserts
   something false. The regex must be anchored on the declaration
   (`var BOARD_COLUMNS = [...]`), not a bare bracket search that could match
   any array in the file.

**Both extraction failures and mismatches must be reachable in tests** — see
reds 3 and 4 in § 6. This is the same discipline QA applied to the
cross-realm fixture on PT-28 and to C13's fixture on PT-33: prove the thing
*can* fail, or you have only proved that it runs.

### 4. AC2 — zero behaviour change

The only production edit in this issue is `cairn.py:1277`, replacing an
inline expression with the constant that has the identical value. Everything
else is a new test file plus a new module constant. Nothing in board-logic.js
or board.js changes at all.

`test_snapshot.py` is edited, so PT-35's replacement gate applies verbatim:
**the diff to that file must be single-sourcing only — no expected value may
change.** Any moved expectation is a stop-and-escalate, not a test update.

### 5. Outside PT-36's scope — `board.columns` is documented, user-editable, and inert

Not part of this ruling's mechanism; recording it because it is the most
consequential thing I found and it needs a **product decision, not an
architectural one**.

`board.columns` appears in `process/cairn/config.yml` (checked in, hand-typed:
`columns: [backlog, todo, in-progress, in-review, done]`) and is documented in
`TRACKER.md:70`. It is **read by nothing** — cairn.py sets it at :644 and never
consumes it; it never reaches the client. So a user who reads the tracker doc,
edits that key, and reloads the board sees no change. That is worse than
drift: it is a documented feature that silently does nothing.

Three options, none of which I should pick unilaterally:

1. **Implement it** — real feature work, needs the `STATUS_LABELS` fallback
   from § 1 and a decision about what a custom column set means for the
   cancelled toggle.
2. **Remove it** from `config.yml`, `TRACKER.md` and the `setdefault` — honest,
   small, but shrinks a documented surface and touches a doc I own.
3. **Leave it and document it as reserved.**

Note that a parity guard is the **wrong** tool here: `config.yml` is
user-editable and every downstream project instantiated from this template has
its own, so asserting it matches `DEFAULT_COLUMNS` would fire on a legitimate
customization. Recommend a separate issue. Flagging rather than deciding.

### 6. Red-first test surface — QA's lane

**Python (`scripts/cairn/tests/test_column_parity.py`):**

1. extracted JS `BOARD_COLUMNS` == `cairn.DEFAULT_COLUMNS`
2. extracted append composes to == `cairn.STATUS_ORDER` (cancelled last)
3. **negative control — the comparison can actually fail.** Run the extractor
   against an inline JS source string whose list differs, and assert the
   parity check reports a mismatch. Without this, a parity test that always
   passes looks identical to one that works.
4. **extractor sanity — a missing/renamed declaration FAILS loudly.** Feed a
   source with no `BOARD_COLUMNS` declaration and assert the test raises with
   a message naming the symbol, rather than returning `None`/`[]` and quietly
   comparing empty to empty (§ 3.3).
5. `cairn.STATUS_ORDER == ["backlog","todo","in-progress","in-review","done","cancelled"]`
   exactly — a rename or reorder must break a test.
6. `STATUS_ORDER` is not an alias: mutating it does not affect
   `DEFAULT_COLUMNS`.
7. `test_snapshot.py`'s expected values unchanged (§ 4 gate).

**JS suite:** nothing new. board-logic.js is untouched; `board-columns.test.js`
already pins `boardColumns` from the JS side, and this guard pins it to Python.

> **Judgment call (JC2) — I am NOT adding a `STATUS_LABELS`-coverage
> assertion**, though I considered it and the hole is real (§ 1: `board.js:622`
> has no fallback, so a seventh column added tomorrow ships `undefined` as a
> header). It is *intra*-JS drift, not the cross-language drift PT-36 was
> filed for; it needs a regex over an object literal in a third file; and its
> natural fix is a one-line fallback at :622, not a test. Cost: that hole
> stays open until someone files it. Reversal: add red 8 asserting every
> status in `STATUS_ORDER` has a `STATUS_LABELS` key. **Recommend filing the
> `:622` fallback as its own small issue** — say the word and I'll rule it
> into this one instead.
