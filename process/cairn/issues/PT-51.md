### @team-lead — 2026-08-24

Mosko ask (2026-08-24): milestone/major cards are read-only — no field edits, no comments. Read-only was the deliberate 0.7.0 ruling (no second mutation endpoint, no seen tokens for record schemas; mark-done via cairn set). Architect design ruling first: mutation endpoint for records (reusing the issue drawer's seen/403-archived machinery), which fields are board-editable vs CLI-only, and comments on milestone/major files (schema today has no Comments section — cairn comment is issue-only; decide schema + CLI + drawer support together).

### @architect — 2026-08-24

**Ruling — milestone/major cards editable + comments.** Lifts 0.7.0's read-only ruling. One new write endpoint, one widened payload, one shared comment component.

**§1 Endpoint: a new `POST /api/record/<id>`, not a widening of `/api/issue/<id>`.** `find_issue_path` being the only resolver reachable from the issue write path is a **structural** guarantee (PT-3/PT-39), not a runtime check; widening it would convert a structural property into a branch someone can forget. Body is the identical `{seen, patch?, comment?}`. Six behaviours, **in this order** — the order is part of the ruling:
1. `find_record_path(data_dir, id)` — already primary-root-scoped by construction, exactly like `find_issue_path`. `None` → `find_record_in_roots(roots, id)` (new, mirroring `find_issue_in_roots` and under the same contract: used only to tell 403 from 404, **never** to locate a file to write) → `403 read_only_root` or `404 not_found`.
2. `_record_schema_for_path(...) == "issue"` → `400 {"error": "wrong_endpoint"}` naming `/api/issue/<id>`. Without this, the record endpoint becomes a second write path to issues with a different field policy — the exact drift the single-write-path rule exists to stop.
3. `is_archived_path` → `403 {"error": "archived"}`, **before** the seen comparison so it holds regardless of body. Verbatim the issue path's rule; the predicate is already parts-based and already correct for `archive/milestones/` and `archive/majors/`.
4. `seen` missing → `400`; then the **same `with write_lock:`** critical section, `get_seen(path)` (path-generic already — no change), mismatch → `409 {"error": "stale", "current": <fresh record payload>}`.
5. `patch` → field policy (§3) → `apply_patch`, already record-aware (`_is_issue_shaped` keeps `updated` off records, PT-13).
6. `comment` → `append_comment` (§4).
200 returns the fresh record payload, same shape as the 409's `current`; the drawer re-renders from the response exactly as `submitPatch` does for issues.

**§2 No new read endpoint — the board payload widens.** Records already carry `body`, `path`, `archived`, `released`. Add **`seen`** (`get_seen(p)` inside `_stamped_with_body`, exactly as the issue loop already does) and **`comments`**, with `body` becoming the pre-`## Comments` half via the existing `split_comments` — one parser, and for every record that exists today (none has a Comments section) the value is byte-identical to what it is now. The record drawer stays a **lookup** against `state.board` (PT-40 §1 rejected a second read path for data already in the payload); the POST response supplies the post-write refresh. Issues keep carrying no comment bodies in the board payload; records carry them because the record drawer has no second fetch, and records number in the tens. If that ever costs, the answer is a record read endpoint, not a special case here.

**§3 Field policy — board-editable vs CLI-only.**
*Editable in the drawer* — milestone: `name` (text), `status` (select over RECORD_STATUSES), `major` (select over known major ids), `target_tag` (text, nullable), `ga` (select true/false). Major: `status` (select), `health` (select: on-track | at-risk | off-track), `owner` (text, nullable), `target_ship` (text, nullable).
*CLI-only, no editor rendered* — **`id`**: the filename is authoritative, a rename is a `git mv`, and patching `id` alone produces a lint error by construction. (`cairn set` currently permits `id=` because it sits in the field order — a pre-existing CLI foot-gun; the board must not reproduce it, and closing it in the CLI is a separate optional follow-up.) **milestone `kind`**: its legal value is pinned to the id shape by lint and the id is not board-editable, so every use of that control would break the lint.
*Server-side validation* — unknown field for the resolved schema → 400; `id`/`kind` → 400; `status` against `RECORD_STATUSES`; `health` against its enum; `ga` must be a JSON bool. **Cross-record invariants are not enforced at the write path** (one `ga: true` per major, `target_tag == v<N>.0.0`, `major:` resolves) — `cairn check` is the backstop, the same posture `cairn set` and `blocked_by` already take. Rejected alternative: replicating the GA-cap check here — a second implementation of a lint rule, in a surface with nowhere to report a *sibling* record's failure.

**§4 Comments on records — schema, CLI, drawer, one design.**
- **Schema:** milestone and major files may carry a `## Comments` section, **identical format, parser, and author vocabulary** as issues. No second convention. `process/TRACKER.md`'s Milestone file / Major file / Comment format sections say so explicitly. *(Ledger-worthy: this is a schema change.)*
- **Prerequisite engine fix this exposes:** `append_comment` unconditionally sets `frontmatter["updated"] = _today()`. Records have no `updated` field (PT-13 deliberately kept it off them), so the first record comment injects an off-schema key that `dump_frontmatter`'s record branch faithfully emits. **Gate the bump on `_is_issue_shaped(frontmatter)`** — the same guard `apply_patch` already uses. Not a nicety; land it first.
- **CLI:** `cmd_comment` switches `find_issue_path` → `find_record_path` and its error string to "no such record". One line, and it makes `cairn comment` work on milestones, majors, and archived records uniformly — matching what `cairn set` already does. `tests/INTERFACE.md` updated to match.
- **Drawer:** extract the issue drawer's comment log + add-comment box into one `commentSectionEl(record, opts)` taking a submit callback (issue → `/api/issue/<id>`, record → `/api/record/<id>`), used by both drawers — the `issueLinkListEl` precedent: one function at the second use, not the third.

**§5 Read-only computation and the drawer's note.** `renderRecordDrawer` computes `readOnly = record.archived || record.repo !== <primary root id>` — the same disjunction the issue path folds into `read_only` server-side. Read-only → editors suppressed (`inlineField`/`inlineSelect` already take the flag) and no add-comment box. The existing note **must be re-scoped**, since its claim that every record is read-only stops being true: archived → "Archived — read-only on the board; use `cairn set` / `cairn comment`."; foreign root → the cross-root wording; **live primary-root record → no note at all**.

**§6 Sequencing.** PT-48 lands `archived` rendering on record surfaces first; PT-51 then consumes `record.archived` for §5's branch in the same function. Both edit `renderRecordDrawer` — do not run them concurrently.

**§7 Tests to pin.** Server: 200 patch + fresh seen; 409 on stale seen with a record payload in `current`; 403 archived (checked before seen, proven with a garbage body); 403 read_only_root; 400 for an issue id, for `id=`/`kind=`, for a bad status, for a bad health. Comments: `append_comment` on a milestone adds no `updated` key; `cairn comment PT-1.0` succeeds; `split_comments` round-trips a record body. JS: record drawer renders editors for a live record and none for an archived one; the comment box posts to `/api/record/`.

### @implementation-lead — 2026-08-24

Implemented §1–§7 exactly. **Prerequisite (§4) landed first, TDD, own test**: `append_comment`'s `updated` bump gated on `_is_issue_shaped(frontmatter)` (`cairn.py`) — new test `test_append_comment_on_a_record_injects_no_updated_key` (`test_frontmatter_rewrite.py`), red→green before anything else.

**§1 server** — new `POST /api/record/<id>` (`Handler._mutate_record`), a separate route from `/api/issue/<id>`, six checks in the ruled order: `find_record_path` → (miss) `find_record_in_roots` (new, mirrors `find_issue_in_roots`, 403/404 discrimination only) → an issue id → `400 wrong_endpoint` → `is_archived_path` → `403` (before the seen compare, proven with a garbage body) → missing `seen` → `400` → `write_lock` + `get_seen` + `409 stale` with `build_record_payload(...)` as `current` → `patch` → `_validate_record_patch` → `apply_patch` → `comment` → `append_comment`. `200`/`409` both return `build_record_payload` (new: the milestone/major analog of `build_issue_payload`, single-file `O(1)`, reuses a new shared `_release_status` helper so its `released` computation and `build_board_payload`'s milestone loop can't drift onto two answers).

**§2 payload** — `build_board_payload`'s `_stamped_with_body` (majors/milestones) now stamps `seen` (`get_seen`) and `comments`, with `body` becoming the pre-`## Comments` half via the existing `split_comments` — confirmed byte-identical for every record with no Comments section (dedicated test). Issues unchanged (still no `comments` key).

**§3 field policy** — new `_RECORD_BOARD_EDITABLE_FIELDS` (milestone: name/status/major/target_tag/ga; major: status/health/owner/target_ship) is deliberately narrower than the CLI's `_RECORD_FIELD_ORDER`: `id`/milestone `kind` are simply absent from the editable set, so "unknown field" and "id/kind rejected" collapse into one check, not two. New `MAJOR_HEALTH_VALUES` enum validated server-side; `ga` requires a real JSON bool (client-side `<select>` coercion, see below) — no cross-record invariant (GA cap, target_tag shape, major: resolves) re-implemented at the write path, exactly as ruled. Extended `NULLABLE_FIELDS` with `target_tag`/`owner`/`target_ship` so clearing them via the drawer writes `null`, not `""` — same mechanism the issue fields already use, no new one.

**§4 comments/CLI/docs** — `cmd_comment` switched `find_issue_path` → `find_record_path`, error string → "no such record" (regression-tested: still works on a plain issue id). `process/TRACKER.md`: Milestone file / Major file examples now show a `## Comments` section; Comment format section states the shared schema explicitly; API-surface table gained the new endpoint's row and the `/api/board` row's seen/comments note (Six endpoints, was five). `scripts/cairn/tests/INTERFACE.md` gained a "Record mutation (PT-51)" section plus updated `append_comment`/`build_board_payload`/`make_server` entries.

**§5 drawer** — extracted `commentSectionEl(record, opts)` from the issue drawer's own (previously inline) comment log + add-comment box, at the second use (`renderRecordDrawer`) — the `issueLinkListEl` precedent. `opts.mutate` is the submit callback per endpoint (default `apiMutateIssue`; records pass the new `apiMutateRecord`). `inlineField`/`inlineSelect`/`submitPatch` all gained a trailing optional `opts` param (endpoint override + a `boolean` coercion flag for `ga`'s string↔bool DOM boundary) — every pre-existing issue-drawer call site is unchanged (opts omitted, same defaults). `renderRecordDrawer` computes `readOnly = record.archived || (primaryId != null && record.repo !== primaryId)`, renders the schema-appropriate editor set (no editor at all for id/kind), and the note is re-scoped: archived → "Archived — read-only..." wording; foreign-root → cross-root wording; live primary-root record → no note.

**§6 sequencing** — confirmed PT-48's archived-badge work was already on `main` before this branch started; both features' edits to `renderRecordDrawer` landed sequentially, not concurrently.
