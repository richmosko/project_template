### @architect — 2026-08-24

**Mini-ruling — deleting the legacy read leg.** Timing is Mosko's; these are the mechanics. Verified against `scripts/cairn/cairn.py` at 44615b4.

**§1 Keep the helper, collapse it to one glob.** `archived_issue_paths(data_dir)` → `_dir_glob(data_dir / "archive" / "issues")`, body only. Agreed with the lead's instinct: the 8 call sites don't churn again, `scan_data_dir` still needs the path list for its relative-path key shape, and the property that made PT-50 tractable — one place that answers "where do archived issues live" — is worth keeping in reverse. Inlining would trade a one-line future edit for eight.

Three companion deletions, all in the same commit: `find_issue_path` drops its third candidate (`archive/<id>.md`); `_RECORD_SEARCH_SUBDIRS` drops the bare `"archive"` entry; and the new-location-first ordering comments in both become moot — delete them rather than leave them describing a precedence that no longer exists. `_WATCHED_SUBDIRS` needs **no** change (PT-50 already removed bare `"archive"` from it).

**§2 The lint scan survives, with its own helper and stronger text.** Confirmed — silent invisibility of data files is not acceptable, and after §1 this scan is the only remaining reader of the legacy path.

Give the legacy layout its own single definition point, mirroring §1: `legacy_archived_issue_paths(data_dir) -> List[Path]` = `_dir_glob(data_dir / "archive")`, with **exactly two callers** — `check_repo`'s detection scan and `migrate_archive_issues`'s source glob. Those two must never disagree about what counts as legacy: if the lint reports files the migration doesn't move, the error is unactionable.

The error text **must change**. Under PT-50 it meant "lint fails, everything still works"; it now means "the engine cannot see these files". Say that, keep the literal command, and warn about the cascade:

> `N archived issue(s) at the legacy archive/*.md layout are NOT read by the engine -- invisible to the board, to id allocation, and to reference resolution (dangling-reference errors below may be caused by this). fix: scripts/cairn/cairn migrate archive-issues --dry-run   (then re-run without --dry-run)`

Emit it **first** — `errors.insert(0, …)` rather than the current append. A root cause listed after fifteen cascade symptoms gets read last.

**§3 Required companion guard — `cairn new` must refuse, not silently reuse an id.** Everything else the deletion makes invisible degrades loudly or harmlessly. One case does not: `_next_id_candidate` routes through `archived_issue_paths`, so on an unmigrated repo it stops counting legacy ids and `cairn new` re-allocates an id an archived issue already holds — the one invariant the id scheme exists to protect, broken silently, and not repairable by running the migration afterwards.

Guard it at the single allocation path both entry points funnel through — `allocate_and_create_issue` (callers: `cmd_new` and the HTTP `_create_issue`): if `legacy_archived_issue_paths(data_dir)` is non-empty, raise `CairnError` naming the count and the migrate command, before any `O_EXCL` attempt. One non-recursive glob per allocation, on an operation measured in units per day. `_create_issue` must catch `CairnError` and return `400 {"error": "legacy_archive", "message": …}` — today it would surface as a 500. The guard is self-clearing: run the migration and it disappears.

This is a guard, not a rule — it makes the bad state unreachable at the write path instead of asking people to read a lint. The alternative (accept id reuse, rely on `cairn check`) is defensible if you'd rather keep the deletion pure; I'd take the guard.

**§4 `migrate archive-issues` — nothing in its contract changes.** Confirmed. Its source glob is necessarily legacy-aware (that is its job) and now routes through §2's helper; it does not use any engine read path, so the deletion cannot break it; it still does not gate on `check_repo` (it must run on the repo whose lint it is fixing); source-keyed idempotency, all-or-nothing pre-validation, and the differing-destination refusal all stand unchanged.

**§5 Release-note sentence, quotable as-is.**

> **Breaking:** the engine no longer reads flat `archive/*.md` — archived issues must live in `archive/issues/`. Run `scripts/cairn/cairn migrate archive-issues` when you upgrade; until you do, files left at the old path are invisible to the board, to id allocation and to reference resolution, `cairn check` fails naming the count and the command, and `cairn new` refuses to allocate rather than risk re-using an archived id.

**§6 Tests — inverted, not deleted.** PT-50's dual-read tests keep their fixtures and flip their assertions; that is the cheapest way to prove the leg is actually gone rather than merely unused.
- Legacy-only fixture now asserts: `archived_issue_paths()` omits it; `find_issue_path` returns `None` for a legacy-only id; `/api/board?archived=1` omits it; `check_repo` errors with the count + command **as the first error**.
- **Delete** the new-location-first precedence tests (`find_issue_path`, `_RECORD_SEARCH_SUBDIRS`) — they pin an ordering that no longer exists; keeping them green by construction is worse than removing them.
- **New pins:** `cairn new` raises on a legacy-bearing repo and creates nothing (§3), and `POST /api/issue` returns `400 legacy_archive` on the same tree; `check_repo` and `migrate_archive_issues` report the identical file set on a mixed tree (§2's two callers cannot drift); migration still succeeds on a repo whose lint is failing.

**§7 Docs.** `process/TRACKER.md` → Archive: replace PT-50's transition language ("reads accept both layouts") with the single-layout rule plus the invisibility consequence and the guard; `tests/INTERFACE.md`: update the `archived_issue_paths` entry and add `legacy_archived_issue_paths`; the CLI table's `migrate archive-issues` row stays exactly as-is.
