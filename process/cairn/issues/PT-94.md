| Measure | Value |
|---|---|

| Messages mentioning a crossing ("crossed") | 102 |
| Commits per PR | 28, 26, 54, 19; PT-85 has 36 so far, 19 of them tracker/ruling chores |

The work shipped and the defects it caught were real. The cost is in the shape of the loop, not
the code: rulings written before measurement and then amended three to eight times; every
correction relayed by message and crossing another; every teammate turn producing two or three
messages to the lead; every gate re-running the whole suite; tracker comments committed one at a
time; reviewer prose growing without a cap. Each item below names the guardrail and where it is
enforced. Enforcement that is mechanical (a hook, a lint, a script) beats enforcement that is a
sentence in WORKFLOW.

## Directive (user, 2026-09-05) — transcript audit is the method, agent definitions are the fix

Observed live during PT-85: implementation-lead ran the full Python suite, edited a markdown
file, then ran the full suite again — a 155 s run that could not have changed anything. This is
the unit of waste PT-94 exists to remove, and it is not one agent's habit: **audit the PT-85
transcripts for every agent, step by step** (each tool call in order: what ran, what it could
have changed, whether the next step needed it), classify every unnecessary step, and fix the
cause in the agent definitions (`.claude/agents/*.md`, `.claude/roles/team-lead.md`) and the
skills, not in a reminder message. PT-94 is assigned to team-lead: the lead owns the roles and
the workflow surface, and the audit is of the lead's own team.

Transcript sources: `~/.claude/projects/-Users-mosko-Projects-project-template/<session>.jsonl`,
one per agent process (identify by `agentName`/`agentSetting` in the header). The audit records,
per agent and per loop: full-suite runs and what preceded each; module-only runs; edits followed
by a re-run that the edit could not affect; messages sent per turn; idle summaries; commits;
re-reads of files already read this turn; and every "confirm before I proceed" round trip. The
table lands on this issue with the per-step classification, and each class maps to the guardrail
that removes it (A1–F19 above) or to a new one.

## Guardrails (numbered; A–F are themes)

### A. Message traffic
1. **One report per turn, no idle summaries.** Teammates end a turn with one message to the lead
   (sha-first, ≤ 8 lines: paths changed, broken, one bubble-up only if it changes a decision).
   The idle-notification "result" text is suppressed or reduced to a fixed one-liner; task
   assignment/claim echoes and "dropping silently" replies are never sent. Enforced in each
   `.claude/agents/*.md` (a "Reporting" section) and in `.claude/roles/team-lead.md`.
2. **Messages carry pointers, not rulings.** Any decision goes to the issue file first; the
   message says "read PT-NN.md from <sha>". No restating, no reversal by message (WORKFLOW Loop
   discipline rule 1 — make it the agents' message template).
3. **No confirmation round-trips.** "Confirm before I proceed" is replaced by "proceeding on X
   unless the file says otherwise"; the lead answers only when the file disagrees.

### B. Ruling discipline
4. **A ruling cites its measurement or marks the claim unmeasured.** Every factual claim in a
   gating ruling carries the command and output that established it, or the tag `(unmeasured)`;
   unmeasured claims are not operative and cannot gate a build. (This loop: day convention,
   palette family, quote-strip, and the `--follow` premise were all unmeasured and all amended.)
5. **Ruling budget.** One gating ruling per issue plus at most two addenda before the build
   starts; a third addendum means the ruling is reopened as a whole and the pair pauses. Each
   addendum ≤ 15 lines stating only what changes.
6. **Comment budget and shape.** Issue comments ≤ 40 lines; verdicts as a table (axis → result →
   evidence sha); constructions, harness output, and retro prose go to `temp/` (retro) or a
   `review-log` file referenced by path, not into the issue file. `cairn check` warns on a
   comment over the cap.
7. **Pre-registered review, run once.** The reviewer publishes the full checklist (mutation
   matrix, constructions, measurements) before the build; the review runs that list and adds an
   axis only for a defect found. Deltas are batched into one round; a second round is a defect
   in the ruling, recorded as such.

### C. Gate count and suite runs
8. **Four gates, fixed:** ruling in the file → tests red for the right reason → build green +
   pre-registered review → finish (pre-flight, PR). No extra "head-match" or "re-verify" rounds:
   the head-match is a script (`cairn gate --head <sha>` prints `git diff --stat <verified>..HEAD`
   and pass/fail on "docs/tracker only").
9. **One full-suite run per gate, by the gate owner** (qa at tests-red and build-green, the lead
   at finish); everyone else runs the touched modules (PT-93's tiered rule) and cites the sha.
10. **Live measurements are scripted.** Receiver probes (spawn/shutdown/flush/status) are one
    script with fixed output, run once; never ad hoc against the real registry (PT-84's cost
    measurement drained it).

### D. Bloat caps
11. **Test budget per feature.** Each AC gets its tests; every new test names the mutation that
    turns it red (in a docstring); no per-feature test file for a subject that has one — extend
    the subject's file; a feature may add at most N seconds to the suite (N set by PT-93's
    runner; suggest 5 s serial-equivalent) or must pay it back.
12. **Tracker commits at gates, not per comment.** Comments accumulate in the working tree and
    are committed (by pathspec, after the binary `git diff --quiet` gate) at the four gates;
    exception: a ruling or its addendum, which lands the moment it is written.
13. **Operative text caps.** TRACKER/WORKFLOW paragraphs ≤ 8 sentences; rationale to the ledger;
    an "instruction-shaped phrase" lint in `cairn check` for docs (`say why`, `state both`,
    `not just`, `flag`, `worth noting`) that fails on match.
14. **Issue-file size cap** (e.g. 24 KB): over the cap, `cairn check` warns and the lead moves
    review logs out to `temp/` or a linked file at the next gate.

### E. Mechanical enforcement
15. **Pre-commit hook: foreign-hunk guard.** Refuses a pathspec commit of a shared file when the
    working-tree diff of that path contains hunks not authored this turn (implementation: the
    committer runs `git diff --quiet -- <path>` semantics via a small script; the hook blocks on
    non-empty).
16. **`cairn loop-stats <ID>`** prints the per-loop scorecard (commits, chore commits, comments,
    KB added, tests added, suite seconds added, full-suite runs from the transcript dir, messages
    to the lead, $ from `/api/tokens`) and `/finish-feature` pastes it into the PR body with the
    soft caps; exceeding a cap requires a one-line justification in the PR. This is the guardrail
    that makes drift visible instead of remembered.
17. **Agent-definition templates.** Each `.claude/agents/*.md` gains the same "Reporting" and
    "Rulings" sections (A1, A2, B4–B6) so the rules bind at spawn, not by reminder.
20. **Message-cap hook** (from the audit, waste class 3). PreToolUse on `SendMessage`: a message over
    8 lines or 1,200 characters is blocked and the sender is told to put the content in the issue file
    and send the sha (`.claude/hooks/message_cap.py`; tests in `test_message_cap_hook.py`).

### F. Cost
18. **Compaction at gates.** Teammates `/compact` (or are re-spawned) at the build-green gate;
    the architect's context is the heaviest and its cache reads dominate the $ (PT-84: 751M
    tokens). Consider `effort` per agent in WORKFLOW → Tuning Agents for review-only turns.
19. **Idle chatter is paid twice** (the sender's turn and the lead's read): A1 alone removes
    roughly a third of the lead's inbound messages.

## Gate-traffic analysis (consolidated from the retired PT-95, 2026-09-05)

Design decisions in a loop move between agents as commits to the issue file plus messages. PT-85
(the most instrumented loop, 2026-09-05) is the specimen: **20 issue-file commits in 69 minutes
(12:20–13:29)** against 7 code/docs commits and 8 test commits. Each issue-file commit produced
2–3 messages to the lead (the report, an idle summary, often a task echo), and several crossed
in flight. This issue analyses every gate commit, classifies what it changed, and proposes which
gates to drop and which to fold into a fixed four-gate flow.

## Which gates can be ignored (dropped), and which consolidated

**Drop (never a separate commit or message):**
- **The lead's acceptance comment.** A ruling is operative when committed; the lead objects
  within the gate or is silent. The AC amendment that accompanies an accepted ruling is done by
  the ruling's author in the ruling commit (operative text first, ledger second).
- **"Verified by execution" follow-ups.** Measurement belongs inside the ruling; a ruling that
  needs a follow-up to be trusted wasn't ready (PT-94 B4: cite the measurement or tag
  `(unmeasured)`).
- **Provenance records for swept-in hunks.** The binary pre-commit gate (PT-94 E15) makes the
  event impossible; no record needed.
- **Methodology assertions on someone else's pass.** The verdict cites the pass by sha; a second
  comment restating its method adds nothing.
- **Idle summaries and task echoes** (PT-94 A1).

**Consolidate:**
- **Ruling + seam pin + thresholds → one ruling commit.** #2, #7, #15 were three commits over
  27 minutes; the seam and the guard contract are part of what a build needs before it starts.
- **Corrections → the ruling is reopened, once.** Instead of #4/#5/#6 and #11 and #12/#13 as
  separate commits, a builder's measured objection reopens the ruling; the author re-issues it
  as one amended ruling (PT-94 B5: two addenda max, then reopen).
- **Review → one verdict commit.** #17, #18, #21 (and the lead's browser pass #19 as a section
  inside it, or referenced by sha) become one table: axis → result → evidence. Deltas are one
  batch; a second review round is recorded as a ruling defect.
- **Decisions the lead makes (#3, #10, #14) → fold into the ruling or the verdict they answer**,
  as an "accepted / decided" line, not standalone commits.

## The consolidated flow: four gates, each one commit and one message

1. **Ruling** (architect): measured claims, seam/shape, guard thresholds, AC amendments in place;
   lead's decisions folded in as "decided" lines. One commit; message = "read PT-NN.md @ sha".
2. **Tests red** (qa): the commit is the record; no issue comment. Message = sha + counts.
3. **Build green** (implementation-lead): the commit is the record. Message = sha + counts.
4. **Verdict** (architect, with the lead's visual leg as a section): one table, one batch of
   deltas, then finish. Message = "verdict @ sha".

Everything outside these four is either a ruling being reopened (allowed once) or a defect
being recorded — both rare by construction if rulings are measured first.

Expected effect on PT-85's numbers: 21 issue-file commits → ~6 (ruling, reopen ×1–2, verdict,
finish, feature-start/done); messages to the lead ~100 → ~30; the corrections that changed the
outcome (#8, #9, #12, #16) survive because they came from builders measuring, which the
four-gate flow keeps — it removes the paper around them, not the checking.
