TRACKER.md § Sub-issues already promises more than the tree delivers. The engine
has the `parent` field, `cairn new --parent`, a dangling-parent lint, and a
server-side child count — but the board only renders a `↳ <parent>` chip on the
*child*. Close the spec gap on the delivery end.

## Acceptance criteria

- [x] Board: parent cards show a `n/m` child badge (done-children / total-children), per the spec's `2/3` example — computed **client-side in `board-logic.js`**, mirroring `milestoneProgress`'s done/total-over-a-filtered-set shape.
- [x] `sub_issue_count` is **removed** from `build_board_payload`, and its card-chip consumer in `board.js` retired — one producer for "how many children does this have", never two.
- [x] **Child lookup is repo-scoped from the first line** — key on `(issue.repo || "") + "::" + issue.parent`, mirroring `issueMilestoneKey`. A **red cross-repo test lands before any feature test**: two roots each carrying the same issue id must not fuse their child sets into one number shown on both.
- [x] Board drawer: a parent's children are listed (id + title + status), each linking/opening to the child; a child's drawer links back to its parent.
- [x] `cairn show <id>` on a parent lists its children (id, status, title); on a child, names its parent. **Verify the child→parent half against actual output before building it** — `cmd_show` already prints `parent:` via the `ISSUE_FIELD_ORDER[2:]` loop; if it is already satisfied, record that here rather than adding a redundant line.
- [x] Children sort by id (`_id_sort_key` semantics — numeric, not lexicographic). Python reuses `_id_sort_key`; JS needs a new equivalent (`uniqueSorted` is a plain lexicographic `.sort()` today). **Named drift pair** — both sides tested against the same case list (`PT-2` < `PT-9` < `PT-10`).
- [x] Pure DOM-logic goes through board-logic.js with node:test coverage (PT-22 harness); Python-side changes covered by the pytest suite.
- [x] TRACKER.md § Sub-issues updated only if delivered behavior deviates from the spec text.

## Comments

### @architect — 2026-08-22

Design ruling — pre-read at `5be458b`, four questions settled with team-lead
(all four as recommended). Build-ready.

**1. The `n/m` badge is computed client-side, and `sub_issue_count` goes away.**
`/api/board` already carries every issue's `parent` *and* `status`, so the client
has everything the badge needs, and `milestoneProgress` in `board-logic.js` is
already this exact function — done/total over a filtered set. Computing it there
mirrors a tested pattern and lands the logic under the node:test harness the
acceptance criteria require anyway. The server-side `sub_issue_count` aggregate
is then a *second* answer to "how many children does this have" — the duplicated-
expression class the standing Validate criterion exists to catch — so it is
removed rather than left alongside. Its only consumer is one card chip.

**2. Repo-scoping is not a review finding, it is a starting condition.**
`build_board_payload`'s `child_counts` keys off the bare `parent` id with no repo
dimension. That is safe today only because the function runs per-root. Computed
client-side over the aggregated multi-root payload, two sibling repos that each
carry a `PT-14` fuse their child sets into one wrong number, rendered identically
on both repos' cards.

This is the fourth instance of one defect class: `isDraggable`, `issueMilestoneKey`,
and `groupByMilestone` were all the same bare-id-across-roots mistake, and all
three were caught late. So the red cross-repo test lands *before* the feature
tests, not after — that ordering is the acceptance criterion, not a suggestion.

**3. `cairn show` children is a structural change.** `cmd_show` reads exactly one
file via `find_issue_path` and never scans a directory; listing children adds a
scan to a command that has none. Size it accordingly — it is not a print-statement
tweak. The child→parent half of that criterion may already be green: `cmd_show`
prints `parent:` today via the `ISSUE_FIELD_ORDER[2:]` loop. Check the real output
first and record the finding; do not build to a criterion that is already met.

**4. The numeric id sort will exist twice, in two languages, and that is accepted.**
Python has `_id_sort_key` (PT-2/PT-21) — reuse it. JS has no equivalent:
`uniqueSorted` is a plain lexicographic `.sort()`, so `PT-10` sorts before `PT-2`
in anything built on it today. There is no shared-code seam across Python and JS
in this stack, so the duplication is unavoidable. It is therefore recorded as a
**named drift pair** and both sides are tested against the same case list, so the
two implementations cannot silently diverge.

**No TRACKER.md change expected.** § Sub-issues already specifies the badge, the
drawer nesting, and id-ordering — everything PT-25 builds. The final criterion
resolves to "no doc change" unless delivered behaviour deviates from that text.

RECORD-class findings from the architect's review, no action wanted:

- **R1 — brittle assertion.** `test_show_on_issue_with_no_children_has_no_children_section` asserts `"child" not in stdout.lower()` over the whole output — passes only while fixture text avoids the word. Tighter: assert on the section heading. Not worth a commit now.

- **R3 — archived children are invisible.** `cairn show`'s child scan and `build_board_payload` are both `issues/`-only, so a parent with archived children under-reports. Consistent-by-construction, but previously unwritten behavior — now written here.
- **R4 — `cmd_show` matches children against the filename stem** (`args.id`), not the file's own `id:`. Correct per TRACKER.md's filename-is-authoritative rule on a lint-clean tree; noted so a future reader doesn't "fix" it the wrong way.

Also verified by the architect, outside test reach: `/api/issue/<id>` stamps `repo` unconditionally (cairn.py:1531), so the drawer's `parentKeyOf` can't silently produce an unmatched key.
