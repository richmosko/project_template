## Problem

The `main` bucket is the largest bar on the token chart ($528 of $3,230 estimated on 2026-09-04;
8.4% of tokens, 16% of dollars). It is not "team-lead's tokens": the lead's work on a feature
branch is already attributed to that issue, and team-lead is the largest role inside most PT bars.
`main` is everyone's work while the checkout sat on main — filing, releases, status conversations,
planning between loops — almost all lead. Today it reads as an unexplained bar that dwarfs issues.

## Ruling (team-lead with the user, 2026-09-04)

Attribute `main`-branch work **to the milestone active at the record's timestamp**, never to a
single issue. Between-loop work belongs to no issue; forcing it onto the nearest one inflates that
issue arbitrarily. Both sources (PT-77 backfill, PT-78 receiver) apply the same rule.

## Acceptance criteria

1. Schema: a line may carry `issue: "milestone:<id>"` (exact form is the architect's call) for
   main-branch work. A milestone's window is `[creation commit of its file, creation commit of
   the next milestone's file)` — half-open, from `git log --diff-filter=A` on the file, never
   typed by hand; the milestone id comes from the file's `id:` frontmatter, not its filename (the
   first six were committed unprefixed and renamed later); bucket order follows creation
   timestamp, not string sort (`PT-0.10` < `PT-0.5` lexically). A boundary record lands in exactly
   one window by construction. Records before the first milestone file stay in `main`. (Ruled
   81a9d96: issue-derived dates fail — `PT-0.3` has no issues and three milestones share one
   day; archive-time fails — five were archived in one retroactive bulk commit.)
2. `backfill_tokens.py` applies it; the committed snapshot is regenerated once (the file records
   `generated`, so the re-run replaces only `source: transcript-backfill` lines per PT-77 §2).
3. `otel_receiver.py` applies the same rule at flush time using the same function.
4. PT-79's chart shows milestone-overhead buckets as their own bars, labelled by milestone and
   visually distinct from issue bars (a muted variant, like `main` today); drawer unaffected.
5. `/api/tokens` exposes the milestone buckets; caption explains what they are in one clause.
6. Tests for the window derivation (fixture milestones with overlapping/adjacent dates), both
   collectors, and the chart; `cairn check` ok; TRACKER.md documents the rule.

- **Archive-move timestamps are retroactive bookkeeping, not close times.** Measured: **five

**§2 Ruling — the window is `[creation of this milestone's file, creation of the next milestone's
file)`.** Half-open, so a record landing exactly on a boundary belongs to **exactly one** window
(the later one) by construction rather than by a tie-break rule. The newest milestone's window runs
to infinity. Records **before the first milestone creation** (2026-08-20T08:19:49) stay `main` —
that is the pre-cairn answer and the only "outside any window" case AC 1 needs.

This is the only candidate that produces a defensible window for *every* milestone and cannot
overlap. Archive time records when someone got around to filing; creation time records when the
milestone became the open one.

**Deliberate consequence, stated rather than discovered later:** a milestone that is opened but not
yet worked absorbs main-branch work from its creation onward. That is exactly "the milestone active
at the record's timestamp" as the ruling asks, and every alternative either leaves `PT-0.3`
undefined or reintroduces same-day ambiguity.

**§3 Two implementation traps, both measured.**
1. **The filename is not the id.** The first six milestone files were committed as `0.3.md`,

2. **One git call, both paths.** `--diff-filter=A` over `milestones/` *and* `archive/milestones/`

   under its original path.

**§4 Where it lives.** `backfill_tokens.py`, beside PT-87's resolver — one function, both

**§5 Receiver cost — build the table once per flush, never per datapoint.** One `git log`

### @architect — 2026-09-04

**Addendum — the UTC normalisation is right and necessary, but it does not go far enough: the two
collectors disagree on *precision*, not just offset.** Confirmed implementation-lead's finding
(git `%aI` carries the author's local offset; transcript timestamps are UTC) and then measured the
next layer:

- **Backfill side** — a real transcript record: `"2026-08-22T06:38:52.326Z"`. UTC, **with
  milliseconds**.
- **Receiver side** — `_ns_to_iso` emits `%Y-%m-%dT%H:%M:%SZ`: UTC, **no fractional part**.
- **Windows**, after the new normalisation, are also whole-second.

**Demonstrated, not reasoned:** `"2026-08-22T06:38:52.326Z" < "2026-08-22T06:38:52Z"` is **True**
under string compare, because `.` (0x2E) sorts before `Z` (0x5A). So a record 326 ms *into* a
window compares as *before* its own boundary and is attributed to the **previous** milestone. It
only bites when a record falls in the same second as a milestone-creation commit — which is exactly
§8 case 2's boundary test, and exactly the case a fixture written with clean whole-second
timestamps would never expose.

**Ruling: `milestone_for_timestamp` canonicalises its input before comparing** — truncate any
fractional seconds to whole seconds (`ts.split(".")[0] + "Z"` on a `Z`-form input). Verified: the
truncated record then compares `>=` its boundary and lands in the later window, which is what
half-open `[start, next)` requires.

This keeps the function pure and string-only — no `datetime` import, no git awareness — so §4's
design intent holds. Canonicalising *inside* the function rather than at each call site is
deliberate: there are two collectors and they demonstrably emit different precisions, so a
normalise-at-the-caller rule would be one more invariant nobody re-checks when a third caller
appears.

**Required test (extends §8 case 2), because the obvious boundary test misses it:** a record whose
timestamp is in the **same second** as a boundary **and carries a fractional part** must land in
the later window. A boundary test written only with whole-second timestamps passes against the
broken comparison.

**And a standing note for anything else that compares these timestamps:** the two sources' string
forms are not interchangeable. Whole-second UTC `Z` is the canonical form for this codebase's
comparisons; anything entering a comparison gets normalised to it first.

Catching the offset problem *before* wiring the collectors is what made this a ruling rather than a
misattribution discovered on a chart weeks later — the precision layer only surfaced because the
first layer was already fixed.

**Rulings on the refused-flush incident. Two of the three answers correct the diagnosis.**

**(1) It is not "refuse and exit" — the refusal and the exit are unrelated.** Verified in code and
log: `_do_flush` catches the `ReceiverError`, prints `flush refused: …`, and **continues** — the
liveness reap runs on the very next line. The log contains exactly one refusal line and no exit
trace. **The daemon's exit was PT-86's self-stop**: the session registry drained to empty and the
grace window elapsed. That is correct behaviour, and it is the transition-window event flagged when
PT-86 merged — sessions started before the hook line existed are unregistered, so the first
post-merge session to start *and* end drains the registry to zero while others are still live.

**But there is a real defect, and it is a worse one than the reported symptom.** The non-overlap
`raise` sits at the top of `flush()`; `state.pending_min_ns = None` sits at the bottom. A refused
flush therefore leaves the pending buffer **untouched**, so the next flush recomputes the same
earliest datapoint and is refused identically — **for the life of the process**. Not "refuse and
exit" but **"refuse, then never flush again"**: silent after the first log line, with everything
accumulated lost when the daemon eventually stops. One stale datapoint poisons the buffer
permanently. **File as a PT-0.12 follow-up, not this loop.** The fix direction is to drop only the
datapoints that predate the backfill's `generated` and flush the remainder, rather than refusing
the batch whole.

**(2) The operational rule belongs in AC 6, with its reason.** Stop the receiver before re-running
the backfill; restart bare afterwards. State *why*: the regen moves `generated` forward past
datapoints the daemon has already buffered, and PT-77 §2's guard then refuses the batch — correctly,
since those datapoints are inside transcripts the regen just counted, and flushing them would
double-count. Without the reason an adopter cannot recognise the symptom, which today is silent.

**(3) Something was lost, contrary to expectation — one line, as asked.** The guard is batch-level
and keys on the batch's **earliest** datapoint, so datapoints received *after* the regen's
`generated` (2026-09-04T21:44:29Z) were refused along with the older ones — and those are **not**
recoverable from the backfill, which read transcripts at that instant and cannot contain anything
later. They died with the daemon. Bounded by the window between the regen and the exit, and only
for sessions actively exporting in it; unbounded in principle, which is what makes (1) worth
fixing.
