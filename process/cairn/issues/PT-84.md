## Problem

The `main` bucket is the largest bar on the token chart ($528 of $3,230 estimated on 2026-09-04;
8.4% of tokens, 16% of dollars). It is not "team-lead's tokens": the lead's work on a feature
branch is already attributed to that issue, and team-lead is the largest role inside most PT bars.
`main` is everyone's work while the checkout sat on main — filing, releases, status conversations,
planning between loops — almost all lead. Today it reads as an unexplained bar that dwarfs issues.

## Ruling (team-lead with the user, 2026-09-04)

Attribute `main`-branch work **to the milestone active at the record's timestamp**, never to a
single issue. Between-loop work belongs to no issue; forcing it onto the nearest one inflates that
issue arbitrarily. Both sources (PT-77 backfill, PT-78 receiver) apply the same rule.

## Acceptance criteria

1. Schema: a line may carry `issue: "milestone:<id>"` (exact form is the architect's call) for
   main-branch work; the window is the milestone's active dates (first issue started → milestone
   archived/done), derived from the milestone and issue files, not typed by hand. Records outside
   any milestone window stay in `main`.
2. `backfill_tokens.py` applies it; the committed snapshot is regenerated once (the file records
   `generated`, so the re-run replaces only `source: transcript-backfill` lines per PT-77 §2).
3. `otel_receiver.py` applies the same rule at flush time using the same function.
4. PT-79's chart shows milestone-overhead buckets as their own bars, labelled by milestone and
   visually distinct from issue bars (a muted variant, like `main` today); drawer unaffected.
5. `/api/tokens` exposes the milestone buckets; caption explains what they are in one clause.
6. Tests for the window derivation (fixture milestones with overlapping/adjacent dates), both
   collectors, and the chart; `cairn check` ok; TRACKER.md documents the rule.

### @architect — 2026-09-04

Gating ruling. **§1 is measured against all 14 milestones (13 archived + PT-0.12); it eliminates
two of the three candidate sources outright.**

**§1 What the tracker actually offers.** No milestone file carries a date field — 0 of 14.
- **Issue-derived dates fail on coverage and on collision.** `PT-0.3` has **zero issues**, so no
  issue-derived rule can give it a window at all. And issue dates are day-granular: `PT-0.4`,
  `PT-0.5` and `PT-0.5.1` all carry `created: 2026-08-20`, and `PT-0.7.0`/`PT-0.7.1` both span
  `2026-08-23..24`. A main-branch record on 2026-08-20 would match three milestones with nothing
  to choose between them.
- **`updated` stamps are worse:** same day granularity, and they move whenever anything touches
  the issue — several bumped to `2026-09-04` from my own review comments today, which have nothing
  to do with when that milestone was active.
- **Archive-move timestamps are retroactive bookkeeping, not close times.** Measured: **five
  milestones — `PT-0.3`, `PT-0.4`, `PT-0.5`, `PT-0.5.1`, `PT-0.6` — were archived in a single bulk
  commit, `4d1fc14` at 2026-08-26T09:47:07**, while `PT-0.7.0` was archived two days *earlier*.
  Windows ending at archive time would overlap six ways across 2026-08-23.
- **Milestone-file creation commits are clean.** All 14 are unique, strictly increasing, and
  second-granular — including `PT-0.3`. The same-day cases separate cleanly: `PT-0.3` 08:19:49,
  `PT-0.4` 09:03:41, `PT-0.5` 14:39:56, `PT-0.5.1` 20:24:06.

**§2 Ruling — the window is `[creation of this milestone's file, creation of the next milestone's
file)`.** Half-open, so a record landing exactly on a boundary belongs to **exactly one** window
(the later one) by construction rather than by a tie-break rule. The newest milestone's window runs
to infinity. Records **before the first milestone creation** (2026-08-20T08:19:49) stay `main` —
that is the pre-cairn answer and the only "outside any window" case AC 1 needs.

This is the only candidate that produces a defensible window for *every* milestone and cannot
overlap. Archive time records when someone got around to filing; creation time records when the
milestone became the open one.

**Deliberate consequence, stated rather than discovered later:** a milestone that is opened but not
yet worked absorbs main-branch work from its creation onward. That is exactly "the milestone active
at the record's timestamp" as the ruling asks, and every alternative either leaves `PT-0.3`
undefined or reintroduces same-day ambiguity.

**§3 Two implementation traps, both measured.**
1. **The filename is not the id.** The first six milestone files were committed as `0.3.md`,
   `0.4.md`, `0.5.md`, `0.5.1.md`, `0.6.md`, `0.6.1.md` — unprefixed — and renamed later. Read
   `id:` from the file's own frontmatter; a filename-derived key yields `0.3` and `PT-0.3` for the
   same milestone.
2. **One git call, both paths.** `--diff-filter=A` over `milestones/` *and* `archive/milestones/`
   together, taking the earliest add per file; an archived milestone's creation is only visible
   under its original path.

**§4 Where it lives.** `backfill_tokens.py`, beside PT-87's resolver — one function, both
collectors, same precedent. `milestone_windows(repo_root) -> [(start, id)]` sorted ascending, and
`milestone_for_timestamp(ts, windows) -> Optional[str]`. The second is pure and is where the
boundary tests aim.

**§5 Receiver cost — build the table once per flush, never per datapoint.** One `git log`
invocation returns all 14 creations; hold it in `ReceiverState` for the flush. The receiver already
shells to git per export for the branch, so this is within existing cost and runs at most every 30
minutes, not per record.

**§6 `issue` value form: `milestone:<id>`** verbatim from frontmatter (`milestone:PT-0.12`). No new
schema key — AC 1 puts it in the existing `issue` field. **Sorting is a trap: `PT-0.10` sorts
*before* `PT-0.5` lexicographically.** Milestone buckets rank after all issue buckets and before
`main`, ordered by their own **creation timestamp**, never by string compare.

**§7 `/api/tokens` (AC 5): add an explicit `kind` per bar — `"issue" | "milestone" | "main"`.** The
chart must not infer type by string-sniffing the `issue` value; a prefix convention parsed on the
client is exactly the coupling that breaks the next time the form changes.

**§8 Tests (AC 6).** Fixture milestones with adjacent boundaries and a same-second boundary; a
record exactly **on** a boundary asserted into the later window; a milestone with **zero issues**
(the `PT-0.3` shape); a record before the first milestone staying `main`; and the filename≠id case
from §3.1. Pure-function tests on `milestone_for_timestamp`; no git in the unit tests.
