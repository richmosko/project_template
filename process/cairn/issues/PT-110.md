Mosko (2026-09-08): "Dashboard header should be fixed to top and not scroll."

**Where:** the shell header in `scripts/cairn/dashboard/src/App.svelte` (`<header class="flex flex-wrap items-center justify-between gap-4">`, ~L333) — the Sidebar.Trigger + "Project Dashboard" title/subtitle on the left, the theme/settings cluster on the right. It renders before the route switch, so it is shared chrome on both the Dashboard and Issue Tracking pages. Today it sits inside the `min-h-screen` flex column under `Sidebar.Inset` and scrolls away with the content.

**Acceptance criteria**

1. On both routes (`/dashboard`, `/dashboard/board` or whatever the Issue Tracking route is), scrolling the page content keeps the header at the top of the viewport: after scrolling to the bottom, the header's bounding rect still has `top` ≈ 0 and the title is `elementFromPoint`-visible (not just `position` reads — PT-32/PT-88 rule).
2. Content is not hidden under it: the first card's top edge is fully visible at scroll 0 (no overlap; a spacer or padding equal to the header height), and the page has no horizontal scrollbar at 1280 px and 768 px widths.
3. The header keeps the card canvas convention (opaque `--muted`/`--background` surface with the design system's border or shadow token so scrolled content does not bleed through), in light and dark, in two variants — browser-verified by the lead, screenshots on the issue.
4. The sidebar (`Sidebar.Provider`/`Sidebar.Inset`) still opens/collapses correctly with the header fixed; the Sidebar.Trigger remains inside the header and reachable.
5. The embedded board iframe on the Dashboard page (fixed height, owns its own scrolling) is unaffected; the standalone `/board` + `/list` zero-build fallback is out of scope.
6. `dist/` rebuilt and committed by implementation-lead; `check_dist_freshness.py` rc 0; a source scan test pins the header's positioning classes (sticky/fixed + top-0 + z-index token) so a later layout pass cannot silently drop them.

**Notes for the ruling:** `sticky top-0` on the header inside the existing flex column is the smallest change if the scroll container is the document; if `Sidebar.Inset` owns the scrolling, the header may need to move outside the scroll container instead — the architect decides which, and whether the subtitle line collapses at narrow widths.

### @architect — 2026-09-08

**Ruling (gate 1).** Measured first, statically, because the mechanism turns on which element scrolls: **nothing in the shell path establishes a scroll container**, so the document scrolls and `sticky` will work where the header already is.

| element | classes that matter | overflow |
|---|---|---|
| `body` (app.css:346) | `bg-muted text-foreground` | none |
| `div[data-slot=sidebar-wrapper]` | `flex min-h-svh w-full` | none |
| `main[data-slot=sidebar-inset]` | `relative flex w-full flex-1 flex-col` | none |
| App.svelte page root / inner wrapper | `flex min-h-screen flex-col gap-6 bg-muted px-7 py-7` / `mx-auto flex w-full flex-col gap-6` | none |

`grep overflow` over all four returns nothing. **Note the method's limit:** this is a source read, not a browser measurement — I have no browser tools this session. AC1's `elementFromPoint` leg on the live board is the confirmation, and if the lead's visual leg finds the document *not* scrolling, this ruling's mechanism is the thing to reopen, not the styling.

**(1) `sticky top-0` on the existing `<header>` (App.svelte ~L333). Do not restructure to sidebar-07's shape.** The reference block matters for *where the header lives* — first child inside `Sidebar.Inset`, shared by both routes — and it already does: the header renders before the route switch. Moving it out of the padded `max-w` wrapper would change the page's horizontal rhythm and duplicate the padding rules, for a layout the document-scroll makes unnecessary.

**(2) AC2 needs no spacer, and must not get one.** `sticky` keeps the element's box in normal flow — the first card is never underneath it at scroll 0. A spacer or `padding-top` equal to the header height would double-count and push the first card down by a header's worth of dead space. The AC's "a spacer or padding equal to the header height" is satisfied by the mechanism, not by an added element.

**(3) Surface: `bg-muted` + `border-b border-border`, plus its own vertical padding.** `bg-muted` is what `body` is (app.css:346) — the header is page chrome sitting on the canvas, not a card, so `bg-background` would read as a floating bar. Opaque is the requirement; the border is what separates it from content passing underneath. No negative margins: the header spans the same width as the content inside the same `px-7` wrapper, so nothing scrolls through the side strips.

**Layer: `z-50`, the same tier as the tooltips — deliberately, not by omission.** Ordinary content (cards, charts) is `z-auto`, so the header wins over everything that scrolls under it, which is what AC3 asks. Against the portal'd overlays that are also `z-50` (chart tooltips, dropdown/select/popover/sheet — the codebase's established overlay tier), DOM order breaks the tie in the portals' favour, and that is the behaviour to want: **a header that outranks its own settings menu clips it.** The cost is that a chart tooltip can paint over the header in the rare position where it flips upward near the top edge — transient, and it reads as normal overlay behaviour. If the lead's screenshots show that reading as a defect, raise the header to `z-[60]` and accept the same bump for header-owned menus; that is one line, and the visual evidence should make the call rather than a guess now.

**(4) Narrow widths:** keep `flex-wrap`, and hide the subtitle below `sm` (`hidden sm:block` on the `<p>`). A wrapped two-line header pinned to the top eats viewport on exactly the screens with least of it; the title and the trigger are what must survive. No other responsive change.

**Scan test (qa)** on the `<header>` in App.svelte: `sticky`, `top-0`, `z-50`, `bg-muted`, `border-b` all present — **and a negative: the element must not be `fixed`**. `fixed` would satisfy a naive "header stays at top" reading while silently reintroducing the overlap AC2 forbids, which is precisely the regression a scan test exists to catch.

**dist:** rebuild and commit (source change). Post-PT-106 the rebuild is deterministic; `check_dist_freshness.py` must report rc 0 in the same commit.

**ux-designer: not needed.** Mosko's reference block fixes the pattern and every value here is an existing token. The one thing I would escalate is aesthetic, not structural: if the pinned header reads as a floating bar rather than page chrome in the lead's light/dark screenshots, that is a design call and worth a spawn then — not now.

**Scope** — `App.svelte` (the header element and the subtitle class) plus `dist/`; qa → the scan test. Writers: implementation-lead → source + dist; qa → test.

The wrapper is a flex column with a single child, so its `flex flex-col gap-6` does nothing today; its whole purpose (PT-74) was to give the header the same width rule as the sections below, and the header can carry that rule itself. Not (a) — keeping a wrapper whose only remaining job is to be the sticky element splits one concern across two elements and moves the pinning away from the tag a reader inspects. Not (c) — sidebar-07 remains a style reference; nothing measured requires its layout.

**(2) PT-74's invariant survives in substance and must be re-pointed, not relaxed.** `HeaderWidthMatchesSectionsTests._header_wrapper_class` reads the wrapper immediately preceding `<header`; with the wrapper gone it must read the **header's own** class string and keep every existing assertion (no `max-w-6xl` cap; the same width rule as the `{#if !onIssueTracking}` sections wrapper). Subset assertions, never string equality — the header legitimately carries more classes than the sections wrapper.

**(3) Unchanged from the first issue:** surface `bg-muted` + `border-b` (colour resolves to `border-border` via app.css:340's universal rule — that is not an omission), `py-4`, layer `z-50` on the portal'd-overlay tier, subtitle `hidden sm:block`, and **no spacer** — sticky keeps its box in flow. Mutation: reintroduce any wrapper between them → red. Keep the existing pinning scan (`sticky`, `top-0`, `z-50`, `bg-muted`, `border-b`, never `fixed`) as-is; it was right, it was just not enough alone.
