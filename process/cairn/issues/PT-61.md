### @architect — 2026-08-28

**Ruling — chart data source: (a) git reconstruction, blob-based (not diff-scraped).**
Verified by construction against this repo, not estimated.

**Source.** The status field's history is already stored losslessly in git;
option (b) would add a writer, a trigger that doesn't exist in downstream
template instances, and zero backfill to duplicate it. Reject (b). Reject the
cheap variant of (a) too — `git log -p | grep '^[+-]status:'` is one subprocess
but it is a *third* parser of the file format (PT-54 §4: never a second parser
over the same files), it is fooled by any body text starting `status: `, and it
yields paths, not ids.

**Shape.** New engine function `build_flow_payload(data_dir)` next to
`build_dashboard_payload`, two bounded subprocesses:
1. `git -C <data_dir> log --reverse -M --format=… --raw --no-abbrev -- issues/ archive/issues/`
   → change events `(commit date, path, new blob sha | delete)`.
2. `git cat-file --batch` fed the **deduped** blob shas once, read as **bytes**
   (the batch header's size is a byte count; text mode mis-slices on any
   non-ASCII — em dashes in our issue bodies broke the first cut). Each blob's
   frontmatter goes through the engine's existing frontmatter parser.

Fold oldest→newest into `stem → status`; emit one point per **day** (last commit
of the day wins); status keys come from `STATUS_ORDER`, so the chart taxonomy
cannot drift from the cards'. **Key by filename stem, never by path** —
`check_repo` already enforces stem == `id`, which makes the key immune to the
archive `git mv` (the recurring defect class here is keying on the wrong
dimension). Deletes drop the entity.

**Measured cost, full history of this repo:** 306 change events, 215 unique
blobs, 2 subprocesses, **~55 ms** end to end. The walk is proportional to
issue-file change events (the pathspec filters), not to repo size.

**Endpoint.** `GET /api/flow` — a **separate** endpoint, never a key on
`/api/dashboard`, on PT-56's roster precedent: different cost profile, different
cache key, and different freshness cadence. Payload
`{series: [{date, counts:{…}}], as_of: <head sha>, scope, warning}`. Git missing
or `data_dir` outside a worktree ⇒ `series: []` + `warning`, **200 not 500** —
the whole-group-degrades posture `read_git_state` already sets.

**Caching.** History is a pure function of HEAD, so memoize in-process keyed by
the HEAD short sha (bounded dict, last few entries); a new commit invalidates by
construction. No precompute file, no build step, no new tracked artifact. ETag +
`Cache-Control: no-store` as on `/api/dashboard`. **Not wired to SSE** — the
watcher fires on working-tree changes, which do not change history; the client
polls this on its own cadence (roster's pattern), so no git walk per file touch.

**Retroactivity — and two divergences that must be surfaced in the UI.** Full
backfill to the first commit creating `process/cairn/issues/` (2026-08-19 here),
which is all the data that exists — the pre-cairn Linear era is unrecoverable.
Today that is **7 distinct days**; a fresh template instance has one point or
none, so the few-points and empty states are required, not optional. Measured at
HEAD, reconstruction gives `done: 64` while the status cards show `done: 11`:
(1) **scope** — history must include archived issues (they were live when
counted; excluding them makes `done` collapse the moment a milestone archives),
the cards are live-only; (2) **committed-only** — right now HEAD has PT-61 as
`todo` while the tree has it `in-progress`, so the last point lags the cards by
the uncommitted delta. Label the panel's scope explicitly. Do **not** splice
live state onto the final point — that makes one point a different measurement
from every other. `cairn snapshot` stays out of this entirely.

**Sidebar sanity check (structural landmines, not a redesign).**
`Sidebar.Provider`/`Sidebar.Inset` own the page-level layout and the
`--sidebar-width` vars, so today's root `div.flex.min-h-screen…px-7 py-7` plus
the inner `mx-auto max-w-6xl` must move *inside* `Sidebar.Inset` — wrapping the
Provider in the existing padded shell breaks Inset's peer-based margins and
full-height. All eight `--sidebar-*` tokens (light + dark) are already in
`app.css` from the preset, so `add sidebar` should not introduce colour drift —
diff them anyway if the generator rewrites the block. The real landmine is
dependencies: every ui component in the tree today (badge/button/card/skeleton/
table) is primitive-free, and **`bits-ui` is not currently a dependency** —
Sidebar pulls it in (Sheet/Tooltip/Separator) and Chart pulls `layerchart` + d3.
`dist/` is committed and gated by `check_dist_freshness.py`, so expect a
one-time step up from the current 131 KB `index.js` plus a dist rebuild+commit
in the same PR; dynamic-import the chart panel so layerchart lands in its own
chunk. Finally, **there is no router** — the board is a separate static surface
at `/`; nav items are plain `<a href="/">` / `<a href="/dashboard">` with the
active item derived from `location.pathname`. Do not add a client router for
PT-61.
