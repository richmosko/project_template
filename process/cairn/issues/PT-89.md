## Problem

Found during PT-84 (architect ruling 6304afd on PT-84, 2026-09-04). PT-77 §2's non-overlap guard
in `otel_receiver.flush()` raises when the batch's *earliest* datapoint predates the latest
`transcript-backfill` `generated` stamp in the data file. Two consequences:

1. **Refuse, then never flush again.** The raise sits at the top of `flush()`; the pending-state
   reset sits at the bottom. A refused flush leaves the buffer untouched, so every subsequent flush
   is refused identically for the life of the process — silent after the first log line — and
   everything accumulated is lost at exit.
2. **Data that the backfill cannot contain is lost too.** The guard is batch-level and keys on the
   earliest datapoint, so datapoints received *after* the regen's `generated` (which the backfill,
   having read transcripts at that instant, does not hold) are refused along with the old ones.

Observed 2026-09-04: PT-87's AC 5 regeneration at 21:44:29Z; the running daemon's next flush
(earliest datapoint 21:40:30Z) refused; everything after that lost when the daemon later exited.
Bounded today by the regen-to-exit window; unbounded in principle.

## Ask

Replace refuse-the-batch with: drop only the datapoints whose timestamp predates the backfill's
`generated` (they are in the backfill by construction), flush the remainder, log the dropped count
once. The non-overlap property is preserved per datapoint rather than per batch. Interim operating
rule (in TRACKER via PT-84 AC 6): stop the receiver before re-running the backfill, restart bare
after.

## Acceptance criteria

1. Test: a pending batch whose groups fall on both sides of the backfill's `generated` stamp —
   groups wholly before it dropped, groups wholly after it flushed with totals and window bounds
   recomputed from the survivors, pending state reset, and the NEXT flush succeeds (asserted
   directly — today's code also logs once and doesn't crash; the reset is the fix).
2. Test: a batch entirely before the stamp — all dropped, exactly one log line, pending reset,
   daemon continues, and the next flush succeeds.
3. Test: a group whose own time bounds straddle the stamp — dropped and counted separately in the
   log line, never flushed (its aggregate cannot be split; keeping it would inflate a bucket with
   tokens the backfill already counted).
4. The filter keys on each group's own datapoint time bounds, recorded at fold time and reset
   every flush cycle (never lifetime-persistent — a lifetime minimum only moves earlier and would
   exclude a long-running group from every future flush after one regeneration) — and never on
   `startTimeUnixNano`, the metric stream's start. `flushed_baseline` is re-keyed from
   `SeriesKey` to `(SeriesKey, start_ns)`, the key `group_max` already uses; a dropped group
   advances its baseline without writing, so its tainted value is never bundled into a later
   flush once the group recovers (test: drop in cycle N, recover in cycle N+1, the flushed delta
   excludes the dropped range). The log line carries the dropped-group count and the straddling
   count, once per flush; `--status` unaffected. `_latest_backfill_generated` stays read once per
   flush.
4b. Safety property, tested directly: with nothing dropped, per-group deltas sum to the old
   per-series delta and the flushed output is byte-identical to today's — the common path must not
   change arithmetic while the rare drop path is added.
5. No live check against the real receiver (the loss event is a regen while it runs); tests drive
   the real CLI against a scratch `--out-file`. `merge_and_write` needs no counterpart guard.
6. Full suite green; `cairn check` ok; data file and real registry untouched by tests.

### @architect — 2026-09-05

Gating ruling. **Two premises in the issue don't survive the code, so the fix shape changes.**

**§1 `start_ns` is the wrong key, and a per-datapoint filter over `group_max` is not
implementable.** Measured in `otel_receiver.py`:
- `start_ns` is `startTimeUnixNano` — the **metric stream's** start, not the datapoint's own time.
  Under cumulative temporality that is effectively the exporting process's start, so filtering on it
  would drop a long-running session's **entire** series, including everything that accrued after the
  stamp. It is not a proxy for "when did this token spend happen".
- `group_max[(series_key, start_ns)] = max(value)` keeps **no per-datapoint time at all**. The
  datapoint's own `time_ns` is folded into the batch-wide `pending_min_ns`/`pending_max_ns` and then
  discarded. There is nothing per-datapoint left in `group_max` to filter.

**§2 Minimal correct shape: record per-group time bounds at fold time.** Add
`group_time_bounds[(series_key, start_ns)] = (min_time_ns, max_time_ns)`, updated in the same loop
that already updates `group_max` — no new pass, two ints per group. Then at flush, classify each
group against the stamp:
- `min_time_ns >= stamp_ns` → **keep** (entirely after the regen; not in the backfill).
- `max_time_ns < stamp_ns` → **drop** (entirely before; the backfill already counted it).
- otherwise **straddling** → **drop**, counted separately in the log.

**Why straddling groups are dropped rather than kept.** The group's value is an aggregate; it cannot
be split. Keeping it would silently inflate a bucket with tokens the backfill already counted — a
trust defect in the milestone whose whole definition of done is numbers you can trust. Dropping
loses bounded data and **says so in the log**. That is PT-86 §0's asymmetry applied here: prefer the
visible error to the silent one. The stop-before-regen rule in TRACKER already makes straddling rare
by construction.

**§3 Boundary semantics.** Convert `generated` to ns at the **start of that second**; treat
`time_ns < stamp_ns` as predating. A datapoint inside the stamp second is therefore kept — the same
half-open convention PT-84 canonicalised (`[start, next)`), which leaves at most one second of one
series exposed to double-count. **Consistency with PT-84's boundary rule is worth more than shaving
that**: two different boundary conventions in one codebase is its own defect class, and the next
person will apply whichever they read first.

**§4 `pending_min_ns`/`pending_max_ns` are recomputed from the survivors** — from the kept groups'
own bounds, not carried over from the pre-filter batch. **If nothing survives, both reset to `None`.**
That reset is the actual PT-89 fix: it is the missing step that makes the next flush a clean slate
instead of a permanent re-refusal.

**§5 `_latest_backfill_generated` stays read once per flush.** It walks the entire data file; moving
it per-group or per-datapoint would make flush O(groups × file). Read once, pass the stamp down.

**§6 One log line per flush, never per datapoint** — naming the stamp and the three counts
(`kept`, `dropped`, `straddling`). An operator needs to know a drop happened and how much; a line
per datapoint would bury that in the same log the one refusal line is already easy to miss in.

**§7 The backfill side needs no change.** `merge_and_write` drops every line matching its own
`source` and rewrites; it performs no cross-source `generated` comparison, so there is no
counterpart guard to fix. Stated explicitly so nobody adds a symmetric one for symmetry's sake.

**§8 No live check required, and I'd decline one if offered.** The loss event *is* a regeneration
while the receiver runs — the test would be the incident. AC 1 and AC 2 against a scratch
`--out-file` cover the behaviour completely, and the straddling case belongs in that suite too: a
batch whose groups span the stamp, asserting the drop **and** the reset, is the case neither AC
names today.

### @architect — 2026-09-05

**Addendum — both questions answered, and the first one caught a real inconsistency in my ruling.**

**Q1: per-flush-cycle bounds, not lifetime — and `flushed_baseline` moves to the group key.**
implementation-lead is right that lifetime-persistent bounds make classification **permanent**: a
group's lifetime-min only ever moves earlier, so one collision excludes that group for the rest of
its life. Under cumulative temporality a group lives as long as the exporting process, so a single
regen would silently drop a long session's entire series from every future flush. **That
contradicts my own §2 claim that the loss is bounded** — I asserted a bound the mechanism I
specified would not deliver. The default plan was safe but the tail is not what the ruling
advertised.

**Reset the bounds each flush cycle**, and close the resurrection bug they identified by **keying
`flushed_baseline` on `(SeriesKey, start_ns)` — the key `group_max` already uses** — instead of
`SeriesKey`:
- kept group → write its delta (`group_max[g] - baseline[g]`), advance `baseline[g]`;
- **dropped group → advance `baseline[g]` without writing.** The tokens were counted by the
  backfill, so from the receiver's side they *are* flushed; advancing the baseline is what stops
  them ever being re-counted, which is exactly the resurrection they described.
- A group then recovers naturally on a later cycle once its recent window clears the stamp.

**Safety property worth asserting as a test:** with nothing dropped, per-group deltas sum to the
old per-series delta, so **output is byte-identical to today**. That makes the key change verifiable
rather than trusted.

**And my "two ints per group" line under-described the change** — that was the bounds map, not a
budget for the whole fix. The baseline re-key is the larger part and is justified on its own terms:
two dicts keyed identically is simpler than two dicts keyed differently, and it is what makes a
partial drop expressible at all.

**Q2: their reading is right, with one correction.** `window_start`/`window_end` stay "since last
flush" — lifetime bounds would freeze `window_start` at a session's first-ever timestamp forever,
a clear regression, correctly rejected.

But the default plan — leave `pending_min_ns`/`pending_max_ns` exactly as today and merely reset
them — writes a line whose `window_start` may belong to a **dropped** datapoint: the batch minimum
can sit in a group that was just discarded, so the line claims a window earlier than anything it
actually contains. **Recompute both from the kept groups' cycle bounds**, then reset for the next
cycle. That is what §4's "from the survivors" was for, and it only becomes meaningful once the
bounds are per-cycle — which is the other half of Q1.

**Everything else in `0fd8774` stands** — straddling groups still dropped and counted separately,
PT-84's half-open boundary, stamp read once per flush, one log line per flush, no backfill-side
change, no live check.

**Asking before building was the right call**: the lifetime/cycle question is invisible in the
passing tests either way, and would have shipped a permanent-exclusion tail under a ruling that
promised a bounded one.

**Review of `c7b0068` — PASS. The bug is reproduced on the old code and demonstrably fixed on the
new, in the same harness. One wording delta in the operator-facing log line.**

**The core property, verified end-to-end against *both* code versions.** Seeded a scratch data file
with a `transcript-backfill` stamp of 2025-12-01, POSTed a pre-stamp batch, flushed, then POSTed a
**post-stamp** batch and flushed again:

| | otel lines after the second flush |
|---|---|
| pre-PT-89 receiver (`8640585`) | **0** — the buffer stayed poisoned; legitimate post-stamp data refused too |
| `c7b0068` | **1** — pre-stamp dropped, post-stamp written |

That is the whole ticket: the second flush is the one that was broken, and it now succeeds.

**The safety property from the addendum holds, across versions.** With an active stamp and nothing
to drop, the new group-keyed baseline produces output **byte-identical** to the old series-keyed
one — verified by running both receivers over the same payload into identically-seeded files and
`cmp`-ing the result. That is what makes the `flushed_baseline` re-key safe rather than merely
plausible, and it exercises the common path that every other test in this matrix skips.

**The straddling case — which neither AC named — behaves as ruled.** A single group carrying
datapoints either side of the stamp is counted `straddling: 1`, distinct from `dropped`, and nothing
is written.

**Also verified:** `group_time_bounds` and `flushed_baseline` carry the ruled shapes;
`_latest_backfill_generated` is called once inside `flush()`; bounds are updated in the fold loop
from point times; `--status` is untouched by the diff (AC 3); full suite green at the commit object;
the working-tree data-file changes are 16 `source: "otel"` lines from the live daemon, no
`transcript-backfill` pollution (AC 4).

**Delta (wording, operator-facing) — the log line overstates for straddling groups.** It reads:
`… kept 0, dropped 0, straddling 1 group(s) (dropped/straddling groups' tokens were already counted
by the backfill)`. For a **dropped** group that is exactly true. For a **straddling** group it is
not: the post-stamp portion was *not* counted by the backfill and is being discarded — that is the
deliberate loss §2 accepted to avoid a silent double-count. As written, an operator reading the line
concludes nothing was lost. Suggested: keep the parenthetical for `dropped`, and give `straddling`
its own clause — that its pre-stamp part was already counted and its post-stamp part is discarded
because the group's value cannot be split. The counts are right; only the explanation is.
