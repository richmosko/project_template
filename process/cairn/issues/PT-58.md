### @architect — 2026-08-27

### Peer review — `2545534` — **one blocking fix, then approve**

Reviewed by construction: built four throwaway git repos and drove
`check_dist_freshness` through each, rather than reading the comparison. The
degrade posture (`no-dashboard`, `git-unavailable`, never raises) and the
`uncommitted-src-changes` reason are all correct and match `read_git_state`'s
contract. The design is right; **the comparison mechanism is not.**

#### BLOCKING — the gate reports `fresh` for the exact state it exists to catch

```
repo: commit 1 touches dist/, commit 2 touches src/   (both within one second)
git log: 2026-08-27T22:32:01-07:00  790e0e2  src same second
         2026-08-27T22:32:01-07:00  8d8700b  dist
verdict: fresh          ← source is newer than dist; this must be stale
```

Reproduced live. With the two commits **one second apart** the same repo
correctly reports `stale`, so the logic isn't inverted — the **resolution** is
wrong: `%cI` is second-granularity, and `last_src_ts > last_dist_ts` is strict,
so **a tie resolves to "pass."** For a gate, ties resolving in the unsafe
direction is backwards. Two commits landing in the same second is not exotic
here — agents commit programmatically in rapid succession, and I've watched
several land inside one second in this repo today.

**Second defect, same root, opposite direction.** ISO-8601 strings carry a UTC
offset, and the comparison is lexical, so ordering breaks across timezones —
constructed and confirmed:

```
dist committed 2026-08-26T18:00:00+00:00   (= 18:00Z)
src  committed 2026-08-27T01:00:00+09:00   (= 16:00Z -- EARLIER in real time)
verdict: stale          ← false positive; dist is genuinely newer
```

One machine in one timezone never hits it; a collaborator, a CI runner, or a
laptop that travelled does.

#### The fix: ask git the ancestry question, not the clock question

Both defects dissolve if the check stops being about wall-clock time. The real
question is *"was dist committed at or after the source it must reflect?"* — an
ancestry question about history:

```python
src_commit  = _run_git(repo_root, "log", "-1", "--format=%H", "--", *source_pathspecs)
dist_commit = _run_git(repo_root, "log", "-1", "--format=%H", "--", dist_pathspec)
# exit 0 => src is an ancestor of (or identical to) dist => dist is at least as new
fresh = subprocess.run(["git","merge-base","--is-ancestor",src_commit,dist_commit], ...).returncode == 0
```

Verified on the same fixtures:

| Case | timestamp compare | `--is-ancestor` |
|---|---|---|
| dist, then src (same second) | **fresh** ✗ | **stale** ✓ |
| src + dist in one commit (the mandated discipline) | fresh ✓ | **fresh** ✓ |
| timezone-skewed, dist genuinely newer | **stale** ✗ | fresh ✓ |

A commit is its own ancestor, so the same-commit discipline we actually mandate
stays `fresh` — that case has to keep working and it does. Both commits come from
`git log -1` walks of HEAD, so they're always on one history; there's no
cross-branch ambiguity to handle. Rebases, cherry-picks, and clock skew stop
mattering entirely, because none of them change ancestry within the current
branch.

#### Non-blocking — an untracked new source file reads `fresh`

```
commit src+dist together, then add src/New.svelte (never `git add`ed)
verdict: fresh
```

`--untracked-files=no` on the dirty check means a brand-new, never-added
component doesn't register. Defensible under the tool's stated contract
("verified against the **committed** source") — but the developer intent it
misses is the strongest possible signal that dist is out of date. I ratified that
same flag on `read_git_state` for a different reason (an untracked issue file
mid-`cairn new` is routine there); here the routine case is the *opposite*.
Suggest scoping untracked files **in** for the source pathspecs specifically.
Your call — it's a contract question, not a bug.

Everything else — reason vocabulary, `no-dashboard` short-circuit, the
never-raises posture, the skill wiring as hard gate #3 — I have no objection to.
Approve follows the ancestry fix.

### @architect — 2026-08-27

### Fix verified — plus a correction to my own review, and the three scope answers

#### First: one of my two findings was demonstrated with an invalid fixture

My review above claimed the timestamp comparison produced a **false `stale`** on a
timezone-skewed pair, and gave a fixture to prove it. **That fixture doesn't prove
it.** I committed dist *first* and src second, which makes the src commit a
topological descendant — so the dist genuinely predates the source change and
`stale` was the *correct* answer all along. The old code got it right, and my
table entry predicting ancestry would report `fresh` there was simply wrong.

The skew *class* is real; my evidence for it wasn't. Here it is properly
constructed — dist a genuine **descendant** of src, carrying an earlier committer
stamp (clock skew, or a `--date` override):

```
commit 1: src   @ 2026-08-27T10:00:00+00:00
commit 2: dist  @ 2026-08-27T09:00:00+00:00   (built after, earlier stamp)

OLD (timestamp compare) -> stale    ← false positive
NEW (ancestry)          -> fresh    ← correct
```

Both versions run side by side against the same repo. The conclusion survives;
the earlier proof of it did not, and a review that ships a bad fixture is worse
than one that ships none — the fixture is what a reader would have trusted.

#### The blocking defect is fixed, verified against the same scenarios

| Scenario | verdict | expected |
|---|---|---|
| dist, then src, **same second** | `stale` | `stale` ✓ (was `fresh` — the blocking bug) |
| src + dist in **one commit** (the mandated discipline) | `fresh` | `fresh` ✓ |
| dist a descendant carrying an earlier stamp | `fresh` | `fresh` ✓ |
| src committed, dist never | `dist-never-built` | ✓ |
| untracked new `src/New.svelte` | `uncommitted-src-changes` | ✓ — and this closes my non-blocking finding too |

The untracked case now reports honestly rather than `fresh`. Good — that was the
right call and stronger than what I suggested.

#### The three things team-lead asked me to look at

**1. Source-path scope — covers everything, verified against the actual tree.**
Every file in `scripts/cairn/dashboard/` that can affect the build is watched:
`src/`, `index.html`, `package.json`, `package-lock.json`, `vite.config.ts`,
`svelte.config.js`, `tsconfig{,.app,.node}.json`, `components.json`, `public/`.
The only unwatched entries are `.gitignore`, `.vscode/`, and `README.md` — none
affect output. And **nothing under `src/` imports from outside the dashboard
directory** (checked), so the build's input set really is contained.

*Overreach is present and is the right direction:* a types-only `tsconfig` edit
will demand a rebuild it doesn't strictly need. False-stale is the safe failure
for a gate; don't optimize it away.

*The residual risk is future-facing:* the list is **enumerated by name**, so a
config file added later that Vite picks up automatically — `.env`,
`.env.production`, `postcss.config.js`, a reintroduced `tailwind.config.js`,
`.browserslistrc` — falls outside the watch set and the gate goes quiet with no
signal. The inverse formulation is strictly safer and simpler: watch the whole
dashboard subtree *except* `dist/` and `node_modules/`, via
`git log -1 -- scripts/cairn/dashboard ':(exclude)scripts/cairn/dashboard/dist'`.
**Non-blocking**, but I'd take it — it converts "did we remember to list it?"
into "did we remember to exclude it?", and the second question is much harder to
get wrong.

**2. Which timestamp.** It used `%cI` — committer date — which was the correct
choice of the two (author date survives rebases and cherry-picks and would
misreport freely). The ancestry rewrite makes the question moot: reachability is
invariant under rebase, cherry-pick, and any clock.

**3. Skill wiring reads correctly as a hard gate.** `python3 … || { echo …;
exit 1; }` at step 3, with the old step 3 renumbered to 4, and an actionable
failure message. Verified it also works when invoked from a subdirectory, so the
skill's cwd assumption isn't load-bearing.

**Approve**, pinned to the commit the working-tree fix lands as.
