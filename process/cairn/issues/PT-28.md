## Problem

Majors (`V1`) and milestones (`A`, `B`, `0.5`, `1.0`, `M<n>`) carry bare ids while issues carry the repo prefix (`PT-*`). Bare ids are ambiguous the moment two trackers exist side by side (multi-root board, spin-off components, cross-repo references in briefs/decisions): "milestone 0.5" doesn't say *whose* 0.5. Ruled 2026-08-22 (Mosko): majors and milestones should get the same `PT-*` prefixing for explicitness.

## Scope (architect to design)

This is a tracker spec + tooling change, not a doc edit:

- **Id shape design**: how the prefix composes with the existing semantics — version-named milestones bind to semver (`0.5` → `v0.5.0`), letter milestones (`A`/`B`) are `kind: process`, `M` is reserved, majors are `V<n>`. E.g. `PT-0.5` / `PT-A` / `PT-V1`, or a distinct delimiter. Must keep the name→target_tag derivation unambiguous.
- **`cairn check`** id-shape lint (check_repo) updated to enforce the new shapes.
- **CLI + board**: `cairn ls/show/set --milestone`, board grouping keys, issue frontmatter `milestone:` references, file names under `majors/` and `milestones/`.
- **Migration**: existing repos carry bare ids. Decide grandfather policy — note 0.6 shipped *without* one for the M0/M1→letter change (breaking, recipe in the error string); consistency argues for the same posture, but two breaking tracker migrations in consecutive releases is a real downstream cost. Weigh a transitional accept-both lint.
- **TRACKER.md** spec sections (Milestone ids, id-shape table) updated to match.

## Acceptance criteria

- [ ] Architect design ruling recorded on this issue (id shape + migration policy) before implementation starts
- [ ] `cairn check` enforces the ruled shapes; fixtures + tests updated
- [ ] Board, CLI, and frontmatter references resolve prefixed ids end-to-end

### 1. Id shape

**Delimiter: the hyphen, matching issues** — `PT-0.6`, `PT-A`, `PT-V1`.

The alternatives eliminate cleanly:

- **`PT/0.6`** — illegal. Ids are filenames (`milestones/<id>.md`), and a
  slash makes a directory. Hard constraint, not a preference.
- **`PT:0.6`** — `:` is reserved on NTFS (alternate data streams). cairn is
  files-in-git and a clone can land on Windows. Out.
- **`PT.0.6`** — a dot delimiter sitting beside version dots (`PT.0.6.1`) is
  unparseable by eye. Out.
- **A kind segment** (`PT-ms-0.6`, `PT-maj-V1`) — unambiguous without regex
  work, but it lengthens every prose reference and every CLI invocation,
  which is precisely where this change is supposed to pay off. Explicitness
  that makes the common case wordier defeats its own purpose.

**Shapes**, with `<P>` the configured `prefix:` (not a hardcoded `PT`):

```
issue        ^<P>-\d+$
major        ^<P>-V\d+$
definition   ^<P>-(?!M|V)[A-Z][a-z]?$
development  ^<P>-(?:M\d+[a-z]?|\d+\.\d+(?:\.\d+)?)$
```

**Ruling: reserve `V` in the definition-letter sequence, exactly as `M` is
already reserved.** Without it, `PT-V` is a legal definition milestone sitting
one character from `PT-V1`, the major. Formally the four shapes never collide
even without the reservation — I checked each pair — but "formally
unambiguous" and "readable at a glance" are different properties, and the
whole point of this change is the second one. Reserving `V` makes the four
namespaces separable by their **first character class** instead of by full-regex
disambiguation:

| First char after the prefix | Kind |
|---|---|
| digit, no dot | issue |
| digit, with dot | development milestone |
| `V` + digit | major |
| `M` + digit | development milestone |
| any other capital | definition milestone |

Cost: one more letter out of 26 — the definition sequence is now A–L, N–U,
W–Z (24 usable). A project needing 24 definition phases has a problem this
convention won't fix. Precedent and reasoning are identical to `M`'s existing
reservation, which is what makes this cheap to justify in TRACKER.md.

**The one genuinely confusable pair is `PT-1` (issue) vs `PT-1.0`
(development milestone).** The dot resolves it and no other rule can, given
Mosko's ruling puts both in one prefixed namespace. Stating it as a known,
accepted cost rather than leaving it to be discovered.

> **Considered and ruled against: `PT-v0.6`**, keeping the `v` so version
> milestones can never be visually confused with issues and `PT-v1.0 →
> v1.0.0` reads almost literally. Rejected because `target_tag` is an
> **explicit field** — TRACKER.md is emphatic that the target version is
> "designated at planning time, never inferred" — so the id doesn't carry the
> derivation and doesn't need to look like it does. It also adds a character
> to every reference to fix a confusion the dot already fixes. Closest call in
> this section; reversal is a one-character change to the development regex
> plus the same migration.

### 2. File naming

`majors/PT-V1.md`, `milestones/PT-0.6.1.md`, `issues/PT-29.md`.

**Keep filename ≡ `<id>.md` exactly** — `cairn check` already lints
id/filename mismatch and that invariant is one of the strongest properties the
tracker has. A genuine win of prefixing: all three directories then share one
naming convention instead of issues having a prefix and the other two not.

Worth naming honestly, because it's the crux of § 4: **on disk the prefix
carries zero information.** `process/cairn/milestones/0.6.md` is already
unambiguously *this* repo's 0.6 — the directory supplies the repo dimension.
The prefix's entire value is in the **quoted/rendered** form: a brief, a
DECISIONS entry, a commit message, a cross-repo board row.

### 3. Consuming surfaces

1. **`cairn check` id-shape lint** — regexes built from the configured
   `prefix:`, never a literal `PT`. `check_repo` already opens `config.yml`
   (for `roots:`), so the read exists — but note it currently tolerates a
   **missing** config.yml by design ("out of this function's existing scope").
   That tolerance stops being safe here: with no prefix, the id-shape lint
   either silently skips (a lint that quietly stops linting is worse than no
   lint) or guesses. **Ruling: a missing or prefix-less `config.yml` becomes a
   hard lint error once id shapes depend on it.** This is a behaviour change
   to `check_repo` beyond the id regexes and needs its own test.
2. **CLI `--milestone`** — **accept the bare form on input, always emit the
   prefixed form on output.** `cairn ls --milestone 0.6` keeps working and
   normalizes to `PT-0.6`. The prefix is fixed per repo, so input
   normalization cannot introduce ambiguity, and requiring users to type their
   own repo's prefix on every local invocation is pure friction in the one
   context where the prefix adds nothing. This is not the same as an
   accept-both *lint* (§ 4) — files must be prefixed; typing is forgiving.
3. **Board grouping keys** — `laneStateKey(repoId, milestoneKey)` will produce
   `PT::PT-0.6`. **Leave it.** The repo dimension in the composite is
   load-bearing for multi-root and the prefix inside the id is a different
   fact that merely coincides. Someone will see the doubling and want to strip
   one; a comment must say why not, or a future change reintroduces the
   bare-id-across-roots defect class for the fifth time.
4. **Board milestone display** — `renderHeader` currently renders
   `multiRoot ? ms.repo + " · " + ms.id : ms.id`, which becomes
   **"PT · PT-0.6"**. That one must change: with self-qualifying ids the repo
   prefix in the display is redundant, so drop it and render `ms.id` in both
   modes. Concrete, easy to miss, and visible on every multi-root board row.
5. **Issue frontmatter `milestone:`** — 33 files. The bulk of the migration.
6. **Milestone frontmatter `major:`** — `V1` → `PT-V1`, 6 files.
7. **board-logic.js** — `milestoneMajor`, `primaryMilestones`,
   `milestoneProgress`, `uniqueMilestoneKeys`, `groupByMilestone` all treat
   ids as opaque strings and need **no change**. Worth stating so nobody
   "updates" them.
8. **TRACKER.md** — the Milestone-ids table, both regexes, the `M`-reserved
   paragraph (now `M` and `V`), and the migration note.

### 4. Migration — options for Mosko, with a recommendation

Team-lead flagged this as decision-grade and I agree, so: options, costs, and
what I'd pick, but the call is Mosko's.

**Option 0 — don't change stored ids; qualify at the point of reference.**
Keep `0.6` / `V1` on disk; render and quote the qualified form (`PT-0.6`)
wherever a reference leaves the repo — board display, briefs, DECISIONS,
commit messages. Migration cost: **zero**. Worth knowing before choosing:
the multi-root board *already* does this — PT-3/PT-22 established
`<repo>::<milestone>` composite keys and `ms.repo + " · " + ms.id` display
precisely because bare milestone ids collide across roots, so the ambiguity
the issue cites is already handled in the one place it currently bites. What
Option 0 does **not** give you is a raw file that says `PT-0.6` when you open
it, which is a real part of what "for explicitness" asked for.

**Option 1 — no grandfather, matching 0.6's posture.** Lint rejects bare ids
immediately; recipe in the error string. Consistent, one clean break, no dual
shapes ever. Cost: the second breaking tracker migration in consecutive
releases, and ~40 files rather than 0.6's ~2.

**Option 2 — transitional accept-both lint.** Bare and prefixed both pass for
one minor, bare warns, errors from 0.8. Cost: two valid shapes at once is the
exact ambiguity the change deletes, temporarily — plus dual-shape code in the
lint that must be scheduled for removal or it becomes permanent. I'd avoid
this one: it buys time that Option 1 + a migration command buys more cleanly.

**Option 3 — Option 1, plus `cairn migrate` instead of a hand recipe.** Break
cleanly, but ship a subcommand that performs the rewrite: `git mv` the 7
files, rewrite `id:`, `major:`, and 33 `milestone:` refs, then run
`cairn check` and report. Idempotent, and a `--dry-run` that prints the plan.

**Recommendation.** If the goal is the *stated* one — kill cross-repo
ambiguity — **Option 0 does it for free** and I'd put it in front of Mosko
before spending the migration. If Mosko wants prefixes in the files
themselves, which is a legitimate want that Option 0 doesn't serve, then
**Option 3**, not Option 1.

The distinction matters more than it looks. "Two breaking migrations in
consecutive releases" is only expensive if the second one costs downstream
users an afternoon of careful hand-editing across 40 files. It costs a single
command invocation if we ship the command. **Writing `cairn migrate` is
roughly the same work as writing the recipe and the fixtures for it — and it
converts the downstream cost from care to compute.** That's what makes the
consecutive-migration objection survivable, and it's the reason I'd not take
Option 2's dual-shape window as the answer to it.

Whichever is chosen, the `--dry-run` and the idempotency are not optional:
a migration that can't be previewed won't be trusted, and one that can't be
re-run leaves half-migrated repos when it's interrupted.

### 5. `cairn migrate prefix-ids` — command semantics

**Named migration, not a bare `cairn migrate`.** A generic command that "runs
whatever migration is pending" does different things at different versions with
no record of which. Each breaking change gets its own name, so an invocation in
a shell history or a runbook still means one specific thing a year later. Cost:
a few more characters. This one is `prefix-ids`; the 0.6 letter-milestone change
would retroactively have been `letter-milestones`.

```
cairn migrate prefix-ids [--dry-run] [--data-dir DIR]
```

**Order of operations:**

1. Read `prefix` from `config.yml`. Missing, malformed, or failing
   `^[A-Z]{2,5}$` ⇒ **hard error, exit non-zero, nothing written.** Every
   rewrite below depends on it.
2. For each file in `majors/` and `milestones/` whose id is not already
   prefixed: compute `<P>-<id>`, rewrite the `id:` field, rename the file to
   `<newid>.md`.
3. Rewrite `major:` in every milestone file.
4. Rewrite `milestone:` in every issue file, skipping `null`.
5. Run the lint and report its result.

**Idempotency detection is `id.startswith(prefix + "-")`, and the hyphen is
what makes it airtight.** No bare id in any current shape contains a hyphen, so
a bare id can never be mistaken for a prefixed one even when it happens to
begin with the prefix's letters. Re-running on a migrated repo reports "nothing
to do" and exits 0.

**Idempotency is the crash-recovery story, not a nicety.** Individual file
writes are atomic (cairn's existing `mkstemp` + replace helper), but a 40-file
migration is not atomic as a whole — interrupt it and the repo is half-migrated.
Re-running finishes the job precisely because step 2's detection is per-file.
That is why `--dry-run` and idempotency were made non-negotiable, and the
implementation must not "optimise" the per-file check into a single up-front
whole-repo decision.

**It must run on a repo whose lint is failing.** That is the entire point — a
naive implementation might gate the migration behind a clean `cairn check`,
which would deadlock the exact situation it exists to resolve.

**Lint never mutates; `migrate` is the only mutator.** `cairn check` must not
auto-fix, offer to, or run the migration.

**Plain filesystem rename, not `git mv`.** Don't require a git work tree and
don't shell out; git detects the renames by content similarity at `add` time.

**Exit codes:** 0 = migrated, or nothing to do. Non-zero = could not proceed
(absent/invalid prefix, unwritable file, an id matching no known shape).

### 6. Downstream upgrade ordering

```
1. pull the new template version
2. scripts/cairn/cairn check                          -> FAILS on bare ids   (the trigger)
3. scripts/cairn/cairn migrate prefix-ids --dry-run   -> review the plan
4. scripts/cairn/cairn migrate prefix-ids             -> rewrite
5. scripts/cairn/cairn check                          -> exits 0
6. commit
```

**The break is lint-only, not functional — say this in the release notes.** A
downstream repo that upgrades and never migrates still works: the CLI accepts
bare ids on input (§ 3.2), the board treats ids as opaque strings, and the
frontmatter refs remain internally consistent with each other. The only failure
is `cairn check` exiting non-zero, and CI if it's wired. That materially lowers
the urgency of this migration compared to one that breaks the board, and it is
the fact that makes a second consecutive breaking change tolerable.

**Error-string recipe.** The lint error is the only place most people will meet
this, so it must name the command rather than describe a procedure:

```
milestone id "0.6" is not prefixed -- expected "PT-0.6"
  fix: scripts/cairn/cairn migrate prefix-ids --dry-run   (then re-run without --dry-run)
```

Do **not** reproduce 0.6's hand recipe (`git mv` … edit `id:` … `cairn set` …)
in the error string. At ~40 files that recipe is the wrong instrument, and
offering it invites someone to do by hand what the command does correctly.

### 7. Also ruled in: a `prefix:` format lint

Nothing currently validates `prefix` at lint time — `load_config` merely
defaults it to `"ISS"`. `/setup-tracker` validates a custom answer against
`^[A-Z]{2,5}$`, but that guards only the interactive path, not a hand-edited
config. Once every id shape is derived from the prefix, a malformed one
silently corrupts all four regexes.

**`cairn check` enforces `^[A-Z]{2,5}$` on `prefix:`** — the same regex
`/setup-tracker` already uses, deliberately not a new one. One format, two
enforcement points, one source of truth.

### @architect — 2026-08-22

Addendum — answers to QA's three questions. **§ A.2 corrects an error in § 5 of
the finalization**: the resume predicate I specified doesn't actually survive an
interruption. QA's question 3 is what exposed it, which is the pre-ruling gate
doing its job.

### A.1 — `target_tag`: there is no derivation function, and none is being added

QA is right that nothing in `cairn.py` or the suite derives `target_tag` from a
milestone name, and right to stop rather than invent one. **That is the correct
state and PT-28 does not change it.** TRACKER.md is explicit that the target
version is "designated at planning time, never inferred", and `target_tag` is a
plain stored field the architect sets when creating the milestone.

The issue's phrase "keeping name→target_tag derivation unambiguous" means the
id must remain **legible to a human** as implying its release (`PT-1.0` still
obviously relates to `v1.0.0`), not that code performs a derivation. It was a
constraint on the *id shape design* — it's why I rejected shapes that would
have obscured the version — and it is discharged by § 1. **No derivation
function, no tests for one.**

**The load-bearing consequence for the migration: `target_tag` is a git tag
name, not a cairn id, so it does NOT get prefixed.** `target_tag: v0.6.1` stays
`v0.6.1`. A "consistency" pass that rewrote it to `PT-v0.6.1` would break the
release process, which reads that field to know what to tag. The migration
touches exactly three fields — `id:`, `major:`, `milestone:` — and must leave
`target_tag`, `ga`, `kind`, `status` and everything else untouched. Worth a
test asserting `target_tag` is byte-identical across the migration.

### A.2 — exact algorithm (CORRECTED — § 5's resume predicate was wrong)

**The error:** § 5 said idempotency detection is `id.startswith(prefix + "-")`.
That predicate cannot survive an interruption, because migrating one file is
two observable actions — rewriting its content and renaming it — and the id is
only half of that pair. Crash between them and you get either a file named
`PT-0.6.md` containing `id: 0.6` (resume tries to rename `0.6.md`, which no
longer exists) or `0.6.md` containing `id: PT-0.6` (resume sees a prefixed id,
skips, and never renames). Both resumes are broken. My mistake, corrected here.

**Corrected: phase 1's unit of work is keyed on the FILENAME, and each file's
migration is one atomic write plus an unlink.**

*Phase 1 — `majors/` and `milestones/`. For each `*.md` whose filename stem
does not start with `<P>-`:*

1. Read it. New id = `<P>-<stem>`.
2. In memory, rewrite `id:` to the new id, and — in milestone files — `major:`
   if it is still bare. Same write, so a milestone file is never written twice.
3. Write the complete corrected content to `<P>-<stem>.md` via the existing
   temp-file + `os.replace` helper. Atomic: the new path either doesn't exist
   or is complete.
4. Unlink the old file.
5. **If `<P>-<stem>.md` already exists on entry**, a prior run wrote it before
   being interrupted. It was written atomically, so it is complete — do not
   rewrite it, just unlink the old file.

The filename is the right predicate precisely because it is what the loop
iterates, and "the old-named file is still present" stays true exactly until
that file's work is finished — which is the property `id.startswith(...)` lacked.

*Phase 2 — `issues/`. Keyed on VALUE, per file:* if `milestone:` is non-null and
not already prefixed, rewrite to `<P>-<value>`. Atomic per file, idempotent by
construction.

*Phase 3:* run the lint, report.

**Order between `majors/` and `milestones/` does not matter.** The `major:`
rewrite is a pure string transform that doesn't read the major file, so there
is no dependency to sequence — don't write a test that pins an order the design
doesn't require.

**Scope limit:** the command handles *its own* interrupted states, not
arbitrary hand-edits. A repo someone half-migrated by hand is `cairn check`'s
problem, not `migrate`'s.

### A.3 — interrupted states: not all-or-nothing, and deliberately so

**"Some files migrated, `cairn check` now flags the unmigrated refs" is an
acceptable interrupted state.** QA's second framing is the ruled one.

The required properties are two, and neither is whole-repo atomicity:

1. **Re-running completes it.** Guaranteed by A.2's per-file predicates.
2. **`cairn check` fails loudly until it is complete.** Check this holds for
   every partial state: an incomplete phase 1 leaves bare-shaped milestone or
   major ids ⇒ id-shape error. An incomplete phase 2 leaves `milestone:` refs
   pointing at ids that no longer exist ⇒ dangling-ref error. There is no
   partial state that lints clean, which is the property that makes the
   non-atomic design safe.

That gives QA a sharp, mechanical test rather than a vibe: **for every proper
prefix of the operation sequence, `cairn check` exits non-zero; only the
complete sequence exits 0.** Simulate by interrupting after N file operations
for several N.

Whole-repo atomicity would need a staging directory or a transaction log —
real, permanent complexity in a one-shot command whose failure mode is already
both visible and repairable by re-running. The only cost of the simpler design
is an alarming-looking `cairn check` in a window that exists only if you kill
the process mid-run, and the fix for that window is the same command again.

**What is NOT acceptable, and is worth stating so it doesn't get designed in
later:** any state that passes lint while being wrong. Every safeguard above
exists to keep partial ⇒ loud.
