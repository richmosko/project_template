## Acceptance criteria

Set by the architect's gate-1 ruling below (2026-09-08); every figure there is measured.

1. `token-chart-logic.ts` gains a pure `floorRowForRender(row, seriesKeys, yMax, plotHeightPx,
   minPx = MIN_BAR_PX)`: a row rendering below `minPx` is raised to exactly that, the shortfall
   going to the **single largest segment**; a zero total stays zero; a non-positive `yMax` or
   `plotHeightPx` returns the row unchanged.
2. The floor is applied unconditionally, not per mode — measured, it is a no-op for ranked's
   top-12 cut (12th-largest renders at 60.7 px), and ranked + "Show all" hits the same
   sub-pixel columns a mode branch would have missed.
3. The tooltip and any label resolve the **true** total through `trueTotalFor(payload, issue,
   metric)` from `tokens.issues`, never from the floored row. Without this the feature trades an
   invisible bar for a wrong number.
4. Plot height is measured through the component's existing observer, not hardcoded from the
   `h-[300px]` class.
5. Lead's browser leg: chronological, both themes, **every** column ≥ 1 px measured before any
   size filter (report the minimum height observed), and a floored column's tooltip shows its
   true token count.
6. Full suite green; JS glob green; `dashboard/dist` rebuilt and committed; `cairn check` ok.

### @architect — 2026-09-08

**Gate 1 ruling — PT-101. Decided line (a) is not reachable through layerchart; the floor moves into logic, and the tooltip becomes the honesty condition.**

**Why (a) cannot be done as written, measured in the vendored library.** `Bar.base.svelte` resolves only **style** props per datum — `resolveStyleProp` is applied to `fillOpacity`, `strokeWidth` and `opacity`, and to nothing geometric. `height` is a **scalar** prop, and `Bar.shared.svelte.js:94–96` does `y = y + (height - props.height) / 2` — it re-centres the bar, so a floored bar would float off the baseline. `insets` is scalar too (`insets = props.insets ?? stackInsets`). There is therefore no per-datum hook for rendered geometry, and "a minimum on the rendered height, not on the data" is not expressible through this component's props. Rejected alternative, measured as real but wrong: per-datum `strokeWidth` **does** reach the rect, but the accessor receives only the row — not the `seriesKey` — so it would stroke every segment of the column and straddle the baseline by 0.5 px.

**Seam.** Pure, in `token-chart-logic.ts`, tested in node:
`export const MIN_BAR_PX = 1;` and `export function floorRowForRender(row, seriesKeys, yMax, plotHeightPx, minPx = MIN_BAR_PX)`. Contract: `plotHeightPx <= 0` or `yMax <= 0` → the row is returned **unchanged** (never divide by an unmeasured plot). A summed value of 0 stays 0 (decided line c). Otherwise `minValue = yMax * minPx / plotHeightPx`, and when the row's sum is below it the shortfall is added to the **single largest segment**, every other segment untouched (decided line b), so the segments still sum to the rendered column.

**Apply it unconditionally, not per mode.** Ranked's top-12 cut is measured far above the floor — the 12th-largest issue renders at **60.7 px** (y-max 750,945,497 = PT-84; ~250 px plot; 1 px ≈ 3,003,782 tokens) — so the floor is a no-op there **by construction**. A `chronological`-only branch would be wrong anyway: ranked + "Show all" renders the same 88 bars and hits the same sub-pixel columns.

**The tooltip is the honesty condition, and it is the part that can silently lie.** Once the row handed to the chart carries a floored value, the tooltip formatter — which reads the chart row — would report a false token count for exactly the issues this feature exists to make visible. Rule: add `export function trueTotalFor(payload, issue, metric)` beside the floor, and have the tooltip and any label resolve through it from `tokens.issues`, never from the floored row. This is not optional polish; without it PT-101 trades an invisible bar for a wrong number.

**Plot height must be measured, not assumed.** The component already measures plot **width** through `measureChart` for `tickEveryNth`; extend that same observer to height rather than hardcoding `300 − CHART_PADDING`. A constant would rot silently the day the `h-[300px]` class changes, and the failure mode is a wrong floor with no symptom.

**Measured today: four sub-pixel columns, not the two the issue names** (that pair was PT-88's snapshot; the set grows as issues land): PT-83 **0.712 px**, PT-88 **0.779 px**, PT-95 **0.114 px**, PT-101 **0.632 px**. Pin the visual leg to "every column ≥ 1 px", never to a fixed pair.

**(e) Red tests — qa, `tests/js/token-chart-logic.test.js`.**
1. a row whose total renders below the floor comes back at exactly `minValue` — mutation: drop the `Math.max`.
2. the shortfall lands on the largest segment only, others byte-identical — mutation: distribute it evenly.
3. a zero total stays zero — mutation: floor unconditionally.
4. a row already at or above the floor is returned unchanged — mutation: always add the shortfall.
5. `plotHeightPx = 0` and `yMax = 0` both return the row unchanged and never divide — mutation: remove the guard.
6. `trueTotalFor` returns the payload's total for a floored issue, and the floored row's value differs from it — mutation: read the row instead of the payload. This is the test that proves the tooltip cannot inherit the floor.
