Feature started. Branch: `feature/pt-112-ledger-who-by-run-id`.

**Gate 1 brief (architect):** `.claude/hooks/test_run_record.py::_patch_last_who` (~L82) patches `who` onto the ledger's LAST line, assuming it is the run that just finished; with every teammate in its own worktree, two runs finishing close together cross-attribute, and a stale `who: null` line gets adopted by the next hook. The runner's `_self_record` (`run_tests.py` ~L330-392) writes `ts` (end time), `cmd`, `gate`, `full`, `files`, `seconds`. Rule on: (1) the matching key — a run id minted by the runner, printed in its summary line and read back by the hook from the tool result (the hook already scrapes the summary for `Ran N tests`), vs matching on `cmd` + `ts` proximity; recommend the run id — deterministic, no window; (2) how the hook finds the line — scan the tail for the matching id rather than assume last; leave a non-matching line untouched (never adopt a stale null); (3) the narrowed-run case (PT-107: the hook patches, not appends) and the worktree redirect keep working; (4) PT-111's `_match_ledger` in loop_stats is bookkeeping only now — no change. qa: two interleaved records in a fixture ledger, hook payloads for both, each patched to its own `who`; a stale null line left null; the PT-107 and PT-113 fixtures still pass.
