## Presence-source ruling

Investigated all four candidates against this machine and this repo before
ruling. Measurements first, because they decide it.

### What's actually readable (measured, 2026-08-27)

| Candidate | Measured state | Verdict |
|---|---|---|
| **Agent definitions** | 10 files in `.claude/agents/*.md`, each with `name` + `description` (+ `tools`, `model`) frontmatter; plus `.claude/roles/team-lead.md` | **Usable.** In-repo, versioned, present in every clone |
| **Issue `assignee`** | **All 8 live issues carry `assignee: null`** — after a full day of multi-agent work on PT-54/55/56 | Real field, currently unused |
| **tmux pane liveness** | **No tmux server running at all** (`error connecting to /private/tmp/tmux-501/default`) despite `teammateMode: "tmux"` in settings | **Rejected** |
| **Shared task list** | `~/.claude/tasks/session-<id>/<n>.json`. Schema: `id, subject, description, activeForm, status, blocks, blockedBy, owner`. **Exactly one task file exists across every session on this machine** | **Rejected** — see below |
| **Heartbeat file** | Nothing writes one today | Rejected for now; named as the upgrade path |

**Why the task store loses, despite being the only source that names who-does-what:**
it carries **no timestamps of any kind**. Not created, not updated, not
heartbeat. The single available time signal is the file's mtime — and mtime
measures *task-write recency, not agent liveness*: an agent working heads-down
for an hour writes nothing, while an idle agent whose task was just re-labelled
looks fresh. A presence indicator built on it would be wrong in both directions,
which is precisely the fabrication the AC forbids. Secondary but real: it's a
private, undocumented on-disk format under an experimental feature flag, outside
the repo, and the one file present right now has `owner: qa-engineer` on what is
substantively the lead's anchor task — ownership churn that a roster would have
rendered as fact.

**Why tmux loses:** not "unreliable" — *absent*. Teammates in this very session
are not in tmux panes despite the configured mode. A presence source whose
availability depends on how teammates happen to have been launched is not a
contract, and it would read differently on the maintainer's machine than on any
cloner's.

### Ruling: **no reliable presence source exists. Do not synthesize one.**

Build the roster from two honest in-repo sources and label the third dimension
`unknown`:

1. **Identity — `.claude/agents/*.md` + `.claude/roles/team-lead.md`.** Name and
   role come from frontmatter (`name`, `description`; truncate the description to
   its first sentence for the role line). Include team-lead: a roster that omits
   the one participant present in every session is a worse lie than an empty one.
2. **Work attribution — the cairn tracker's `assignee` field, live issues only.**
   Today that yields nothing for everyone, which is the correct output, not a
   defect.
3. **Presence — derived, never observed.** Three states, and the vocabulary is
   part of the ruling: **`working` / `idle` / `unknown`.** Never "active",
   "online", or "live" — those words claim observation we cannot perform.
   - `working` — assignee of ≥1 live issue with status `in-progress` or
     `in-review`.
   - `idle` — exists, with no such assignment (backlog/todo assignments included
     here, named in the work line).
   - `unknown` — no presence-bearing data at all. **This is today's value for
     every agent**, and the default for any cloner.

**The dot must not imply liveness.** Color-code it to those three states and
carry a one-line legend on the panel: *"Derived from tracker assignments, not
live presence — nobody is being pinged."* If that sentence feels like it
undercuts the panel, that's the panel accurately representing what we know.

**Staleness, defined explicitly as the AC requires:** a row is stale when its
underlying assignment's issue `updated:` field predates today. A stale row
renders as **`idle`, annotated with the date** ("last tracker update 2026-08-25"),
never as `working`. Degradation is one-directional: `working → idle → unknown`,
never upward. Deliberately **not** mtime-based decay on a live assignment — an
agent mid-feature legitimately touches nothing for an hour, and a timer that
flips them to stale would be inventing the very liveness claim this ruling
refuses to make.

### Where the code lives

**A separate composed reader module + a separate `GET /api/roster` endpoint.**
Not an engine change, and not a new key on `/api/dashboard`:

- `.claude/agents/` is outside `process/cairn/`, so per the boundary upheld in
  PT-54 the read belongs in a module the *server* composes, never inside the
  engine. Consequence worth stating: if cairn is ever spun off, this module
  stays with the template — correct, since `.claude/agents/` is a template
  concept, not a tracker one.
- A separate endpoint keeps PT-54's payload contract (and qa's "top-level keys
  are exactly these five" test) intact and meaningful, and isolates failure: a
  missing or unreadable `.claude/agents/` degrades the roster panel alone, not
  the whole dashboard.
- Repo root: `git -C <data_dir> rev-parse --show-toplevel`, falling back to
  `data_dir.parent.parent`. Same never-raises contract as `read_git_tags`.

### Empty state is not empty

Every clone of this template ships `.claude/agents/` — so a cloner with no team
running sees **eleven cards, all `unknown`**, which is the roster the template
actually provides. That is a genuinely useful first run, not a placeholder.

### Two follow-ups, neither in this feature

- **The `assignee` field is unused.** This panel makes that visible, which is the
  cheapest possible path to it being used. Whether `/start-feature` (and agents
  claiming work) should start setting `assignee` is a **process call for
  team-lead**, not mine to make — but the roster becomes materially more useful
  the day it happens, and nothing about this ruling needs revisiting when it does.
- **Heartbeat is the designated upgrade path**, not a rejection on principle. A
  `Stop`/`PostToolUse` hook writing `{agent, ts}` per turn would give real
  liveness. Whether those hooks fire for spawned teammates is **unverified** —
  I'm not ruling from assumption, and a wrong guess here manufactures exactly
  the fake-presence the AC forbids. If we want it, that's a spike first.

### Ruling addendum — evidence correction + a stronger reason to reject the task store

Two corrections to the ruling above. **The ruling itself is unchanged**; one of
its stated measurements was overclaimed, and one rejection turns out to rest on a
better fact than the one I gave.

#### Correction: what I actually measured about tmux

The table says "No tmux server running at all." That overstates what I can know.
What I measured is **"no tmux server reachable from an agent's sandboxed
execution context"** — I cannot distinguish that from a host tmux I simply have
no visibility into. implementation-lead independently hit the same wall from
their own context and flagged it rather than letting it stand, which is the only
reason this got corrected before it hardened into a cited fact.

**The verdict does not change, and now rests on three reasons that don't depend
on any measurement:**

1. **Pane liveness is the wrong signal even when readable.** A live pane proves a
   *process exists*, not that it is doing this project's work. A teammate sitting
   idle at a prompt and one mid-turn are indistinguishable — so the source cannot
   answer the question the panel asks.
2. **It vanishes under `teammateMode: "in-process"`.** A presence contract that a
   single settings toggle can delete is not a contract; the panel would work on
   the maintainer's machine and be permanently empty on a cloner's.
3. **A cloner may not use tmux at all** — and constraint (3) makes the cloner a
   first-class case, not a degraded one.

If anyone wants tmux genuinely ruled in rather than out, the probe has to be run
from **team-lead's context**, not an agent's. I am not ruling from a measurement
I can't trust in either direction.

#### The task store: a sharper disqualifier than the one I gave

I rejected it primarily on the absence of timestamps. implementation-lead's recon
found something worse, and it becomes the lead reason: **completed tasks are
deleted from the store** — their own PT-54 and PT-55 tasks were already gone
while PT-56's remained.

So an agent between tasks is not represented as idle there. It is **absent**. A
roster built on that store would **silently drop agents from the panel** rather
than show them honestly idle — a failure the AC's honesty clause doesn't even
name, because it's worse than the fabricated-`active` case it does name: a
missing row makes no claim a reader can catch being wrong.

Three independent disqualifiers now, any one sufficient: agents vanish when
between tasks; no timestamps, so liveness can't be derived at all; and
session-UUID → project correlation is a cross-referencing heuristic against a
private undocumented layout, not a contract.

#### One live consequence of the assignee decision

team-lead has adopted claim-time `assignee` population (PT-62's board card already
renders an assignee chip). Nothing in this ruling needs revisiting — it was
written to be correct while `assignee` is universally null and to gain content the
day it isn't, and that day is now. `working`/`idle` become populated rather than
merely derivable, and the staleness clause starts doing real work.

**One process point that follows, flagged not ruled** (it's team-lead's, not
mine): roster honesty now depends on release-time hygiene too. An issue that
reaches `done` carrying a stale assignee still reads as that agent's last known
work. This ruling contains the blast radius — only live issues in `in-progress`/
`in-review` can produce `working` — but whether `/finish-feature` clears or
deliberately preserves `assignee` is a choice worth making on purpose.

### Ruling addendum — the `done`-but-live cell, newly reachable

team-lead's decision to **preserve `assignee` on done issues** (deliberate, for
provenance) creates a state my ruling didn't enumerate, and which will now occur
constantly: an agent whose assignment sits at status `done` in the **live**
`issues/` dir — done issues stay live until they're archived at release close, so
this is the common case, not an edge one.

My original three-state definition covers `in-progress`/`in-review` (⇒ `working`)
and `backlog`/`todo` (⇒ `idle`), and says `unknown` means "no presence-bearing
data at all." `done` falls between the cracks of that text. Closing it
explicitly, since an implementer could reasonably read it either way:

**Presence is computed from `in-progress` and `in-review` only.** Then:

| The agent's live assignments | Presence |
|---|---|
| ≥1 `in-progress`/`in-review`, updated today | `working` |
| ≥1 `in-progress`/`in-review`, `updated:` predates today | `idle` + the date (stale) |
| only `backlog`/`todo` | `idle` |
| **only `done`** | **`idle`** — known to the tracker, nothing live |
| none at all (no issue names this agent) | `unknown` |
| archived issues only | `unknown` (archived is not live; already ruled) |

The `idle`-not-`unknown` call for done-only: `unknown` should mean *we have no
data about this agent*, and a completed assignment is data — it says the agent
exists in this project's record and has nothing in flight. Collapsing that to
`unknown` would throw away the provenance the preserve-on-done decision exists to
keep.

**A done assignment may appear in the work line only as history** — "last shipped
PT-55", or in the expandable detail — **never as current work**, and it can never
contribute to `working`. team-lead's framing is exactly right: if the roster ever
surfaces a done-issue assignee as anything but history, that's the bug, not the
field.

**qa:** the existing suite pins archived-issues-don't-count and
nothing-stale-ever-reads-as-working, but nothing currently pins the done-but-live
cell. Two cases worth adding — an agent whose only assignment is `done` reads
`idle` (not `unknown`, not `working`), and a `done` assignment never appears in
the work line as current work. Both are newly reachable as of the assignee
decision; before it, they were unwritable.

### Answer to the browser-pass question + two follow-ups

(The main diff review is above at `85ca585` — approve, one non-blocking fix.
This answers the question from the Validate pass, which crossed with it.)

#### "Clicking a card expands nothing" — the detail EXISTS and gates correctly

Confirmed by reading the component, not inferred: the expandable detail is a
`<details>` element inside each card, and it is wrapped in `{#if agent.work}`.
`work` is `null` for every `unknown` agent — by design, from the ruling: *"`work`
carries a human-readable line for the card's work line — `None` for `unknown`
(nothing to report)."*

So in today's all-`unknown` state there is genuinely nothing to expand, and the
implementation renders **no affordance at all** rather than an empty one. That is
the honest behaviour, not a missing feature. It will start expanding on its own
the moment claim-time assignees populate — no code change needed.

The `<summary>` shows the work item's id (`agent.work.split(':')[0]`), which
resolves correctly for all four work-line shapes: `PT-3`, `PT-3` (stale),
`PT-2`, and `last shipped PT-1`.

#### Non-blocking: the empty card reads as truncated, not as complete

Your click found something real even though the gating is correct. A card in the
`unknown` state renders dot / name / role and then simply stops — there's no
affordance *and* no statement, so a reader can't tell "nothing to report" apart
from "something failed to load." One muted line inside the card — *"No tracked
work"* — makes the empty state explicit rather than implied, at the cost of one
line, and matches the honest-empty-state posture the rest of this panel already
takes. Recommended, not required.

#### Non-blocking debt: `work` is a presentation string the client re-parses

`build_roster_payload` composes human-readable strings server-side
(`"PT-3: Live work"`, `"last shipped PT-1: Ship it"`), and the component then
splits on `":"` to recover the id for the summary line. It works today for every
shape, and I'm not asking for a change now — but it's the wrong direction of
travel: presentation composed in Python, then partially un-composed in the
client.

When this panel next grows (the expandable detail is the natural place for more
fields), the right shape is a structured `work` object — `{id, title, status,
kind}` where `kind` ∈ `current | stale | history` — leaving phrasing entirely to
the component. That also removes the one place where the ruling's *semantics*
currently live in a string's prefix (`"last shipped "` is load-bearing framing
that only exists as English).

#### Ratified: poll-only refresh, no SSE

Deliberate and correct, and it was part of the ruling rather than a deviation
from it. The SSE watcher scans `process/cairn/` only, so a change under
`.claude/agents/` emits **no** event — subscribing the roster to that channel
would give the appearance of live updates while silently missing every identity
change. Polling on the same 15s cadence is the honest mechanism.

Worth stating the residual: a change to an *issue's* `assignee` does move the
roster and *would* have been pushed by SSE, so the roster can lag the board by up
to 15s on that one path. That's the correct trade — one refresh mechanism whose
staleness bound is uniform beats two where the user can't tell which fields are
live.
