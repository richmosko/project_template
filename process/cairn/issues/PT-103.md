### @architect — 2026-09-08

**Ruling (gate 1).** Measured over `process/cairn/metrics/token-usage.jsonl` (655 rows) before ruling:

| source | rows | distinct windows | distinct (issue, role, model) keys | issues | granularity |
|---|---|---|---|---|---|
| `transcript-backfill` | 330 | **1** — `2026-08-18 … 2026-09-04` | 330 | 90 | day |
| `otel` | 325 | 8, each `start == end` | 99 | 30 | day |

**Framing, so the change stays small:** PT-102 retired the `first_active` ordering that motivated this issue (`token-chart-logic.ts:183` records the retirement), so nothing user-visible is broken today. What remains is that a record claims a three-week span for rows that may cover one day — the data is simply false, and every future per-issue consumer inherits it. That justifies fixing the writer; it does not justify widening the change.

**(1) The window belongs to the record's own bucket — `(issue, role, model)`, not the issue.** Each record's `window_start`/`window_end` = min/max day over the timestamps that fed *that* bucket. A per-issue window would attach a span wider than the record's own rows (a role active one day would claim the issue's whole span), which is the same class of lie in a smaller font; the issue-level span is then min/max across that issue's records, which any consumer can compute and `build_tokens_payload` already does. Multi-day backfill records alongside single-day `otel` records is not new — it is what the schema holds today.

**Min/max, never first-seen/last-seen.** Records are not guaranteed chronological across files; assignment in file order yields a `window_start` later than its `window_end`.

**The run-level span stays exactly where it is — the operator's stdout line (`print(f"window: …")`) — and gains no record field.** `stats["window_start"/"window_end"]` keep serving that report and the `or generated[:10]` fallback. A per-record copy of the run span has no consumer, and a field with no consumer is the next drift.

**(2) Timestamp source: the message's own `timestamp`, the same value `_process_record` already passes to `cairn.milestone_for_timestamp`.** Never the sidecar's mtime — that is a second clock, and a record whose window and milestone bucket come from different clocks cannot be reconciled later. Granularity stays `str(timestamp)[:10]`, day: all 8 `otel` windows measured are day-granular, the existing 330 are too, and ISO dates compare correctly against instants if that ever changes.

**Invariant this change must preserve** (and the reason it is cheap to verify): the payload-level window in `build_tokens_payload` is min/max across all rows, so per-bucket windows leave it identical — `min(window_start) == 2026-08-18`, `max(window_end) == 2026-09-04` over the same transcripts. That is both a qa assertion and, below, the data-loss detector.

**(3) The data re-run is in scope, executed by the lead on the main checkout after green — but only behind four checks, computed on the regenerated file BEFORE it is committed.** `merge_and_write` drops every `transcript-backfill` line and rewrites from whatever transcripts exist, so a scan missing the 67 archived transcripts silently deletes real data:
1. key set ⊇ the current 330 `(issue, role, model)` keys;
2. row count ≥ 330;
3. `min(window_start) ≤ 2026-08-18` and `max(window_end) ≥ 2026-09-04` (≥/≤, not equality — a restored archive may legitimately extend the span earlier);
4. distinct windows > 1, and at least two issues with different windows — the point of the change.

Any check failing: **do not commit the regenerated file.** Ship the code change alone; the data corrects itself the next time a full-archive scan is possible. Report all four counts at the verdict; I will re-derive them from the committed file.

**Guards (qa), `backfill_tokens.py`'s existing test module:** (a) fixture transcript, two issues active on different days → two records with different windows, each equal to its own bucket's first/last day; (b) a bucket spanning several days with its records **out of chronological order** in the file → `window_start < window_end` (mutation: first-seen/last-seen assignment → inverted); (c) min/max across all produced lines equals the run-level span the CLI prints; (d) the existing backfill tests stay green and unedited.

**Scope** — `backfill_tokens.py` and its tests; plus the regenerated data file if and only if (3)'s four checks pass. Writers: implementation-lead → the script; qa → tests; lead → the data commit.
