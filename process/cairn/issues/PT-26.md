New capability: an issue can declare other issues as blocking it. No
`blocked-by`/`depends` support exists anywhere in engine, board, or spec today.

Design points for the architect at start-feature (settle before implementation):
field name (`blocked-by` proposed), list-valued frontmatter semantics (precedent:
`labels`), and whether blocking is purely informational or the board/CLI warns
when a blocked issue moves to in-progress.

## Acceptance criteria

- [ ] Schema: **`blocked_by`** (snake, not kebab), `list[id]`, **absent ≡ `[]`** — no backfill of existing issue files, and **not** a required field. Sits in `ISSUE_FIELD_ORDER` immediately after `parent`. **Not** added to `NULLABLE_FIELDS`. TRACKER.md frontmatter table + worked example updated.
- [ ] `cairn check` lints, **same-root only**: dangling reference, self-reference, and dependency cycles, all errors. Cycles use a three-colour DFS and are **reported once per cycle** (canonical rotation, `_id_sort_key`-smallest id leading) with the full path in the message. A `blocked_by` entry naming a `done`/`cancelled` issue is **legal and resolved — never an error**.
- [ ] CLI: `cairn new --blocked-by` and `cairn set blocked_by=` write the field (comma-separated; empty clears to `[]`, never `null`). **One shared `_split_csv` helper and a `LIST_FIELDS` membership test — no second `if key == "blocked_by"` branch**, and collapse the pre-existing duplicate of that same comprehension in `cmd_new` while there (standing duplicated-inline-expression criterion, at fix time).
- [ ] `cairn show` displays blockers **and** reverse "blocks" links, both directions sorted by `_id_sort_key`.
- [ ] Board: card chip **only when open blockers exist**; drawer carries the full "Blocked by" list (open vs resolved distinguished) **and** the reverse "Blocks" list. Reverse links never appear on cards.
- [ ] Board logic in `board-logic.js` under the node:test harness, **repo-scoped from the first line**. Rename PT-25's `parentKeyOf` → **`issueKeyOf`** and reuse it — it was never parent-specific, and a second identical key function is how this defect class recurs. **Counts derive from the membership lists, never from a parallel filter** (the F1 correction from PT-25, applied before the fact).
- [ ] A **cross-repo red test lands first**, ahead of every other board test: two roots each holding `PT-14`, one's blockers must not leak into the other's.
- [ ] **Informational only in v1** — nothing refuses or warns when a blocked issue moves to `in-progress`, on any path (board drag, `cairn set`, `/start-feature`). Recorded in TRACKER.md § Dependencies.
- [ ] Test-first: pytest for engine/lint/CLI, node:test via board-logic.js for board logic.

### @architect — 2026-08-22

Design ruling — all five questions settled at `5419c08`, verified against the live
tree (`cairn check` green; the field round-tripped through the real parser before
being ruled on). Build-ready.

**1. `blocked_by`, snake — a deliberate deviation from the proposed `blocked-by`.**
Every multi-word key cairn already writes is snake (`target_tag`, `target_ship`,
`read_only`); there is no kebab key anywhere in the schema. Snake also keeps
`issue.blocked_by` dot-accessible in board JS where a kebab key would force
`issue["blocked-by"]` beside `issue.parent` and `issue.labels`, and argparse maps
`--blocked-by` to `args.blocked_by` for free, exactly as `--done-before` already
does. So the flag stays kebab, the key is snake, and no translation code exists.

**Absent ≡ `[]`, and the field is not required.** `dump_frontmatter` never
synthesizes an absent key, so existing issues simply lack it and every reader uses
`fm.get("blocked_by") or []`. Backfilling 20-odd files buys nothing. It sits after
`parent` in `ISSUE_FIELD_ORDER` (grouping the relational fields; safe, since
canonical order only affects keys actually present) and must **not** join
`NULLABLE_FIELDS` — it is list-valued, so `blocked_by=` clears to `[]`, never
`null`, and the list branch must precede the nullable branch as `labels` already
does. Zero parser work: `blocked_by: [PT-1, PT-2]` already parses and `[]` already
dumps.

**2. Three lint errors, same-root only.** Dangling refs and self-reference keep the
lint's own terse existing vocabulary (`dangling blocked_by 'PT-99'`, mirroring
`dangling parent`) — consistency inside `check_repo` beats verbosity for errors
that are self-evident. Only cycles get the PT-27 self-servicing treatment, because
"there is a cycle" is unactionable without knowing which: three-colour DFS,
reported **once per cycle** on its canonical rotation, with the full path and the
fix in the message. Reporting an N-node cycle from N entry points is how a lint
becomes noise.

`known_ids` already spans `issues/` **and** `archive/`, so a reference to an
archived blocker is correctly not dangling — that falls out for free.

**A blocker that is `done` or `cancelled` is resolved, not an error.** The entry
stays. "Resolved" is computed at render time; erasing a blocker on completion would
make the field self-erasing and destroy the dependency record, which is the part
anyone would later want to read.

**Same-root only, and the reason is structural, not conventional:** `check_repo`
runs per-root, so a cross-root reference could never be validated by the very lint
whose job is referential integrity. The guarantee would be unavailable, not merely
unimplemented. Ids are unique only within a repo, writes are primary-root-only, and
`parent` is same-root-only by identical construction.

**3. Informational only in v1 — nothing refuses or warns.** Enforcement would need
the same predicate at three write paths (board drag, `cairn set`, `/start-feature`),
which is the duplication class that has bitten this board four times, bought before
anyone has felt the need. More decisively, it cannot be enforced against a plain
`Edit` at all — and "the files are the interface, hand-editing fully supported" is a
stated principle here, so a rule the files can bypass teaches confidence the system
cannot honour. The information is already at the decision point: the card being
dragged carries the blocker chip. Someone moving a blocked issue in-progress is
usually doing it deliberately, and sometimes correctly.

A non-blocking `note:` line from `cairn set` was considered as a half-step and
declined for v1 — one more surface, and stderr noise for scripted callers. Recorded
so it is not re-litigated.

**4. Board — one rename prevents instance #5 of the collision class.** PT-25's
`parentKeyOf` is `(issue.repo || "") + "::" + issue.id` — that is the issue's own
identity key, not anything parent-specific, and PT-26 needs exactly it. Rename to
`issueKeyOf` and use it for both features; adding a `blockerKeyOf` with an identical
body is how this keeps recurring.

`blockersOf` and `blocksOf` are the two membership functions, both repo-scoped from
the first line, both sorted by `idSortKey`. **Counts derive from those lists, never
from a parallel filter** — that is the F1 correction from PT-25's review, applied
before the fact rather than after. Card chip only when open blockers exist (an
all-resolved list gets no chip; a card flagging a dependency that no longer
constrains anything is noise on the scarcest surface). Drawer gets both directions.
Reverse "blocks" links live in the drawer and `cairn show` only — never on cards.

**5. TRACKER.md** gains a `blocked_by` frontmatter row, a `blocked_by: []` line in
the worked example, a new § Dependencies after § Sub-issues, the dependency clause
on the `cairn check` CLI row, and Resolutions row 10 (cross-root + informational).
Commit-ready text for all five went to team-lead; I own that doc, so those land
verbatim.
