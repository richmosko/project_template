## Comments

### @team-lead — 2026-09-08

Observed on PT-92 (the first loop with a worktree teammate, ux-designer) in `process/cairn/metrics/test-runs.jsonl`: each of ux-designer's narrowed `run_tests.py -p …` runs from `.claude/worktrees/pt92-ux` produced TWO records in the main ledger — `11:03:47 who=ux-designer gate=null branch=feature/pt-92-… files=2` (the PostToolUse hook's own append for a narrowed run) and `11:05:56 who=null gate=null branch=worktree-pt92-ux files=2` (the runner's self-record redirected to the main checkout by PT-82's git-common-dir rule, with `branch` resolved from the worktree's HEAD). PT-82's spike only exercised gated full runs, which record once (the runner writes, the hook patches `who`). Consequences: per-agent tool/run counts in `cairn loop-stats` double-count narrowed worktree runs, and the unattributed line carries a `worktree-*` branch name that nothing should ever see. Ask: one record per run for narrowed runs too — the hook should patch the runner's line (matching on ts/argv) rather than append when a runner record exists, and the runner should resolve `branch` from the main checkout's feature branch (or the linked worktree's upstream) never `worktree-*`; tests on a real `git worktree add` fixture for both the narrowed and gated cases. Not attached to PT-0.12.1 (closing).

### @architect — 2026-09-08

**Ruling (gate 1).** Delete `args.gate and` from `run_tests.py:367`. That single clause is the whole fix — **no hook change**. Measured on a real `git worktree add` fixture (main checkout on `feature/pt-107-x`, linked worktree on `worktree-x`, `CLAUDE_PROJECT_DIR`/`CAIRN_TEST_RUNS_FILE` unset), running the narrowed case before and after the deletion, then driving the real `.claude/hooks/test_run_record.py` with `CLAUDE_PROJECT_DIR=<main checkout>`:

| case | main checkout's ledger | worktree's tracked copy |
|---|---|---|
| current, `-p` (runner only) | no file | 1 line, `who=null`, `branch=worktree-x` |
| current, `-p` + hook | 1 line, `who=architect`, `branch=feature/pt-107-x` (hook **scraped and appended**) | 1 line, `branch=worktree-x` |
| patched, `-p` (runner only) | 1 line, `who=null`, `branch=feature/pt-107-x` | no file |
| patched, `-p` + hook | **1 line**, `who=architect`, `branch=feature/pt-107-x` (hook **patched**, no append) | no file |
| patched, `--gate red` | 1 line, `gate=red`, `full=true`, `branch=feature/pt-107-x` | no file |

Both halves of the ask fall out of the one deletion. (a) One record per run: with the redirect live, the runner's `who: null` line is the last line of the main ledger, so `_patch_last_who` fills it and returns before the scrape-and-append fallback — the second record existed only because there was nothing to patch. (b) `branch` is never `worktree-*`: `sha`/`branch` are already resolved with `_run_git(records_repo_root, …)`, and `records_repo_root` becomes the main checkout under the redirect. No upstream lookup — a fresh `EnterWorktree` branch has no upstream at all, so upstream resolution would fail exactly where it is needed.

**Ruled, not open:** `sha` and `branch` both stay resolved from the main checkout. They must come from one root: a record naming a `sha` that is not on its own `branch` is worse than a `sha` a few commits behind the worktree that ran. Accepted and to be stated in the `_self_record` docstring.

**Also update the docstring**, same commit: its PT-82 paragraph says the redirect applies "ONLY when `--gate` is present". That sentence is the superseded ruling's text and must not outlive the clause it describes — replace with the `--git-dir != --git-common-dir` discriminator alone (unchanged, still the safety property).

**Guards (qa, gate 2)** — reuse `_make_main_checkout_with_worktree` in `test_worktree_metrics_path_resolution.py`; real git, real subprocesses, no stand-ins:
1. Narrowed `-p` run from the linked worktree → exactly **one** line in the main checkout's file, `full=false`, `gate=null`, `branch` == the main checkout's branch; the worktree's own copy must not exist. (Mutation: restore `args.gate and` → main has no file and the worktree copy gains a line.)
2. No record, in either file, carries a `worktree-`-prefixed `branch` — a standing invariant, cheap, catches any future re-resolution from the worktree root.
3. Hook leg (this is the "one record per run" property; test 1 alone does not prove it): after that narrowed run, drive the real `.claude/hooks/test_run_record.py` on stdin with `CLAUDE_PROJECT_DIR=<fixture main checkout>` and a `Ran N tests …`/`OK` stdout → still exactly one line, `who` now filled. (Mutation: hook appends instead of patching → 2 lines.) Recipe measured above; it needs no copy of the hook.
4. The four discriminator contexts already in that file stay green **and unedited** — they are the safety property, not scaffolding.

**Scope** — `run_tests.py` (one clause + its docstring) and `test_worktree_metrics_path_resolution.py`. No hook file, no `loop_stats.py`.

**Known gap, not this issue:** `_patch_last_who` only ever inspects the ledger's last line, so two teammates running concurrently — likelier now that worktrees are the norm — can cross-attribute `who`, and a stale `who: null` line gets adopted by the next run's hook. Pre-existing, documented in the hook, unchanged here. Worth a P3 follow-up; the lead's call.
