#### The single git-tags read: measured, not taken on report

Instrumented `subprocess.run` and built one dashboard payload against this repo,
before and after:

```
BEFORE (b26c816~1): 2 for-each-ref calls, of 5 git subprocesses
AFTER  (HEAD):      1 for-each-ref call,  of 4
```

The threading is clean: `git_tags: Optional[Tuple[Optional[Set[str]],
Optional[str]]] = None` on both `read_git_state` and `build_board_payload`, with
`read_git_tags(data_dir) if git_tags is None else git_tags` — every existing
caller is untouched and behaviourally identical. Worth stating what this buys
beyond the saved subprocess: the two reads could previously return **different
tag sets** if a tag landed between them, so a single payload could disagree with
itself about what had shipped. That's now structurally impossible, which is the
better reason for the change than the ~8ms.

#### `milestone_paths` — consolidation confirmed, and the non-threading is right

Three call sites now share it (`_find_release_milestone`, `build_board_payload`,
`compute_etag`), and `compute_etag` mirroring `build_board_payload`'s flag is the
subtle one that matters — an etag that fronts a payload must vary over exactly
the same inputs.

**The decision not to thread it through `check_repo`'s PT-59 lint is correct.**
That loop needs to know *which* directory each file came from (the archived half
runs its own status checks), and a flat list can't carry that. Forcing it would
mean re-deriving the distinction at the call site — replacing one duplicated glob
with one duplicated inference, which is worse.

**Non-blocking, and I'd take it eventually:** there's a third option neither of us
named — a sibling `archived_milestone_paths(data_dir)`, exactly mirroring the
existing `archived_issue_paths()` (11 call sites, and it exists for precisely
this reason). `check_repo` could then call `_dir_glob(live)` + that helper,
keeping its distinction *and* single-sourcing the archive spelling. That would
leave `_RECORD_SEARCH_SUBDIRS` as the only other literal, which is a different
concern (id resolution) and legitimately its own. Not for this PR.

#### Skeleton + aria-live — the PT-54 finding, closed properly

`Skeleton` is installed as a real shadcn component and used at all three fetch
boundaries with shapes that match the content they stand in for — eyebrow
(`h-3 w-20`), stat value (`h-7 w-16`), badge (`h-5 w-14`); table rows; roster
dot + name + role. That's the spec's requirement (*"shaped like the real
card/row/table it's replacing"*), not decorative spinners.

`aria-live="polite"` on the header badge cluster is the right element: it wraps
the branch/tag/loading badges, which are exactly the region that mutates without
a focus change. Verified the dist carries all of it.
