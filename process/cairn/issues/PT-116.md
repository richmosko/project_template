### @architect — 2026-09-08

**Gate 1 ruling (architect). The reported defect does not reproduce — measured at `4ef79ef`, both paths, with a deliberately failing fixture suite.**

- **Runner path.** An isolated copy of `run_tests.py` plus a fixture with one failure and one error, run narrowed with `CAIRN_TEST_RUNS_FILE` pointed at a scratch ledger: record written, `{"ok": false, "tests": 3, "seconds": 0.05, "session": "817d7be4-…"}`. Written **also** when stdout is fully suppressed (`> /dev/null 2>&1`, rc 1) — `_self_record` is in-process and has no stdout dependency.
- **Hook scrape path.** A real failing `python3 -m unittest discover -s tests -p "test_red.py" 2>&1 | tail -3` from this session wrote to the **live** ledger at `2026-09-09T06:19:09Z`: `{"runner": "unittest", "tests": 3, "ok": false, "who": "architect"}`.

**So red runs already reach the ledger on both paths, and `ok: false` is already recorded.**

**What my PT-112 observation actually was.** I measured the symptom correctly (a failing narrowed run, no record) and inferred the cause wrongly. The likeliest cause is the *pre-PT-112* `_patch_last_who`: it patched the ledger's last `who: null` line and returned, so the red run produced no record of its own and an older line silently took my `who`. PT-112's session-keyed patch removed exactly that path. The inference, not the measurement, is what carried into this issue — my error, and worth naming so the next follow-up filed off an observation says which part is measured.

**Narrowed scope for this feature — two things are still true and cheap.**
1. **Failure detail.** Records carry `ok` but never *how* red. The runner has the numbers in-process (it prints `FAILED (failures=1, errors=1, files=1)`); the hook can parse `failures=<n>` / `errors=<n>` out of stdout exactly as it already parses `skipped=`. Add **`failures` and `errors`** to the record on both paths. They are `null` when unknown — never 0-filled from ignorance, the same rule `tests`/`ok` already follow (a scrape with no parseable summary still writes nothing).
2. **A regression guard.** Nothing in the suite asserts that a red run records at all; that is why a wrong inference could stand for a day. Both paths get one.

**Explicitly unchanged.** PT-111's classification: a red run is an **executed** run — `Ran N tests` beats exit status, `full`/`gate` semantics untouched, and a guard-refused command still records nothing (PT-111/PT-115 negative controls stay negative).

**Guards (qa writes; red at gate 2).**
1. Runner path: a fixture suite with one failure and one error, run narrowed against a scratch ledger, writes exactly one record with `ok: false`, `tests: 3`, `failures: 1`, `errors: 1`; control — an all-green fixture writes `ok: true`, `failures: 0`, `errors: 0`.
2. Runner path, suppressed stdout: same red run with stdout and stderr discarded still writes the record (guards the in-process property).
3. Hook scrape path: a payload whose stdout carries `Ran 3 tests in 0.0s` + `FAILED (failures=1, errors=1)` appends `ok: false, failures: 1, errors: 1`; controls — an `OK` payload gives `ok: true, failures: 0, errors: 0`, and a payload with no parseable summary still writes **nothing** (`failures`/`errors` are never invented).
4. `loop_stats` counts a red run as executed, not blocked — one row asserting a red `run_tests` step with a `Ran N tests` result classifies `FULL_SUITE`.

**Carried forward, measured, out of scope (each worth its own issue if Mosko wants it).**
- A bare-`unittest` run whose stdout is suppressed records nothing — **not red-specific**, identical for green runs, 49 measured instances at PT-111. Only a self-recording runner fixes it; `unittest` is stdlib.
- **The prefilter is text-based, so an indirectly invoked run reaches neither hook.** Measured live in this session: `sh probe116.sh` (whose script ran a full unittest suite) matched neither `*unittest*` nor `*run_tests*` in the payload, so nothing was recorded — **and nothing would have been refused**. That is a guard evasion, not just a metrics gap.
- `CAIRN_TEST_RUNS_FILE` is honoured by the runner but not by the hook, so records written under the override never receive `who`.

**If the lead prefers, guards 1–4 alone are a defensible close** (the reported defect is absent, the guards pin the behaviour). I recommend keeping the `failures`/`errors` fields: they are two parsed integers and they let a scorecard say how red a loop was.
