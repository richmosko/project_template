`process/STATE.md`'s header promises "**No history accumulates here**". Its `## Releases`
section contradicts that: it is an append-only log, one row per tagged release, and the rows
have grown into full release notes. Measured 2026-09-02 on `5b93de9`:

| Measurement | Command | Result |
|---|---|---|
| Whole file | `wc -c process/STATE.md` | **10145 bytes** |
| `## Releases` heading → EOF | `awk '/^## Releases/{f=1} f' process/STATE.md \| wc -c` | **8489 bytes — 83.7% of the file** |
| Data rows only | `grep '^\| v' process/STATE.md \| wc -c` | **7768 bytes across 11 rows** (v0.3.0 → v0.9.0), mean 706 chars/row |
| Longest / shortest row | `grep '^\| v' … \| awk '{print length}' \| sort -n` | **1223** (v0.7.0) / **223** (v0.4.0) |

Every release adds ~700–1200 bytes, unbounded. The content is duplicated across GitHub Releases
(canonical per the 2026-05-25 ruling in `process/TEMPLATE_DECISIONS.md`), the archived milestone
files, the issue files, and git tags.

## Ruling (team-lead, 2026-09-02)

The Releases table becomes a **pointer, not a log**:

1. It holds exactly **one** row: the latest tagged release. `/merge-pr` **replaces** that row
   instead of appending.
2. Hard limit: the entire markdown table row — pipes, link URL, everything — is **at most 200
   characters**. Machine-checked, not a style note. (Note: the *shortest* row on disk today is
   223 chars, so the retained v0.9.0 row must be **rewritten** to fit, not merely kept.)
3. The section keeps a one-sentence lead-in linking to the GitHub Releases page for full history.
   Breaking-change / migration notes for downstream instances live in the GitHub release notes
   and `process/TRACKER.md` — never in this row.
4. `process/WORKFLOW.md` and `.claude/skills/merge-pr/SKILL.md` are updated to match:
   replace-not-append, the 200-char rule, and a **fixed row template**. Every other surface that
   says "append a row" is corrected.
5. The existing 11-row table collapses to the single v0.9.0 row. Removed rows are not lost —
   see the recoverability criterion below, which supersedes the ruling's "already exist verbatim
   on GitHub" assumption (it is false; see @architect comment).
6. A decision entry is written to `process/TEMPLATE_DECISIONS.md` (this repo *is* the template,
   so that is the right ledger), superseding the "Releases table kept" clause of the 2026-08-19
   and 2026-08-22 rulings.
7. Enforcement mechanism: architect's call — see the @architect comment below. **Chosen: a new
   test in `scripts/cairn/tests/`**, which `/finish-feature` step 2 already runs as a hard,
   `exit 1` gate.

## Comments

### @architect — 2026-09-02

**Enforcement mechanism — chosen: a Python test in `scripts/cairn/tests/`.**

`scripts/cairn/tests/test_state_releases_bound.py`, reading `process/STATE.md` as text.
Rationale, in the order that decided it:

- **It actually fails a merge.** `/finish-feature` step 2 runs
  `( cd scripts/cairn && python3 -m unittest discover -s tests )` with
  `|| { echo "GATE FAIL…"; exit 1; }`. That is the repo's only hard, machine-enforced gate today
  — there is no CI (`git ls-files` shows no `.github/`), so a GitHub Actions check would be new
  infrastructure and a new branch-protection dependency for the same predicate.
- **Zero new infrastructure.** No new runner, no new file convention, and it rides the suite QA
  already runs at every gate.
- **Precedent exists for asserting outside `scripts/cairn/`.** The suite is nominally
  spin-off-scoped, but `test_skill_id_literals.py` (PT-45) already reads
  `.claude/skills/setup-tracker/SKILL.md` via `helpers.CAIRN_DIR.parent.parent`, and
  `test_column_parity.py` / `test_dashboard.py` reach outside too. This adds no new boundary
  crossing — but **it does add one more file a `git subtree split --prefix=scripts/cairn` would
  drag out**, so follow PT-45's shape: an explicit `SETUP_TRACKER_SKILL.exists()`-style
  precondition assert naming the expected path, so a spun-off repo fails with a legible message
  rather than a stack trace.

**Rejected:** a `cairn check` rule (STATE.md is not tracker data; `cairn check` lints
`process/cairn/` and widening it would make the tracker lint own a process doc); a prose step in
`/merge-pr` alone (the lead asked for something that *fails*, and a skill instruction is
agent-obedience, not a gate); a standalone `scripts/check-state.py` (a second, unhooked runner —
the existing suite is already invoked by the gate).

### @architect — 2026-09-02

**Two premises in the ruling need correcting before implementation. Neither changes the ruling;
both change its stated justification, so the TEMPLATE_DECISIONS entry should not repeat them.**

**1. The Releases table is NOT in the session-startup context.** The ruling's motivation — "every
release adds roughly 1KB to every future session's startup context, unbounded" — is false. The
`SessionStart` hook in `.claude/settings.json:44` is
`awk '/^## Releases/{exit} {print}' process/STATE.md` — it exits *at* the `## Releases` heading,
so the table has never been injected. `README.md:165` documents this ("top → just before
`## Releases`"). Confirmed empirically: this session's injected state block ends after
`## Active Feature`.

The ruling still stands on its own, on two grounds that *are* true:
- **The header lies.** STATE.md says "No history accumulates here" while carrying an append-only
  log. A doc that contradicts itself teaches agents to distrust it.
- **The full-read cost is real and paid often.** `CLAUDE.md` → *Resume runbook* step 1 says
  "**Read the full `process/STATE.md`**" on every cold resume. That read is 10145 bytes today, of
  which 8489 (83.7%) is duplicated release history — and the resume path is exactly where a lead
  is trying to orient quickly.

**2. The removed rows do NOT already exist verbatim on GitHub Releases.** Spot-checked v0.9.0:
`gh release view v0.9.0 --json body` returns the `--generate-notes` PR list plus a Full Changelog
link. The STATE.md row's synthesis — issue count, PR range, per-issue one-liners, the "Board
renamed Issue Tracking; standalone `/board`+`/list` survive" note — appears nowhere in it. That
synthesis is genuine, non-duplicated signal.

It is not *unrecoverable* (git holds the table forever at `5b93de9`, and the facts are
reconstructible from the PR list + issue files), but deleting it on the stated belief that GitHub
already has it would be deleting on a false premise. Hence the recoverability criteria above:
verify per-version, and port the synthesis into the release body where it is missing, before the
row goes. Flagging rather than deciding unilaterally — if the lead prefers to accept the loss and
cite `git show 5b93de9:process/STATE.md` as the record, that is a legitimate call and cheaper;
say so and I will trim those criteria.
