## Problem

Found during the PT-77 architect review (comment at 0e8832c on PT-77). `cairn.load_config()`
returns the built-in defaults (`prefix: "ISS"`, default port and columns) when the data dir or
its `config.yml` does not exist, instead of raising. `find_data_dir()` walks up from the current
working directory, so any caller invoked from outside the repo gets defaults and exit 0.

`process/TRACKER.md`'s standing rule says a missing or config-less data dir is an error, never
an empty result. The loader violates it, and every caller inherits the trap: the CLI, the board
server, the tests' `--data-dir` seam, and any future script. PT-77's backfill hit it and had to
add its own guard; that guard belongs in the loader.

## Ruling from the architect at filing

The fix is not a smarter `find_data_dir`. A loader that returns defaults for a non-existent
directory is the wrong shape. `load_config` raises a named error carrying the path it looked
for; callers that legitimately want defaults (if any exist) opt in explicitly.

## Acceptance criteria

1. `load_config(path)` raises a `CairnError` (or the module's existing error type) naming the
   path when `config.yml` is absent. No silent defaults.
2. Every CLI subcommand and `cairn serve` exit 1 with that message when run from outside a repo
   with no `CAIRN_DATA_DIR`. `cairn check` included.
3. `backfill_tokens.py`'s local guard from PT-77 is removed or reduced to a call into the loader,
   with its cwd-outside-repo test still green.
4. Tests: a test invokes the CLI with cwd in a tmpdir and no `CAIRN_DATA_DIR`, asserts exit 1 and
   the path in stderr; a test asserts `load_config` raises on a missing file.
5. `process/TRACKER.md` states the loader contract in one sentence next to the existing rule.
