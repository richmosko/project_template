## Problem

Found during the PT-77 architect review (comment at 0e8832c on PT-77). `cairn.load_config()`
returns the built-in defaults (`prefix: "ISS"`, default port and columns) when the data dir or
its `config.yml` does not exist, instead of raising. `find_data_dir()` walks up from the current
working directory, so any caller invoked from outside the repo gets defaults and exit 0.

`process/TRACKER.md`'s standing rule says a missing or config-less data dir is an error, never
an empty result. The loader violates it, and every caller inherits the trap: the CLI, the board
server, the tests' `--data-dir` seam, and any future script. PT-77's backfill hit it and had to
add its own guard; that guard belongs in the loader.

## Ruling from the architect at filing

The fix is not a smarter `find_data_dir`. A loader that returns defaults for a non-existent
directory is the wrong shape. `load_config` raises a named error carrying the path it looked
for; callers that legitimately want defaults (if any exist) opt in explicitly.

## Acceptance criteria

1. `load_config(path)` raises a `CairnError` (or the module's existing error type) naming the
   path when `config.yml` is absent. No silent defaults.
2. Every CLI subcommand and `cairn serve` exit 1 with that message when run from outside a repo
   with no `CAIRN_DATA_DIR`. `cairn check` included.
3. `backfill_tokens.py`'s local guard from PT-77 is removed or reduced to a call into the loader,
   with its cwd-outside-repo test still green.
4. Tests: a test invokes the CLI with cwd in a tmpdir and no `CAIRN_DATA_DIR`, asserts exit 1 and
   the path in stderr; a test asserts `load_config` raises on a missing file.
5. `process/TRACKER.md` states the loader contract in one sentence next to the existing rule.

### Answer: keep `resolve_data_dir`'s check. Do not delegate.

**Keep it.** The two checks assert the same predicate at different layers for different audiences, and that is not the harmful kind of duplication:

- The messages are correctly different. `resolve_data_dir` speaks to a **CLI user** — it names `--data-dir` and `/setup-tracker`. `load_config` speaks to a **library caller** — it names the path and says what the directory isn't. Delegating would force one message to serve both, and the CLI one would get worse.
- Delegating means `resolve_data_dir` calls `load_config` purely to validate, which parses YAML as a side effect of *path resolution*. Wrong coupling, and every resolve pays a parse it doesn't need.
- Harmful duplication is two **sources of truth that can disagree**. These can't produce different verdicts — only different wording — and whichever fires first is correct. The layered check also means the CLI keeps its friendly error even if `load_config`'s contract is ever loosened again.

That is consistent with the filing ruling: it was about the loader's **shape** (a loader must not return defaults), not about there being exactly one check site.

### Delta 1 (minor) — the error can render a path that names nothing

`load_config(Path("."))` produces `no config.yml at config.yml`. AC1 requires the error to name the path it looked for; a bare `config.yml` names nothing and is actively confusing in a traceback. Resolve the path when building the message so any relative-path caller gets an absolute one:

```python
config_path = (Path(data_dir) / "config.yml").resolve()
```

Verified today: `load_config(Path('.'))` → `at config.yml`; `load_config(Path('nope'))` → `at nope/config.yml`. Absolute callers are already fine.

### Delta 2 (minor) — an unreachable fallback is now the only way to reach Delta 1

`build_multi_board_payload` line ~3431:

```python
primary_config = load_config(roots[0].path) if roots else load_config(Path("."))
```

`resolve_roots` initialises `roots = [primary]` and never removes it — its docstring says the primary "is never skipped", and it has a single `return roots, warnings`. So the `else` branch is **unreachable in production**; the only caller that can hit it is a test passing `[]`, and none does. Before `109fd25` it silently returned defaults; now it raises `CairnError: no config.yml at config.yml` on every `/api/board` request that reached it. **Delete the branch, or make it an explicit assertion.** As written it converts an impossible state into a confusing error rather than a clear one — and it is the one production path that can produce Delta 1's message.

Neither delta blocks the merge: Delta 1 is cosmetic on a path no shipping caller takes, and Delta 2 is dead code. Both are one-line fixes and cheaper to land now than to rediscover from a board 500 later.
