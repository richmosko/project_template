## Comments

### @team-lead — 2026-09-08

Found closing PT-0.12.1 (2026-09-08), the first `cairn archive` since PT-94 E15 landed. `cmd_guard_commit` runs `git diff --cached -- <rel>` without rename detection, so a moved issue (`issues/X.md → archive/issues/X.md`) diffs as 100 % added lines and every historical comment author counts as "someone else's uncommitted hunk" — 16 refusals on the archive commit, all false. The commit was made with `--no-verify` after confirming `git diff --cached -M --name-status` showed pure renames (R100).

Fix: run the cached diff with `-M` (or `--find-renames`) and skip `R` entries whose similarity is 100 %; for partial renames diff against the rename source. One regression test: stage a rename of a multi-author issue into `archive/issues/` and assert guard-commit returns 0. Same defect class as archive's own precondition note at cairn.py ~L215.

### @architect — 2026-09-08

**Ruling (gate 1).** One code path, no `R100` special case, no similarity parsing. Measured on real staged renames of a three-author issue into `archive/issues/` (`cairn._added_comment_authors` over each diff form):

| staged change | `-M --name-status` | today: `diff --cached -- <dest>` | ruled: `diff --cached -M -- <src> <dest>` |
|---|---|---|---|
| pure archive move | `R100` | 3 authors → **refuse (false)** | **0 authors → pass** |
| move + 1 added comment (architect) | `R078` | 3 authors → refuse (false) | `{architect}` → pass |
| move + 2 added comments | `R065` | 4 authors → refuse (right answer, wrong reason) | `{architect, devops-engineer}` → **refuse, naming only the two real ones** |
| move + >50 % rewrite | `A` + `D` (no rename) | 1 author → pass | same → pass |

The paired diff is empty at `R100` and exactly the genuinely-added authors below it, so **items (1) and (2) of the brief collapse into one rule**: never branch on the similarity number. A threshold branch is a special case that rots; the pairing is the fix.

**Also measured, and it changes the shape of the fix:** `git diff --cached --name-only` lists **only the destination** for a rename (rename detection is on by default since git 2.9), so the current loop never sees the source path and cannot pair anything from inside its own per-file call. The enumeration must come from the rename-aware call.

**Implementation (implementation-lead), `cmd_guard_commit` at cairn.py:6418:**
1. Replace both `git diff --cached --name-only` and the per-path diff enumeration with a single `git diff --cached -M --name-status -z`, parsed as NUL-separated records (a rename record is three fields: status, src, dst). `-z` because git quotes paths with spaces or non-ASCII in the plain form, and a guard that silently skips a path it failed to parse is worse than one that refuses.
2. Per entry, keep the existing filter (`.md` and `/cairn/` in the path), then: status `R*`/`C*` → authors from `git diff --cached -M -- <src> <dst>`; `A`/`M`/`T` → authors from `git diff --cached -- <path>` (unchanged); `D` → skip, a deletion adds no comment header.
3. `-M` is passed explicitly on both calls: `diff.renames` is user config and must not be able to turn the guard's correctness off.
4. Nothing else changes — the refusal message, the `len(authors) > 1` rule and the exit codes stay as they are.

**Brief item (3): yes, `cairn archive` stays the sanctioned path, and `--no-verify` stops being part of it.** `cairn archive` performs the moves and makes no commit; `.githooks/pre-commit` execs `cairn guard-commit`, so the archive commit is exactly where E15 fired 16 times. Nothing in cairn hardcodes `--no-verify` (grepped). Acceptance for this issue includes that a PT-0.12.1-shaped archive commit passes the hook with **no flag** — a sanctioned flow that requires a bypass trains the bypass, and the next real two-author hunk rides in behind it.

**Guards (qa) — `test_comment_guard.py`, real git repos, real staged state:**
1. Pure rename of a multi-author issue into `archive/issues/` → `cmd_guard_commit` returns 0. (Mutation: drop the pairing → 1, naming three historical authors — measured above.)
2. Rename + one added comment by one author → 0.
3. Rename + added comments by two authors → 1, **and the message names exactly those two**, not the historical ones. This is the load-bearing guard: it proves the fix narrowed the guard rather than disabling it.
4. Ordinary (non-rename) modification adding two authors → still 1. Regression control for the untouched path.
5. A staged tracker `.md` whose path contains a space is still evaluated. (Mutation: parse the name-status output by splitting on whitespace → the file is skipped and the guard goes silently blind.) Cheap, and it is the only thing keeping the `-z` parser honest.
6. The existing guard-commit tests stay green and unedited.

**Scope** — `cairn.py` (`cmd_guard_commit` only) and `test_comment_guard.py`. No hook shim change, no `cmd_archive` change.

### @architect — 2026-09-08

**Verdict (gate 4): NO-GO on one axis.** The deviation's *structure* is accepted — it is measured, the alternative was tried and reverted for a stated reason, and enumerating with the hook's own index is right. What I cannot accept is the comparison it uses, which I reproduced as a **silent pass of a genuine two-author violation**. Suite runs deferred until the correction lands; running them against code that must change is waste.

Measured against the green code (7a459fa), real repo, real `.githooks/pre-commit` shim, real `git commit -m … -- <dest>`:

| case | required | 7a459fa | with the correction below |
|---|---|---|---|
| pure archive move of a 2-author issue | pass | pass | pass |
| move + comments by two **new** authors | refuse | refuse | refuse |
| move + comments by two authors **already in the file's history** | refuse | **PASSED — commit made** | refuse |

**Cause.** `authors = _comment_headers(dst) - _comment_headers(src)` is a set difference over *author names*, so an author who already appears anywhere in the file can add an unlimited number of fresh comments and never register as added. Two such authors ride in together and the guard says nothing. This is the same failure the commit message cites as the reason for reverting the blanket `GIT_INDEX_FILE` drop — it survived in the replacement. It is also the shape PT-100 ruled on: aggregating before diffing. Diff the raw multiset, aggregate after.

**Correction (implementation-lead, ~4 lines, measured working — third column above).** Replace the set difference with a `collections.Counter` difference over the header **lines**, then take the authors of the surplus:
```
surplus = Counter(header lines in dst_content) - Counter(header lines in src_content)
authors = {_COMMENT_HEADER_RE.match(l).group(1) for l in surplus.elements()}
```
A pure move gives identical multisets → empty → pass. A second comment by an already-present author gives count 2 vs 1 → surplus 1 → that author counted once. `collections` is already imported in cairn.py. `_comment_headers` becomes unused — delete it rather than leave a helper whose only caller was the defect.

**Guard (qa), one:** archive rename staged, plus new comments by **two authors who already appear in the file at HEAD**, committed as `git commit -- <dest>` through the real hook → refuses, naming those two. (Mutation: restore the set difference → the commit is made and the violation ships.) The two existing rename-with-new-authors guards do not catch this: both use authors absent from history, which the set difference happens to get right.

**Everything else verified and passing**, from the commit objects: single `-M --name-status -z` enumeration with NUL parsing (7a459fa); `R`/`C` entries diffed as `-M -- <src> <dst>` with no similarity branch; `A`/`M`/`T` path unchanged; `D` skipped; `-M` passed explicitly on both calls; refusal message, `len(authors) > 1` rule and exit codes untouched; scope confined to `cmd_guard_commit` + `test_comment_guard.py`; the six red guards including the no-flag end-to-end hook path (2d48bf6, 592c8a8).
