## Problem

PT-29 makes collapsed the default, which creates two wants (Mosko, 2026-08-22):

1. **View-state persistence.** Expanded/collapsed lane state is view-local in-memory (PT-16 contract, reasserted by PT-29's ruling) — a refresh resets to all-collapsed. Persist the expanded-lane set **client-side** in `localStorage` (ruled over sessionStorage: a personal dashboard should look how you left it across restarts; reset gesture = collapse the lanes again). The server stays stateless — no disk, no network, no server-side change. Keyed by the existing repo-scoped lane keys (`laneStateKey`), so multi-root safe.
2. **Expand-all / collapse-all control.** Flagged by the architect during PT-29 design: with every lane closed on load, restoring the whole-board view costs N clicks. One control (or pair) in the filter bar.

## Acceptance criteria

- [ ] Toggling a lane persists the expanded set to localStorage; reload restores it exactly (per repo-scoped key — two roots with the same milestone id restore independently)
- [ ] Storage failures (private mode, blocked storage) degrade silently to current in-memory behavior — every read/write guarded
- [ ] Expand-all / collapse-all control present; collapse-all also clears the persisted set (returns to default state, not a stored "everything closed")
- [ ] `collapsedRepos` polarity asymmetry (documented at the state declaration) handled deliberately — either brought into the same persistence model or explicitly excluded with the reason stated
- [ ] Pure logic (set serialization, restore-merge with lanes that appeared/vanished between sessions) in board-logic.js, red-first via node:test
- [ ] No network request on toggle (contract preserved); Swimlanes-off mode untouched

## Notes

- Builds directly on PT-29's `laneExpanded`/`nextExpandedLanes` seam in board-logic.js.
- Supersedes the "flag if state survives reload" line in PT-29's checklist — after this ships, surviving reload is the spec.

### 0. The hazard the issue doesn't mention: localStorage is scoped to ORIGIN, not to project

`localStorage` partitions by origin — `http://localhost:8766`. `config.yml`
ships `port: 8766` as the default, so **every project instantiated from this
template serves its board from the same origin** and therefore shares one
localStorage namespace. Two projects can't run simultaneously (port conflict),
but sequentially they will read each other's blob. Lane keys are
`<repo>::<milestone>` composites, so most cross-project keys won't collide by
value — but they accumulate in one bucket, and two projects whose root ids
happen to match (both `PT`, both `V1`-era defaults) collide outright.

This is the bare-id-across-roots defect class wearing a new coat: a key that
looks unique because it's scoped to the wrong thing. Ruling: **namespace the
storage key by the primary root id.** Double-scoping (namespace by project,
keys scoped by root) is a few bytes and closes the outer dimension.

> **Judgment call.** The primary root id is a *weak* project discriminator —
> two projects both using `PT` still collide. A strong one would need the
> server to expose a board identity, which AC6's "no server-side change"
> forbids. Cost: residual collision between same-prefixed projects on the same
> port, degrading to "some lanes open that you didn't open" — annoying, not
> destructive, and cleared by collapse-all. Reversal: add a board-identity
> field server-side and namespace on that instead; the `v` field below makes
> that a migratable change rather than a silent reset.

### 1. Storage schema

**Key:** `cairn.board.expandedLanes.<primaryRootId>`

**Value:** JSON — `{"v": 1, "lanes": ["PT::0.6.1", "PT::(none)"]}`

Three rulings inside that:

**(a) An ARRAY of expanded keys, not the map.** The map's values are always
`true` — PT-29's invariant is that absence is the only encoding of "closed"
and `false` is never stored. Serializing the map as an object would persist a
redundant value and reopen the door to a stored `false` arriving back from
disk, which is the exact second-encoding hazard PT-29 closed structurally. An
array *cannot* express "closed". Keep it that way.

**(b) The array is SORTED on serialize.** Two sessions holding the same set
then produce a byte-identical blob regardless of the order lanes were
clicked — so a test can assert the exact string, and a human can eyeball the
blob in devtools and diff it. Cost: a sort per write, on a list of dozens.

**(c) The version goes INSIDE the value, not in the key name.** Versioning by
key (`...expandedLanes.v2.PT`) means a schema bump silently orphans the user's
state — it reads to them as "the board forgot everything after an update" —
and leaves the old key as permanent garbage nobody will ever remove. With `v`
in the value you can decide per-bump whether to migrate or reset, and you can
`removeItem` the old shape deliberately. The parse guard has to exist anyway
(see § 5), so the version branch costs one comparison on top of work you're
already doing.

**Unknown `v` → return the empty map** (and let the caller `removeItem`). No
forward-migration attempt.

> **Judgment call.** Silently resetting on an unrecognised version means a
> user who downgrades cairn loses their expansions. Cost: a few clicks, once,
> in a scenario that barely occurs. Reversal: add a migration branch keyed on
> `v` — which is possible precisely because of ruling (c).

### 2. Restore-merge semantics — and why there is NO pruning

The issue's AC5 asks for "restore-merge with lanes that appeared/vanished
between sessions". Here is the ruling, and it is smaller than the AC implies:

- **A current lane with no stored key** → collapsed. Not a special case at
  all; it is PT-29's absence-means-collapsed invariant doing its job. Zero
  code.
- **A stored key with no current lane** → **kept, untouched, inert.**

**Do not prune stale keys.** Pruning is the tempting move and it is a trap,
for two independent reasons:

1. *The current lane set is filter-dependent.* If the user has a text filter
   active that hides milestone 0.5, pruning against what's rendered deletes
   their 0.5 expansion. Clearing the filter then shows 0.5 collapsed. That is
   real data loss caused by a transient view.
2. *Pruning against the unfiltered universe requires reconstructing lane keys
   exactly the way `renderKanban` does — and the two branches don't build them
   the same way.* Single-root uses `primaryRootId(board)` for **every** lane
   regardless of each issue's own `issue.repo`; multi-root uses the section's
   `root.id`. A "universe" builder that reads `issue.repo` uniformly would
   disagree with the single-root branch and prune **live** keys on the first
   save. That's a second copy of a key-construction rule that must stay in
   sync with a first copy — the duplicated-inline-expression class PT-22/PT-29
   exist to close.

Not pruning deletes both problems and costs almost nothing: the stored set
grows by at most one entry per milestone that has ever existed per root, ~15
bytes each. That is bounded by project history, not by user input — it is not
an unbounded-growth path. And a stale key is genuinely inert: `laneExpanded`
is only ever consulted for a lane being rendered, so a key with no lane is
never read.

> **Judgment call.** AC5 reads as though a merge algorithm is expected; the
> ruling is that the merge is a plain union with nothing discarded. The
> *decision* still lands in board-logic.js as tested pure logic (§ 5) — it is
> the function's contract that's simple, not its absence. Cost: the blob
> retains keys for deleted milestones indefinitely. Reversal: add a pruner —
> but only against a lane universe built by a function `renderKanban` itself
> calls, never a parallel reimplementation.

**Instead of pruning, cap.** If the parsed `lanes` array exceeds
`VIEW_STATE_MAX_LANES` (500), discard the whole blob and start empty — treat
it as corrupt. One line, no ordering metadata needed, and it bounds a
pathological or foreign blob. No real user has 500 expanded lanes.

**Restore fires EXACTLY ONCE, in the board-load path — not in the render
path.** Guard it with a `state.viewStateRestored` flag and do it where the
first board payload lands. `renderKanban` runs on every refresh and every
toggle; restoring there would overwrite a toggle with the stored value the
instant the user made it. The storage key isn't even derivable until the
board arrives (it needs `primaryRootId`), so the load path is also the
earliest correct moment.

### 3. `collapsedRepos` — excluded from persistence, deliberately

AC4 demands a stated call. **Exclude it.** Three reasons, in order of weight:

1. **It has the opposite polarity, so persisting it means persisting
   closures.** One blob would then hold two collections with opposite
   meanings — the asymmetry PT-29 documented as a defect source, promoted
   from an in-memory quirk one comment can cover to a durable on-disk
   compatibility surface that outlives the comment.
2. **There is no problem to solve.** Repo sections default to *expanded*. The
   N-clicks-to-restore complaint that motivates this whole feature simply
   doesn't apply to them.
3. **Its failure mode is much worse than a lane's.** A persisted collapsed
   repo means opening the board next session to an entire repository reduced
   to one header row, with nothing on screen explaining why its issues are
   gone.

> **Judgment call.** A user who collapses a noisy repo re-collapses it each
> session. Cost: one click per session, for a control that is not the
> feature's subject. Reversal has a **precondition** — normalise
> `collapsedRepos` to `expandedRepos` (opt-in-open, matching `expandedLanes`)
> *first*, so both collections mean the same thing, and only then add a
> `repos` array to the same blob under `v: 2`. Persisting the asymmetry as-is
> is the one path that should not be taken.

### 4. Expand-all / collapse-all

**Two buttons, not one toggle**, in the `.filters` bar after the Swimlanes
checkbox. A single toggle has to derive its own label from current state, and
with a mixed set — some lanes open, some closed — there is no correct label;
it's a tri-state control wearing a two-state affordance. Two buttons are
unambiguous and each is idempotent.

**Expand all** = union the currently-**rendered** lane keys into the existing
set. Additive only; it never removes a key, so lanes hidden by an active
filter keep whatever they had.

**Collapse all** = set the map to empty **and `removeItem` the storage key** —
not `setItem("[]")`. AC3 says this in words ("returns to default state, not a
stored 'everything closed'") and it falls straight out of PT-29's invariant:
the default state *is* the empty set, and no-key is the cleanest
representation of empty. This is also the reset gesture the Problem section
names.

> **Judgment call — and note it goes the OPPOSITE way to § 2, on purpose.**
> Expand-all builds from the *filtered* lane set while § 2 refuses to prune
> against the filtered lane set. The distinction is destructive vs
> non-destructive: filter-dependent *pruning* destroys state the user created;
> filter-dependent *expanding* merely declines to create state they never
> asked for. Cost: clear a filter after expand-all and the newly-revealed
> lanes are collapsed. Reversal: build from the unfiltered lane set instead —
> which needs the same universe builder § 2 warns about, so take the warning
> with it.

**Both buttons are `hidden` when Swimlanes is off** — no lanes exist to act
on. Hidden, not disabled: a disabled control invites "why is this greyed
out", and `filter-repo` already establishes the toggle-the-`hidden`-attribute
precedent in `renderHeader`.

### 5. What lands where

**board.js** (touches a browser global, so not board-logic.js) — three
guarded primitives, each wrapping the `localStorage` reference **inside** the
`try`, never at module top level: merely *touching* `localStorage` throws in
some blocked-cookie configurations, so a top-level `var LS = localStorage`
would take the whole board down on load rather than degrading.

- `readViewState(key)` → string or null
- `writeViewState(key, value)` → void, silent on failure
- `clearViewState(key)` → void, silent on failure

No `storageAvailable` flag — silent per-call degradation is enough, and a
cached flag is state that can go stale. A failing write costs one throw/catch
per toggle and nothing else.

**board-logic.js** — pure, tested, synchronous-render-pass convention as
always:

| Export | Contract |
|---|---|
| `VIEW_STATE_VERSION` = 1, `VIEW_STATE_MAX_LANES` = 500 | Constants, exported so tests assert the same values the code uses |
| `viewStateKey(primaryId)` | `"cairn.board.expandedLanes." + primaryId` |
| `serializeExpandedLanes(map)` | JSON string; own+truthy keys only; `lanes` sorted |
| `parseExpandedLanes(raw)` | → `Object.create(null)` map. Never throws, for any input |
| `expandAllLanes(map, laneKeys)` | Union, non-mutating, returns a fresh `Object.create(null)` map — same contract shape as `nextExpandedLanes` |

`viewStateKey` does **not** guard a null `primaryId` — it yields
`"cairn.board.expandedLanes.null"`, matching `laneStateKey`'s explicitly
documented non-guarding rather than inventing a third convention for absent
repo ids. Noting the tension honestly: unlike `laneStateKey`'s, this string
*is* user-visible in devtools, which is the argument the other way. Consistency
with the neighbouring key builder wins; if that's ever revisited, revisit both
together.

**No `collapseAllLanes()` function.** Collapse-all is `Object.create(null)`
plus `clearViewState` — a helper whose entire body is one expression
containing no decision is indirection, not abstraction.

### Red-first test surface (QA's lane)

`parseExpandedLanes` is the highest-value target in this feature — it parses
untrusted persisted input that survives across versions, and it is the one
function a hostile or stale blob reaches first.

1. round-trip: `serialize` → `parse` yields an equal map
2. `serialize` emits sorted `lanes`; **byte-identical output** for the same
   set built in different insertion orders
3. `serialize` never emits a `false` value and never emits a key absent from
   the map
4. `parse` returns an empty map and **does not throw** for every one of:
   `null`, `""`, `"not json"`, `"[]"`, `"{}"`, `'{"v":1}'`,
   `'{"v":1,"lanes":"x"}'`, `'{"v":1,"lanes":[1,2]}'`, `'{"v":9,"lanes":["a"]}'`,
   and an array longer than `VIEW_STATE_MAX_LANES`
5. `parse` returns an `Object.create(null)` map — a prototype-shaped entry in
   `lanes` restores as a real key and reads correctly through `laneExpanded`
6. after restore, `laneExpanded` agrees for every stored key, and a lane key
   absent from the blob reads collapsed
7. a stale key (no corresponding lane) survives a round trip and changes no
   live lane's state
8. **two roots, same milestone id: only the stored one restores expanded** —
   the bare-id guard, mandatory, and it must build both keys via
   `laneStateKey` rather than hand-writing the composite
9. `expandAllLanes` unions rather than replaces, does not mutate its input,
   and is a no-op on an empty lane list
10. `viewStateKey` differs across primary root ids and is stable for one

Everything the ruling specified is met, and two things are better than
specified:

- **Guarded storage is exactly the toc.js shape.** All three primitives
  reference `localStorage` *inside* their own `try`; no module-level
  reference, no cached `storageAvailable` flag. A blocked-storage
  configuration degrades per-call instead of taking the board down at load.
- **No pruning anywhere.** `parseExpandedLanes` has no notion of which lanes
  are live and nothing else prunes; a stale key rides through inert, and
  there's a test asserting exactly that.
- **Expand-all cannot drift from the render's key construction — this is
  better than the ruling asked for.** I warned against a parallel "universe
  builder"; the implementation avoids reconstruction *entirely* by capturing
  the keys at the point of render. At both call sites the **same local
  `stateKey` variable** is passed to `milestoneLaneEl` and pushed to
  `state.renderedLaneKeys` — not a recomputation that must agree, the
  identical value. The array is reset at the top of each `renderKanban`
  pass, so it describes one pass only, and it naturally respects both the
  active filters and `collapsedRepos` because a collapsed repo section never
  reaches the `forEach` that pushes. There is no drift surface left to guard.
- **Collapse-all removes the key** rather than storing an empty array, and
  **restore fires once from the board-load path**, never from `renderKanban`.
- **`collapsedRepos` exclusion is documented at the state declaration** with
  all three reasons, alongside the PT-29 polarity comment it extends.
- **The bare-id guard is present** and builds both keys via `laneStateKey`.
- **The malformed-input table covers all ten cases** from the ruling plus the
  at-cap boundary.

### RECORDED findings

**1. Both new buttons are visible in LIST view, where Collapse-all is
destructive and silent. This is a gap in my ruling, not a deviation from
it.** `/` and `/list` are served the same `board.html` (`cairn.py`,
`_send_static("board.html")` for both paths), and `renderHeader` runs in both
views, so `expandAllBtn.hidden = !state.swimlanesOn` leaves both buttons
showing in list view whenever the Swimlanes checkbox is checked — its default.
In list view `renderKanban` never runs, so `state.renderedLaneKeys` is
permanently `[]`:

- *Expand all* → unions nothing. Harmless no-op.
- *Collapse all* → clears the map **and `removeItem`s the storage key**, from
  a view where no lanes are visible to give any feedback that it happened.
  The user discovers it on returning to Kanban, everything collapsed.

A destructive control shown where its effect is invisible. My § 4 said
"hidden when Swimlanes is off" and simply didn't enumerate list view — the
same under-enumeration as PT-29's `.repo-group > .board` gap. One line each:

```js
expandAllBtn.hidden = isListView || !state.swimlanesOn;
collapseAllBtn.hidden = isListView || !state.swimlanesOn;
```

`isListView` is already a module-level var in scope at that point. Recommend
taking it inside PT-30: it is two lines, and the alternative is shipping a
button that can silently discard the user's state from the wrong screen.

**2. Two storage representations of "nothing expanded".** Collapse-all
`removeItem`s the key; individually collapsing the *last* expanded lane calls
`persistExpandedLanes`, which writes `{"v":1,"lanes":[]}`. Both parse to an
empty map, so there is no correctness impact — but it is the same
two-encodings-of-one-state smell this design eliminates everywhere else
(PT-29 refusing to store `false`; the serialized array making "closed"
structurally unrepresentable). One-line tightening makes "the key exists iff
at least one lane is expanded" a true invariant: have `persistExpandedLanes`
call `clearViewState` when the map is empty. Cheap, and it gives the storage
layer the same shape the in-memory layer already has.

**3. `restoreViewStateOnce`'s comment describes call sites that don't
exist.** It has exactly one caller — `init`'s first `apiGetBoard().then`. The
comment says it is "a no-op on every subsequent apiGetBoard resolution
(refreshBoardSilently's 4s poll, SSE push, focus/visibilitychange)", but it
is never invoked from any of those. The `viewStateRestored` guard is
therefore defending a pattern that doesn't occur — harmless, and cheap
insurance if a call site is ever added, but the comment reads as though the
guard is load-bearing when it isn't. Separately, the flag is set *before* the
`if (!state.board) return;` line, so a null first payload would mark the
restore done without doing it and never retry. Not reachable today (no ETag
on the first request, so no 304, so `data` is non-null), but moving one line
makes it robust rather than accidentally-safe.

**4. `parseExpandedLanes` is lenient on mixed-type arrays, strict everywhere
else.** `'{"v":1,"lanes":["PT::0.5",1]}'` keeps the valid string and drops the
number, where every other malformation discards the whole blob. Both postures
are defensible; only the inconsistency is worth noting, and the practical
impact is nil. Recording once, not proposing a change.

**5. For the Chrome pass.** The filter bar gains two always-present controls;
it is `flex-wrap: wrap` so it should degrade fine, but confirm at a narrow
width, and confirm `.view-state-btn` reads as secondary next to the accent-
coloured `+ New` button rather than competing with it.

# PT-30 browser-verification checklist (team-lead's Chrome pass)

Acted against sha `f88ee71` (red tests) on `feature/pt-30-view-persistence`, on top of the
architect's ruling at `214a13a`. Run this AFTER implementation-lead's task #9 lands and the
JS suite (`node --test scripts/cairn/tests/js/*.test.js`) is green — this checklist covers
what only a real browser/localStorage can confirm: persistence across an actual reload,
private-mode degradation, and the two new buttons' visible behavior.

## Setup

1. Start the board on this branch. Open DevTools → Application → Local Storage →
   `http://localhost:8766` so you can inspect the raw blob directly.
2. Note the primary root id shown in the board (single-root is fine; a multi-root board is a
   bonus for step 5 but not required — the mandatory cross-root case is unit-tested).

## 1. Persistence across reload

1. Expand two or three milestone lanes (mix of adjacent and non-adjacent).
2. In DevTools, confirm a key named `cairn.board.expandedLanes.<primaryRootId>` now exists
   under Local Storage, with a value shaped like `{"v":1,"lanes":[...]}` — lanes sorted
   ascending, one entry per lane you expanded.
3. Hard-reload the page. Assert: **the exact same lanes are expanded** — not "roughly the
   same", the identical set, in the identical (collapsed-by-default-elsewhere) state.
4. Collapse one of the previously-expanded lanes. Assert: the localStorage value updates
   immediately (re-check DevTools) — the removed lane's key is gone from `lanes`, not present
   with some falsy marker.
5. Reload again. Assert: the collapse from step 4 also survived — the lane is collapsed on
   this reload too.

## 2. Expand-all / Collapse-all

1. With Swimlanes **on**, locate the two new buttons in the `.filters` bar, after the
   Swimlanes checkbox. Assert: two distinct buttons (not one toggle) — confirm by their
   labels/tooltips reading like "Expand all" / "Collapse all", not a single control that
   changes label.
2. Click **Expand all**. Assert: every currently-rendered lane opens (respecting any active
   filter — a lane hidden by a text/milestone/assignee filter should NOT be forced open).
3. Apply a filter that hides at least one lane, then click **Expand all** again. Assert: only
   the lanes still visible under the filter get expanded — this is the ruling's deliberate
   "expand-all builds from the filtered set" asymmetry, not a bug if a hidden lane stays as it
   was.
4. Click **Collapse all**. Assert: every lane collapses, AND the DevTools localStorage entry
   for `cairn.board.expandedLanes.<primaryRootId>` is **entirely removed** (key absent, not
   present with `"lanes":[]`) — this is the explicit "returns to default state, not a stored
   'everything closed'" acceptance criterion.
5. Reload after Collapse all. Assert: board loads all-collapsed (the PT-29 default), and no
   stale localStorage key reappears.
6. Turn Swimlanes **off**. Assert: both Expand-all/Collapse-all buttons disappear entirely
   (`hidden`, not just greyed out — inspect the DOM, the buttons should carry a `hidden`
   attribute, not `disabled`).
7. Turn Swimlanes back **on**. Assert: both buttons reappear, and their function still works
   (not just the visibility).

## 3. Private-mode / storage-blocked degradation

1. Open the board in an Incognito/Private window (or use DevTools' "block third-party
   cookies and site data" setting, whichever more reliably throws on `localStorage` access in
   your Chrome build).
2. Assert: the board loads normally — **no crash, no blank page, no console error that halts
   rendering**.
3. Toggle a few lanes. Assert: the toggles work exactly like the in-memory PT-29 behavior —
   they open/close, they just don't survive a reload. No error toast, no visible sign anything
   is "wrong" to the user.
4. Reload in the same private window. Assert: board resets to all-collapsed (expected — there
   was nowhere to persist to) rather than erroring.
5. Check the DevTools console throughout this section for any uncaught exception —
   `readViewState`/`writeViewState`/`clearViewState` must swallow storage errors silently, per
   the ruling; an uncaught exception here means a `try` is missing somewhere (possibly around
   the `localStorage` reference itself, not just `.getItem`/`.setItem` — the ruling flags this
   as the "surprising" failure mode: merely *touching* `localStorage` can throw in some blocked
   configs, before you ever call a method on it).

## 4. No network request on any of this feature's actions (PT-16/PT-29 contract, re-check)

1. Open the Network tab, clear it.
2. Toggle a lane, click Expand all, click Collapse all, reload.
3. Assert: no new XHR/fetch fires for any of these actions beyond whatever polling already
   runs independently (e.g. the SSE connection). Persistence is `localStorage`-only, never a
   network round trip.

## 5. Cross-root independence (bonus, only if a multi-root board is available)

1. Expand a milestone lane under root A that shares a milestone id with root B, WITHOUT
   expanding root B's same-id lane.
2. Reload. Assert: only root A's lane is expanded; root B's same-id lane stays collapsed. This
   is the DOM-level twin of the mandatory unit test (`view-state.test.js`, "two roots, same
   milestone id: only the stored root's lane restores expanded").
3. If not available, note "single-root only, cross-root restore not covered live" — the unit
   test is the coverage of record for this case.

## Regressions to re-confirm (nothing here should have moved)

1. Drag a card between status columns inside an expanded lane. Assert: still works, no
   regression from PT-29's containment cards.
2. Open the drawer from a card. Assert: still works, opens/closes cleanly.
3. Collapsed-lane status-breakdown chips (PT-29) still render correctly on a freshly-loaded
   (or Collapse-all'd) board.
4. Disclosure triangles (▼/▶, fixed-size box, aria-expanded) still correct after this feature's
   changes — this feature touches the SAME toggle click handlers, so a regression here is
   plausible and worth one quick look.

## What must NOT happen (regression watch, whole session)

- No uncaught console error anywhere in this checklist, private mode included.
