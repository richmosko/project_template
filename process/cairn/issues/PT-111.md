### @architect — 2026-09-08

**Gate 1 ruling (architect).** Measured first, over the real transcripts (`~/.claude/projects/<slug>/*.jsonl`, 83 files, no duplicate sessionIds) and `metrics/test-runs.jsonl` for 2026-09-05 → 09-10: **165 transcript FULL_SUITE steps, 166 ledger `full` records**. Taxonomy of the 165, by id-linked tool result: **108 ran with a visible `Ran N tests` summary · 49 ran with stdout redirected (`nohup`/`> file`) · 5 refused by the PreToolUse guard · 3 error results.** Of those 3: one wrong-path (`cd scripts/cairn` from a worktree — never ran), one chain failure, and **one `python3 run_tests.py --gate green` that exited 1 because a test FAILED — a real run.**

**The brief's primary rule does not survive that.** One-to-one assignment of steps to records on run start (`ts − seconds`, `who`-keyed, window [−120 s, +300 s]) matches only **80 of 165** steps and leaves **86 records** unmatched (`who`-agnostic: 88/165). The 49 redirected runs *cannot ever* have a record — bare `unittest` doesn't self-record and the hook's scrape needs stdout. Gating "counts as a run" on a ledger match would relabel ~30 % of real runs as blocked. **The ledger is a positive corroborator, never a gate.**

**Ruling — classify from the tool result, in this precedence.** Per transcript, a pre-pass maps `tool_use_id → (is_error, result text, toolDenialKind)`; `audit_agent` resolves each FULL_SUITE step against it (two passes over the same records; results always follow their use).

1. **ledger match → `FULL_SUITE`** (executed). Match one-to-one on start time as above; `who` equality only when the record's `who` is non-null (49 of 166 are null — main-session and unpatched runs). Measured residual for true pairs: p50 1.5 s, p90 5.8 s.
2. **`Ran <N> tests` in the result → `FULL_SUITE`.** Exit status is not the discriminator: a red suite exits 1 and is still a run (case above).
3. **error result carrying `toolDenialKind` + the guard's marker → `full_run_blocked` (reason `guard`).**
4. **error result with no run summary → `full_run_blocked` (reason `no_run`)** — wrong path, bad flag, refused by the runner's own arg parsing.
5. **otherwise → `FULL_SUITE`** (the redirected-stdout case; absence of evidence is not evidence of refusal).

**Item (3) answered: the refusal text is used *in addition to* the ledger, and only id-linked.** A free-text scan is wrong by measurement: `.claude/hooks/test_run_guard.py` quotes its own refusal message in its docstring, so a plain scan counts a `Read` of that file as a denial (hit in my first probe).

**Item (4) dissolves.** Because the ledger only ever promotes a step to "executed", a window with no ledger needs no special case or label — nothing is downgraded by its absence. Rename the scorecard row to `full_suite_runs (executed)` and add a `full_run_blocked` row and a per-agent `blocked` column. **Blocked attempts are shown but never counted against the `full_suite_runs` cap of 4**, and get no cap of their own.

**In scope, same over-count defect (6 of 165 measured).** `classify_bash` tokenises heredoc bodies, so `cat > verdict.md <<'EOF' … python3 run_tests.py --gate verdict … EOF` counts as a full run — five architect steps and one lead step in the window are quoted text, not runs. Strip heredoc bodies **in `loop_stats.py` only** (`_strip_heredocs` before classification). Do **not** touch `_test_run_shared.tokenize`: that is the hooks' guard surface and a heredoc quoting a full run should still be refused there. Hooks unchanged by this feature.

**Guards (qa writes `test_loop_stats.py`; red at gate 2).**
1. Fixture transcript + ledger — one executed gated run, one guard-refused step (`toolDenialKind` + marker, id-linked), one wrong-path step: scorecard shows `full_suite_runs (executed)` 1, `full_run_blocked` 2, and the cap is evaluated against 1.
2. False-positive controls, both: (a) a `Read` result whose content is `test_run_guard.py`'s source is not a denial; (b) a denial result whose `tool_use_id` belongs to a *different* step does not mark this one.
3. Exit-1-but-ran: a result containing `Ran 1577 tests` + `FAILED` classifies `FULL_SUITE`, not blocked.
4. Redirected run: `nohup python3 -m unittest discover -s tests > /tmp/x 2>&1`, empty stdout, no ledger record → `FULL_SUITE`.
5. Ledger override + negative control: an error-result step with a matching record (start within window, same `who`) → `FULL_SUITE`; the same step with the record moved 20 min away → `full_run_blocked`.
6. Heredoc: the `cat > f <<'EOF' … EOF` form is neither `FULL_SUITE` nor `full_run_blocked`; controls — the same command without the heredoc wrapper is `FULL_SUITE`, and `_test_run_shared.is_full_suite_run` on that string is unchanged (True).

### @architect — 2026-09-08

**Addendum 1 to the gate-1 ruling (architect), for qa's fixture.** The ruling @ ec75732 already answers (3): the refusal signal stays in, paired by `tool_use_id`, and it is `audit_agent` that gains the pre-pass — qa is right that none exists today. Here is the record shape to build the fixture from, read off a real denial in `~/.claude/projects/<slug>/8cdf13a4-….jsonl` (2026-09-07T06:51:53Z), so the fixture is faithful rather than invented:

- The **use**: an `assistant` record, `message.content[]` block `{"type": "tool_use", "id": "toolu_…", "name": "Bash", "input": {"command": …}}`.
- The **denial**: a later `user` record carrying a top-level **`toolDenialKind`** key, with `message.content[]` block `{"type": "tool_result", "tool_use_id": "<same toolu_…>", "is_error": true, "content": "PreToolUse:Bash hook error: [in=$(cat); case \"$in\" in *unittest*|*run_tests*) … ]: test_run_guard: refusing an un-tiered full-suite run. Mid-loop, narrow it: …"}`. The same text also appears in that record's top-level `toolUseResult` as `"Error: PreToolUse:Bash hook error: …"` — pair on the content block, not on `toolUseResult`.
- The marker to match is the guard's own first sentence, `test_run_guard: refusing an un-tiered full-suite run`, **and** `toolDenialKind` must be present. `is_error` alone is not enough: measured, 3 of 8 error results on full-run steps are ordinary failures, one of them a real run that exited 1 on a failing test.
- A denial record follows its use in file order, so a single forward pass that buffers unresolved steps works; the ruling's two-pass is the simpler reading, not a requirement.

Guard 2(a) in the ruling exists because the marker string is *also* present in `.claude/hooks/test_run_guard.py`'s docstring: a fixture whose `Read` result contains that file's source must not count as a denial. Keep that fixture case verbatim from the file rather than a paraphrase.
