## 1. App location — `scripts/cairn/dashboard/` (source), `scripts/cairn/dashboard/dist/` (built)

Sibling of `board/`, under the server that serves it. `DASHBOARD_DIR =
Path(__file__).resolve().parent / "dashboard" / "dist"`, exactly the `BOARD_DIR`
constant's shape — cwd-independent, one line of binding.

Why not `apps/dashboard/`: **this is a template.** `apps/` is the most natural
home for the *downstream project's own product code*; template tooling must not
squat it. A cloner who runs `apps/` for their real app would find our tool
already living there and infer a monorepo convention we are not prescribing.

Second reason, load-bearing: cairn is a spin-off candidate (`/spin-off-component`).
Keeping the dashboard inside `scripts/cairn/` keeps that extraction one directory
move. It survives the extraction functionally too — see §4: the payload reads
only tracker files + git, nothing else in this repo.

Third: PT-57 (board → shadcn) gets an obvious home next door, and can share the
same package.json rather than standing up a second toolchain.

**Trade-off accepted:** a Node project nested under `scripts/` is unusual, and
root-level tooling that auto-discovers `package.json` won't find it. Cost is one
line of README. If the dashboard ever must outlive cairn, the move is mechanical
(one constant + one route prefix).

**Framework flavour: plain Vite + Svelte 5 + TypeScript (SPA), not SvelteKit.**
There is no SSR, no server route, no prerender need — the Python server is the
backend. SvelteKit + adapter-static buys a router and prerender semantics we'd be
configuring around for a single page. shadcn-svelte ships a first-class Vite
install path. Scaffold: `npm create vite@latest` (svelte-ts) → `npx sv add
tailwindcss` → `npx shadcn-svelte@latest init` (npm, not bunx — no bun on this
machine; node 26.7.0 / npm 11.19.0 present). If `sv add` refuses a non-Kit
project, fall back to manual Tailwind v4: `npm i -D tailwindcss @tailwindcss/vite`,
`@import "tailwindcss";` in `app.css`, plugin in `vite.config.ts` — do not let
that block you and do not switch to SvelteKit to dodge it.

**Two Vite settings are not optional** (see §3 and §4):
- `base: '/dashboard/'` — emitted asset URLs must be absolute under the prefix.
- `build.rollupOptions.output.{entryFileNames,chunkFileNames,assetFileNames}` set
  to stable `[name]` forms — no content hashes. Rationale in §3.
- `server.proxy` for `/api` → `http://127.0.0.1:8766` so `npm run dev` runs
  against real data.

`package-lock.json` is committed. `node_modules/` stays ignored.

## 2. Fonts — self-hosted via Fontsource variable packages. No CDN, confirmed.

This resolves the design spec's Pushback #2 in the direction the spec itself
flagged: the board's offline/zero-network contract still holds for `cairn serve`,
and a template that phones Google on every page load is a worse default than one
that ships 380KB once.

Concrete packages (all present on npm at **5.3.0**, verified today):

| Family | Package | Family name in CSS |
|---|---|---|
| Merriweather (body, `--font-sans`) | `@fontsource-variable/merriweather` | `'Merriweather Variable'` |
| Space Grotesk (headings, `--font-heading`) | `@fontsource-variable/space-grotesk` | `'Space Grotesk Variable'` |
| Geist Mono (`--font-mono`) | `@fontsource-variable/geist-mono` | `'Geist Mono Variable'` |

Those family strings match the stacks already written in the spec's Typography
table verbatim — don't re-invent them.

**Import the package default entry only** (`import '@fontsource-variable/
merriweather'` etc. in `src/main.ts`, not a CSS `@import` — keeps Tailwind v4's
`@import "tailwindcss";` at the top of `app.css` where it must be). The default
entry is the `wght` axis, normal style, all unicode subsets, `font-display: swap`.

Measured emitted weight at that import (unpkg file metadata, 5.3.0): Merriweather
5 files / 263KB, Space Grotesk 3 / 47KB, Geist Mono 6 / 69KB — **~14 woff2,
~380KB**, committed once and inert until a version bump. Do **not** import
`opsz.css` / `wdth.css` / the italic entries: Merriweather's full axis set is
4.6MB of woff2 and we use none of it.

Available trim if dist size ever annoys: hand-write `@font-face` blocks against
`…/files/*-latin-wght-normal.woff2` for latin+latin-ext only → ~245KB → ~140KB.
Not worth owning the declarations today.

No manual `<link rel=preload>` in v1. If FOUC is visible on first paint, preload
the *latin* Merriweather file only — one file, not the set.

Reminder from the spec that bites here: display/stat numbers are Merriweather
**bold**, not Space Grotesk. Face is by role, not size.

## 3. Build output — committed, unhashed, at `scripts/cairn/dashboard/dist/`

**Commit the built output.** The template's strongest property is that a fresh
clone runs `python3 scripts/cairn/cairn serve` with nothing but python3 — it is
why the board is vanilla in the first place. Making `/dashboard` require `npm ci`
(hundreds of MB of node_modules) before it renders would break that property for
every cloner, on the one surface most meant to be seen immediately.

The root `.gitignore` ignores `dist/` globally, so this needs an explicit,
commented negation — ordering matters, negation must come after:

```
dist/
!scripts/cairn/dashboard/dist/
```

(`dist/` matches only directories *named* dist, so nested `dist/assets/` is
re-included fine once the parent is un-ignored.)

**Disable content hashing.** `_send_static` already sends `Cache-Control:
no-store` on every asset (PT-49 §7) — hashed filenames buy exactly nothing
against a no-store server, while guaranteeing that every rebuild adds new blobs
and orphans old ones, so the repo grows monotonically with each UI change. Stable
names mean a rebuild overwrites the same paths. Keep `no-store`; that and
unhashed names are one decision, not two.

**What `cairn serve` does when dist is missing: nothing clever.** It does not
build, does not shell out to npm, does not crash, does not 500. `GET /dashboard`
returns **503** with a small python-generated HTML page naming the fix literally
(`cd scripts/cairn/dashboard && npm ci && npm run build`). `GET /api/dashboard`
keeps working — it is pure python and has no build dependency. `cairn check` does
**not** lint on dist presence: dist is not tracker data, and a lint error on a
clean clone of a repo whose dashboard was never built is noise.

Build-at-serve-time was rejected outright: it makes a fast read-only localhost
tool depend on a Node toolchain at runtime and turns a 40ms startup into seconds.

**The accepted cost is staleness** — a source edit shipped without a rebuild
serves an old bundle. Discipline, documented in `scripts/cairn/dashboard/
README.md`: *any PR touching dashboard source rebuilds and commits dist in the
same PR.* Same class of accepted risk as the vendored Mermaid bundle. A
`/finish-feature` freshness check (dist mtime vs newest src mtime) is a
reasonable follow-up, not this issue.

## 4. Serve integration — extend the existing server; one static sender; SSE + slow poll

**Extend `cairn.py`'s server. No second process, no second port.** Roots
resolution, the engine payload builders, the ETag machinery and the SSE
broadcaster all already live there; a second server would duplicate roots
resolution and invent a CORS problem we don't have.

**Static:** do not write a second static handler. Widen the existing one to
`_send_static(rel_path, base=BOARD_DIR)` so the traversal guard (`resolve()` +
`relative_to`) stays in exactly one place, and pass `DASHBOARD_DIR` from the
dashboard branch. Extend the MIME map — it currently knows html/js/css only; add
`.woff2 → font/woff2`, `.svg`, `.png`, `.ico`, `.json`, `.map`. A woff2 served as
`application/octet-stream` mostly works and is still wrong.

**Routing:**
- `/dashboard` and `/dashboard/` → `dist/index.html` (200). No redirect needed —
  `base: '/dashboard/'` makes every asset URL absolute, so there is no
  relative-resolution hazard at either spelling.
- `/dashboard/<rel>` → static from `DASHBOARD_DIR` when the resolved target is a
  file.
- **SPA fallback, narrowly:** target not a file **and** the path has no file
  suffix → `index.html` (200). A path *with* a suffix that doesn't exist → **404**.
  Returning HTML for a missing `.js` is the classic hours-lost debugging trap;
  don't.
- dist absent → 503 per §3.

Take `dashboard_dir: Path = DASHBOARD_DIR` as a `make_server` keyword — the
`source_path: Path = Path(__file__)` parameter is the existing precedent, and it
is what lets the harness test the missing-dist 503 branch without monkeypatching
a module global.

**`GET /api/dashboard`** — new endpoint, sibling of `/api/board`, assembled
server-side only (no git from the browser, per the AC). Payload:

- `git`: `{branch, dirty, head, latest_tag}` — `git -C <primary root path> …`
  (`rev-parse --abbrev-ref HEAD`, `status --porcelain`, `rev-parse --short HEAD`).
  Bounded `timeout=5`, **never raises**: git missing or not-a-worktree degrades
  to `null` + a warning string, exactly the `read_git_tags` / `_git_mv_or_rename`
  contract. Reuse `read_git_tags` for the tag set rather than a fourth subprocess.
- `tracker`: counts by status, **from the same load/parse path `/api/board`
  uses**. No second parser — two counters over the same files is a guaranteed
  future disagreement.
- `check`: `check_repo(primary_root.path)` → `{ok, errors}`.
- `release`: **derived from the tracker + git tags, NOT by parsing `STATE.md`.**
  This is the one place the AC's wording ("latest tag + release row") had to be
  interpreted, so flagging it explicitly: `read_git_tags`'s comment records a
  deliberate engine constraint — cairn reads *no file outside `process/cairn/`*,
  which is what keeps it spin-off-able (a git subprocess's own `.git` reads don't
  count, which is why branch/dirty above is fine). Parsing `STATE.md` would break
  that, and would couple the server to a human-maintained markdown table that has
  already been restructured twice this month. Milestones carry `target_tag` and
  `ga`; git carries the tags. The release row is that join: latest tag → the
  milestone whose `target_tag` matches → its name/status/ga. If a genuinely
  STATE.md-only field is ever needed, the correct shape is a separate reader
  module the *server* composes, never a read inside the engine.
- `generated_at`.

ETag it: hash the serialized body, honour `If-None-Match` → 304, `Cache-Control:
no-store`. Cheap to write, makes the poll below near-free on the wire.

**Freshness — SSE plus a slow poll, and the reason both are needed.** Subscribe
to the existing `/api/events` and refetch `/api/dashboard` on any frame (coarse
contract, same as the board — never a targeted diff). But the watcher scans
`process/cairn/` only, so a branch switch, a new tag, or a dirty working tree
emits **nothing**. Those fields therefore also need a **15s poll** of the same
endpoint. Do **not** extend the watcher to scan `.git` — that widens the fs-scan
that every board client already pays for, to serve one panel.

**Testing shape** (for qa-engineer): the committed gate is the python harness —
`/api/dashboard` 200 + payload keys + the git-unavailable degradation + ETag/304 +
`/dashboard` 200 + the missing-dist 503 (via the `dashboard_dir` kwarg) + the
suffix-vs-no-suffix fallback split. Build smoke: assert `dist/index.html` exists
and that the asset URLs it references resolve to real files under dist — that
catches a half-committed or stale-by-deletion dist. **No vitest/testing-library
in this feature** — `npm run build` succeeding plus `svelte-check` is the app-side
gate; a component-test harness is a follow-up ruling once there is component logic
worth testing.

Nits for implementation-lead: print the Dashboard URL in `cmd_serve`'s startup
banner next to Kanban/List, and put a link to `/dashboard` on the board header —
an unreachable surface is a broken one.

Also found and fixed along the way (not scope creep, both were bugs in my own
first pass, not the ruling): `git.dirty` needs `status --porcelain
--untracked-files=no` — plain `--porcelain` flagged the tree dirty on any
untracked issue/milestone file, which is the routine, expected state of a
`cairn`-managed repo, not an uncommitted-code signal. And the ETag hash
excludes `generated_at` — hashing the full body meant every request's own
timestamp changed the ETag, defeating 304 entirely.
