## Comments

### @implementation-lead — 2026-08-24

Found during PT-50's real-repo migration. `_git_mv_or_rename` (PT-8-era) runs `git mv` with `cwd=str(src.parent)` but passes the ORIGINAL (possibly relative) path strings as arguments — with a relative `--data-dir` the cwd/arg mismatch makes `git mv` fail, the failure is silent (only `returncode==0` is checked, stderr never logged), and the fallback plain filesystem move leaves an untracked add + unstaged delete instead of a staged rename. Every existing test uses an absolute tempdir `--data-dir`, so untested. Affects `archive_milestone`, `archive_major`, `cmd_archive --done-before`, and `migrate archive-issues` — any real invocation with a relative `--data-dir`. Fix shape: resolve paths before the subprocess call (or run from repo root with repo-relative args) + log stderr on fallback + a relative-data-dir test.

### @implementation-lead — 2026-08-24

Fixed. `_git_mv_or_rename` now resolves `src`/`dest` to absolute paths (`Path(...).resolve()`) before the subprocess call — the `cwd=str(src.parent)` argument was already correct in spirit, but the git-mv argument strings staying relative-to-the-caller's-cwd is what actually caused the mismatch once the subprocess cwd moved; resolving both up front removes the mismatch regardless of the caller's cwd or the relativity of what it passed in. A genuine git-mv failure (returncode != 0 with stderr) now logs one `cairn: warning: ...` line before falling back — never raised, so the fallback still completes; a non-git data dir's expected "fatal: not a git repository" now surfaces as a visible (harmless) warning instead of vanishing silently, same posture the file's other degrade-with-a-warning paths (e.g. `read_git_tags`) already take.

Reproduced the exact symptom first: a new test with a git repo, cwd at the repo root, and RELATIVE `src`/`dest` Path arguments nested under a subdirectory (`sub/old.md` → `sub/new.md`, mirroring `cairn/milestones/PT-1.0.md`'s real nesting) — before the fix, `git status --porcelain` showed ` D sub/old.md` + `?? sub/new.md` (unstaged delete + untracked add, the bug's exact fingerprint); after, `R  sub/old.md -> sub/new.md`. A second case (relative paths where `src.parent` happens to equal the caller's own cwd, i.e. no subdirectory nesting) already passed even pre-fix — confirming the bug is specifically about NESTED relative paths, not relative paths in general, which is why the flat tempdir `--data-dir` every prior test used never caught it.

Tests: `scripts/cairn/tests/test_git_mv_or_rename.py` (new, 4 tests, at the shared helper — not duplicated per caller): the two relative-path/nested-cwd cases above, the pre-existing "fallback still works outside a repo" regression guard, and a new one pinning the warning-logged-but-not-raised contract. All red before the fix (2 failures: untracked-add/unstaged-delete symptom exactly as described above, and an empty-stderr assertion), green after. Full suite: 658/658 (654 baseline + 4 new). `./scripts/cairn/cairn check --data-dir process/cairn` → `ok`. JS untouched (grepped — zero references to `_git_mv_or_rename`/`archive_milestone`/`archive_major` under `scripts/cairn/board/` or `scripts/cairn/tests/js/`), so the JS suite wasn't run for this change.
