From the architect's post-merge PT-60 verification (preserved via PR #131,
see PT-60's addendum comment): the status cards and tracker table render
`{#if data} … {:else}` skeletons with NO error branch, and `data` is only
assigned on success — a failed *initial* load pulses skeletons
indefinitely under the error card. The roster already does it correctly
(`{#if rosterError && !roster}` → message, `{:else if roster === null}` →
skeleton). "A permanently-animating skeleton is the loading-state
equivalent of a fabricated presence value."

**Acceptance criteria**
- [x] Status cards + tracker table mirror the roster's three-state shape
      (error → message, null → skeleton, data → content)
- [x] Guard in qa's established source-guard shape pinning the error
      branch's existence at both sites
- [x] dist rebuilt in the same PR
