## Problem

Feature request (Mosko, 2026-08-22): pull-down-to-refresh on the board — the mobile-style gesture (drag down from the top of the scroll container, release to reload board data). Today freshness comes from SSE live push with poll fallback (PT-1); pull-to-refresh adds an explicit manual gesture for when the viewer doubts freshness (SSE dropped, polling window, laptop resume) or is on a touch device where ⌘R is awkward.

## Acceptance criteria

- [ ] Pull-down past a threshold at scroll-top triggers a board data refetch (same path the poll fallback uses — no full page reload), with a visible pull indicator and release-to-refresh affordance
- [ ] Works with touch (trackpad overscroll deferred to PT-33 — Mosko ruling 2026-08-22, architect-recommended: wheel has no release signal, momentum heuristics fragile); never hijacks normal scrolling mid-list (gesture arms only at scroll-top)
- [ ] No interference with drag-and-drop card moves (gesture must not arm while a card drag is active)
- [ ] Degrades to nothing on browsers without the needed events — no errors, existing SSE/poll behavior untouched
- [ ] Pure logic (threshold/state machine) in board-logic.js, red-first via node:test

and `.drawer` is `position: fixed; overflow-y: auto` (its own scroller,
overlaying the page).

### 1. Event strategy — touch only; the trackpad half of AC2 should be dropped

Four mechanisms get discussed for this gesture. They are not four options:

- **Touch events** (`touchstart`/`touchmove`/`touchend`) — explicit finger
  position, so pull distance is a subtraction; and, critically, a **release
  signal**. Doesn't fire for trackpads.
- **Pointer events** — buys nothing here. Trackpad two-finger scroll does
  **not** emit pointer events (it emits `wheel`), so pointer events don't
  deliver the trackpad case they're usually proposed for. They *would* add
  mouse-drag on the page as a false-positive surface, where a click-drag is
  text selection, not a pull.
- **`wheel` events** — the *only* way to see trackpad overscroll, and the
  reason to say no (below).
- **`overscroll-behavior`** — **not a gesture mechanism at all.** It's a CSS
  property controlling whether overscroll chains or bounces; it exposes no
  event and no hook. The issue lists it alongside the other two as though it
  were an alternative. It isn't — it's a *companion*, and a mandatory one
  (§ 3).

**Ruling: implement the gesture on touch events only. Do not implement
trackpad overscroll.**

> **Judgment call — and this one changes scope, so it needs a decision from
> team-lead/Mosko rather than my say-so.** AC2 currently reads "Works with
> touch and trackpad overscroll". I'm ruling the trackpad half out:
>
> 1. `wheel` has **no release signal**. The whole gesture grammar — pull,
>    hold, decide, release — has no analogue. A wheel implementation must
>    accumulate `deltaY` at scroll-top and fire on a *timer*, guessing when
>    the user stopped.
> 2. **Momentum makes that guess wrong in the common case.** Flick up hard
>    through a long board, hit the top, and the OS keeps delivering negative
>    `deltaY` for hundreds of milliseconds. That is indistinguishable from a
>    deliberate pull without velocity-decay heuristics that are
>    platform-specific and fragile. The failure mode is a board that refetches
>    when you didn't ask — cheap in consequence, but it makes the UI feel
>    haunted, and "why did it just do that" is a worse bug than "it didn't do
>    anything".
> 3. **macOS already draws a native rubber-band bounce** at scroll-top on
>    trackpad overscroll. Layering a second indicator with different physics
>    on top of the OS one reads as breakage.
> 4. **The issue's own Problem statement names touch as the motivating case**
>    ("on a touch device where ⌘R is awkward"). On a trackpad, ⌘R is right
>    there, and SSE + poll already cover freshness.
>
> Cost: trackpad users don't get the gesture, and AC2 must be **amended
> rather than quietly failed** — I'd rather leave the criterion unmet and
> visible than reword it myself. Reversal is deliberately cheap: § 5's state
> machine is **input-agnostic** — it consumes a pull distance, not a touch —
> so adding trackpad later is a new *adapter* feeding the same machine, not a
> redesign.

### 2. Arming state machine

Phases: `idle → pulling → armed → refreshing → idle`.

| Transition | Trigger |
|---|---|
| `idle → pulling` | `touchstart` while `window.scrollY === 0` and no cancel condition, then a `touchmove` with net downward delta > 0 |
| `pulling → armed` | pull distance ≥ `PULL_THRESHOLD` |
| `armed → pulling` | pull distance falls back below the threshold |
| `armed → refreshing` | `touchend` |
| `pulling → idle` | `touchend` below threshold — snap back, no refetch |
| `refreshing → idle` | the refetch settles (§ 4) |

**`armed` must not latch.** Dragging past the threshold and then back up
returns to `pulling`, and releasing there does nothing. Users routinely change
their mind mid-gesture; a latched arm makes the gesture feel like a trap.

**Threshold: 64px** of finger travel. iOS native sits around 60–80px; below
~50px a sloppy scroll attempt at the top triggers it.

**Resistance.** The indicator moves at **half** finger speed, capped at 96px —
the rubber-band feel that tells the user the surface is resisting. This is
presentational and does not affect the phase decision, but it's computed by a
pure function so it's testable.

**Cancel conditions.** Any one of these means the gesture never arms and no
refetch happens:

1. **Not at scroll top on `touchstart`.** This is AC2's "never hijacks normal
   scrolling mid-list", and it's checked at gesture *start*, not continuously.
2. **A card drag is active.** HTML5 DnD is a mouse/trackpad affair and largely
   doesn't fire on touch, so this is mostly a same-device belt-and-braces —
   but it's AC3 and it's two lines. Add `state.cardDragActive`, set in the
   existing `dragstart` handler and cleared in `dragend`. **Do not** infer it
   by querying the DOM for `.dragging`; a state flag set at the same two call
   sites that already toggle that class is one fact, not two.
3. **The drawer is open.** This one is easy to miss and would be a real bug:
   `.drawer` is `position: fixed`, so scrolling *it* never changes
   `window.scrollY`. With the board at top and the drawer open, a pull inside
   the drawer sees `scrollY === 0`, bubbles to the document, and arms the
   gesture. Gate on `state.openIssueId !== null` — one flag already in state,
   no DOM containment test.
4. **Multi-touch** — `e.touches.length > 1`. Pinch-zoom is not a pull.
5. **Horizontal dominance** — `|dx| > |dy|` on the first significant move.
   `.board` is `overflow-x: auto`, so a horizontal swipe across a lane's
   columns is a real gesture that must not be stolen.
6. **Already refreshing.** Ignore new gestures until the in-flight refetch
   settles, so repeated pulls can't stack requests.

### 3. `preventDefault`, and the Android trap

The `touchmove` listener must be registered **non-passive**
(`{ passive: false }`) and call `preventDefault()` **only while in `pulling`
or `armed`**. Calling it unconditionally breaks normal scrolling; not being
able to call it at all means the native bounce fights the indicator.

**Add `overscroll-behavior-y: contain` to `body`.** This is not polish:
**Chrome on Android ships its own native pull-to-refresh that reloads the
whole page** — precisely what AC1 forbids ("no full page reload"). Without
`overscroll-behavior-y: contain`, a pull on Android Chrome can trigger both
the browser's gesture and ours. This single CSS line is the difference
between the feature working and the feature reloading the page out from under
itself, and it is the reason `overscroll-behavior` belongs in this design even
though it is not a gesture mechanism.

### 4. Indicator UX and the refetch path

**Indicator:** one `#pull-indicator` element, `position: fixed; top: 0`,
`z-index: 9` — one below the sticky header's 10, so it emerges from *under*
the header rather than covering it. `transform: translateY(<offset>)`.
Hidden entirely in `idle`.

| Phase | Copy |
|---|---|
| `pulling` | `↓ Pull to refresh` |
| `armed` | `↑ Release to refresh` |
| `refreshing` | `↻ Refreshing…` |

Copy lives in one pure function (§ 5) so there's a single home for it. Do
**not** overload the existing `.connection-state` pill — that reports the SSE
connection, a standing fact; this reports a transient gesture.

**Refetch path: reuse `refreshBoardSilently()`.** It already does the
ETag-conditional GET, applies data only when the server sends some, ignores
304, swallows errors, and re-renders. AC1's "same path the poll fallback
uses" is satisfied with zero new network code.

**But it currently resolves to `undefined`, and that's a problem for this
feature.** Because the GET is ETag-conditional, a pull when nothing has
changed produces a 304, no re-render, and therefore **no visible response at
all** — the user performs a deliberate gesture and the UI does nothing. That's
the dead-end case, and it's the *common* case in live mode (§ 6).

Ruling: **make `refreshBoardSilently()` resolve to a boolean** — `true` when
new data was applied, `false` on 304 or error. Every existing caller ignores
the return value, so this changes no existing behaviour. The pull path then
toasts through the existing `showToast`: "Board updated" or "Already up to
date". Do not give the pull path its own `apiGetBoard()` call to distinguish
the cases — that duplicates the refresh logic, which is how the two copies
start to drift.

**Minimum `refreshing` duration: 400ms.** A refetch against localhost can
resolve in 20ms; the spinner would flash and read as a glitch rather than as
confirmation.

> **Judgment call.** I'm ordinarily against deliberate delay. Here the delay
> *is* the feedback — the user asked a question and needs to see it being
> answered. Cost: every pull takes at least 400ms even when the answer is
> instant. Reversal: drop the `Promise.all` floor.

### 5. What lands where

**board-logic.js** — pure, tested, and **deliberately input-agnostic** so § 1's
trackpad reversal stays cheap: the machine consumes a *pull distance*, never a
touch event.

| Export | Contract |
|---|---|
| `PULL_THRESHOLD` = 64, `PULL_MAX_OFFSET` = 96, `PULL_RESISTANCE` = 0.5, `PULL_MIN_SPINNER_MS` = 400 | Constants, exported so tests assert the values the code uses |
| `pullPhase({atScrollTop, deltaY, cancelled})` → `"idle"\|"pulling"\|"armed"` | The phase decision |
| `pullIndicatorOffset(deltaY)` → number | `min(deltaY * PULL_RESISTANCE, PULL_MAX_OFFSET)`, floored at 0 |
| `pullIndicatorLabel(phase)` → string | The single home for the three strings |
| `shouldCancelPull({cardDragActive, drawerOpen, multiTouch, horizontalDominant, refreshing})` → bool | Any true ⇒ cancel |

**`pullPhase` is deliberately PARTIAL — it does not return `refreshing`.** That
phase is entered and left by promise resolution, which is the async caller's
business, not a pure function's. A reader will be tempted to "complete" the
machine; the reason not to is that doing so would require passing async state
into a synchronous decision. Say so in the comment.

**board.js** — listener wiring, the `passive: false` registration, the
`preventDefault` decision, `state.cardDragActive`, `state.pullRefreshing`, and
the indicator DOM. Bail early if `#pull-indicator` is absent.

**No feature detection.** Attach the touch listeners unconditionally; on a
device that never produces touches they never fire, which is exactly AC4's
"degrades to nothing". A `"ontouchstart" in window` branch is one more thing
that can be wrong for zero benefit.

### 6. SSE-live interaction — the gesture behaves identically in both modes

The question was whether a manual refresh is even meaningful when SSE is live.
**Yes, and it must not branch on mode.**

- **"Live" means the EventSource is open, not that every mutation arrived.** A
  stream can stall behind a proxy while the connection object still reports
  open; a suspend/resume can drop messages before `onerror` fires; a server
  restart leaves a window where the client still believes it's live. The pill
  says "live" in all of those.
- **The gesture exists for subjective doubt** — the issue says so directly. A
  user who doubts freshness and performs an explicit gesture should not be
  told by a status pill that their doubt is invalid.
- **Branching would be user-visible and worse.** "Sometimes the gesture does
  nothing, depending on a pill I wasn't looking at" is a worse experience than
  one extra conditional GET.

So: no mode gating, no different indicator, no different copy. The one real
interaction is a *good* one — in live mode a pull will almost always 304, which
is exactly why § 4's "Already up to date" toast earns its place. It converts
a silent no-op into the confirmation the user was asking for.

> **Judgment call.** I could have made the gesture a no-op while live to save
> a request. Cost of not doing so: one conditional GET per gesture — a 304 with
> an ETag, which is about as cheap as an HTTP round trip gets. Reversal: gate
> on the connection state. Don't.

### 7. Mode cross-product — every combination, including the ones that don't matter

Recording this explicitly because my last two rulings each shipped a gap by
covering only the modes the issue text named:

| Mode | Behaviour |
|---|---|
| Kanban (`/`) | Gesture active |
| List (`/list`) | **Gesture active — same behaviour, no branching.** Both views scroll the document and both are served the same `board.html`; the refetch path is view-agnostic and `render()` already dispatches correctly |
| Swimlanes on / off | No effect — the gesture is about the document scroller, not lane structure |
| Single-root / multi-root | No effect |
| Drawer open | **Cancelled** (§ 2 condition 3) |
| Card drag active | **Cancelled** (§ 2 condition 2) |
| SSE live / polling | Identical behaviour (§ 6) |
| Touch device | Gesture active |
| Trackpad / mouse | **Nothing.** No listeners fire; existing scroll and SSE/poll behaviour bit-for-bit unchanged (§ 1) |

### Red-first test surface (QA's lane)

1. `pullPhase`: `idle` when `atScrollTop` is false, for any `deltaY`
2. `pullPhase`: `idle` when `cancelled` is true, even at scroll top past threshold
3. `pullPhase`: `idle` for `deltaY <= 0` (an upward or zero move)
4. `pullPhase`: `pulling` for `0 < deltaY < PULL_THRESHOLD`
5. `pullPhase`: `armed` at exactly `PULL_THRESHOLD` (boundary — at, not past)
6. `pullPhase`: **`armed → pulling` when deltaY drops back below threshold** — the
   no-latch rule; this is the one a naive implementation gets wrong
7. `pullIndicatorOffset`: applies resistance, caps at `PULL_MAX_OFFSET`, floors
   at 0 for negative input
8. `pullIndicatorLabel`: a distinct non-empty string for each of the three
   phases, and something safe for an unknown phase
9. `shouldCancelPull`: true for each of the five flags **independently** (five
   cases, not one combined) and false when all are absent
10. `pullPhase` never returns `refreshing` for any input — the partiality is
    the contract, so it gets a test
