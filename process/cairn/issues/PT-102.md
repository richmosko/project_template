## Problem

Found by Mosko on the merged PT-88 (2026-09-08): chronological mode orders issues by id, which is the order they were *opened*, and the caption says so. The question it was built to answer — is per-issue usage creeping up over *time* — is about when the tokens were *spent*, and the two orders diverge whenever an issue waits in the backlog. Measured from `process/cairn/metrics/token-usage.jsonl` (`window_start` per record):

| Issue | Opened (`created:`) | Tokens spent |
|---|---|---|
| PT-88 | 2026-09-04 | 2026-09-08 |
| PT-93 | 2026-09-05 | 2026-09-06 |
| PT-95 | 2026-09-05 | 2026-09-06 |
| PT-99 | 2026-09-07 | 2026-09-08 |

So today's work (PT-88) renders between last week's PT-87 and PT-89. PT-88's issue premise ("id order is chronological order") holds for filing, not for work. `GET /api/tokens` per-issue payload carries only `issue, kind, roles, total` — the chart has nothing else to order by.

## Ask

1. `GET /api/tokens` adds per-issue `first_active` / `last_active` (ISO date, min/max `window_start`/`window_end` over that issue's records, both sources); milestone/main buckets may carry them too but chronological mode still omits those bars (PT-88 ruling).
2. Chronological mode orders by `first_active` ascending, tie-break by id; issues with no records keep id order at the end, or are omitted — architect's call, stated.
3. Caption: "Showing all N issues in the order worked" (replacing "in the order opened"); the Ranked caption unchanged.
4. Unit tests: ordering by `first_active` with an id tie-break; the divergence fixture above (PT-88 after PT-99); the caption string; a Python test that the endpoint's `first_active` equals the min `window_start` over a fixture file.

## Acceptance criteria

Restated by the architect's amended gate-1 ruling below (2026-09-08), which supersedes the earlier
`first_active` ruling per Mosko's decision. Every figure there is measured.

1. `GET /api/tokens` carries per-issue `closed_at` (the `status → done` transition date, reusing
   the throughput chart's own derivation — never a second git walk), null for issues not done.
   The payload's own order stays id-ascending: PT-88's pinned contract must not regress.
2. Chronological mode sorts closed issues by `closed_at` ascending, open issues after all of them,
   both blocks holding payload order via a **stable** sort — so the id tie-break is never re-derived
   by parsing an id in the client.
3. With live data: PT-102 (open, has records) is the rightmost bar; PT-93, PT-96 and PT-97
   (closed 2026-09-07) render **left** of PT-83 and PT-88 (closed 2026-09-08) despite higher ids;
   within 2026-09-08 the order is PT-83, PT-88, PT-90, PT-99. 31 of 87 positions differ from id
   order at the measured HEAD. Positions are not pinned absolutely — the bar set grows as records
   land during the loop.
4. The caption says "in the order closed", and names the count of still-open issues shown last
   whenever any exist.
5. Lead's browser leg: both themes, chronological only (ranked unchanged), leftmost bar = the
   earliest-closed issue by tooltip, count every column before filtering by size (PT-88 lesson),

**Gate 1 ruling — PT-102. The ask's premise holds for 13 of 88 issues; build it anyway, with a caption that says so.** ACs amended in place below.

**The measurement that changes the feature.** All 330 `transcript-backfill` records carry the **same** `window_start` (`2026-08-18`) and the **same** `window_end` (`2026-09-04`) — the backfill run's own span, not per-issue activity. Only the 213 `otel` records vary (5 distinct dates each). Consequence: `first_active` is `2026-08-18` for **75 of 88 issues**; `last_active` is `2026-09-04` for the same 75. Ordering by either changes **14 of 88 positions** (max displacement 12) and leaves 85 % of the axis in filing order under a caption that claims otherwise. `window_start`/`window_end` are **date-only** (`generated` is the only ISO datetime, and it records when the aggregate was written, not when work happened), so same-day work cannot be ordered at all.

**AC1 as written is false, measured.** PT-83, PT-88 and PT-99 all have `first_active = 2026-09-08`; the id tie-break puts PT-88 **left** of PT-99, not right. The true, checkable claim: the last six become **PT-90, PT-96, PT-97, PT-83, PT-88, PT-99** where id order gives PT-93, PT-94, PT-95, PT-96, PT-97, PT-99 — PT-83 moves +12, PT-88 +8.

**Decision for the lead, stated not taken:** the data half — re-deriving per-issue windows in the backfill so the other 75 issues get real dates — is a different subsystem (`backfill_tokens.py` against archived transcripts, which must be restored first) and is **not in this loop**. I am ruling that this loop ships the endpoint, the ordering and an honest caption, and that the backfill fix is filed as a follow-up. Overrule me if you would rather hold PT-102 until the data can support the caption.

**(a) Endpoint seam.** In `build_tokens_payload`'s existing per-row loop (`cairn.py`, the block that already folds global `window_start`/`window_end`/`generated`), add one accumulator keyed by issue: `issue_windows[issue] = [min ws, max we]`, fed from the same `row.get("window_start")` / `row.get("window_end")` already read there — both sources, no source filter. Attach to each `issues_out` entry as two new sibling keys: `"first_active": <ISO date> | null`, `"last_active": <ISO date> | null`. Milestone and `main` buckets get them too (they cost nothing and the omission of those bars is a client rule, PT-88). **The payload's own order does not change** — it stays id-ascending, the contract PT-88 pinned.

**(b) Issues with no dated record: kept, sorted last, in id order.** Measured unreachable today (0 records lack `window_start`, 0 buckets lack a dated record), so this is a guard, not a live branch. Kept rather than omitted because omitting silently drops real spend from a view whose caption says "all N issues"; the caption clause in (c) names them, so a tail position cannot be misread as "most recent".

**(c) Tie-break and captions, exact.** Tie-break is **payload order**, obtained for free: the payload is id-ascending and `Array.prototype.sort` is stable (ES2019), so a stable sort on `first_active` alone reproduces the id tie-break **without the client parsing an id** — which PT-88 forbade. Ranked caption unchanged. Chronological caption:

> `Showing all ${total} issues in the order worked, by ${basis}.`
> then, when more than one issue shares the earliest `first_active`: `${n} issues share the earliest recorded date and hold filing order.`
> then, when any issue has no date: `${k} issues have no recorded date and are shown last.`
> The PT-88 omission sentence, the retention-window sentence and the unpriced-models suffix are unchanged; `milestone_caption` is still never appended in this mode.

**(d) Client sorts, server owns the key.** The server cannot sort by `first_active` without breaking the id-ascending contract ranked mode and PT-88's pin depend on, and a second ordered-id list in the payload is a field that can disagree with the bars it orders. So the ordering operation moves to the client while the key stays computed once, server-side. This reverses PT-88's "no client-side re-sort" only because the sort key is no longer the payload's own order.

**(e) Red tests.** `tests/js/token-chart-logic.test.js`: 1. orders by `first_active` ascending — mutation: sort descending. 2. **stability**: three issues sharing a date stay in payload order — mutation: a comparator returning non-zero for equal dates. 3. the divergence fixture (an issue with a late `first_active` and a low id sorts right of a high-id issue with an earlier one) — mutation: fall back to id order. 4. undated issues sort last, kept not dropped — mutation: filter them out. 5. the three caption sentences, each present only under its own condition — mutation: emit the shared-date clause unconditionally. `tests/test_tokens_endpoint.py`: 6. `first_active`/`last_active` equal the min `window_start` / max `window_end` over a fixture spanning both sources — mutation: swap min for max. 7. payload order is still id-ascending (PT-88's pin must not regress) — mutation: sort `issues_out` by `first_active`.

**Addendum 1 to the amended ruling — the cost question, measured. The reuse call stands; one decided line is added.**

implementation-lead's location is confirmed and matches what the amended ruling already names: `_compute_flow_payload`, `git log --reverse` over `issues/` + `archive/issues/`, blob frontmatter `status`, a close at `status == "done" and previous_status != "done"`, keyed by stem, day from `%cI`.

**Measured just now** (`process/cairn`, this HEAD): `build_flow_payload` **cold = 278.3 ms**, **warm = 0.10–0.25 ms**; `build_tokens_payload` as it stands today = **220.6 ms** for 104 buckets. The memo is process-global, keyed on the HEAD sha, and its freshness probe (`_flow_read_head_sha_pure`) is a **pure file read** — no subprocess on the warm path. So my "cache hit in practice" line is now measurement, not reasoning: the cost is one 278 ms walk per commit, paid by whichever of `/api/flow` or `/api/tokens` polls first, and ~0.2 ms for every poll after it. The dashboard already fetches `/api/flow`, so in the common case the token endpoint pays the probe only.

**No shared helper is extracted, and there is no re-walk.** `build_flow_payload` already *is* the shared memoized entry point; extracting a second one would add a cache to keep coherent with the first, and re-walking would cost the full 278 ms on **every** poll while duplicating the transition rule.

**Added decided line (a2):** `build_tokens_payload` calls **`build_flow_payload`**, never `_compute_flow_payload` directly. Reaching past the wrapper is a one-word mistake that silently turns a 0.2 ms probe into a 278 ms git walk on every poll, and nothing in the output would reveal it. **qa test 9:** patch `_compute_flow_payload` with a call counter, call `build_tokens_payload` twice at an unchanged HEAD, assert it walked **once**. Mutation: call `_compute_flow_payload` directly from `build_tokens_payload` — the counter reads 2.
