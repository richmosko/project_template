## Problem

Found at PT-90's gate-4 re-check (2026-09-08). In **1 of 26** full parallel runs at 652ff3c,
`test_otel_receiver_self_stop.py` errored in `tearDownModule`:

    ERROR: tearDownModule (test_otel_receiver_self_stop)
      File .../tests/test_otel_receiver_self_stop.py, line 339, in tearDownModule
        raise AssertionError(
    AssertionError: the real, committed process/cairn/metrics/token-usage.jsonl must never be
    touched by this test module -- every test must point --out-file at a fake root

The guard is PT-91's and it is doing its job as written. The problem is that **as written it
cannot distinguish the two things it might have caught**, and they have opposite severities:

- a **test** wrote the real file — a seam defect, serious, exactly what the guard exists for; or
- the **live receiver daemon** flushed while the module was running — a false positive, because
  the guard compares the whole file for byte equality and any concurrent append trips it.

The recovered traceback says only that the bytes changed, never how. That is why the single
occurrence could not be adjudicated at PT-90's gate.

Measured alongside it, none of which settles the question:

- across 4 monitored full runs the real file did not change at all (518 lines before and after,
  sha identical), and the running daemon (pid 37774) wrote nothing in a 25 s idle window — so a
  daemon write is infrequent, which is consistent with a ~1-in-26 event but does not prove it;
- the module's receivers are all spawned with `--out-file` inside a fake engine root, so a
  test-driven write to the real file would require a genuine seam mistake;
- PT-93/PT-96 made the module's wall-clock window overlap the entire rest of the suite, which
  can only raise the odds of any concurrent-write race.

Recovering the traceback at all depended on `run_tests.py --json` carrying `outputs` for failed
files (PT-96 verdict delta 1). Without it this would have been an unexplained `errors=1`.

## Ask

1. Make the guard **self-diagnosing**: on a mismatch, report *what* changed — line-count delta,
   whether the snapshot is still a prefix of the current file, and the first differing line —
   instead of only that it changed. A pure append by a live daemon and a rewrite by a test then
   look nothing alike in the failure message.
2. Decide, with that evidence in hand, whether the guard should tolerate a pure append while
   the receiver pidfile exists (prefix comparison) or stay byte-exact and instead require the
   suite to run with the daemon stopped. Do not weaken it before the diagnosis exists.
3. Apply the same treatment to the sibling guards for `.receiver.pid` and `.sessions/`.

## Acceptance criteria

1. A synthetic append and a synthetic rewrite of the guarded file produce visibly different
   failure messages, each with a test naming the mutation that turns it red.
2. Whatever tolerance is adopted is justified from measurement recorded on this issue, not from
   the inconvenience of the failure.
3. 25 consecutive full parallel runs with no guard trip, count recorded here.
