## Problem

Found at PT-90's gate-4 re-check (2026-09-08). In **1 of 26** full parallel runs at 652ff3c,
`test_otel_receiver_self_stop.py` errored in `tearDownModule`:

    ERROR: tearDownModule (test_otel_receiver_self_stop)
      File .../tests/test_otel_receiver_self_stop.py, line 339, in tearDownModule
        raise AssertionError(
    AssertionError: the real, committed process/cairn/metrics/token-usage.jsonl must never be
    touched by this test module -- every test must point --out-file at a fake root

The guard is PT-91's and it is doing its job as written. The problem is that **as written it
cannot distinguish the two things it might have caught**, and they have opposite severities:

- a **test** wrote the real file — a seam defect, serious, exactly what the guard exists for; or
- the **live receiver daemon** flushed while the module was running — a false positive, because
  the guard compares the whole file for byte equality and any concurrent append trips it.

The recovered traceback says only that the bytes changed, never how. That is why the single
occurrence could not be adjudicated at PT-90's gate.

Measured alongside it, none of which settles the question:

- across 4 monitored full runs the real file did not change at all (518 lines before and after,
  sha identical), and the running daemon (pid 37774) wrote nothing in a 25 s idle window — so a
  daemon write is infrequent, which is consistent with a ~1-in-26 event but does not prove it;
- the module's receivers are all spawned with `--out-file` inside a fake engine root, so a
  test-driven write to the real file would require a genuine seam mistake;
- PT-93/PT-96 made the module's wall-clock window overlap the entire rest of the suite, which
  can only raise the odds of any concurrent-write race.

Recovering the traceback at all depended on `run_tests.py --json` carrying `outputs` for failed
files (PT-96 verdict delta 1). Without it this would have been an unexplained `errors=1`.

## Ask

1. Make the guard **self-diagnosing**: on a mismatch, report *what* changed — line-count delta,
   whether the snapshot is still a prefix of the current file, and the first differing line —
   instead of only that it changed. A pure append by a live daemon and a rewrite by a test then
   look nothing alike in the failure message.
2. Decide, with that evidence in hand, whether the guard should tolerate a pure append while
   the receiver pidfile exists (prefix comparison) or stay byte-exact and instead require the
   suite to run with the daemon stopped. Do not weaken it before the diagnosis exists.
3. Apply the same treatment to the sibling guards for `.receiver.pid` and `.sessions/`.

## Acceptance criteria

Restated by the architect's gate-1 ruling below (2026-09-08); every figure there is measured.

1. One shared helper in `scripts/cairn/tests/helpers.py` — snapshot / diagnose / assert — used by
   all six modules carrying real-file guards, raising explicitly (never a bare `assert`). Every
   diagnosis names four facts: line-count delta, whether prior identity keys survived, whether
   counters are monotone, and the first differing line index.
2. A synthetic daemon-shaped flush, a synthetic rewrite, an unbacked-issue append and a decreased
   counter each produce visibly different outcomes, each with a test naming its red mutation.
3. The adopted tolerance is **multiset containment**: the daemon reads every line, adds the new
   ones and re-sorts the whole file (`otel_receiver._append_lines`), so old lines survive verbatim
   but move. Tolerated iff every pre-existing line is still present **and** every new line's
   `issue` resolves to a real issue id. Neither a prefix check nor a counter-monotonicity check is
   valid — identity keys are **not unique** (558 lines, 401 distinct keys, one key 32 times), and
   keying by identity is what produced the retracted first ruling.
4. `.receiver.pid` and `.sessions/` are gitignored runtime state and get their own rules:
   additions to the registry are tolerated, a **removal or content change raises**.
5. AC3's 25-run battery is withdrawn (lead's amendment, per Mosko 2026-09-07): the mechanism above
   plus **one** confirming `run_tests.py --gate verdict`.

**Gate 1 ruling — PT-100. The Ask's tolerance option does not exist: the daemon does not append, it rewrites.** ACs restated in place below.

**Measurement 1 — the live receiver rewrites the whole file.** Comparing `HEAD:process/cairn/metrics/token-usage.jsonl` against the working tree this turn: 550 → 558 lines, **155 lines differ**, and the current file **does not** start with the old bytes (first differing line 396, where a `PT-101` row became a `PT-100` row with grown counters). So a prefix/append tolerance would never match, and — the part that matters — **a daemon flush and a test rewriting the file are the same shape**: "the whole file changed". The Ask's option 2 is measured out.

**Measurement 2 — the rewrite is semantically monotone, and that is the discriminator.** Every one of the 397 pre-existing `(issue, role, model, source)` identity keys is still present in the 401 current ones (`HEAD keys ⊆ current`), counters only grew, and `generated` advanced. Flush cadence, from the file's own stamps: `07:45:42, 08:16:42, 08:17:42, 08:18:02, 08:18:42` — every 20–60 s while a session is producing telemetry, which is what makes a ~1-in-26 overlap plausible without either theory being proven by frequency alone.

**Ruled tolerance — classify, never compare bytes.** The guard tolerates exactly the shape measurement 2 describes and nothing else: every prior identity key still present, **no counter decreased**, `generated` not older, and every *new* key's `issue` resolving to a real cairn issue id (or `main` / a `milestone:` bucket). Anything else — a key that vanished, a counter that fell, truncation, or a new row for an id no issue file backs — raises. Rejected alternative: requiring the suite to run with the daemon stopped. That trades a test-harness defect for an operational one, and stopping live telemetry to run tests is a larger change than the thing being fixed.

**Residual risk, stated rather than left to be found.** A seam mistake in which a *real* receiver writes plausible rows for a *real* issue id into the real file would be classified as a daemon flush and pass. The issue-id check is what makes this narrow: the modules spawn receivers over fake engine roots with synthetic sessions, so their rows carry ids no issue file backs. Anyone widening the fixtures to real ids reopens this.

### @architect — 2026-09-08

**Addendum 1 — the aggregate refinement is declined, with the measurement, and one thing from it is adopted.**

**Measured over the file's real history**, 18 consecutive transitions of `token-usage.jsonl` (18 commits + the worktree), testing raw-line containment (old lines ⊆ new lines, no aggregation): **16 pass with 0 lines missing**. The only two failures are the two oldest — `7cf42b9→a25ff0f` (262 missing) and `a25ff0f→2b8e3d2` (285) — and they are **not daemon flushes**: they are PT-87's role-attribution change and PT-84's milestone-overhead change, each of which **re-ran the backfill and retroactively rewrote every `transcript-backfill` line**. Field sets are identical across both; only values moved.

**So containment needs no aggregation to describe the daemon.** The "3 keys / 9 counters shrinking" the refinement responds to is produced by **last-occurrence-wins over duplicate keys** — the same method this ruling retracted at @0487f33. Containment never does last-wins, so under the ruled predicate those shrinking counters do not exist; there is nothing to repair.

**And per-key summed counters would be strictly weaker.** Summing before comparing tolerates a pre-existing line being **replaced** by a different line for the same key whenever the sum does not shrink — which is exactly the "a test rewrote the real file" shape the guard exists to catch. Containment forbids it. I am not trading an exact predicate for a lossy one to accommodate an artifact of a method we no longer use.

**Adopted from the refinement, unchanged in intent:** qa's daemon-shaped fixture **carries two lines for one identity key differing only in `generated`**. Under containment it passes; under any dict-by-identity implementation the removal of one copy goes undetected. That is already ruling test 6 and this fixture is what makes it bite — keep it exactly as the lead specified.

**Added to the diagnosis, because this is the issue's whole point.** When lines *are* missing, the message must separate the two causes it now has evidence for: if every missing line carries `source: "transcript-backfill"`, report it as **"looks like a backfill re-run, not a test write"**; otherwise report a suspected test write. A backfill re-run during a suite is a real, loud failure and must stay one — it is a whole-file rewrite mid-run — but it should never be adjudicated as a seam defect again, which is the exact ambiguity PT-90's gate could not resolve.

**qa: unblocked, nothing else in the ruling moves.** Tests 1–8 stand as written at @0487f33; test 1's fixture gains the duplicate-key pair above, and test 5's four facts gain the backfill-vs-test classification.
