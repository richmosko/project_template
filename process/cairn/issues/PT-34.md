## Problem

`GET /api/board` intermittently returns 503 — observed twice (2026-08-22): during PT-29's Chrome pass at page load (two 503s racing the SSE connection setup), and during PT-32's Validate on a pull-triggered refetch while the SSE stream was open. Suspected: the single-threaded board server can't serve a fetch while an SSE (`/api/events`) long-lived connection is being established/held. Split out of PT-31 item 4 (architect, PT-32 Validate): it's a server-side defect and doesn't belong in a client-polish bundle — the client-side symptom hardening (PT-32's three-state refresh outcome + `apiGetBoard` resp.ok guard) already shipped and makes the failure honest, not absent.

## Acceptance criteria

- [ ] Race reproduced deliberately (concurrent /api/board fetch during /api/events connection churn) or ruled out with the actual 503 source identified
- [ ] The identified source gets its remediation — server-side fix if the server; a recorded tooling/instrumentation note if an observation artifact; client change only if evidence warrants (AC amended 2026-08-22 by team-lead under the standing order: the original "fix lands server-side (threading/handler model)" presumed the filed hypothesis, which the tree falsified — server is already threaded, no 503 emitter exists)
- [ ] Regression test or documented manual repro in the Python suite
- [ ] Localhost-only threat posture unchanged (seceng review not required unless the handler model changes exposure)

### 0. Evidence, verified independently rather than relayed

I re-checked all three claims against the tree rather than taking them from the
dispatch:

- `scripts/cairn/cairn.py:1989` — `class Server(socketserver.ThreadingMixIn, http.server.HTTPServer)`. **The server has been threaded since PT-1**, with `daemon_threads = True`, which predates both sightings.
- `grep -n "503\|SERVICE_UNAVAILABLE"` over `cairn.py` returns **nothing**. There is no emitter.
- L1743–1746's comment describes the single-threaded model in the **past tense**, as the thing PT-1 replaced.

Adding a fourth fact that matters more than any of them: **Python's
`BaseHTTPRequestHandler` never synthesizes a 503.** It emits 400/501/505/431
and whatever `send_error` is explicitly called with. So a literal 503 cannot
originate inside cairn without code that says `503`, and no such code exists in
any version of this file.

That collapses the space: **either no 503 was ever on the wire (a reporting
artifact), or one was, and something between Chrome and cairn produced it.**
Neither branch is "the board server has a concurrency bug," which is what the
issue was filed as.

### 1. Blocking obstacle — the server currently cannot tell us what it returned

`log_message` is overridden at L1772 to write only the method and path:

```python
def log_message(self, fmt, *fmt_args):
    sys.stderr.write("  %s %s\n" % (self.command, self.path))
```

The default `BaseHTTPRequestHandler.log_request` includes the status code; this
override discards it. **Every experiment below depends on knowing what the
server actually returned, so this is the first change, not a nice-to-have.**
One line — include the code:

```python
def log_message(self, fmt, *fmt_args):
    sys.stderr.write("  %s %s %s\n" % (self.command, self.path, fmt_args[1] if len(fmt_args) > 1 else ""))
```

or, more simply, stop overriding `log_request` specifically and keep the
override only for the noisier `log_message` paths. The implementer should pick
whichever keeps the log terse — the requirement is only that **a status code
appears for every served request.** This is worth keeping permanently
regardless of how the investigation ends: a board server whose log can't
distinguish a 200 from a 500 will cost us this same investigation again.

### 2. Hypotheses, with priors

**H1 — the 503 is the Chrome MCP tooling's representation of a failed or
aborted fetch.** *Leading.* A fetch that fails at the network layer has **no**
HTTP status; DevTools shows `(failed)` / `net::ERR_*`. A layer that must report
a number can synthesize one, and 503 is a plausible choice for "service
unavailable." Four things raise this prior: both sightings came through the
same instrument; **that instrument has a demonstrated representation artifact
in this very milestone** (PT-32's element-property reads were blind to
occlusion and produced a section of false positives); PT-31's original note
recorded **`curl` returning 200** for the same endpoint, which is consistent
with a Chrome-path-specific artifact and inconsistent with a server defect; and
cairn has no 503 emitter.

**H2 — a stale server process.** A previous `cairn serve` still holding
:8766 while the current session believes it started a new one, so the browser
talks to stale code. `allow_reuse_address = True` permits rebinding a
TIME_WAIT port but does *not* let two live listeners share one, so the failure
shape is "the new server failed to bind and you didn't notice" rather than
"two servers." Explains intermittency and non-reproducibility. Does **not**
explain a literal 503 on its own — no cairn version emits one — so it only
works in combination with H1.

**H3 — a proxy between Chrome and localhost.** A PAC file or system proxy that
doesn't bypass `127.0.0.1` will happily return a genuine 503 that never reaches
Python. This is the **only** hypothesis that produces a real 503 on the wire.
The recorded "curl 200" datum is a positive indicator here too, since curl
honours a different proxy configuration than Chrome.

**H4 — genuine but indirect server behaviour under connection churn.** Thread
per connection, plus `request_queue_size` (default 5) on the listen backlog,
plus EventSource auto-retry churning connections. A full backlog means the OS
**refuses** connections — `ECONNREFUSED`, not 503. So H4 can produce failed
fetches but cannot produce a 503 except via H1's representation. Lowest prior,
but it's the one that would be a real defect, so it gets a real experiment.

### 3. Discriminating experiments

**E0 — server-side ground truth. Gate: run this first, alone.** With § 1's
logging fix in place, start `cairn serve`, capture stderr, and reproduce the
Chrome pass. Then ask one question: **does a 503 appear in the server's own
log?**

- No 503 server-side, but the browser reports one ⇒ **H4 dies, and the answer
  is H1 or H3.** Every server-side hypothesis is closed by this single
  observation.
- A 503 server-side ⇒ something is calling `send_error(503)` that grep can't
  see (a dependency, an exception path) and the investigation becomes an
  ordinary bug hunt.

Nothing else should be attempted until E0 has run. It is cheap, and it
partitions the hypothesis space in one shot.

**E1 — concurrent-load harness (kills H4, and is the AC3 artifact).** In the
Python suite: start a real server, open an SSE connection to `/api/events`,
fire N concurrent `GET /api/board` (N ≫ `request_queue_size`, say 50), assert
every response is 200 or 304 **as observed server-side**. Also assert it under
SSE connect/disconnect churn. **Build this regardless of E0's outcome** — a
concurrent-load test against a threaded server with a long-lived stream open is
coverage the suite genuinely lacks, and it is the one artifact of this
investigation that survives if the answer turns out to be "tooling artifact."
That converts a possibly-null investigation into a net gain.

**E2 — port ownership (kills H2).** During a repro:
`lsof -nP -iTCP:8766 -sTCP:LISTEN` — confirm exactly one PID and that its start
time matches this session. Separately, and worth knowing either way: start a
second `cairn serve` on an already-bound port and confirm it **fails loudly**
rather than appearing to succeed. If it doesn't, that's a real usability defect
worth its own issue independent of the 503.

**E3 — proxy path (kills or confirms H3).** `scutil --proxy` on macOS, plus
Chrome's own view via `chrome://net-internals`. Compare against curl's
environment. The question is narrow: **does Chrome route `127.0.0.1:8766`
through anything?**

**E4 — abort representation (confirms H1 directly).** In the browser, abort a
fetch deliberately — `AbortController`, or navigate away mid-request — and read
what the MCP network log reports as its status. If an aborted fetch surfaces as
`503`, H1 is confirmed at the source and the whole thing is closed. This is the
cleanest single discriminator available and it's entirely under team-lead's
control.

|---|---|---|

| No server-side 503; E4 shows aborted fetches reported as 503 | **H1 confirmed.** One-line note recording that the instrument represents network-layer failures as 503 | AC1's "ruled out with the actual 503 source identified" branch; **AC2 struck as inapplicable**; AC3 met by E1's harness |

### 5. What not to do

- **Do not speculatively change the handler model** — bumping
  `request_queue_size`, adding retries, swapping the server class — to chase a
  symptom whose source is unidentified. It would be unfalsifiable (you can
  never show it worked, only that the thing stopped being observed), and it
  touches AC4's threat posture for no established reason.
- **Do not add client-side retry.** PT-32's three-state outcome already makes
  the failure honest; retrying would make it silent again, which is the defect
  that ruling fixed.
- **Do not close on non-reproduction.** See the table's last row.

Addendum — team-lead's `.catch` observation, folded in. It materially
strengthens H1 and changes how QA should weigh the two sightings, so it
belongs in the ruling rather than in a message.

**Neither sighting is evidence that an HTTP response existed at all.**

Verified at the sha the second sighting was taken against (`295785c`):

```js
function refreshBoardSilently() {
  return apiGetBoard().then(function (data) {
    if (data) { state.board = data; render(); return true; }
    return false;
  }).catch(function () { return false; });   // <- everything lands here
}
```

`apiGetBoard` had no `.catch` of its own (confirmed: zero), so
`refreshBoardSilently`'s was the only one. And `fetch()` **rejects** on a
network-layer failure — no response object, no status, nothing on the wire to
have a status *about*. That rejection landed in the same `.catch` as a genuine
HTTP error and returned the same `false`, which at the time rendered as
"Already up to date".

So the PT-32 observation — *"a 503 refetch toasted Already up to date"* — is
**exactly as well explained** by a fetch that never got a response as by one
that got a 503. The client could not tell those apart at that sha; that
indistinguishability is precisely the defect PT-32's three-state ruling fixed.
The toast is therefore evidence about the *client's* collapsing of outcomes,
**not** evidence that a 503 came back.

The first sighting has the same property from the other direction: it was read
off the MCP network log, which is the artifact H1 questions.

**Consequence for the investigation:** every datum we have for a real HTTP 503
traces to one of two instruments, and neither can distinguish "server returned
503" from "fetch failed at the network layer." That is not a weak version of
the evidence — it means **we have no evidence of an HTTP 503 at all**, only
evidence of two failed fetches. H1 moves from "leading hypothesis" to "the
default explanation, which the others must beat."

It does not change the experiments — E0 still partitions the space, and E4 still
tests H1 at its source — but it changes the burden of proof. QA should treat
"there was a 503" as **unestablished** rather than as the premise under
investigation, and E0's likeliest correct outcome is "no 503 was ever served."

It also sharpens the closure table's last row. If E0 finds nothing server-side
and E3/E4 don't identify a source, the honest close is **not** "unexplained
intermittent" but "two failed fetches whose network-layer cause was not
captured, with no evidence a 503 was ever served" — a different and more
accurate statement, and one that argues for keeping the § 1 status logging
permanently so the next occurrence is captured at the server rather than
inferred from a client that can't see it.

### Instrument-corroborated claims (Chrome pass)

An observation tool reports what it can see. Where it cannot see, it may report *something* rather than nothing — and a fabricated value is indistinguishable from a measured one at the point of reading. Two artifacts of this kind surfaced in consecutive milestones, both from the same instrument, and both cost a review cycle: a visibility check that was structurally blind to what it was checking, and a status code invented for a response that never existed. The defense is not to distrust the instrument but to know which of its claims are self-supporting: **a Chrome-pass finding is either directly established by the instrument or needs corroboration, and the report should say which** (adopted 2026-08-22 from PT-32 and PT-34).

- **Establishes directly — geometry and paint.** `elementFromPoint` at an element's centre, and screenshots, answer "can a human see this" because they resolve the actual composited stack. Prefer them for any visibility claim.
- **Needs corroboration — network-log status codes.** Measured on PT-34 for two independent failure modes: an `AbortController`-aborted fetch (`AbortError`) and a connection refused by a closed port (`TypeError: Failed to fetch`) **both** appear in the network log as `statusCode: 503`, with no HTTP response received in either case. The log's `statusCode` is therefore **not evidence of a server response**. Corroborate server-side — the server's own access log — before treating any status as an HTTP fact. PT-34 was filed as a server concurrency bug on the strength of two such readings; there was no defect.
- **Needs corroboration — that a request happened at all.** A monkey-patched `fetch` returning a synthetic `Response` that never touched the wire still appears in the log as a network request. Entry *presence* is not evidence of network activity, which is a separate property from the status being wrong.
- **Needs corroboration — element-property reads of visibility.** Reading an element's own properties (dimensions, offsets, computed style) cannot see occlusion: an element with entirely correct geometry can sit under an opaque sticky header and never be visible to anyone. On PT-32 this produced a section of false positives, and the defect it masked was found by arithmetic rather than by the pass.
- **Say which mode a claim is in.** "Verified via `elementFromPoint`" and "read from the network log" carry different weight, and a reader cannot tell them apart from the claim alone. Reporting the method costs a clause and is what lets a reviewer know whether to ask for corroboration.

format-string guard (`fmt.startswith('"%s"')`) would make the comment true but
couples to a CPython internal; not worth it.

Small irony worth noting on an issue about instruments fabricating values: the
new log line can print `Not Found` in a column a reader will scan as a status
code. Harmless here, and the second line resolves it — but it's the same shape
as the thing we just documented.
