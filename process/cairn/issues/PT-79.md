## 1. The price table

**File: `scripts/cairn/prices.json`.** Beside the engine, **not** under `process/cairn/`. — the rates are identical for every project that ever uses cairn; they are engine data, not this project's state. `git subtree split --prefix=scripts/cairn` must carry the table with the engine, and a spun-off cairn must not drag this repo's usage history along with it.

**Format** — flat, dated, explicit per-model rates in $/MTok:

```json
{
  "source": "https://platform.claude.com/docs/en/about-claude/pricing",
  "retrieved": "2026-09-04",
  "currency": "USD",
  "unit": "per_mtok",
  "models": {
    "claude-fable-5-1":          {"input": 10,  "cache_write_5m": 12.50, "cache_write_1h": 20, "cache_read": 0.25, "output": 50},
    "claude-fable-5":            {"input": 10,  "cache_write_5m": 12.50, "cache_write_1h": 20, "cache_read": 1.00, "output": 50},
    "claude-opus-5":             {"input": 5,   "cache_write_5m": 6.25,  "cache_write_1h": 10, "cache_read": 0.50, "output": 25},
    "claude-opus-4-8":           {"input": 5,   "cache_write_5m": 6.25,  "cache_write_1h": 10, "cache_read": 0.50, "output": 25},
    "claude-sonnet-5":           {"input": 2,   "cache_write_5m": 2.50,  "cache_write_1h": 4,  "cache_read": 0.20, "output": 10},
    "claude-haiku-4-5-20251001": {"input": 1,   "cache_write_5m": 1.25,  "cache_write_1h": 2,  "cache_read": 0.10, "output": 5}
  }
}
```

Those six are exactly the models present in the committed data — verified, zero unpriced buckets.

**Store explicit rates per model, never multipliers.** The docs express caching as multipliers (5m = 1.25×, 1h = 2×, read = 0.1× base input) and that is *wrong for one of our models*: **Claude Fable 5.1's cache read is 0.025×, not 0.1×** — $0.25/MTok against Fable 5's $1.00/MTok on the same $10 base. A multiplier-based table overcharges `claude-fable-5-1` cache reads by 4×. Rates are data; derived formulas silently encode an exception you did not know about.

**Dating: one flat snapshot with `retrieved`, not a list of effective periods.** — proportionate to a three-week window in which no listed rate changed (Sonnet 5's $2/$10 introductory rate became permanent on 2026-09-01 at the same numbers, so nothing in range moves). **Cost:** if a rate ever changes, updating the table silently re-prices *history*. **Reversal:** promote each model's value to a list of `{effective_from, rates}` and pick by the line's `window_end`; the consumer changes in one place. Say so in TRACKER so the next person updating rates knows what they are doing to the past.

**An unknown model is never priced at zero.** Its cost is `null`, the bucket still renders its **tokens**, and the block names the unpriced models in its caption. — a missing rate must look like missing information, not like free work. This is the guard that catches the next model rename, which is certain: the data already contains one dated id (`claude-haiku-4-5-20251001`) and five undated ones.

**Documented assumption:** rates are standard-speed, global-inference list prices. Fast mode (Opus 5/4.8 at $10/$50) and the `inference_geo: "us"` 1.1× multiplier are not modelled — the backfill did not persist `speed` or `inference_geo`, and every transcript record observed carried `speed: standard` / `inference_geo: not_available`. Batch and volume discounts are not modelled either. This is why the chart says *estimated*.

## 2. The API

**`GET /api/tokens`, a separate endpoint.** — PT-56's roster and PT-61's flow both set this precedent: a different cost profile and a different refresh cadence do not belong bolted onto `/api/dashboard`. Memoize in-process keyed by the data file's `(mtime, size)`; the file changes rarely and a full re-read per request is waste.

**Payload:**

```json
{
  "issues": [
    {"issue": "PT-69", "total": {"input": 0, "cache_write": 0, "cache_read": 0, "output": 0, "cost_usd": 226.57},
     "roles": [{"role": "implementation-lead", "input": 0, "cache_write": 0, "cache_read": 0, "output": 0, "cost_usd": 0.0}]}
  ],
  "window_start": "2026-08-18", "window_end": "2026-09-04",
  "generated": "2026-09-04T02:18:03Z",
  "sources": ["transcript-backfill"],
  "prices": {"retrieved": "2026-09-04", "source": "<url>", "unpriced_models": []},
  "warning": null
}
```

- Aggregated to **issue × role**; model detail is folded into `cost_usd` server-side and does not cross the wire. — AC2 needs the four counters and AC4 needs the role split; nothing on the page needs a per-model breakdown, and computing cost server-side keeps the price table on one side of the boundary.
- `cost_usd` is `null` — not `0` — when any contributing model is unpriced.
- `window_start`, `window_end`, `sources` and `prices` come from the data, never hardcoded, so the caption in §5 cannot go stale.
- A missing or unreadable data file is `warning: "no token data"` with `issues: []`, HTTP 200. — the dashboard degrades to an empty block; it does not 500 because a metrics file has not been written yet. (This is the one place the "missing means error" rule does *not* apply: `token-usage.jsonl` is optional data, unlike `config.yml` which defines the tracker.)

## 3. Block placement

`scripts/cairn/dashboard/src/lib/components/TokenCostChart.svelte`, placed **directly below** the PT-61 `IssueFlowChart` in `App.svelte`, in a full-width `Card.Root` matching the flow chart's own `sm:col-span-2 lg:col-span-4` span. **Lazy-loaded by the same dynamic-import pattern `IssueFlowChart` already uses** — the chart library is already kept out of the main bundle deliberately; a second eager chart import would undo that.

## 4. What the block shows

- **Bars: top 12 issues by the *currently displayed* metric, plus `main`, ordered descending by that same metric.** A "Show all" control expands to all 69. The caption names the basis: `showing the top 12 of 68 issues by estimated cost` (or `by tokens`).
  - **Selection follows the metric, not just the order** (team-lead ruled order; selection is the consequence). Measured on the committed data: the top 12 by tokens and the top 12 by cost **share only 8 members — 4 swap out each way** (`PT-3`, `PT-22`, `PT-26`, `PT-58` leave; `PT-32`, `PT-54`, `PT-59`, `PT-73` enter). If selection were pinned to tokens, the **cost** view would silently omit four of the twelve most expensive issues while calling itself a cost chart. A changing bar set is surprising; a cost chart that hides top costs is wrong, and wrong beats surprising here. The caption naming the basis is what makes the change legible rather than glitchy.
  - **Departure from AC1's literal "one bar per issue".** **Cost:** the default view hides 56 buckets. **Reversal:** change one constant. **Why:** there are 68 issue buckets plus `main` today and the number only grows; 69 bars in a dashboard card is not a chart, it is a texture. The top 12 carry the story and the toggle keeps AC1 satisfiable on demand.
- **`main` gets its own bar** — kept, not spread, not hidden. It is **8.4% of all tokens ($528.72, the single largest bucket)**, so dropping it would make the bars visibly fail to sum to the stated total, which is exactly the kind of quiet inconsistency that makes people stop trusting a chart. Render it last, visually muted, with **no drawer link** — it is not an issue and must not look clickable.
- **Stacked by role** within each bar.
- **Toggle: tokens ↔ estimated cost.** In **tokens** view the series are `input`, `cache_write`, `cache_read`, `output` — four distinguishable series, satisfying AC2's "input and output separate" and "cache read and cache write distinguishable from fresh input" in one encoding rather than two. In **cost** view a single `cost_usd` per role. — the role stack and the token-type stack cannot both occupy the same axis; role is the stack (AC1) and token type is the toggle's tokens mode.

## 5. Caption — both caveats, derived from data

**Only the dollar view is labelled "estimated"; the token view is not** (AC3). If `prices.unpriced_models` is non-empty, append: `{n} model(s) have no published rate and are excluded from cost: {names}`.

### Server

- `load_prices(engine_dir: Path) -> dict` — reads `scripts/cairn/prices.json`, resolved from the **engine directory** (`Path(__file__).parent`), never from cwd. A missing or malformed table is **not** fatal: it yields `cost_usd: null` everywhere plus a `warning`, because the token half of the block must still render.
- `build_tokens_payload(data_dir: Path) -> dict` — returns §2's shape. Memoized in `_TOKENS_CACHE` keyed by `(str(path), st_mtime_ns, st_size)`; a vanished file invalidates rather than serving a stale hit. Follows `_FLOW_CACHE`'s existing pattern.
- Route `/api/tokens` in `do_GET`, beside `/api/flow`.
- **Cost is computed per `(issue, role, model)` before aggregation, then summed.** Aggregating tokens across models first and pricing the total is wrong by construction — the models have different rates.

## 2. The role palette — mechanism ruled, hues escalated

**This is the moment `design-system-spec.md` named.** That document already says, verbatim, that `--chart-1`…`--chart-5` is a single-hue sequential ramp that "reads badly for **categorical data**", that "there is genuinely **no multi-hue categorical palette anywhere in this system**", and that the need should be flagged "at chart-spec time… that is the point to bring a token proposal to the team, decided against a concrete use case rather than pre-emptively invented here." Roles are exactly that case: unordered categories, ~12 of them today.

**What I rule (engineering):**

- **Do not reuse `--chart-flow-*`.** Those six are keyed one-per-`STATUS_ORDER` status and validated as an **ordinal** ramp (monotone lightness). Roles have no order; borrowing an ordinal ramp would render `architect` and `qa-engineer` as if one ranked above the other, and would couple this block to a status taxonomy it has nothing to do with.
- **Do not reuse `--chart-1`…`--chart-5`.** Same single-hue problem, and two of the five already fail the 2:1 light-end gate against the white `--card` (`--chart-1` at 1.33:1, `--chart-2` at 1.91:1) — the finding that produced `--chart-flow-*` in the first place.
- **The validator to run is the dataviz skill's *categorical* check, not `validate_ordinal`.** Applying the ordinal validator here would enforce monotone lightness across roles, which is meaningless for unordered categories and actively misleading. Whatever palette lands must be validated in **both** modes against each mode's own real `--card`, and guarded mechanically the way `test_dashboard_chart_ramp.py` guards the flow ramp — re-running the validator against whatever values actually sit in `app.css`, never a snapshot of today's numbers.
- **Token count: 8.** — beyond roughly eight hues, categorical series stop being reliably tellable apart, and 8 covers every role that has ever appeared in real data except the ad-hoc probes. This is a distinguishability limit, not a roster count; the roster will outgrow it.
- **Assignment is a pure function of the role name, via an explicit ordered list checked into `token-chart-logic.ts`** (`ROLE_TOKEN_ORDER`), **not** derived from roster directory order and **not** from rank in the current payload. — a role must keep its colour across reloads *and* across data changes; deriving from `sorted(.claude/agents/*.md)` means adding one agent file silently reshuffles every colour after it alphabetically, and deriving from payload rank means a role changes colour when its usage changes. Appending to an explicit list can only ever add.
- **Fold rule:** roles not in `ROLE_TOKEN_ORDER` aggregate into a single **`other`** series, rendered last in a muted neutral, never one of the 8 hues. The caption states it: `{k} other role(s) grouped: {names}`. — the same posture as `cost_usd: null` for unpriced models; a grouped bucket must announce itself rather than silently absorb.

**What I am not ruling, and why it goes to ux-designer + you:** the eight hue values, and which roles occupy the list. Both are design-system decisions the spec explicitly reserves for a team token proposal, and the membership question has a real trade-off I should not settle alone:

- **Option A — roster-only:** the 8 slots go to `team-lead` plus the seven most-used `.claude/agents/` roles. `auxiliary` and `subagent-unattributed` fold into `other`. Cleanest reading of "who did the work", but it hides the two diagnostic buckets in a grey lump.
- **Option B — two reserved slots:** 6 hues for roles, plus fixed distinct treatments for `auxiliary` (cheap-model overhead) and `subagent-unattributed` (the role-resolution failure guard). Costs two hues but keeps the failure signal visible on the chart, which is where someone would actually notice it.
- **Option C — 8 role hues, and `auxiliary`/`subagent-unattributed` rendered as neutral hatched/muted segments outside the hue palette.** Keeps all 8 for real roles and still distinguishes the two synthetic buckets.

I lean toward the shape of B or C on the grounds that `subagent-unattributed` is a guard and guards should be visible — but the hue budget is ux-designer's to spend, so I am stopping here rather than picking.

**Blocked until that lands:** implementation-lead should not touch `app.css`. The block can be built against the existing tokens with a `TODO` marker and the palette swapped in afterwards; the structure, selection, caption and drawer work in §§1–8 are all independent of which hues win.

**Amendment — the role-palette guard uses an in-repo validator and never skips.**

**Ruling:** the categorical role-palette check runs against `scripts/cairn/tests/palette_check.py` — an **in-repo, stdlib-only** module — not the external dataviz skill script. The external script stays optional and keeps backing the **ordinal** `--chart-flow-*` ramp test exactly as today. — a skipping guard is indistinguishable from a passing one in a green run, and fail-on-missing would leave this harness permanently red; vendoring the two checks we actually need removes the choice between an invisible skip and a useless failure.

**The module implements exactly two checks, both of which I ran independently against ux-designer's hand-computed table (11/11 hex values and 22/22 contrast figures reproduced exactly):**

1. **WCAG contrast ≥ 2:1** for all 8 role tokens and all 3 neutral fold/guard tokens, against **each mode's own `--card` — both parsed from the same `app.css` under test**, never hardcoded. — the surface is half of a contrast ratio; a guard that pins it cannot catch someone re-tuning `--card`.
2. **Minimum pairwise OKLab ΔE ≥ 0.06** among the eight role hues. — this is the categorical criterion. **Do not substitute the ordinal validator's monotone-lightness check**: it is meaningless for unordered categories and would render roles as though ranked. Measured minimum today is **0.078** (`team-lead` / `seceng`, the two blues), 3.9× the ~0.02 JND, so 0.06 has headroom without being toothless.

**Values are parsed from the CSS under test, never snapshotted** — same posture as `test_dashboard_chart_ramp.py`, which is what caught the original `--chart-1`/`--chart-2` failure.

**Verified before handing over — the guard is decisive in both directions**, which is the property that matters:

- **Passes** the 11 proposed values, reporting the same figures ux-designer published.
- **Fails** a token pushed under the contrast floor (`--chart-role-6` at the old `--chart-1` yellow → `1.32:1`).
- **Fails** two role hues collapsed together (ΔE 0.005).
- **Fails** a deleted token, by name.
- **Fails** a change to the *surface* side — lightening the dark `--card` produces 10 failures. A snapshot-based guard would miss this entirely, and it is the realistic future edit.
