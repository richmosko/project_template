## Problem

Three receiver hazards found by the architect on 2026-09-04 while writing the v0.11.0 migration
note, each verified by construction with two fake project roots. One of them produced a real
contamination during PT-79: a payload POSTed from an unrelated directory was accepted and written
into this repo's committed `token-usage.jsonl` as a PT-79 row (removed before commit).

- **H1** The SessionStart hook starts the receiver even when telemetry is off. `ensure_running`
  gates only on `config.yml`, so every downstream cairn project gets a bound port and an idle
  daemon it never opted into.
- **H2** A second project on the same port dies silently. `ensure_running` exits 0 while its child
  fails with `Address already in use`; no pidfile, no listener, the only trace in a gitignored log.
- **H3** The receiver's port (`otel_port` in `config.yml`) and the exporter's destination
  (`OTEL_EXPORTER_OTLP_ENDPOINT`) are configured independently and nothing checks they agree. A
  mismatch does not lose telemetry; it delivers it to whatever else is listening, which writes
  rows into its own data file under its own branch.

## Rulings (architect, 2026-09-04; lead adjustment on H3)

1. `ensure_running` requires `CLAUDE_CODE_ENABLE_TELEMETRY` truthy in its environment; otherwise
   it returns False, spawns nothing, exits 0 quietly. The settings `env` block reaches hook-spawned
   subprocesses, so one block controls exporter and receiver.
2. `ensure_running` verifies the child bound. On failure it distinguishes "port held by another
   process" from "spawn failed", prints a message naming the port and `otel_port`, returns False.
   The hook still exits 0 but stops redirecting stderr to /dev/null. Add `--status` (running?,
   port, out-file).
3. `otel_port` in `config.yml` is the single source of truth. At start the receiver compares it with
   the port in its own inherited `OTEL_EXPORTER_OTLP_ENDPOINT` (not by parsing settings.json —
   telemetry env may legitimately live in settings.local.json or the shell). If the variable is set
   and the ports disagree, the receiver refuses to start, naming both. If unset, H1 already
   declined. `/setup-tracker` writes both from the single `otel_port` answer.

## Acceptance criteria

1. Tests with two fake project roots (each with `process/cairn/config.yml` + engine scripts):
   telemetry off → no process, exit 0; second project on a held port → return False, message names
   the port, exit 0 from the hook line; endpoint/port mismatch → refusal naming both; match → start.
2. `--status` output covered by a test.
3. Hook line in `.claude/settings.json` keeps stderr; `TRACKER.md` documents the three behaviours
   and `/setup-tracker` writes `otel_port` and the endpoint from one answer.
4. Full suite green; `cairn check` ok; committed data file byte-identical to a4f702c.
