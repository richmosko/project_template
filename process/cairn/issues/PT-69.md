### @architect — 2026-08-29

**Architect ruling — theme-variant architecture (gating).** Read first: `dashboard/src/app.css`, `board/tokens.css`, `board.html`, `board.js` §PT-30 storage, `board-logic.js` `viewStateKey`, `test_board_tokens_parity.py`, `test_css_parse_sanity.py`, `test_dashboard_chart_ramp.py`, `cairn.py` static routes.

**Facts this ruling rests on** (verified, not recalled): both surfaces are served by ONE Python process on ONE port (`/board/<rel>` and `/dashboard/<rel>`), so they share a localStorage origin. `board.css` is fully tokenized — zero hex, and the only literal colors left are three black-alpha shadows/scrim (the `rgb(9, 30, 66)` hit is inside a comment). **Nothing in either surface ever adds the `.dark` class today** — both files carry `.dark` token blocks that are, right now, dead code. Mode is therefore a new mechanism on both surfaces, not a toggle of an existing one.

### 1. Variant token source — hand-vendored, generated from checked-in data. No network, ever.

Registry-fetch-at-build is rejected outright: the board is zero-build and "clone and it works" is the template's strongest property. A fetch on the user's machine breaks it; a fetch in CI makes the palette a moving target.

Source of truth: **`scripts/cairn/design/variants.json`** — vendored palette data (option sets + their token values), with `scripts/cairn/design/NOTICE.md` carrying provenance/extraction date per dimension, exactly the PT-63 font-vendoring precedent. Values are *extracted from shadcn-svelte's own generator* (browser pass, per the 2026-08-26 preset-extraction precedent — WebFetch does not work for this), not computed by us: these are shadcn's dimensions, and inventing our own hues would defeat the point.

Emission: **`scripts/cairn/design/gen_variants.py`** — stdlib-only, zero deps, no network — writes three generated CSS files. It is an *authoring* tool run by an agent, never on the clone path.

Guard: a test regenerates to a temp dir and asserts **byte-identical** to the committed files. That is strictly stronger than `test_board_tokens_parity.py`'s value-comparison and it retires hand-editing as a drift class for everything it covers. Generator output must be deterministic (sorted keys, fixed block order).

### 2. Runtime mechanism — one shared CSS file per surface, `data-*` on `<html>`, cascade composition.

**Do not swap stylesheets.** FOUC on every change, N requests, and for the dashboard it turns per-variant CSS into an enumerated build output.

The dimensions are near-orthogonal *token subsets*, and that is what keeps this from exploding:

| Dimension | Attribute | Owns |
|---|---|---|
| Base Color | `data-cairn-base` | neutrals: `--background --foreground --card(-foreground) --popover(-foreground) --secondary(-foreground) --muted(-foreground) --accent(-foreground) --border --input --ring --destructive(-foreground) --sidebar --sidebar-foreground --sidebar-accent(-foreground) --sidebar-border --sidebar-ring` |
| Theme | `data-cairn-theme` | brand hue: `--primary --primary-foreground --sidebar-primary --sidebar-primary-foreground` |
| Chart Color | `data-cairn-chart` | `--chart-1..5` + `--chart-flow-*` |
| Mode | `.dark` class (unchanged) | selects the light/dark half of each block above |

Blocks are **O(B + T + C)**, not O(B×T×C) — ~2×(B+T+C) blocks total, order ~16KB uncompressed. That is the whole reason to compose in the cascade rather than ship whole themes.

**Hard invariant: the three groups must PARTITION the token set.** A variable declared under two dimensions is a cascade race whose winner depends on source order. Require a test asserting no variable name appears in more than one dimension's blocks. This invariant is what makes the composition sound; it is not a style preference.

Selectors — attributes and `.dark` both live on `<html>`, so they compound on one element:
```
:root { /* existing defaults — unchanged */ }
.dark { /* existing defaults — unchanged */ }
:root[data-cairn-base="zinc"] { … }          /* (0,2,0) */
:root.dark[data-cairn-base="zinc"] { … }     /* (0,3,0) */
```
Specificity does the work: every variant block outranks the defaults, and dark outranks light, so nothing depends on inter-block source order beyond "variants come after defaults." No `!important`.

**`data-cairn-*`, not `data-base`/`data-theme`/`data-chart`.** `data-chart` is already taken — `lib/components/ui/chart/chart-container.svelte` sets it and `chart-style.svelte` generates `[data-chart=<id>]` rules. Namespacing is not cosmetic here.

Mode keeps the **`.dark` class**, not a `data-*` attribute. Changing it would mean rewriting app.css's `@custom-variant dark (&:is(.dark *))`, both existing token files, and the parity test, and buys nothing. `<html>` is the carrier: `:is(.dark *)` covers everything under `<body>`.

Files (generated): `scripts/cairn/board/variants.css` (linked in `board.html` **after** `tokens.css`, before `board.css`), `scripts/cairn/dashboard/src/variants.css` (`@import './variants.css';` immediately after app.css's existing three imports — still ahead of any rule, so Tailwind v4's import-ordering rule holds), `docs/DESIGN/variants.css` (spec copy, ux-designer documents the option sets prose-side in `design-system-spec.md`). **All three go into `test_css_parse_sanity.py`'s file list** — a generated stylesheet is exactly as capable of shipping dead as a hand-written one, and a `0 cssRules` variants.css would fail silently as "theme just doesn't change."

### 3. Persistence — one origin-global key, per-dimension fallback, inline head bootstrap.

Key: **`cairn.theme`** (not under `cairn.board.*` — it spans surfaces). Value: `{"v":1,"mode":"system|light|dark","base":"…","theme":"…","chart":"…"}`.

**Deliberately NOT repo-scoped**, and this is the one place I am departing from PT-30. `expandedLanes` is keyed by primary root id because it is a fact *about a project*. A theme is a fact about *the person looking* — a user who picks Zinc does not want it to revert when they open a different repo's board on the same port. Wrong-dimension keying is this codebase's recurring defect class, so: the dimension here is the user/origin, and origin-global is the correct scope. If someone later wants per-repo themes, that is a new key, not a re-scoping of this one.

Access: reuse PT-30's contract verbatim — `localStorage` referenced *inside* each `try`, no hoisted module-level reference, no cached `storageAvailable` flag, silent per-call degrade to in-memory.

Read discipline: **per-dimension fallback**, not whole-blob rejection. An unrecognized or absent `base` falls back to the default base while leaving the user's `chart` choice intact; a future v2 adding a dimension must not wipe the other three. A `v` this reader doesn't know → ignore the blob entirely.

**FOUC:** a small **inline** `<script>` in `<head>` — before the stylesheet links in `board.html`, before the module script in `dashboard/index.html` — reads the key and sets `document.documentElement.className` / `dataset` synchronously. It must be inline: an external file is a second blocking request on the board and a Vite asset on the dashboard. That snippet is a fourth accepted copy; **generate it from the same `variants.json` and assert both heads contain it verbatim.**

**Defaults disagreeing is a build-time failure, not a runtime one.** The default tuple (`{mode:"system", base:"stone", theme:"sky", chart:"yellow"}` — preset b6XadDxmQS) is emitted into both bootstrap snippets from `variants.json`, and the byte-identity test is the enforcement. The offered option sets likewise come from one file, so "dashboard offers a variant the board doesn't" cannot arise; the per-dimension fallback above is the defensive backstop, not the plan.

**Cross-surface propagation:** same origin ⇒ same bucket, so a reload is already correct. For two live tabs, listen for the `storage` event (fires in *other* tabs on write) and re-apply. Cheap, and without it board-and-dashboard-side-by-side — the obvious way to demo this — looks broken.

### 4. Chart-ramp validation — per-variant, extremal-surface, test-enforced.

Each Chart Color variant ships its own 6-step `--chart-flow-*` ordinal ramp, authored into `variants.json` alongside its `--chart-1..5`, derived with the dataviz skill's `validate_ordinal` (see implementation-lead's technique notes — the ≥0.065 gap for hex-quantization noise, and the OKLCH→hex inverse you have to write yourself). PT-61's light-end floor failure is a property of the hue, so **it will recur per hue**; assume every variant needs re-stepping, not just some.

The gate is structural: **parameterize `test_dashboard_chart_ramp.py`'s `ChartRampOrdinalValidationTests` over every chart variant.** A promise to run the validator is not a gate.

**Which surface to validate against** — the ramp's surface is `--card`, which is Base-Color-dependent, so the naive obligation is C×B×2 validator runs. It collapses to **C×2**, exactly and not heuristically: for a fixed ramp, contrast against the card is monotone in card luminance on each side. So take the set of all `--card` values across every (base × mode) combination and validate every ramp's **light end against the maximum-luminance card** and its **dark end against the minimum-luminance card**. If the extremes pass, every base passes. **Compute the extrema from the data in the test** — do not hardcode which base is extremal; that is a fact about the option set, and the option set will change.

**Budget, ux-designer:** Chart Color is the expensive dimension — PT-61 was a whole feature for *one* ramp. Cap it at **≤5 chart variants** for PT-69; more is a follow-up issue, not scope creep here. Base Color and Theme are cheap (vendored, no derivation) — spend the option-count budget there.

### 5. Scope fence

**Out, explicitly:** Style, Radius, Font, Icon Library, Heading, Menu, Menu Accent, Shuffle, Reset, Undo/Redo — every reference-menu row except the four Mosko named. Also out: per-repo or per-major theming, any server-side persistence or cross-device sync (localStorage only), and the docs HTML artifacts (`docs/_assets/toc.js` keeps its own independent `doc-theme` toggle — do not merge them; different surface, different lifecycle).

**In, and under-estimated:** *dark mode on the board has never been rendered.* The `.dark` block in `board/tokens.css` has been dead since PT-57. `board.css` is token-clean so this should be mostly mechanical, and the three remaining black-alpha shadows/scrim are mode-tolerant — but "should be" is not a measurement. Per this project's browser-visibility precedent, the board in dark mode needs an **actual rendered check** (screenshot / computed-style-at-point), not a token-presence assertion. If it turns out worse than mechanical, split it out rather than letting it swallow PT-69.

**Ledger at finish:** the 2026-08-26 preset-pure ruling relaxes to "b6XadDxmQS as the default point in a variant space along shadcn's own dimensions" — `process/DECISIONS.md` entry required, along with the origin-global key-scoping departure from PT-30 in §3.
