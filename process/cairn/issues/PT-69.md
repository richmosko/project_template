### @architect — 2026-08-29

**Architect ruling — theme-variant architecture (gating).** Read first: `dashboard/src/app.css`, `board/tokens.css`, `board.html`, `board.js` §PT-30 storage, `board-logic.js` `viewStateKey`, `test_board_tokens_parity.py`, `test_css_parse_sanity.py`, `test_dashboard_chart_ramp.py`, `cairn.py` static routes.

**Facts this ruling rests on** (verified, not recalled): both surfaces are served by ONE Python process on ONE port (`/board/<rel>` and `/dashboard/<rel>`), so they share a localStorage origin. `board.css` is fully tokenized — zero hex, and the only literal colors left are three black-alpha shadows/scrim (the `rgb(9, 30, 66)` hit is inside a comment). **Nothing in either surface ever adds the `.dark` class today** — both files carry `.dark` token blocks that are, right now, dead code. Mode is therefore a new mechanism on both surfaces, not a toggle of an existing one.

### 1. Variant token source — hand-vendored, generated from checked-in data. No network, ever.

Registry-fetch-at-build is rejected outright: the board is zero-build and "clone and it works" is the template's strongest property. A fetch on the user's machine breaks it; a fetch in CI makes the palette a moving target.

Source of truth: **`scripts/cairn/design/variants.json`** — vendored palette data (option sets + their token values), with `scripts/cairn/design/NOTICE.md` carrying provenance/extraction date per dimension, exactly the PT-63 font-vendoring precedent. Values are *extracted from shadcn-svelte's own generator* (browser pass, per the 2026-08-26 preset-extraction precedent — WebFetch does not work for this), not computed by us: these are shadcn's dimensions, and inventing our own hues would defeat the point.

Emission: **`scripts/cairn/design/gen_variants.py`** — stdlib-only, zero deps, no network — writes three generated CSS files. It is an *authoring* tool run by an agent, never on the clone path.

Guard: a test regenerates to a temp dir and asserts **byte-identical** to the committed files. That is strictly stronger than `test_board_tokens_parity.py`'s value-comparison and it retires hand-editing as a drift class for everything it covers. Generator output must be deterministic (sorted keys, fixed block order).

### 2. Runtime mechanism — one shared CSS file per surface, `data-*` on `<html>`, cascade composition.

**Do not swap stylesheets.** FOUC on every change, N requests, and for the dashboard it turns per-variant CSS into an enumerated build output.

The dimensions are near-orthogonal *token subsets*, and that is what keeps this from exploding:

| Dimension | Attribute | Owns |
|---|---|---|
| Base Color | `data-cairn-base` | neutrals: `--background --foreground --card(-foreground) --popover(-foreground) --secondary(-foreground) --muted(-foreground) --accent(-foreground) --border --input --ring --destructive(-foreground) --sidebar --sidebar-foreground --sidebar-accent(-foreground) --sidebar-border --sidebar-ring` |
| Theme | `data-cairn-theme` | brand hue: `--primary --primary-foreground --sidebar-primary --sidebar-primary-foreground` |
| Chart Color | `data-cairn-chart` | `--chart-1..5` + `--chart-flow-*` |
| Mode | `.dark` class (unchanged) | selects the light/dark half of each block above |

Blocks are **O(B + T + C)**, not O(B×T×C) — ~2×(B+T+C) blocks total, order ~16KB uncompressed. That is the whole reason to compose in the cascade rather than ship whole themes.

**Hard invariant: the three groups must PARTITION the token set.** A variable declared under two dimensions is a cascade race whose winner depends on source order. Require a test asserting no variable name appears in more than one dimension's blocks. This invariant is what makes the composition sound; it is not a style preference.

Selectors — attributes and `.dark` both live on `<html>`, so they compound on one element:
```
:root { /* existing defaults — unchanged */ }
.dark { /* existing defaults — unchanged */ }
:root[data-cairn-base="zinc"] { … }          /* (0,2,0) */
:root.dark[data-cairn-base="zinc"] { … }     /* (0,3,0) */
```
Specificity does the work: every variant block outranks the defaults, and dark outranks light, so nothing depends on inter-block source order beyond "variants come after defaults." No `!important`.

**`data-cairn-*`, not `data-base`/`data-theme`/`data-chart`.** `data-chart` is already taken — `lib/components/ui/chart/chart-container.svelte` sets it and `chart-style.svelte` generates `[data-chart=<id>]` rules. Namespacing is not cosmetic here.

Mode keeps the **`.dark` class**, not a `data-*` attribute. Changing it would mean rewriting app.css's `@custom-variant dark (&:is(.dark *))`, both existing token files, and the parity test, and buys nothing. `<html>` is the carrier: `:is(.dark *)` covers everything under `<body>`.

Files (generated): `scripts/cairn/board/variants.css` (linked in `board.html` **after** `tokens.css`, before `board.css`), `scripts/cairn/dashboard/src/variants.css` (`@import './variants.css';` immediately after app.css's existing three imports — still ahead of any rule, so Tailwind v4's import-ordering rule holds), `docs/DESIGN/variants.css` (spec copy, ux-designer documents the option sets prose-side in `design-system-spec.md`). **All three go into `test_css_parse_sanity.py`'s file list** — a generated stylesheet is exactly as capable of shipping dead as a hand-written one, and a `0 cssRules` variants.css would fail silently as "theme just doesn't change."

### 3. Persistence — one origin-global key, per-dimension fallback, inline head bootstrap.

Key: **`cairn.theme`** (not under `cairn.board.*` — it spans surfaces). Value: `{"v":1,"mode":"system|light|dark","base":"…","theme":"…","chart":"…"}`.

**Deliberately NOT repo-scoped**, and this is the one place I am departing from PT-30. `expandedLanes` is keyed by primary root id because it is a fact *about a project*. A theme is a fact about *the person looking* — a user who picks Zinc does not want it to revert when they open a different repo's board on the same port. Wrong-dimension keying is this codebase's recurring defect class, so: the dimension here is the user/origin, and origin-global is the correct scope. If someone later wants per-repo themes, that is a new key, not a re-scoping of this one.

Access: reuse PT-30's contract verbatim — `localStorage` referenced *inside* each `try`, no hoisted module-level reference, no cached `storageAvailable` flag, silent per-call degrade to in-memory.

Read discipline: **per-dimension fallback**, not whole-blob rejection. An unrecognized or absent `base` falls back to the default base while leaving the user's `chart` choice intact; a future v2 adding a dimension must not wipe the other three. A `v` this reader doesn't know → ignore the blob entirely.

**FOUC:** a small **inline** `<script>` in `<head>` — before the stylesheet links in `board.html`, before the module script in `dashboard/index.html` — reads the key and sets `document.documentElement.className` / `dataset` synchronously. It must be inline: an external file is a second blocking request on the board and a Vite asset on the dashboard. That snippet is a fourth accepted copy; **generate it from the same `variants.json` and assert both heads contain it verbatim.**

**Defaults disagreeing is a build-time failure, not a runtime one.** The default tuple (`{mode:"system", base:"stone", theme:"sky", chart:"yellow"}` — preset b6XadDxmQS) is emitted into both bootstrap snippets from `variants.json`, and the byte-identity test is the enforcement. The offered option sets likewise come from one file, so "dashboard offers a variant the board doesn't" cannot arise; the per-dimension fallback above is the defensive backstop, not the plan.

**Cross-surface propagation:** same origin ⇒ same bucket, so a reload is already correct. For two live tabs, listen for the `storage` event (fires in *other* tabs on write) and re-apply. Cheap, and without it board-and-dashboard-side-by-side — the obvious way to demo this — looks broken.

### 4. Chart-ramp validation — per-variant, extremal-surface, test-enforced.

Each Chart Color variant ships its own 6-step `--chart-flow-*` ordinal ramp, authored into `variants.json` alongside its `--chart-1..5`, derived with the dataviz skill's `validate_ordinal` (see implementation-lead's technique notes — the ≥0.065 gap for hex-quantization noise, and the OKLCH→hex inverse you have to write yourself). PT-61's light-end floor failure is a property of the hue, so **it will recur per hue**; assume every variant needs re-stepping, not just some.

The gate is structural: **parameterize `test_dashboard_chart_ramp.py`'s `ChartRampOrdinalValidationTests` over every chart variant.** A promise to run the validator is not a gate.

**Which surface to validate against** — the ramp's surface is `--card`, which is Base-Color-dependent, so the naive obligation is C×B×2 validator runs. It collapses to **C×2**, exactly and not heuristically: for a fixed ramp, contrast against the card is monotone in card luminance on each side. So take the set of all `--card` values across every (base × mode) combination and validate every ramp's **light end against the maximum-luminance card** and its **dark end against the minimum-luminance card**. If the extremes pass, every base passes. **Compute the extrema from the data in the test** — do not hardcode which base is extremal; that is a fact about the option set, and the option set will change.

**Budget, ux-designer:** Chart Color is the expensive dimension — PT-61 was a whole feature for *one* ramp. Cap it at **≤5 chart variants** for PT-69; more is a follow-up issue, not scope creep here. Base Color and Theme are cheap (vendored, no derivation) — spend the option-count budget there.

### 5. Scope fence

**Out, explicitly:** Style, Radius, Font, Icon Library, Heading, Menu, Menu Accent, Shuffle, Reset, Undo/Redo — every reference-menu row except the four Mosko named. Also out: per-repo or per-major theming, any server-side persistence or cross-device sync (localStorage only), and the docs HTML artifacts (`docs/_assets/toc.js` keeps its own independent `doc-theme` toggle — do not merge them; different surface, different lifecycle).

**In, and under-estimated:** *dark mode on the board has never been rendered.* The `.dark` block in `board/tokens.css` has been dead since PT-57. `board.css` is token-clean so this should be mostly mechanical, and the three remaining black-alpha shadows/scrim are mode-tolerant — but "should be" is not a measurement. Per this project's browser-visibility precedent, the board in dark mode needs an **actual rendered check** (screenshot / computed-style-at-point), not a token-presence assertion. If it turns out worse than mechanical, split it out rather than letting it swallow PT-69.

**Ledger at finish:** the 2026-08-26 preset-pure ruling relaxes to "b6XadDxmQS as the default point in a variant space along shadcn's own dimensions" — `process/DECISIONS.md` entry required, along with the origin-global key-scoping departure from PT-30 in §3.

## UX proposal — theme/color settings dropdown (Mode / Base Color / Theme / Chart Color)

**Method note:** no browser tool was available in this session (`ToolSearch`/claude-in-chrome disabled), so I could not re-scrape the live shadcn-svelte.com settings menu myself — this proposal is grounded in the design-system-spec's already-*confirmed* preset extraction (Style Mira / Base Stone / Theme Sky / Chart Yellow) plus shadcn's well-documented, stable neutral/accent vocabulary, not a fresh live read. Recommend a quick confirm pass against the reference page before frontend-lead locks exact swatch order — team-lead's 2026-08-28 anatomy pass already covers row structure, so this is a narrow follow-up, not a re-do.

### 1. Option sets

**Base Color** — swaps only the neutral family (`--background`/`--foreground`/`--muted`/`--border`/`--card`/`--sidebar` etc.), no accent or chart impact, no new a11y risk beyond what Stone already carries. This is shadcn's own **closed** 5-way set, so "curated" and "complete" are the same thing here — ship all 5, no cost to trim:
- **Stone** — DEFAULT (current preset)
- Neutral
- Zinc
- Gray
- Slate

**Theme** — swaps the accent family (`--primary`, `--primary-foreground`, `--sidebar-primary(-foreground)`, `--ring`). Each addition costs one contrast check (primary-foreground on primary, same flag the spec already raises for the current Sky pair), not a full ramp. Recommend **4 total**, spread across hue families so the choices actually read as different rather than clustering near Sky:
- **Sky** — DEFAULT (current preset)
- Violet
- Rose
- Green

**Chart Color** — swaps the chart hue (`--chart-1`…`--chart-5` sequential ramp **and** PT-61's 6-step ordinal chart-flow ramp). This is the expensive one: every variant needs both ramps re-derived and run through the dataviz validator (`validate_ordinal` — monotone lightness, ≥0.06 ΔL, ≤40° hue spread, ≥2:1 light-end contrast) against **both** light and dark `--card` surfaces, per the PT-61 precedent. Recommend the smallest defensible set, **3 total**:
- **Yellow** — DEFAULT (current preset, already validated)
- Blue
- Violet

Flagging for architect: Theme=4 / Chart=3 (both counts include the default) is my judgment call on "small and curated" — trim further if the validator-run budget is tighter than I'm assuming, especially on Chart Color.

### 2. Dropdown anatomy

- **Row order:** Mode (top — most-used, single toggle), then Base Color, Theme, Chart Color — each a **submenu**, not cycle-on-click.
- **Submenu over cycle-on-click, recommended:** cycle-on-click makes reaching option 3-of-4 cost 3 blind clicks with no visibility into what's ahead. A submenu (`DropdownMenu.Sub` + `DropdownMenu.RadioGroup`) shows the full option set and the current selection (native checkmark) in one view — this also reuses shadcn's existing RadioItem/CheckboxItem selection idiom rather than inventing a stateless cycling interaction with no precedent elsewhere in this design system.
- **Row content:** label + current-value text + right-side indicator (swatch dot for Base/Theme/Chart, sun/moon icon for Mode) — matches the reference anatomy exactly.
- **Placement — dashboard:** `Sidebar.Footer`. This is the natural home per the spec's own Sidebar section ("dashboards are assumed to ship a persistent nav sidebar as a first-class surface") — always visible, doesn't compete with the page header. Trigger = icon button (Lucide `Settings2`, this system's stated icon library) with an "Appearance" label when the sidebar is expanded, icon-only when collapsed (mirrors how Sidebar already handles nav items at collapsed width).
- **Placement — board:** the board is vanilla HTML/CSS/JS with no Svelte sidebar (`board.css`, per Legacy/migration). Recommend a small trigger pinned to the board's own top-right header — the natural fallback for a page with no sidebar, and it happens to match the reference pattern's own top-right placement. Style it with the same OKLCH values already mapped in the Legacy/migration table (popover surface, `radius-lg`, `shadow-sm`) so it reads as intentional rather than bolted-on, even though it can't literally mount the Svelte `DropdownMenu` primitive. Both surfaces read/write the same `localStorage` key per the issue's "one persisted choice, both surfaces" ruling — the swap *mechanism* (data-attribute vs. class vs. full token replacement) is architect's call, not mine; this proposal only fixes the UI/visual contract.
- **Mode row:** **light/dark toggle (2-state)**, not a 3-state light/dark/system — this matches Mosko's own scope note ("Mode (light/dark toggle)"), so it's confirmation not a new recommendation. Rationale for the record: a toggle keeps Mode a single click with an immediate dot/icon flip, consistent with every other row being one visible current-value indicator; a 3-way "system" option would need its own submenu, which breaks the row's single-toggle simplicity. Adding "follow OS" later is a strict additive change (promote Mode from toggle to submenu), not a redesign.

### 3. States

- **Indicator dot:** ~8px circle, filled with the *token* the row currently resolves to — Theme dot shows current `--primary`, Base Color dot shows current `--foreground` (reads cleanest as a neutral chip at that size), Chart Color dot shows current `--chart-3` (a representative mid-ramp step). Mode swaps a Lucide `Sun`/`Moon` icon instead of a dot, since it isn't a hue choice.
- **Hover/focus:** stock shadcn `DropdownMenu.Item` — `accent`/`accent-foreground` hover surface, `focus-visible:ring-ring` on keyboard focus, per the Components table. No new CSS.
- **Selected submenu row:** native checkmark + bold label, not a border/fill change — stays lightweight at 3–5 rows per submenu.
- **Reset:** recommend **OUT**, confirming the issue's own steer. It's not one of the four named controls; at only 4 settings (vs. the reference's 10+), manually re-selecting defaults is ≤4 clicks; and "reset to what" (page default vs. last-saved vs. the b6XadDxmQS preset) is a real open question with no forcing note to answer it here. Revisit if a future ticket grows this dropdown past ~4 knobs.
- **First paint:** before `localStorage` is read (SSR/hydration gap), fall back to preset defaults (Stone/Sky/Yellow/light) — no flash-of-unstyled-content, no skeleton needed since this is a synchronous local read, not a network fetch.

## Addendum — Mode row, 3-state shape (per team-lead's ruling)

Ruled: `system|light|dark`, default `system`. Spec'ing the row to match the reference anatomy exactly, consistent with the other three rows rather than as a special case:

- **Main row:** label "Mode" + current-value text (`System` / `Light` / `Dark`) + right-side icon indicator — same label+value+indicator shape as Base Color/Theme/Chart Color, not a toggle. (Supersedes my earlier 2-state-toggle recommendation, which is now moot.)
- **Submenu:** `DropdownMenu.Sub` + `DropdownMenu.RadioGroup`, three items in this order — **System, Light, Dark** (System first: it's the default, and matches the System→Light→Dark ordering convention most apps with this exact pattern use, e.g. GitHub/Vercel settings menus). Each item: icon + label, native checkmark on the active one — identical selection idiom to the other three submenus.
- **Icons (Lucide, this system's stated icon library):** `Monitor` = System, `Sun` = Light, `Moon` = Dark. The main row's right-side indicator icon mirrors whichever of the three is currently *selected* (not the OS-resolved effective appearance) — i.e. if the user has picked System and the OS happens to be in dark mode right now, the row still shows the Monitor icon, not Moon. Showing the resolved appearance instead of the selection would make the row lie about what's actually stored, and would flicker on every OS-level theme change without the user touching anything.
- **Live-follow requirement (state, not just visual):** when `mode="system"`, the effective `.dark` class must track `prefers-color-scheme` at runtime, including *while the page is open* — listen for the media query's `change` event, not just read it once at load. This is in addition to architect's cross-tab `storage` event listener (§3 of the ruling) — two different triggers for the same "the visible mode can change without a click" requirement, both needed.
- **First paint / FOUC:** covered by architect's inline bootstrap script (§3) — for `mode="system"` specifically, that script must evaluate `matchMedia('(prefers-color-scheme: dark)').matches` synchronously, not just fall through to the light default, or a system-dark user gets a light flash on every load.

This closes out the anatomy proposal — option sets (Base 5 / Theme 7 / Chart 3) and all four rows' shapes are now fully specified. Adding the DropdownMenu component + these dimensions to `design-system-spec.md` next.

### @architect — 2026-08-29

**Architect addendum — three corrections, all gating.** Read the tree after ux-designer's proposal and team-lead's Mode ruling. Option-set counts stand as adopted: Base ×5, Theme ×7, Chart ×3 — 2×(5+7+3) = 30 variant blocks, well inside the mechanism's budget. Three things in the proposal will build wrong as written.

**1. `--ring` belongs to Base, not Theme — this is the partition violation, and it's not theoretical.** ux-designer's §1 lists `--ring` under Theme; my §2 table assigns it to Base. Base wins, on the data: `--ring` is `oklch(0.709 0.01 56.259)` light / `oklch(0.553 0.013 58.071)` dark — chroma 0.010–0.013 at hue ~57, which is the stone *neutral* hue, whereas `--primary` is chroma 0.134 at hue ~241. `--ring` is a neutral that tracks the base scale; it is not the accent. Same for `--sidebar-ring` (identical values). Theme owns exactly four tokens: `--primary`, `--primary-foreground`, `--sidebar-primary`, `--sidebar-primary-foreground`.

This is precisely the cascade race §2's partition invariant exists to prevent — had it shipped, `--ring` would be declared under two dimensions and the focus-ring color would depend on which block the generator happened to emit last. The partition test is what catches the next one; it isn't ceremony.

**2. First paint must resolve `system`, not fall back to light.** ux-designer's §3 specifies the first-paint fallback as "Stone/Sky/Yellow/**light**". With Mode now ruled 3-state defaulting to `system`, forcing light on first paint hands every dark-OS user a white flash on every cold load — the exact FOUC the inline `<head>` bootstrap exists to prevent, just relocated. Correct fallback: **Stone/Sky/Yellow + `prefers-color-scheme` resolved synchronously in the bootstrap.**

Related, and worth stating so nobody builds for it: there is **no SSR/hydration gap** on either surface. The dashboard is a static Vite SPA, not SSR, and the bootstrap is an inline `<head>` script that runs before first paint on both surfaces. The `localStorage` read is synchronous and complete before anything renders. No skeleton, no deferred-apply, no hydration reconciliation.

**3. The 3-state ruling adds a runtime obligation nobody has written down yet: a `matchMedia` change listener.** If stored mode is `system` (or absent), the OS flipping light↔dark *mid-session* must re-resolve `.dark` live — `window.matchMedia('(prefers-color-scheme: dark)').addEventListener('change', …)`, attached only while mode resolves to system, and torn down or no-op'd once the user picks an explicit light/dark. `docs/_assets/toc.js` already does exactly this for its own `auto` state; copy that shape. Without it, "System" is a lie that only tells the truth at load time. Both `"system"` stored explicitly and the key being absent resolve identically — no need to distinguish them.

**Correcting my own earlier note to ux-designer: Theme is cheap, but I called it "almost nothing" and that was imprecise.** Each Theme variant is two text-on-fill contrast pairs per mode (`--primary-foreground` on `--primary`, `--sidebar-primary-foreground` on `--sidebar-primary`); each Base variant likewise carries `--foreground`/`--background`, `--card-foreground`/`--card`, `--muted-foreground`/`--muted`. Cheap *per check* and trivially parameterized — one test walking every (dimension, variant, mode) tuple from `variants.json` and asserting its declared foreground/background pairs clear the WCAG floor, reusing the OKLCH→hex bridge the chart-ramp tests already carry. But not zero, and not assumable: PT-61's whole lesson is that a published shadcn palette *did* fail a floor nobody thought to check. Seven Theme variants is still the right call — the cost is one more row in a parameterized test, not one more derivation.

**Scope fence on that gate — and this one matters for schedule.** If a Base or Theme variant fails its contrast check, **drop the variant from the option set; do not re-derive it.** We are not in the business of repairing shadcn's published neutrals, and a re-derived "Zinc" that isn't shadcn's Zinc is worse than four base colors. Chart Color is the deliberate exception: `--chart-flow-*` is our own token and PT-61 already established we re-step it per hue, so a failing chart variant gets re-derived, not dropped.

**Non-gating, ux-designer's call — the Base Color indicator dot won't discriminate.** §3 has the Base dot filled with `--foreground`. ### @architect — 2026-08-29

**Architect ruling — contrast gate semantics (gating).** The gate that's failing is mine, and the first finding is that I specified it wrong. Verified against the tree, not reasoned from the token names.

## The error

I derived the gate's pair list from **token-name symmetry** — "`X-foreground` renders on `X`" — and wrote it out as a cross-product. That's a naming convention, not evidence that anything renders it. Gating a pair nothing renders asserts a property of something that doesn't exist: the same class of mistake as fabricating a measured value, pointed the other way. It also caused the opposite error in the same stroke — the cross-product **missed** the most common real pair in both surfaces. I over-tested and under-tested simultaneously.

## Q1 — Pair reality: the gate tests RENDERED pairs, derived from usage

**DROP `--sidebar-primary-foreground` / `--sidebar-primary`.** Verified zero references across `board.css`, `board.js`, `board.html`, and all of `dashboard/src` — *including* the vendored shadcn `lib/components/ui/sidebar/` component, which carries no `sidebar-primary` reference at all and styles its active item off `--sidebar-accent`. These two tokens are declared in all three token files and referenced by nothing. They are dead tokens in this project.

This one removal restores the **entire Theme dimension**. Every one of the 7 Theme failures was on this pair; `--primary-foreground`/`--primary` — the pair that *is* rendered (`bg-primary`) — passes everywhere, both modes. Theme goes from 0 viable options back to 7.

**KEEP `--muted-foreground` / `--muted`.** This one is real and does not get waved away. The board's `body { background: var(--muted) }` makes the entire canvas a muted surface, as do `.column`, `.swimlane`, `.drawer pre`, `.markdown-body`; `--muted-foreground` text sits inside them (`.column-header`, `.swimlane-header`, `.empty-state`, and ~20 more rules). The dashboard's body is `bg-muted` with 8 `text-muted-foreground` usages. Genuinely rendered, heavily, on both surfaces.

**ADD `--muted-foreground` / `--card`** — meta text inside cards, the single most common foreground/surface combination in both surfaces, which my cross-product never tested. It passes at **4.79:1**, and that number is the sharpest fact in this whole finding: *the identical text passes on cards and fails on the canvas.* The defect is the surface, not the ink.

**`--foreground` / `--background`:** `--background` is never used as a surface on the board and the dashboard's body is `bg-muted`. Keep it only if the browser confirmation below finds it actually rendered; otherwise it's another naming-convention pair.

**The rule going forward:** the gate's pair list is **derived from source usage and re-derived on every run**, never hand-maintained — same discipline as `test_board_small_label_face.py`, which re-derives its selector set from source rather than pinning today's list. A pair enters the gate when something actually renders that foreground on that background, and leaves when nothing does.

**Method caveat, stated because it is exactly the trap this project keeps stepping in:** statically deriving "what surface does this text sit on" is text-level inference about a DOM that doesn't exist until it's rendered. The derived pair list must be **confirmed once in a real browser** — walk the rendered DOM, take each text node's computed color against its effective *composited* background — and that confirmation is the authority. The static derivation is the regression guard afterwards, not the source of truth. Do not let a passing text-level test stand in for that first confirmation.

## Q2 — Role-dependent floors: by the standard, not by convenience

Each pair carries a **role**, and the gate applies the floor the standard gives that role:
- **Normal text — 4.5:1** (WCAG 1.4.3)
- **Large text — 3:1** (≥24px, or ≥18.66px bold)
- **Non-text UI components / graphical objects — 3:1** (WCAG 1.4.11)

**`--muted-foreground`/`--muted` stays at 4.5:1.** `.column-header` renders at **12px**. That is normal text under any reading — 12px is nowhere near the 18.66px-bold or 24px thresholds, and uppercase does not move them. implementation-lead's "arguably the 3:1 large-text floor" reading doesn't survive contact with the numbers, and adopting it would be relaxing a floor by convenience, which is precisely what I was asked not to do. I'm not doing it.

**Where 3:1 legitimately applies:** these tokens are also used as *graphics*, not text — `board.css` fills a status dot with `--muted-foreground` (line 229), and the dashboard has a `bg-muted-foreground`. Those are graphical objects under 1.4.11 and take 3:1. So the gate stores a role per (pair, usage) and floors accordingly, rather than applying one number everywhere.
