### @ux-designer — 2026-09-08

**Derivation rule (ux-designer).** Scope correction first: the role family is `--chart-role-1..8` (8, not 7 — team-lead's shorthand undercounted) plus 3 neutral guards (`-guard-aux`, `-guard-unattributed`, `-other`). The guards stay fixed across all variants — they're near-achromatic (C≈0.01–0.02), deliberately built to blend with `--muted-foreground`, not carry a role hue; rotating them serves nothing and risks pulling them into a visible hue.

**Mechanism: one global hue rotation per Chart Color variant, applied to the fixed families, L/C untouched.** `Δh(variant) = variant["chart-1"].h − yellow.chart-1.h` (98.111°), read from already-vendored `variants.json` — no new hue authoring. Apply `Δh` to every hue in `--chart-flow-{opened,closed,wip}`, `--chart-counter-{input,cache-write,cache-read,output}`, `--chart-role-1..8`, both modes (ramp hue is mode-invariant, confirmed in current data), holding each token's own L and C exactly at today's ratified value. Same code shape as `derive_muted_foreground()` — computed in `gen_variants.py` at render time, not hand-baked into `variants.json`. Yellow is `Δh=0` by construction → byte-identical, trivially, no regression risk.

**Why this clears PT-92 structurally:** pairwise (≥60°) and role-collision (≥25°) are hue-*difference* tests; a uniform rotation preserves every pairwise delta exactly, so those two guards pass in all 24 variants by construction — no per-variant hand-tuning.

**What does NOT come free — mechanical re-check per variant×mode, not hand-verified:**
1. PT-83 contrast floors (≥2:1 vs both `--card`s) — sRGB luminance isn't hue-invariant at fixed OKLCH L/C; some rotations may fail.
2. In-gamut check — `-role-3`/`-role-4` sit at C=.24/.237, near sRGB's edge; `_oklch_to_linear_rgb` silently clamps out-of-gamut today. Clamping must be a hard fail, never silent, at any rotated hue.
3. CVD (deutan) resim — original hues were placed partly for CVD safety; that's not rotation-invariant (confusion depends on absolute hue region, not just relative spacing). Re-simulate per variant; rescue via the existing L/C-nudge-hue-fixed pattern (PT-92 precedent), never re-placing hue.
4. Cross-dimension: role hues now vary with Chart Color while `--primary` varies with Theme — the role-vs-`--primary` ΔE_OK check was a single fixed pair before, now needs Theme(7)×Chart(24)×mode(2) coverage. Flagging as a real test-cost/architecture point, not absorbing it silently — loop in architect on budget.

**Fallback for any variant×mode that fails #1–3 after rotation:** nudge that token's L/C only (hue fixed) to clear the floor, recorded per-variant like the existing `--chart-flow-closed` light-mode nudge — never re-derive hue placement.

**Next:** I'll land the spec section (`design-system-spec.md` → Chart-local ramp) once the guard sweep's shape is settled; implementation-lead adds `derive_chart_family_hue_rotation()` to `gen_variants.py`; qa extends the variant-sweep test to all 24×2 for guards 1–4 above.

### @ux-designer — 2026-09-08

**Role-family recommendation (ux-designer): `--chart-role-1..8` (+3 guards) stay fixed; only `--chart-flow-*` and `--chart-counter-*` rotate.**

**The one reason:** role hue is a durable *identity* mapping, not a stylistic preference — PT-79 cross-checked each role hue once against `--primary`/`--destructive` specifically so a role segment never gets mistaken for brand/danger, and PT-69 already ruled once that a token's meaning must not silently change depending on which control the user is looking at (the Paused-badge/`--chart-2` collision). Letting role hue drift with an unrelated Chart Color preference reintroduces that exact defect at a wider scale (8 identities × 24 variants) for a palette whose entire value is "this hue = this person, always" across both the cost view and the tokens view of the same block. Flow/counter carry no such cross-view identity contract — they're free to rotate.

**Cost corollary:** since role stays fixed, role-vs-`--primary` stays the single pair it is today — no 336-combination surface opens. This is a consequence of the identity argument, not an independent reason on its own.

**Acceptance risk, named not hidden:** if the token chart's *cost* (role-colored) view is what gets sampled during browser acceptance, it won't visibly change — only its *tokens* (counter-colored) view will. Flow chart changes either way. If Mosko wants literal "every listed token rotates" parity instead, that's a call for him/architect to make against this tradeoff, not one I'm making silently.

**CVD re-simulation: stays a design-time observation, not mechanical.** `palette_check.py`'s own header already rules this exact question for the role palette — "Deliberately NOT covered: CVD/deuteranopia simulation... reimplementing them here would be a second unverified implementation checking a second unverified implementation." Re-implementing Machado/Oliveira/Fairchild a third time (once in design-doc prose, once hypothetically here) repeats the anti-pattern already rejected. What **is** mechanical and free, provably (not just typically): a global hue rotation is a rigid rotation of the OKLab a/b plane, which is an isometry — it preserves every pairwise Euclidean distance and every angular separation *exactly*. So `palette_check.py`'s pairwise ΔE≥0.06 categorical guard and PT-92's pairwise/role-collision ΔH guards hold for all 24 rotated variants with no new test surface, by the same geometric fact that made yellow byte-identical. CVD safety of the *fixed* role/flow/counter values at their current placement was already checked once (design-doc); rotation of flow/counter changes their absolute hue, so their CVD read against each other and against the (now-fixed) role rainbow should get one fresh design-time pass per variant family shape, same posture as PT-85/92 — not a new automated matrix.

### @architect — 2026-09-08

**Gate 1 ruling (architect).** I ran the sweep before ruling, against the real data (`app.css` base values, `variants.json`'s 23 chart variants + `yellow`), through `gen_variants`' own helpers.

**Finding 1 — the gamut check the brief asks for cannot be written through the existing helper.** `_oklch_to_linear_rgb` clamps to `[0,1]` **on return** (`gen_variants.py:101`), so any gamut test built on it passes by construction. Control: `L .6 / C .40 / h 300`, wildly outside sRGB, comes back `min 0.000 max 1.000`. My first sweep reported "0 of 46 combinations fail" — a vacuous result I nearly ruled on. The gate needs an **unclamped** conversion (second implementation, deliberately: the thing being detected is the clamp).

**Finding 2 — with the unclamped check, `--chart-flow-wip` is already out of gamut today, at its PT-92 value, in both modes.** `oklch(0.62 0.15 200.8)` → red channel **−0.091**; the largest in-gamut chroma at that L and hue is **0.1054** (authored 0.15 → 29.7 % over). Dark: `0.13` vs max `0.1020`, 21.5 % over. The browser gamut-maps it, the generator clamps it — two different approximations of a colour that cannot render. **A hard-fail gate therefore fails the default variant on day one.** ux-designer's call, two options: re-author wip's chroma to the in-gamut maximum as a PT-92 amendment, or land the gate with wip explicitly grandfathered and recorded. **I recommend re-authoring** — a value that cannot render is not a ratified value, and every variant inherits its L and C.

**Finding 3 — rotation alone is not enough; gamut mapping is the common case, not a fallback.** Applying ux-designer's Δh to flow + counter across 23 variants × 2 modes × 7 tokens = 322 checks: **61 land outside sRGB** (19 %). Median chroma over the limit **22.6 %**, worst **53 %** (`chart-flow-opened` under zinc/indigo/violet: the light-mode red line becomes a much duller blue-violet). Sixty-one instances cannot be hand-recorded per variant — mapping must be mechanical in `gen_variants.py`: **hold L and h, binary-search the largest in-gamut C**. That is ux-designer's own L/C-nudge rule, promoted from fallback to step 2 of the derivation.

**Finding 4 — the isometry argument holds for rotation, not for what follows it.** A uniform hue rotation is a rigid rotation of the OKLab a/b plane, so pairwise hue deltas are exact — but chroma reduction moves points *radially*, and the categorical ΔE guard is a distance test. So it must be **measured after mapping**, never inferred. Measured: **0** pairs below ΔE 0.06, min pairwise ΔE **0.0705 before and after**, and **0** contrast failures against both `--card` surfaces in the two-model form, across all 322. The sweep passes — because it was run, not by construction.

**Rulings.**
1. **Seam.** `dimensions.chart.ownedVars` gains the four `--chart-counter-*` (flow's three are already there). Values are **derived in `gen_variants.py`** from `app.css`'s yellow base — one source of truth, same shape as `derive_muted_foreground` — never precomputed into `variants.json`, which stays vendored hue data.
2. **Derivation = rotate, then map.** `Δh(variant) = variant.chart-1.h − yellow.chart-1.h` (98.111, mode-invariant for all 23 — verified), applied to every flow and counter hue at fixed L and C; then gamut-map each result as above. `yellow` is `Δh = 0` and the mapping is a no-op for in-gamut tokens, so byte-identity is structural, not a coincidence — the existing three-copy generator guard covers it.
3. **The role family stays fixed.** ux-designer's identity argument (PT-69/PT-79) is ratified, and the mechanics agree: rotating roles would put **146 of 368** checks outside sRGB (40 %), at chroma up to 0.2403. **Acceptance consequence, stated because it is the one place the decision is visible:** the token chart changes in its *tokens* (counter-coloured) view, not its *cost* (role-coloured) view. The browser leg must sample the tokens view. Mosko can overrule with one word if he wants role identity to follow the setting; that costs the identity contract and a 40 % gamut-mapping rate, not just a bigger diff.
4. **`--chart-1..5` stay** — they are the Δh source, which is now their only job. The spec should say so, or someone will delete them as dead.
5. **No component change.** Both charts pass `var(--chart-flow-*)` / `var(--chart-counter-*)` straight through (`IssueFlowChart.svelte:62-64`, `TokenCostChart.svelte:79-82`); nothing resolves a colour in JS, so a data-attribute-scoped redefinition takes effect on reload.

**Guards (qa; red at gate 2).**
1. Unclamped gamut hard-fail across 24 × 2 × 7, **with the clamp-detection control** — assert the far-out probe fails the check, or the whole sweep is vacuous again.
2. Contrast floors (2:1 vs both `--card`s, two-model) across the same matrix.
3. Categorical ΔE ≥ 0.06 **after** mapping, per variant × mode, plus min-ΔE reported.
4. `yellow` byte-identical to today's `app.css` values in all three generated copies.
5. A guard that the gamut check does not import the clamping helper (the defect in finding 1, pinned).

**Writers.** ux-designer → the wip decision (finding 2) + spec section. implementation-lead → `gen_variants.py` (rotate + map), regenerate ×3, rebuild dist. qa → the five guards.
