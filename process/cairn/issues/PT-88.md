## Problem

The dashboard's token/cost chart (`TokenCostChart.svelte`, via `selectBars` in
`token-chart-logic.ts`) ranks issues by the currently displayed metric, descending, and cuts to
the top N (with "Show all" lifting the cut; `main` always appended last). That answers "which
issues cost the most" and nothing else. It cannot answer the question the user actually asked
for (2026-09-04): **is per-issue token usage creeping up over time?** Sequence is destroyed by
the ranking, so a steady upward drift across PT-80 → PT-87 looks identical to a flat series
with one outlier.

The payload already carries the order needed — `GET /api/tokens` sorts issues numerically
ascending by id (`_issue_sort_key` in `cairn.py`), and issue ids are allocated in creation
order, so id order is chronological order for a single project. The chart discards it.

## Ask

A toggle on the chart — alongside the existing tokens/cost metric toggle — between
**Ranked** (today's behaviour, default) and **Chronological** (issues left → right in id
order, every issue shown, no top-N cut; `main` still last or omitted per the architect's call).
Chronological mode keeps the same role stack and the same metric toggle; only selection and
order change. The caption already states what's shown (top-N-of-total / "all N"); it should
say "in order opened" in chronological mode.

Trend cue (a thin per-issue total line or a 3-issue rolling mean over the bars):
**deferred by the architect's gate-1 ruling below** — the ordered bars alone satisfy the ask, and
whether a cue helps is only knowable once the ordered axis exists. A follow-up issue, not this one.

## Acceptance criteria

Amended by the architect's gate-1 ruling below (2026-09-07); every figure there is measured.

1. `selectBars` gains a fifth optional `order: 'ranked' | 'chronological'` parameter (not a
   sibling). Chronological returns the `kind: 'issue'` bars **in payload order**, no limit, with
   `main` and milestone bars **omitted** — the x-axis means position in the issue sequence and
   neither bucket has one. Unit tests for ordering, no-limit, omission, metric orthogonality and
   the caption per mode; plus a Python test pinning the server contract the client now leans on
   (`/api/tokens` emits `kind: 'issue'` bars id-ascending), which nothing asserts today.
2. The chart has a visible Ranked / Chronological control matching the metric toggle's two-Button
   pattern; "Show all" is hidden in chronological mode (there is no cut to lift). State home is
   component `$state`, matching `mode`/`showAll` — measured: no URL param or localStorage in the
   component, and it is mounted once with no `{#key}`, so the choice survives every poll.
3. Browser-verified per `technique_browser_visibility_verification`: both modes render, order
   is visibly different, no bar is clipped or occluded in either theme.
4. Full suite green (Python + the dashboard's JS runner); `cairn check` ok; `dashboard/dist`
   rebuilt and committed alongside the source.

Natural home: milestone PT-0.12 (telemetry attribution), beside PT-85's dashboard change —
not attached yet; team-lead + user to place at the next planning touch.

### @architect — 2026-09-07

**Gate 1 ruling — PT-88.** Chronological mode is a mode of `selectBars`, not a sibling; `main` and milestone bars are omitted from it; the trend cue is deferred.

**(a) Seam.** `export type Order = 'ranked' | 'chronological';` and a fifth optional positional: `selectBars(issues, metric, limit = DEFAULT_BAR_LIMIT, showAll = false, order: Order = 'ranked')`. Every existing call site and test stays valid on the default. A sibling function was rejected: `selectBars` is the single place that decides which kinds appear and in what order, and a sibling would have to restate the milestone/`main` placement rules, which is how two orderings drift apart.

Chronological branch, exactly: `issues.filter((i) => i.kind === 'issue')` — **payload order preserved, no client-side re-sort, no limit, no `main`, no milestone bars.**

- **Payload order, not a re-sort (measured).** `cairn.py:3652–3662`'s `_issue_sort_key` returns `(0, int(id))` for issues, `(1, rank)` for milestones, `(2, 0)` for `main`/unparseable — so `/api/tokens` already emits issue bars id-ascending and the server owns what the sequence means. Parsing ids again in the client is a second implementation of that rule, free to disagree with it.
- **Consequence:** the client now depends on a server contract nothing tests. Measured: `tests/test_tokens_endpoint.py` contains no ordering assertion. qa adds one (test 6 below).
- **`main` omitted, not last.** In this mode the x-axis means position in the issue sequence. `main` has no id and no position; drawing it at the right-hand end reads as "the most recent issue" — the exact misreading the mode exists to remove. Milestone buckets go for the same reason: their `milestone_rank_map` order is a different sequence, not this one.

**(b) State home: component state (measured).** `TokenCostChart.svelte:26–29` holds `tokens`, `tokensError`, `mode`, `showAll` as `$state`; there is no URL param and no `localStorage` anywhere in the file. `App.svelte:529–531` mounts it once with no `{#key}`, and `subscribeTokens` replaces `tokens` in place, so component state already survives every poll. `let order = $state<Order>('ranked')` matches, and AC2's persistence follows from the same mechanism that holds `mode` today. Control markup mirrors the metric pair at L356–359 — two `Button`s, `Ranked` / `Chronological`. **"Show all" is hidden in chronological mode** (`realCount > DEFAULT_BAR_LIMIT && order === 'ranked'`): there is no cut to lift.

**(c) Caption, exact.** `formatCaption(payload, metric, shown, total, order: Order = 'ranked')`. The ranked branch is byte-identical to today. The chronological branch changes only the middle sentence, to `Showing all ${total} issues in the order opened, by ${basis}.`, then appends when the payload carries any non-issue bucket: `Milestone and main buckets are omitted here — neither has a place in the issue sequence.` Leading sentence, retention-window sentence and unpriced-models suffix unchanged. **`payload.milestone_caption` is not appended in chronological mode** — it explains milestone bars, and there are none.

**(d) Trend cue: deferred, with the reason.** Ordered bars are the minimum the ask names; a rolling-mean overlay adds an SVG path, its own tests and its own browser leg, and whether it is needed is only knowable once the ordered axis exists. Judgment call — the lead may file it as a follow-up after seeing the real chart, or overrule and fold it in here.

**(e) Red tests, each with its mutation.** In `scripts/cairn/tests/js/token-chart-logic.test.js`:
1. chronological order equals payload order for issue bars. Mutation: `.reverse()` the branch's result.
2. no limit: 20 issue bars, `limit = 12`, `showAll = false` → 20 bars. Mutation: apply `.slice(0, limit)` in the branch.
3. `main` and milestone bars absent in chronological, present in ranked — one call each on the same payload. Mutation: append `main` in the branch.
4. metric orthogonality: on a payload where the tokens and cost rankings differ, chronological output is **identical** for both metrics while ranked output differs. Mutation: sort the branch by `barValue`.
5. captions: the ranked strings unchanged, the chronological string exact, and `milestone_caption` absent from it. Mutation: append `milestone_caption` in the branch.
6. In `scripts/cairn/tests/test_tokens_endpoint.py`: `/api/tokens` emits `kind:'issue'` bars id-ascending. Mutation: reverse `issues_out` after the sort.

**(f) Writers.** qa: `scripts/cairn/tests/js/token-chart-logic.test.js`, `scripts/cairn/tests/test_tokens_endpoint.py`. implementation-lead: `token-chart-logic.ts`, `TokenCostChart.svelte`, and the rebuilt `dashboard/dist` committed with the source. Full runs via `run_tests.py --gate <g>`; JS via `node --test "scripts/cairn/tests/js/**/*.test.js"`; commit by pathspec.

**(g) Visual leg (the lead's, on the verdict).** Both themes × both modes. Per `technique_browser_visibility_verification`: `elementFromPoint` at each bar's centre plus a screenshot per mode — never property reads. Two things to establish beyond "it renders": the leftmost bar in chronological mode is the lowest-numbered issue, and no `main` bar is present in that mode.
