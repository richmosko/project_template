4. **~~Transient /api/board 503s~~ — MOVED to PT-34** (2026-08-22): second sighting during PT-32 Validate met the investigate-if-seen-again gate, and the architect ruled it out of this client-polish bundle — it's a server-side defect (suspected single-threaded fetch/SSE race).

### Item 1 — cancelled-count: take the AC's **second** option (total excludes non-column statuses)

**Ruling: `.swimlane-count` and `laneSummary.total` count only issues whose
status is in `BOARD_COLUMNS`.**

The AC offers "a cancelled chip" or "total excludes non-column statuses", and
they are not equivalent — **only the second fixes the expanded lane.** Measured
the current behaviour rather than reasoning from the bug report: `columnsFor`
builds columns for `BOARD_COLUMNS` only and filters `i.status === status`, so a
cancelled issue matches no column and **renders nowhere**, expanded or
collapsed. Meanwhile `countSpan.textContent = issues.length` at both call sites
(board.js:706, :783). So with Show-cancelled on, an *expanded* lane already
reads "5" above four visible cards — a mismatch that predates PT-29 and that a
cancelled chip would not touch, because chips render only when collapsed.

Option two makes the number mean **"what this lane shows"**, which is true in
both states, and chips then sum to the total for free rather than by a second
mechanism.

Implementation: in `laneSummary`, return `total` as the sum of `byStatus`
counts rather than `list.length`; then have both `countSpan` call sites use
`laneSummary(issues).total` instead of `issues.length`, so the header count and
the chips have **one** source rather than two that must agree.

> **Judgment call.** This changes the meaning of a pre-existing number: the
> lane count shrinks when Show-cancelled is on, where a user might expect "all
> issues in this milestone". Cost: the count no longer answers "how much is in
> this milestone", only "how much is on screen". Reversal: `total: list.length`.

**Recorded separately, deliberately not fixed here:** the root cause is that
"Show cancelled" admits issues the kanban renders in no column, so the checkbox
is inert in this view while being meaningful in list view. The honest fix is a
conditional sixth column — a layout change, not polish, and it would make
`BOARD_COLUMNS` conditional, which ripples into `laneSummary`'s purity. **Not
in this bundle.** Worth its own issue; this ruling makes the count honest, not
the checkbox useful.

### Item 2 — header wrap: `flex-wrap` alone is a **non-fix**

`.swimlane-header` is `display: flex` with no wrap, and `.swimlane-label` is
`flex: 1` — i.e. `flex: 1 1 0%`, a basis of zero and shrink enabled, so **the
label will always shrink before anything wraps.** Adding `flex-wrap: wrap` on
its own changes nothing: wrapping triggers when items can't fit at their
minimum, and this item's minimum is zero.

**Ruling — both parts, or it doesn't work:**

```css
.swimlane-header { flex-wrap: wrap; }
.swimlane-label  { flex: 1 1 auto; min-width: 8em; }
```

The `min-width` is the load-bearing declaration: it gives the label a floor to
refuse to shrink past, which is what forces the summary onto a second line
instead of crushing the milestone name. Flagging this because "add
`flex-wrap`" is the obvious reading of the AC and would ship a fix that
doesn't fix it.

### Item 3 — `aria-controls`: set it **only when expanded**, id supplied by the caller

The disclosed `.board` is **not in the DOM when collapsed** — `milestoneLaneEl`
appends it only in the expanded branch. So there is no id to point at half the
time, and `aria-controls` referencing a nonexistent id is worse than omitting
it: assistive tech either announces a broken relationship or ignores the
attribute, and neither is an improvement on today.

**Ruling: `aria-expanded` always (unchanged); `aria-controls` set only in the
expanded branch, alongside the `.board` element that carries the matching id.**
This is conformant — `aria-controls` is optional in the ARIA disclosure
pattern — and it preserves the roll-up's entire point, which is that collapsed
lanes render no card DOM. Do **not** "fix" this by always rendering `.board`
and hiding it with CSS; that would restore the wall of DOM PT-29 removed.

**Id scheme:** computed at the **call site**, not inside `milestoneLaneEl`, and
passed in — the same two places that already compute `stateKey` and push to
`state.renderedLaneKeys`, so it's the PT-30 capture-at-point-of-use pattern
rather than a third derivation:

```
"lane-" + laneIndex + "-" + stateKey.replace(/[^A-Za-z0-9_-]/g, "-")
```

The index makes it collision-proof **by construction** regardless of how the
sanitizer folds `::` and `.` together; the sanitized key makes it legible in
devtools. Neither alone is sufficient — sanitizing can collide, and a bare
index tells a debugger nothing.

### Item 5 — helpers.js self-tests: the fixture must live in a **foreign realm**

**The single most important instruction, and the one a natural implementation
gets wrong: the synthetic fixture must be evaluated inside a `vm` context, not
defined as a literal in the test file.** `rehome`/`wrapForRealm` exist entirely
to fix cross-realm identity. A fixture defined in the test file is already
same-realm, every assertion passes trivially, and the suite would test nothing
while looking thorough — which is worse than no test, because it reports
coverage that doesn't exist.

Fixture shape — a synthetic `CairnLogic`-alike, deliberately **independent of
what board-logic.js actually exports**, covering both historical escapes plus
the general contract:

| Export | Why it's there |
|---|---|
| a function returning a plain object | the base case |
| a **data array** export | PT-29's gap — an array wrapped as a callable read back as `[Function]` |
| a data export with a **null prototype** | PT-30's gap — a JSON round-trip silently restored `Object.prototype` |
| a function returning a nested mix: array of objects, object containing arrays, a null-proto object nested inside a normal one | the recursion, which is where a per-case fix would have missed |
| a function returning a primitive, `null`, and `undefined` | the non-object short-circuit |
| a non-object data export (string, number) | must pass through untouched |
| an object with keys named `constructor` and `__proto__` | the prototype-collision class this codebase keeps meeting |

Assertions: `assert.deepStrictEqual` against same-realm literals (this is what
actually catches a foreign-realm object); `Object.getPrototypeOf(x) === null`
where it was null and `=== Object.prototype` where it wasn't, **at every
nesting level**; and `Array.isArray(x) && x instanceof Array` for arrays —
`instanceof` is the half that fails for a foreign-realm array while
`Array.isArray` passes, so both are needed.

### Item 6 — PT-32 residue

**6a. `resetPullGesture` partial reset — complete it.** It currently resets
four of seven gesture vars; `pullAtScrollTop`, `pullLastDeltaY` and
`pullLastPhase` are left standing and are safe *only* because every read is
guarded by the `pullStartY === null` early return. Move them in. Verified the
ordering is already compatible: `onPullTouchEnd` reads `pullLastPhase` and
`pullLastDeltaY` into locals **before** calling reset, so completing the reset
changes no behaviour. Zero cost, and it removes a trap for whoever next adds a
read path.

**6b. Per-`touchmove` `getElementById` — hoist it.** `wirePullToRefresh`
already proves the element exists and bails if it doesn't; cache it in a
closure var there. `#pull-indicator` is static in `board.html` and never
re-created, so the cache cannot go stale.

**6c. Static `↻ Refreshing…` glyph — spin it.** One CSS keyframe on a class
applied only during the refreshing phase.

> **Judgment call.** Leaving it is defensible at 400ms. But `PULL_MIN_SPINNER_MS`
> is a *minimum*, not a duration — a slow or stalled network makes the hold
> arbitrarily long, and that is precisely when a motionless glyph reads as a
> frozen page rather than a working one. Cost: a keyframe and a class toggle.
> Reversal: delete both.

### Item 7 — un-migrated-root disambiguation: **declined, with the predicate recorded**

I proposed this one-liner at PT-28's review and explicitly left "is it worth
closing" open. Closing it now: **no.**

The trigger needs a multi-root board aggregating two roots that are *both*
un-migrated **and** whose milestone ids **and** names both collide, and it
self-heals the moment either root runs `cairn migrate prefix-ids`. Against that,
the fix adds a permanent conditional in display code that inspects an id's
*shape* to decide how to render it — a small instance of exactly the
derive-type-from-the-string fragility PT-28 spent a ruling avoiding. **Permanent
complexity to serve a transitional state is the wrong trade.**

The predicate stays on the record here so it's recoverable rather than
re-derived if anyone actually hits it — no bare id contains a hyphen:

```js
var qualify = multiRoot && String(p.milestone).indexOf("-") === -1;
```

Declining is itself the judgment call. Cost: a narrow transitional display
ambiguity. Reversal: the line above, at both display sites.

**Item 1 — correct, and at both call sites.** `laneSummary.total` is now the
sum of `byStatus`, and `milestoneLaneEl` computes **one** `summary` backing
both the header count and the collapsed chips, so "chips sum to total" holds by
construction rather than as a second invariant. `repoSectionEl`'s count went
the same way, which is right for the same reason — a repo section renders
through `columnsFor` too, so its count should also mean "what's on screen."

**Item 2 — both halves present.** `flex-wrap: wrap` on the header **and**
`flex: 1 1 auto; min-width: 8em` on the label. Team-lead asked me to confirm
the `auto` basis composes with the floor: **it does.** Flex line-breaking works
on each item's hypothetical main size clamped by its min/max, so the label's
`8em` floor is what makes the line genuinely unable to fit and forces the
summary to wrap, where a `0%` basis never refuses to shrink. The `grow: 1` half
is unchanged from `flex: 1`, so wide viewports behave exactly as before — no
regression at the sizes that were already fine.

**Item 3 — correct, including the part that's easy to get backwards.**
`aria-controls` is set only in the expanded branch, and the `.board` carrying
the matching id is created only there. The id index is read from
`state.renderedLaneKeys.length` **before** that lane's own push at both call
sites, so every lane in a render pass gets a distinct index and the scheme is
collision-proof regardless of how the sanitizer folds `::` and `.` together.

**Item 5 — done better than ruled.** The fixture is built by
`vm.runInNewContext` from a source string, as required. What I didn't ask for
and should have: **a fixture-sanity test asserting the loaded fixture's objects
are *not* same-realm as this file's literals.** My instruction was a rule a
future refactor could quietly violate; that test makes the violation fail
loudly instead. It converts "don't make the suite vacuous" from a comment into
a check. Assertions carry both `Array.isArray` and `instanceof Array`, and
prototype identity is asserted at every nesting level.

**Item 6 — all three.** Reset completed (and the ordering is still safe:
`onPullTouchEnd` reads `pullLastPhase`/`pullLastDeltaY` into locals before
calling it); lookup hoisted into `wirePullToRefresh`, which already proved the

**Item 8 — the comment now says the true thing**, including that no

### RECORDED — non-blocking

**6c partially undoes 6b's intent, in the same commit.** `updatePullIndicator`
now clears and rebuilds the glyph span plus a text node on **every**
`touchmove` — so item 6b removed one `getElementById` per move and item 6c
added two node creations per move. Net still cheap, and invisible at 60Hz, but
it's the same micro-cost in the same function that 6b existed to remove.

It also creates a latent hazard rather than a present one: `.spinning` is
applied to a **freshly created** element each call, so the rotation restarts
from 0° every time `updatePullIndicator` runs. Harmless today because the
`refreshing` phase calls it exactly twice (enter, then idle) — but any future
change that updates the indicator *during* refreshing (a progress count, an
elapsed timer) would make the spin visibly stutter, and the cause would be
non-obvious.

Both are closed by the same two lines: cache the last rendered label string and
skip the rebuild when it hasn't changed, updating only the transform. The label
is constant throughout `pulling`, constant throughout `armed`, and changes only
at phase boundaries, so the rebuild would run three or four times per gesture
instead of once per frame.

Not worth blocking the milestone's closing PR. Recording it with the mechanism
spelled out so that whoever adds an in-progress indicator later doesn't spend
the afternoon I would have.
