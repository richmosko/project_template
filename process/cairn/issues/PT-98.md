## Problem

Split from PT-96's gate-1 ruling (2026-09-06). PT-96 removes the `serve_forever` poll-interval
cost — serial 176.6 s → 109.6 s, parallel 26.4 s → 19.9 s. Two files stay above the 8 s ceiling
afterwards, and neither yields to fixture work. Consolidation was measured and is not a speed
lever. Data: `process/reviews/PT-96/timings.md`.

## Ask

1. `test_otel_receiver_self_stop.py` — 18.64 s, the suite's floor at any worker count. Twelve
   tests ≥ 0.5 s sum to 18.92 s of real daemon waiting. The grace period is already shrunk
   (`GRACE = 0.4`); what remains is deliberate slack — `sleep(GRACE + 1.0)`,
   `sleep(PERIODIC_REAP * 6)`. Cutting it trades wall time against flake risk on the daemon's
   own timing contract, so it needs a flake budget and repeat runs, not a quick edit.
2. `test_backfill_tokens.py` — 11.27 s, 40 tests each spawning `python3 backfill_tokens.py`
   (~0.28 s median). Calling `main()` in-process would delete the CLI boundary these tests
   exist to cover. If it converts, the CLI boundary needs its own smaller set of subprocess
   tests, not silent removal.
3. **Consolidation**, carried over from PT-96 ask 2 on hygiene grounds only: merge per-feature
   sliver files (2–5 tests on one subject) by subject; retire tests whose subjects were retired
   (PT-85's ramp guard is one). Measured cost of a file is ~0.03 s of interpreter start, and
   merging coarsens the parallel packing — do this for readability, and expect no speed-up.

## Acceptance criteria

1. Each converted test names the mutation that turns it red; timing-sensitive conversions are
   run 10× and the flake count recorded on this issue.
2. Any test deleted has a comment here naming the retired rule and why it is no longer true.
3. Before/after per file appended to `process/reviews/PT-96/timings.md`; `cairn check` ok.
