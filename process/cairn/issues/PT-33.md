## Problem

PT-32 ships pull-to-refresh touch-only (Mosko ruling 2026-08-22, on architect recommendation). The trackpad-overscroll path was deferred: `wheel` is the only event surfacing trackpad overscroll and has no release signal, so the pull/hold/release grammar needs delta accumulation + a momentum-decay heuristic to avoid firing on flick-to-top momentum — plus macOS draws its own rubber-band, giving two indicators with different physics.

## Scope

PT-32's state machine deliberately consumes pull *distance*, not touch events — this issue is a new **wheel adapter** feeding that machine, not a redesign. The momentum-decay heuristic must be explicitly designed (architect) and red-tested against the flick-to-top false-positive case before implementation.

## Acceptance criteria

- [x] Architect ruling on the momentum heuristic recorded here before code
- [ ] Flick-to-top momentum does NOT trigger a refetch (red-first test on the adapter's delta stream handling)
- [ ] Deliberate sustained trackpad pull at scroll-top does trigger, with the same indicator states as touch
- [ ] Touch path (PT-32) behavior unchanged

### 1. The core problem restated, because it decides everything else

`wheel` gives us a delta stream with **no start and no end marker**. Touch got
three things free that we now have to synthesize:

| Touch gives | Wheel equivalent |
|---|---|
| `touchstart` — "a gesture begins **now**" | *must be inferred* |
| finger position — distance is a subtraction | accumulate deltas |
| `touchend` — "decide **now**" | *must be inferred* |

The flick-to-top false positive is entirely a consequence of the **first** row,
not the third. Momentum deltas at scroll-top are indistinguishable from a pull
*if you look only at the deltas*. They are trivially distinguishable if you ask
the right question: **momentum is never preceded by stillness.** A flick's
momentum tail is the continuation of an event stream that has been running
without a break since the user's fingers were moving. A deliberate pull at a
board that is sitting still is preceded by a gap.

**So the ruling's central rule is a time gate, not a velocity model:**

> A wheel gesture **opens** only on an event preceded by ≥ `WHEEL_PULL_IDLE_MS`
> of wheel silence. That gap is the wheel's `touchstart`.

This is worth stating plainly because it is the opposite of what "momentum-decay
heuristic" suggests. I considered and rejected detecting the decay curve itself
(monotonically non-increasing magnitudes, velocity slope fits): momentum has
plateaus, humans decelerate smoothly, and every constant in such a model is
platform- and OS-version-specific. The quiet gate needs **one** constant, is a
subtraction of two timestamps, and is exactly testable. Decay detection would
have been the fragile thing the PT-32 deferral was worried about; this isn't it.

The same constant serves as the release signal (§ 3), so the gesture has one
notion of "boundary" in both directions.

### 2. Guards at gesture-open — and the rule that they are open-only

Five conditions are evaluated **only on an opening event** (one preceded by the
quiet gap). Any one of them refuses the gesture:

| Gate | Rejects | Why |
|---|---|---|
| `atScrollTop` false | mid-list scrolling | AC-equivalent of touch cancel condition 1 |
| normalized distance ≤ 0 | downward scroll, pure-horizontal | a pull is downward |
| distance > `WHEEL_PULL_BURST_MAX` | momentum burst **and mouse wheels** | § 2.1 |
| `horizontalDominant` (`abs(deltaX) > abs(deltaY)`) | a swipe across `.board`'s columns | board.css:273 is a real scroller |
| — | | |

**These gates are evaluated at open and never again.** A large delta *mid*-pull
is the user accelerating, which is legal; a naive implementation that applies
`WHEEL_PULL_BURST_MAX` to every event silently kills every pull that finishes
fast. That behaviour gets its own test (QA red C12) precisely because it is the
sort of thing a later "tidy up the duplication" refactor reintroduces.

#### 2.1 The burst gate is load-bearing twice, and the second job is the important one

`WHEEL_PULL_BURST_MAX = 40` (normalized px, inclusive — the boundary opens,
matching `PULL_THRESHOLD`'s inclusive convention).

- **Against momentum:** belt-and-braces. If the quiet gate is ever satisfied
  spuriously — a browser that batches wheel delivery, an OS that pauses before
  starting momentum — the first momentum event is still fast, and fast is
  refused. Two independent mechanisms, neither relying on the other.
- **Against mouse wheels:** this is the gate's real day job. A mouse wheel
  notch is a single discrete event of roughly 100px (Chrome, `deltaMode 0`) or
  3 lines = 48px (Firefox, `deltaMode 1`, normalized below). A human finger
  starting from rest cannot produce 40px in one frame — that's ~2400px/s at
  60Hz. **So the gate cleanly separates "trackpad" from "mouse wheel" without
  any device detection**, which we could not do reliably anyway.

> **Judgment call — mouse wheels deliberately never trigger this gesture.**
> Two notches up at the top of a board is something people do idly; firing a
> refetch on it is the "why did it just do that" failure the PT-32 deferral
> named. And a mouse user has ⌘R/F5 right there. Cost: desktop-mouse users get
> no gesture, which is a silent non-feature rather than a visible one.
> Reversal: raise `WHEEL_PULL_BURST_MAX`.

#### 2.2 `deltaMode` normalization — and why it needs no special case

`wheelPullDistance(ev)` returns pull-down pixels: `-deltaY` for
`deltaMode 0` (pixels), `-deltaY * WHEEL_LINE_HEIGHT` for `deltaMode 1`
(lines, `WHEEL_LINE_HEIGHT = 16`), and **`0` for anything else**.

`deltaMode 2` (pages) therefore blocks *through the existing "distance ≤ 0"
gate* rather than through a branch of its own — a page-granularity wheel cannot
express a sustained pull, and any pixel constant we invented for it would be a
fabrication. One rule, one test (QA red A3), no dead branch.

Without normalization, a `deltaMode 1` stream contributes 3px per notch and the
machine's 64px threshold is unreachable — the classic Firefox-on-Windows wheel
bug. We normalize so the discrimination happens on **magnitude**, one axis, not
on a device guess.

### 3. Firing semantics: quiescence is the release

The gesture fires when the wheel stream goes silent for `WHEEL_PULL_IDLE_MS`
and the accumulated distance is still at or past `PULL_THRESHOLD`.

`WHEEL_PULL_IDLE_MS = 120`. During an active trackpad scroll, events arrive
every ~16ms (~8ms on 120Hz displays); 120ms is seven-plus missed frames, which
is not a stutter, it is a stop. Longer and the refetch feels detached from the
gesture; shorter and a delivery hitch mid-pull reads as a release and fires
early.

**Why quiescence and not "fire the moment distance crosses the threshold":**
firing at the crossing destroys the no-latch property that PT-32 went out of
its way to build. Pull past 64, think better of it, push back up — on touch
that gesture does nothing, and the reducer below preserves exactly that on
wheel (§ 4, retreat). Firing at the crossing also makes momentum *more*
dangerous, not less, since a momentum tail blows through 64px in three frames.

> **Judgment call.** Cost: ~120ms between the user stopping and the spinner
> appearing, and a user who pulls past the threshold and then holds their
> fingers still on the pad gets a fire without ever "releasing". Reversal:
> fire inside the reducer at the crossing.

### 4. The pure surface — `board-logic.js`

The adapter is a reducer plus two helpers. All pure, all reachable from
`node:test`, which is what makes AC2 ("red-first test on the adapter's delta
stream handling") a real test rather than a browser ritual.

| Export | Contract |
|---|---|
| `WHEEL_PULL_IDLE_MS` = 120 | gesture boundary, both directions |
| `WHEEL_PULL_BURST_MAX` = 40 | max normalized magnitude of an **opening** event (inclusive) |
| `WHEEL_LINE_HEIGHT` = 16 | `deltaMode 1` → px |
| `wheelPullInitialState()` → fresh `{status:"idle", distance:0, lastTs:-Infinity}` | a **function**, not a shared frozen object |
| `wheelPullDistance({deltaY, deltaMode})` → number | § 2.2; positive = pull-down |
| `wheelPullReduce(prev, ev)` → next state | the machine; `ev` = `{deltaY, deltaX, deltaMode, timeStamp, atScrollTop, horizontalDominant}` |
| `wheelPullShouldFire(state, cancelled)` → bool | `pullPhase({atScrollTop: state.status === "pulling", deltaY: state.distance, cancelled}) === "armed"` |

`status` ∈ `"idle" | "pulling" | "blocked"`.

```
wheelPullReduce(prev, ev):
  dist    = wheelPullDistance(ev)
  opening = (ev.timeStamp - prev.lastTs) >= WHEEL_PULL_IDLE_MS
  if opening:
     if !ev.atScrollTop              -> blocked(ev.timeStamp)
     if dist <= 0                    -> blocked(ev.timeStamp)
     if dist >  WHEEL_PULL_BURST_MAX -> blocked(ev.timeStamp)
     if ev.horizontalDominant        -> blocked(ev.timeStamp)
     -> {status:"pulling", distance: dist, lastTs: ev.timeStamp}
  if prev.status !== "pulling"       -> blocked(ev.timeStamp)
  next = prev.distance + dist        // dist may be negative: retreat
  if next <= 0                       -> {status:"idle", distance:0, lastTs: ev.timeStamp}
  -> {status:"pulling", distance: next, lastTs: ev.timeStamp}
```

Four properties of that shape are deliberate and each has a red:

1. **`lastTs` advances on EVERY event, including blocked and downward ones.**
   This is the single most load-bearing line in the design. If the reducer only
   recorded timestamps for events it liked, a momentum tail's first at-top event
   would see a stale `lastTs`, read as "preceded by silence", and open a
   gesture — the exact false positive we are here to prevent. QA red C14 pins
   it; anyone optimizing the handler with an early return must route through
   the reducer anyway (§ 6, JC2).
2. **`blocked` needs no explicit clearing.** A new gesture opens whenever a
   quiet gap precedes an event, whatever the previous status was. So momentum
   rejection is automatically temporary (red D18) and there is no "unblock"
   path to forget.
3. **Retreat is decrement, not termination**, which is the wheel's version of
   PT-32's no-latch rule: pull 80 (armed), push back 30 → 50 → `pulling`,
   quiescence fires nothing. A retreat that would take distance to ≤ 0 **ends
   the gesture and returns to `idle`** so that board.js stops calling
   `preventDefault` and the page can scroll — otherwise a user who changes
   their mind finds the page frozen. One frame of scroll is consumed at that
   boundary; that is the whole cost, and it is the right trade.
4. **`blocked` and `idle` are behaviourally identical to the caller.** Both
   yield `shouldFire === false` and no `preventDefault`. The distinction exists
   so tests can assert *why* a stream was refused and so a console log is
   legible. Collapsing them would change no behaviour — stated here so nobody
   has to work that out from the code.

`wheelPullShouldFire` exists so the mapping of `status === "pulling"` onto
`pullPhase`'s `atScrollTop` parameter lives in **one** place. The mapping is
sound because the reducer refuses to open off scroll-top: `"pulling"` *is* the
wheel path's at-scroll-top predicate. Reusing `pullPhase` rather than
re-deriving the threshold is the entire point of PT-32's input-agnostic design,
and it means the arm threshold cannot drift between the two inputs.

### 5. Cancel conditions on the wheel path

board.js computes the union and hands it to the **existing** `shouldCancelPull`:

- `cardDragActive` — `state.cardDragActive`, unchanged.
- `drawerOpen` — `state.openIssueId !== null`. **This trap is worse on wheel
  than it was on touch.** `.drawer` is `position: fixed; overflow-y: auto`, so
  scrolling inside it never changes `window.scrollY`; its `wheel` events bubble
  to `document`, where they would look like a pull at scroll-top — and we would
  `preventDefault` them, jamming the drawer's own scrolling. Same flag, higher
  stakes.
- `refreshing` — `state.pullRefreshing`, unchanged. Also the re-entrancy guard.
- `multiTouch` — `false`. No wheel analogue.
- `horizontalDominant` — **`false` on the wheel path, deliberately.** The axis
  decision is made upstream, in the reducer's opening gate, because only the
  reducer knows where a wheel gesture begins; board.js has no `touchstart` to
  latch it at. Passing the flag twice would gate the same fact in two places,
  and removing either would look harmless. One gate, in the reducer, with a
  comment at the `false` saying so.

### 6. `board.js` wiring

```
onWheel(e):
  if (pullSource === "touch") return;                  // § 7
  wheelState = wheelPullReduce(wheelState, {
    deltaY: e.deltaY, deltaX: e.deltaX, deltaMode: e.deltaMode,
    timeStamp: e.timeStamp,                            // NOT Date.now() — one clock
    atScrollTop: window.scrollY === 0,
    horizontalDominant: Math.abs(e.deltaX) > Math.abs(e.deltaY),
  });
  cancelled = <the union in § 5>
  phase = wheelState.status === "pulling"
        ? pullPhase({atScrollTop: true, deltaY: wheelState.distance, cancelled})
        : "idle";
  if (phase === "pulling" || phase === "armed") { pullSource = "wheel"; e.preventDefault(); }
  updatePullIndicator(phase, wheelState.distance);
  clearTimeout(wheelIdleTimer);
  wheelIdleTimer = setTimeout(onWheelQuiesce, WHEEL_PULL_IDLE_MS);

onWheelQuiesce():
  if (wheelPullShouldFire(wheelState, <union>)) runPullRefresh(wheelState.distance);
  else updatePullIndicator("idle", 0);
  wheelState = {status:"idle", distance:0, lastTs: wheelState.lastTs};  // keep lastTs
  pullSource = null;
```

Reuses `updatePullIndicator`, `pullIndicatorOffset`'s resistance and cap, and
`runPullRefresh` verbatim — so AC3's "same indicator states as touch" is
satisfied structurally rather than by matching behaviour twice.

Registration: `document.addEventListener("wheel", onWheel, { passive: false })`,
added inside the existing `wirePullToRefresh`, after its `#pull-indicator` bail.
**No feature detection**, consistent with PT-32 § 5.

> **Judgment call (JC2) — `window.scrollY` is read on every wheel event**, i.e.
> ~60/s during any desktop scroll of the board, where the touch path read it
> once per gesture. Cost: one property read per event, which can flush pending
> layout. Reversal exists but is the subtle one, which is why I am not taking
> it pre-emptively: gate the read behind `e.deltaY < 0 || status === "pulling"`
> **while still routing every event through the reducer** so `lastTs`
> bookkeeping stays complete (§ 4.1). An early `return` that skips the reducer
> reopens the momentum hole.

> **Judgment call (JC3) — the listener is non-passive.** A non-passive `wheel`
> listener on `document` means the compositor waits on the main thread for
> every scroll of the board, and this board re-renders on SSE pushes. Cost:
> potential scroll jank on a busy main thread, on desktop, always — a cost paid
> by every user to serve a gesture only trackpad users get. Reversal:
> `{ passive: true }` and accept the native rubber-band alongside our indicator
> (§ 8). I am taking non-passive because `preventDefault` is what keeps there
> from being two indicators, and because the handler is a dozen arithmetic ops.
> **If the Chrome pass measures jank, take the reversal** — it degrades
> legibly.

### 7. Devices with both touch and trackpad — no double fire, by construction

A single arbiter variable, `pullSource ∈ null | "touch" | "wheel"`:

- Set to `"touch"` in `onPullTouchStart` when tracking begins; cleared in
  `resetPullGesture`.
- Set to `"wheel"` only once a wheel gesture actually reaches `pulling`/`armed`
  (not on every wheel event, or ordinary desktop scrolling would hold the
  token); cleared at quiescence.
- `onWheel` returns immediately if `pullSource === "touch"`.
- `onPullTouchStart` discards any in-flight wheel gesture first
  (`clearTimeout(wheelIdleTimer)`, reset `wheelState`, `updatePullIndicator("idle", 0)`)
  and takes the token.

> **Judgment call (JC7) — touch wins.** Touch has an explicit release signal;
> wheel only has an inference. When both are live, keep the input that knows
> when the user let go. Cost: a hypothetical device that emits both for one
> physical gesture drops the wheel half mid-flight. Reversal: flip the priority.

I am **not** relying on the claim that touch scrolling never synthesizes `wheel`
events — I have not measured that on every platform, and the arbiter makes the
answer irrelevant. `state.pullRefreshing` remains the second, independent
re-entrancy guard: even a double fire cannot stack two refetches.

**Degradation (AC-equivalent of PT-32 AC4):** on a device with no wheel input
the listener never fires. On a mouse-only desktop it fires constantly and does
nothing — every notch is refused by § 2.1, no indicator, no `preventDefault`,
existing scroll and SSE/poll behaviour untouched.

### 8. The native rubber-band, and the double-indicator question

macOS draws its own elastic bounce at scroll-top. The mechanism that suppresses
it is the **same `preventDefault` the touch path already uses** — a cancelable
`wheel` event whose default action is prevented produces no scroll and no
overscroll. Where that holds, there is exactly one indicator: ours.

Where it does not hold, the browser marks wheel events **non-cancelable during
an already-latched scroll** — which is *precisely the momentum case*, where our
reducer has already refused to open a gesture. So the degradation is aligned:
the native band appears exactly when we are not drawing anything.

**Do not change `overscroll-behavior-y: contain` to `none`.**

> **Judgment call (JC4).** `none` would kill the native bounce outright and
> guarantee a single indicator. Cost of not doing it: on a browser that ignores
> our `preventDefault` at scroll-top, the user sees the native band *and* our
> indicator moving at different rates. Cost of doing it: the bounce is a real
> "you have reached the end" affordance on every page scroll, removed globally
> to serve one gesture — and board.css:34's comment records that this exact
> property is load-bearing for a *different* reason (Android Chrome's native
> page-reloading pull-to-refresh), so retuning it casually is how that
> protection gets lost. Reversal: one word in board.css, after the Chrome pass
> reports what actually happens.

### 9. Red-first test surface — QA's lane

All of A–D are pure `node:test` against `board-logic.js`, no DOM. **Do not edit
`scripts/cairn/tests/js/pull-refresh.test.js`** — that suite passing byte-for-byte
unchanged *is* AC4. If a change there seems necessary, stop and escalate; it
means the adapter is not an adapter.

**A. `wheelPullDistance`**
1. `deltaMode 0`: `deltaY: -12` → `12`; `deltaY: 12` → `-12`
2. `deltaMode 1`: `deltaY: -3` → `3 * WHEEL_LINE_HEIGHT`
3. `deltaMode 2` (and any unknown mode) → `0`, and therefore never opens a gesture

**B. Opening gates — each independently**
4. first-ever event (`lastTs === -Infinity`), at top, small upward delta → `pulling`, `distance` = normalized magnitude
5. opening event with `atScrollTop: false` → `blocked`
6. opening event with distance ≤ 0 (downward) → `blocked`
7. opening event with distance > `WHEEL_PULL_BURST_MAX` → `blocked`
8. opening event with `horizontalDominant: true` → `blocked`
9. boundary: distance **exactly** `WHEEL_PULL_BURST_MAX` → opens (inclusive)

**C. Continuation**
10. gap < `WHEEL_PULL_IDLE_MS` while `prev.status !== "pulling"` → stays `blocked`, never opens
11. successive in-gesture events accumulate distance
12. **a delta > `WHEEL_PULL_BURST_MAX` mid-gesture does NOT block** — gates are open-only (§ 2)
13. retreat: a downward delta decrements; a decrement to ≤ 0 yields `idle` with `distance: 0`
14. **`lastTs` advances on every event, including blocked and downward ones** (§ 4.1)

**D. The momentum property — the reason this issue exists**
15. *flick-to-top fixture*: ~15 events 16ms apart, magnitudes decaying 140→4, `atScrollTop` false for the first few then true, first event ≤ 16ms after a prior scroll event. Assert `status` is never `"pulling"` at **any prefix**, `distance` stays 0, and `wheelPullShouldFire` is false at every prefix and after quiescence.
16. *deliberate-pull fixture*: first event ≥ `WHEEL_PULL_IDLE_MS` after `lastTs`, at top, ~20 events of ~6px at 16ms → `distance ≥ PULL_THRESHOLD`, `status "pulling"`, `wheelPullShouldFire` true.
17. *invariant, over generated sequences*: for **any** sequence with no gap ≥ `WHEEL_PULL_IDLE_MS` and a first-event magnitude > `WHEEL_PULL_BURST_MAX`, `wheelPullShouldFire` is false at every prefix. Randomize the decay curve — this is the property, 15 is one witness of it.
18. *recovery*: after 15's blocked stream, an event ≥ `WHEEL_PULL_IDLE_MS` later at top with a small delta opens a gesture. Momentum rejection must not be permanent.
19. `wheelPullShouldFire` false when `cancelled` is true, at distance ≫ threshold (delegation to `pullPhase`)
20. `wheelPullShouldFire` false for `blocked`/`idle` whatever the distance
21. constants export exactly 120 / 40 / 16
22. `wheelPullReduce` does not mutate `prev` (deep-equal before/after), and `wheelPullInitialState()` returns a fresh object on each call

**E. Browser pass** (Chrome, trackpad — none of this is reachable from node):
(a) hard flick up to the top → **no refetch, no toast, no indicator**; (b) slow
deliberate pull at top → `pulling` → `armed` → `refreshing` → toast; (c) whether
a native rubber-band appears alongside our indicator (§ 8 / OQ2); (d) normal
downward scroll at top → page scrolls, nothing appears, nothing sticks; (e)
horizontal two-finger swipe across a lane's columns → the lane scrolls; (f)
drawer open with board at scroll-top, scroll inside the drawer → the drawer
scrolls, no gesture, no jam; (g) mouse wheel, several notches up at the top →
nothing; (h) if a Firefox run is cheap, one `deltaMode 1` sanity check.

### 10. Open questions — measure these in the Chrome pass, don't guess

1. **`event.cancelable` during momentum.** If it is reliably `false` for
   momentum-phase wheel events at scroll-top, it is a *stronger* momentum
   discriminator than the quiet gate — the browser telling us directly that
   this stream is a continuation. Report what you observe. I am not building on
   it unmeasured, and the quiet gate stands either way.
2. **Does `preventDefault` actually suppress the macOS rubber-band here?**
   § 8 predicts yes; it is the pivot for JC4.
3. **Trackpad gain.** OS scroll acceleration means 64px of accumulated wheel
   delta is *less* physical finger travel than 64px of touch. If the gesture
   arms after an implausibly short flick of the fingers, the fix is a
   `WHEEL_PULL_GAIN` divisor inside `wheelPullDistance` — **not** a second
   threshold constant. Keep the machine's threshold single-sourced; put the
   calibration on the adapter.
4. **Safari mouse-wheel magnitudes.** Safari's legacy mouse-wheel deltas may be
   smaller than Chrome's ~100px notch and could fall under
   `WHEEL_PULL_BURST_MAX`. Accepted residual: the consequence is one spurious
   conditional GET and an "Already up to date" toast. Noting it rather than
   claiming coverage I have not measured.
