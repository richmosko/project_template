## Problem

The PT-78 §5 end-to-end check (2026-09-04, comment on PT-78) showed a real teammate's OTel export
resolving to `role: qa-telemetry-probe` — the teammate's *spawn name* — not `qa-engineer`, its
roster role. The transcript header carries both fields: `agentSetting: "qa-engineer"` (line 2 of
the probe's transcript) and `agentName: "qa-telemetry-probe"` (line 5). `_resolve_role_from_session`
in `scripts/cairn/otel_receiver.py` reads only `agentName`, and `backfill_tokens._normalize_role`
only strips a trailing `-<digits>` when the remainder is a roster name; any other spawn name passes
through verbatim (the deliberate no-alias-guessing rule).

Consequence: PT-79's per-role split buckets every distinctly named spawn as its own role. The
backfill has the same blind spot — its "unmapped agentName" paper trail (`impl`, `impl2`, …)
exists because the roster-anchored `agentSetting` field was never consulted.

## Proposed fix

Resolve role from `agentSetting` first (it is the `subagent_type` / roster name by construction),
falling back to the existing `agentName` path when `agentSetting` is absent or not a roster name.
Apply in both consumers — the live receiver's header scan and the backfill's record walk — so the
two sources bucket identically. Keep the `-<digits>` normalisation for the fallback. No new field
in the output schema; `role` values simply become roster names where the header allows it.

Open question for the architect: whether to re-run the backfill once (re-pricing nothing, but
re-bucketing historical `impl`/`impl2`-style lines under their roster roles) or leave history as-is.

## Acceptance criteria

1. Fixture-driven tests for the shared resolver: `agentSetting` present and non-empty → that value
   verbatim, roster member or not (a non-roster value stays on the unmapped paper trail);
   `agentSetting` absent → existing `agentName` behaviour unchanged (all three PT-78 cases still
   pass); `agentSetting` present with `agentName` absent → the `agentSetting` value, never
   `team-lead`. Every fixture carries `agentSetting` on a properly-typed `agent-setting` record,
   never on an `assistant` record, and at least one test runs over a transcript shaped like a
   real one (record types and field placement). One fixture places `agentName` before
   `agentSetting` in the file, so a scan that early-returns on `agentName` fails. The existing
   PT-78 golden fixtures (`qa-engineer-76`, `impl2`, `guide-pt18`) keep `agentSetting` absent —
   they are the fallback path's only coverage; new `agentSetting` coverage goes in new fixtures.
2. Same matrix for `backfill_tokens`, resolved once per file by a header scan that inspects
   records regardless of `type`; the `type == "assistant"` usage filter is unchanged.
3. Live check: repeat the PT-78 §5 procedure with a custom spawn name and confirm the flushed
   `source: "otel"` line carries the roster role.
4. TRACKER.md → "Role resolves per `session.id`…" paragraph updated, after the code lands, to name
   `agentSetting` as the primary field, the measured line-1/2 position and 50-record margin, and
   that a non-roster `agentSetting` is kept verbatim and still reported as unmapped. Full suite
   green; `cairn check` ok; data file untouched by tests.
5. Backfill re-run, once, after the resolver lands: the regenerated `transcript-backfill` lines
   replace the previous snapshot in `token-usage.jsonl` with every `source: "otel"` line
   byte-for-byte unchanged; the unmapped-names note lists only non-roster `agentSetting` values (on today's corpus: `claude-code-guide`, a built-in type with no roster file) and no spawn names; the regenerated
   data file is committed in the PR.

fixture shape. None is (a); none is (b); the resolver is not wrong.** Read against the working
tree, each test body and the golden fixture, not inferred from names.

The golden tree is four files that each mix **many roles and many issues across records** —
`session-a.jsonl`, `session-b.jsonl`, `session-c/subagents/agent-1.jsonl`, `session-e.jsonl`. Real

Per-file resolution collapses each file to one role, so every assertion that depended on two roles

the fixture shape has to change.

| # | Test | Cat. | Remedy — rule unchanged in every case |
|---|---|---|---|
| 1 | `bucketing_..._hand_counted_totals` | c | One role per file; **re-derive all 9 buckets by hand** from the new fixtures |
| 2 | `dedupe_by_request_id_across_files` | c | Pair must span two files resolving to the **same** role (see the order-dependence note) |
| 3 | `dedupe_fallback_to_uuid_...` | c | Same; today's sibling is a `subagents/` file, so give both files the same role or assert role-agnostically |
| 4 | `role_defaults_to_team_lead_when_agent_name_is_absent` | c | A file with **neither** `agentName` nor `agentSetting` anywhere |

**Nothing here is category (b).** Test 4 is the `agentName`-fallback guard, and it *can* pass

**New finding — cross-file duplicates now have an order-dependent role.** With per-file roles, a
dedupe key appearing in two files of *different* roles lands in whichever bucket the walk reaches
first; the losing record is dropped as a duplicate. Measured on the real corpus: **0 of 20,155**

(Control: the identical query against the golden fixture finds exactly the two known duplicates,
`req-lead-1` and `uuid-fallback-1`, so the zero is a real absence and not a broken query.) But
tests 2 and 3 deliberately construct that shape, and rebuilding them naively across two
differently-roled files would produce an **order-dependent, flaky** test. Constrain the fixture:
same role on both files, or assert the surviving contribution without naming a role.

**Does "all three PT-78 cases still pass" survive? Not as things stand — the AC is currently
unmet.** Tests 4, 5 and 6 *are* those three cases, and they are red. It survives only after the
split, and only if each case gets **its own single-role fixture asserting its own rule**. It must
not be "met" by re-pointing the assertions at whatever role the merged file now resolves to: that

**One more, and it cuts the other way: a green test in this file is not evidence either.**
`test_roster_suffixed_role_name_is_normalised` (`qa-engineer-76` → `qa-engineer`) currently
**passes** — but only because some file happens to resolve to `qa-engineer`, not because the
suffix-stripping rule was exercised. After the split, every test in this class needs re-checking
that it still tests its stated rule, not just that it is green.
