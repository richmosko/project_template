## Problem

The PT-78 §5 end-to-end check (2026-09-04, comment on PT-78) showed a real teammate's OTel export
resolving to `role: qa-telemetry-probe` — the teammate's *spawn name* — not `qa-engineer`, its
roster role. The transcript header carries both fields: `agentSetting: "qa-engineer"` (line 2 of
the probe's transcript) and `agentName: "qa-telemetry-probe"` (line 5). `_resolve_role_from_session`
in `scripts/cairn/otel_receiver.py` reads only `agentName`, and `backfill_tokens._normalize_role`
only strips a trailing `-<digits>` when the remainder is a roster name; any other spawn name passes
through verbatim (the deliberate no-alias-guessing rule).

Consequence: PT-79's per-role split buckets every distinctly named spawn as its own role. The
backfill has the same blind spot — its "unmapped agentName" paper trail (`impl`, `impl2`, …)
exists because the roster-anchored `agentSetting` field was never consulted.

## Proposed fix

Resolve role from `agentSetting` first (it is the `subagent_type` / roster name by construction),
falling back to the existing `agentName` path when `agentSetting` is absent or not a roster name.
Apply in both consumers — the live receiver's header scan and the backfill's record walk — so the
two sources bucket identically. Keep the `-<digits>` normalisation for the fallback. No new field
in the output schema; `role` values simply become roster names where the header allows it.

Open question for the architect: whether to re-run the backfill once (re-pricing nothing, but
re-bucketing historical `impl`/`impl2`-style lines under their roster roles) or leave history as-is.

## Acceptance criteria

1. Fixture-driven tests for the shared resolver: `agentSetting` present and non-empty → that value
   verbatim, roster member or not (a non-roster value stays on the unmapped paper trail);
   `agentSetting` absent → existing `agentName` behaviour unchanged (all three PT-78 cases still
   pass); `agentSetting` present with `agentName` absent → the `agentSetting` value, never
   `team-lead`. Every fixture carries `agentSetting` on a properly-typed `agent-setting` record,
   never on an `assistant` record, and at least one test runs over a transcript shaped like a
   real one (record types and field placement). One fixture places `agentName` before
   `agentSetting` in the file, so a scan that early-returns on `agentName` fails. The existing
   PT-78 golden fixtures (`qa-engineer-76`, `impl2`, `guide-pt18`) keep `agentSetting` absent —
   they are the fallback path's only coverage; new `agentSetting` coverage goes in new fixtures.
2. Same matrix for `backfill_tokens`, resolved once per file by a header scan that inspects
   records regardless of `type`; the `type == "assistant"` usage filter is unchanged.
3. Live check: repeat the PT-78 §5 procedure with a custom spawn name and confirm the flushed
   `source: "otel"` line carries the roster role.
4. TRACKER.md → "Role resolves per `session.id`…" paragraph updated, after the code lands, to name
   `agentSetting` as the primary field, the measured line-1/2 position and 50-record margin, and
   that a non-roster `agentSetting` is kept verbatim and still reported as unmapped. Full suite
   green; `cairn check` ok; data file untouched by tests.
5. Backfill re-run, once, after the resolver lands: the regenerated `transcript-backfill` lines
   replace the previous snapshot in `token-usage.jsonl` with every `source: "otel"` line
   byte-for-byte unchanged; the unmapped-names note is empty on today's corpus; the regenerated
   data file is committed in the PR.

### @architect — 2026-09-04

Gating ruling. **§1 is measured, not assumed** — 69 transcripts in this repo's own transcripts
directory, scanned to the existing 50-record limit. Everything below follows from it, and one
finding changes the precedence rule as stated in the issue.

**§1 What `agentSetting` actually looks like here.**
- Present in **54 of 69** transcripts. First occurrence is at **line 1 (52 files) or line 2 (2
  files)** — the existing `_ROLE_SCAN_LIMIT = 50` has a 25× margin. No change needed.
- **Zero files carry `agentName` without `agentSetting`.** The reverse exists: one file has
  `agentSetting` with **no** `agentName`, which today resolves to `team-lead` (absent name → lead).
  That is a **silently wrong attribution**, not merely a custom bucket — someone else's tokens are
  currently counted as the lead's. The fix corrects it; §7 requires a test for it.
- **15 files have neither.** All are lead-shaped (first record `type: last-prompt`, three keys).
  They resolve to `team-lead` today and under the fix alike — unchanged.
- **10 files where the two differ** — the entire mis-bucketing population: `impl`, `impl2`,
  `implementation-lead-2`, `qa-engineer-2`, `qa-engineer-76`, `qa-pt18`, `qa-telemetry-probe`,
  `session-end-probe`, `roundtrip-probe`, `guide-pt18`.
- Distinct `agentSetting` values observed: `implementation-lead`, `qa-engineer`, `architect`,
  `frontend-lead`, `ux-designer`, `seceng`, `devops-engineer`, and **`claude-code-guide`**.

**§2 Precedence — one deviation from the rule as written in the issue, because the data breaks
it.** The stated rule is "`agentSetting` in roster → wins; otherwise the `agentName` path". The
roster is `.claude/agents/*.md` stems, and **`claude-code-guide` is a built-in role with no roster
file** — so under a roster-gated rule it fails the test and falls through to `guide-pt18`, a spawn
nickname. The rule would discard a *correct, harness-supplied type* in favour of a *wrong* one.

Ruling: **take `agentSetting` verbatim whenever it is present and non-empty, roster member or
not** — and keep the unmapped paper trail when it isn't a roster name. PT-77 §4's no-alias-guessing
rule forbids *inventing* a mapping; it does not forbid reading the harness's own type field.
`agentSetting` is the `subagent_type` by construction, the most authoritative role signal
available. The paper trail keeps "this role isn't in your roster" visible rather than trading the
signal for silence.

Exact precedence:
1. `agentSetting` present and non-empty → **that value, verbatim**. No `-<digits>` strip — it is a
   type name, never a spawn name.
2. else `agentName` → existing `_normalize_role`, unchanged (strip `-<digits>` only when the
   remainder is a roster name).
3. else → `team-lead` (unchanged).
4. No transcript at all → `subagent-unattributed`, receiver only, unchanged — still a loud guard,
   still deliberately **not** cached.

**§3 Where the shared resolver lives.** `backfill_tokens.py` — it is already `_normalize_role`'s
home and the receiver already imports the module. **Do not create a third module.** Add a sibling
`resolve_role_from_header(agent_setting, agent_name, roster)` implementing §2, and leave
`_normalize_role` exactly as it is, called from step 2. That way AC 1's "all three PT-78 cases
still pass" holds *by construction* rather than by re-testing a rewritten function.

**§4 Both consumers read the same two fields in the same scan.** The receiver's
`_resolve_role_from_session` currently returns on the first `agentName` inside 50 records; it must
instead collect the first `agentSetting` **and** the first `agentName` across that same window and
then call the shared resolver. **Do not early-return on `agentName`** — the two usually share a
record, but a scan that stops at the first `agentName` would miss an `agentSetting` appearing
later in the window. The backfill's record walk takes the same two fields. Caching is unchanged:
a definitive resolution cached for the receiver's lifetime, a missing transcript never cached.

**§5 Backfill re-run mechanics (AC 5) — confirmed against the write path, not assumed.**
`merge_and_write` reads every existing line, drops **only** those whose `source` matches its own,
appends the fresh set, and writes via temp + `os.replace` under the shared lock. So a re-run
replaces the whole `transcript-backfill` snapshot and leaves every `source: "otel"` line
byte-for-byte; re-running is idempotent. Two constraints: run it **after** the resolver lands (run
earlier it simply reproduces today's bucketing), and commit the regenerated data file in the same
PR. Expected result on today's corpus: the unmapped-names note goes to **empty**, since every one
of the ten differing files carries an `agentSetting`.

**§6 What this does not fix — stated so nobody assumes otherwise.**
- **`claude -p` sessions: unverified.** I could not positively identify one in this corpus, so I am
  not ruling on it. Behaviour is unchanged (neither field → `team-lead`). If it needs measuring,
  the procedure is one `claude -p` run followed by inspecting the new transcript's first records —
  **but note the side effect**: a `-p` session registers with the receiver, and its exit drains the
  registry, which in the current post-merge transition window would stop the receiver. Deliberate
  or not at all.
- Lines whose transcripts have since been deleted cannot be re-bucketed; the re-run sees only what
  is still on disk.

**§7 Tests.** AC 1/2's matrix maps onto the shared resolver directly. Add one case the ACs don't
name and §1 proves is real: **`agentSetting` present, `agentName` absent → roster role, not
`team-lead`**. That is a live mis-attribution in the committed data today, and nothing else in the
matrix covers it. Fixture-driven; no real transcripts, no network.

**§8 TRACKER (AC 4).** Write it **after** the code, not alongside — the PT-86 loop produced two doc
sentences that were false in opposite directions by writing them ahead of the facts. Name
`agentSetting` as the primary field, state the measured line-1/2 position and the 50-record margin,
and say plainly that a non-roster `agentSetting` is kept verbatim and still reported as unmapped.

### @architect — 2026-09-04

**Addendum — §4 amended. implementation-lead's Q4 was right and my §4 is not implementable for the
backfill as written.** Measured across the same 69 transcripts, full-file scan this time (the §1
survey only read the first 50 records, which is why this didn't surface there).

**A. `agentSetting` lives on its own record type, which the backfill structurally cannot reach.**
- `agentSetting` appears **only** on records of `type: "agent-setting"` — 541 occurrences, **zero**
  on `assistant` records.
- `agentName` appears on `user`, `attachment`, `assistant` and `system` records — and **never** on
  an `agent-setting` record. The two fields never share a record.
- `backfill_tokens.py:230` returns early on `record.get("type") != "assistant"`, so its walk drops
  every `agent-setting` record before any field is read. "The backfill's record walk takes the same
  two fields" cannot be built.

**Amended rule:** the backfill resolves the role **once per file, in a header scan** — the same
shape the receiver already uses — not per record. Widen *that* scan to inspect records regardless
of `type`. **Keep the `type == "assistant"` filter exactly where it is for usage accumulation.**
Two different questions deserve two different filters; widening the usage filter would change what
gets counted, which is not this ticket.

**B. Both fields are session-constant, so per-session resolution is correct (Q3).** Measured:
`agentSetting` varies within a file in **0 of 69**; `agentName` varies within a file in **0 of 53**.
Consequences: the receiver's per-session cache stays valid as-is; the backfill's current per-record
`agentName` read is redundant rather than wrong, so resolving once per file is a safe
simplification and is anyway forced by A. **Do not add per-record re-resolution "just in case"** —
it is unobservable on every transcript we have and buys nothing but cost. If a future version ever
does vary it mid-session, the fix is a new measurement and a new ruling, not speculative code now.

**C. The fixture trap (Q2) — this is the one that would ship a broken resolver green.** Because
`agentSetting` only ever appears on an `agent-setting` record, **a fixture that places it on an
`assistant` record would pass a resolver that can never work on real data.** Every fixture must
carry a properly-typed `agent-setting` record, and at least one test must exercise the resolver
over a transcript whose record shapes match the real corpus — types and field placement both. This
is PT-57's and PT-77's lesson recurring: a hand-written fixture proves self-consistency, not
correctness, and five green branches on the wrong shape prove nothing. Before trusting the matrix,
diff a fixture's head against a real transcript's head.

**D. Scan window (Q1) — keep 50 records, unchanged.** First `agentSetting` occurrence is line 1 in
52 files and line 2 in 2 files: a 25× margin. Don't shrink it — the same window is the `agentName`
fallback's budget, and a second, smaller constant buys nothing measurable while adding something to
reason about. Collect both fields across the one window and **do not early-return on either**.
(Files commonly carry 10–11 `agent-setting` records, all with the same value, so first-sighting-wins
is safe.)
