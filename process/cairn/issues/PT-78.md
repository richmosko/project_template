## Problem

PT-77 backfills history once. Going forward, token usage should come from Claude Code's own
telemetry, not from scraping transcripts.

## What the export provides (verified against the Claude Code monitoring docs, 2026-09-03)

- Enabled per process by `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus `OTEL_METRICS_EXPORTER` and
  `OTEL_LOGS_EXPORTER` (`otlp`, `console`, `none`; metrics also `prometheus`). OTLP endpoint and
  protocol via the standard `OTEL_EXPORTER_OTLP_*` vars. There is no file exporter.
- Metric `claude_code.token.usage` with attributes `type` (`input`, `output`, `cacheRead`,
  `cacheCreation`), `model`, `query_source` (`main`, `subagent`, `auxiliary`), `agent.name`,
  and `session.id` (on by default).
- Metric `claude_code.cost.usage` in USD, same attributes. Event `claude_code.api_request` with
  `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `cost_usd`.
- **Cost is labelled "estimated" by the docs.** It is Claude Code's client-side computation, not
  Anthropic billing. Token counts are the API's own usage numbers and are exact. The ongoing
  process is authoritative for tokens and an estimate for dollars; the chart must say so.
- **There is no git-branch attribute.** Issue attribution needs `OTEL_RESOURCE_ATTRIBUTES`
  (e.g. `cairn.issue=PT-78`), which is read at process start and attaches to every datapoint.
  Teammates spawned during a feature inherit the environment, so `/start-feature` setting it
  before the team is spawned covers the lead and every teammate for that loop.

## Acceptance criteria

1. A local receiver owned by cairn accepts OTLP (protocol is the architect's call) and appends
   token and cost datapoints to the **same committed data file PT-77 writes**, keyed by issue
   (`cairn.issue` resource attribute, `main` when absent), role (`agent.name`, default
   `team-lead`), and model, split by `type`. It records counts and estimated cost only. No
   prompts, no message bodies, no tool output; `OTEL_LOG_RAW_API_BODIES` stays unset.
2. `.claude/settings.json` ships the `env` block that turns the export on and points it at the
   receiver. Documented, and off by default in the template until `/setup-tracker` opts in.
3. `/start-feature` sets `cairn.issue` for the loop; `/merge-pr` clears it. The mechanism must
   survive teammate spawn and be verified end to end with one real teammate, not assumed.
4. Losing the receiver loses nothing already written; datapoints while it is down are dropped
   and the file says so. No retry queue.
5. Tests: a synthetic OTLP payload through the receiver produces the expected file delta; a
   payload with no `cairn.issue` lands in `main`.
6. `process/TRACKER.md` documents the env vars, the receiver, the schema (shared with PT-77),
   and the "tokens exact, dollars estimated" caveat.

## Open for the architect

- Receiver placement: inside `cairn serve`, or a separate always-on process (the board server
  dies on `/exit`; teammates outlive it in tmux mode).
- Whether `cost.usage` is used at all, or dollars are recomputed from tokens with the same
  dated price table PT-79 needs, so backfill and live numbers agree.

## 0. Corrections to the issue's premises (measured, not assumed)

**C1 — `/start-feature` cannot set `cairn.issue` for the running session. AC3 as written is not implementable.**
`OTEL_RESOURCE_ATTRIBUTES` is read at process start. Measured: an `export FOO=...` in one tool call is gone by the next call (`'<empty>'`), so a skill cannot mutate its own session's environment; and `.claude/settings.json`'s `env` block *does* reach the process (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` reads `1` in-session) but only at start. A session that began during PT-77 keeps PT-77's value — or none — for every later loop. Teammates spawned mid-loop inherit the *lead's* start-time environment, not the value `/start-feature` wanted to set. **Attribution therefore moves to the receiver** (§4).

**C2 — the export carries the user's identity on every datapoint.**
Measured attribute keys on `claude_code.token.usage`: `user.email` (the literal address), `user.id`, `user.account_id`, `user.account_uuid`, `organization.id`, `session.id`, `terminal.type`, plus `type`, `model`, `query_source`, `effort`, and any `cairn.*` resource attributes. PT-77 recorded no session ids by explicit scope ruling; this payload is a large step backwards from that unless the receiver strips it. §6 makes stripping a hard requirement.

**C3 — `agent.name` was not emitted at all in either probe.**
It is absent from the entire captured payload. Both probes were single-process `claude -p` runs with no subagent, so this does **not** prove teammates never emit it — it proves the attribute is not always present, and that role attribution cannot be assumed to work. §5 rules a non-silent fallback and makes end-to-end verification a blocking AC.

## 1. Protocol and endpoint

**OTLP over `http/json`, POST to `http://127.0.0.1:<port>/v1/metrics`. Port default 4318, overridable in `process/cairn/config.yml`.**

Measured working end to end: `OTEL_METRICS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/json`, `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`. The sink received `Content-Type: application/json`, **no** content-encoding, and a body that `json.loads` parses directly — top-level `resourceMetrics`, then `scopeMetrics[].metrics[]`. — this is the whole reason to choose `http/json`: no protobuf dependency, no vendored decoder, stdlib only, which is cairn's standing constraint. The receiver must still handle `Content-Encoding: gzip` (one `gzip.decompress` branch) since it is protocol-legal even though this exporter did not use it.

**`OTEL_LOGS_EXPORTER` stays `none`.** We need counts, and counts are all in metrics; the logs stream is where prompt-adjacent content would ride. `OTEL_LOG_RAW_API_BODIES` stays unset, per the issue.

## 2. Receiver placement

**A separate long-lived process, `scripts/cairn/otel_receiver.py`. Not inside `cairn serve`.**

- The board dies on `/exit` and is usually not running; telemetry that records only while someone happens to have the board open produces a chart that silently under-reports. — the failure is invisible in the data, which is the kind this project keeps getting bitten by.
- **Started idempotently by the existing `SessionStart` hook**: if no process holds the pidfile and nothing is listening on the port, start it detached; otherwise do nothing. — a session starting is exactly the moment data begins to exist, so that trigger has no gap that matters; and it needs no per-machine install step.
- Single instance enforced by pidfile + a listen probe; a second start is a no-op, never an error.
- **Open item for the loop:** if the hook-start proves flaky in tmux mode, the fallback is a launchd user agent. Decide from observed behaviour, not in advance.

## 3. Counting: correct under either aggregation temporality

**Group incoming datapoints by (series key, `startTimeUnixNano`); take the *maximum* value within a group; sum across groups.** Series key = the full attribute set including `session.id`, held **in memory only**.

This is deliberately temporality-agnostic, and that is the point:
- Under **delta** temporality each export window is its own group, so the max-then-sum reduces to a plain sum — correct.
- Under **cumulative** temporality every point of a series shares one `startTimeUnixNano`, so the max is the final running total and it is counted once — correct.
- It is also idempotent against a retried or duplicated delivery, which neither plain summing nor last-value-wins is.

**Why not just read the field:** the payload declares `aggregationTemporality: 1` (DELTA in the OTLP enum), but the console exporter reprinted an identical `897` for four consecutive intervals, which is cumulative-shaped behaviour. I could not resolve the contradiction in three probes and stopped rather than guess. The rule above is correct either way, so the loop is not blocked on the answer. **Do not "simplify" it to a plain sum without first proving delta behaviourally** — that mistake inflates every number by the export count and looks entirely plausible in the output.

**Baseline on first sight.** A series first observed after a receiver restart contributes from that point on; whatever accrued while the receiver was down is dropped, never reconstructed. — PT-78 AC4 already accepts dropping data during downtime, and the alternative (persisting per-session baselines) would mean persisting `session.id`, which §6 forbids.

## 4. Issue attribution — receiver-side, branch first

**Resolve the issue at flush time, in this order:**

1. **The repo's current branch**, through PT-77's exact regex and `main` fallback — call the same function, do not reimplement it.
2. **`cairn.issue`** from the datapoint attributes, used **only when step 1 yields `main`**.
3. Otherwise `main`.

**Branch first, not `cairn.issue` first, is load-bearing.** Per C1 a long-running session carries a stale `cairn.issue`; if it took precedence it would silently override a correct branch signal — the exact misattribution the env-immutability creates. Ordering it second keeps the issue's stated mechanism useful for the cases where it *is* fresh (a `claude -p` run, a `/drive` invocation, any per-feature session) without letting a stale value ever win.

**Departure, labelled:** this overrides AC1's "keyed by issue (`cairn.issue` resource attribute)" and AC3's "`/start-feature` sets `cairn.issue` for the loop; `/merge-pr` clears it". **Cost:** attribution now follows the checkout, so a datapoint exported within one flush interval of a branch switch lands on the wrong issue, bounded by that interval; and two concurrent sessions on different branches in one checkout cannot be told apart (the workflow is one branch at a time, and PT-77 has the identical property). **Reversal:** one line — swap the precedence in step 1/2 — if a per-feature session model is ever adopted. **`/start-feature` and `/merge-pr` need no changes at all under this ruling**, which is also why AC3's "verified end to end with one real teammate" collapses into §5's verification.

## 5. Role attribution

**Explicit table, no guessing, and no silent folding into `team-lead`:**

| Condition | `role` |
|---|---|
| `agent.name` present | that value, through **PT-77's roster-anchored normalisation** (shared function, not a copy) |
| absent, `query_source == "main"` | `team-lead` |
| absent, `query_source` in `auxiliary` / `sdk` | `auxiliary` |
| absent, any other `query_source` (incl. `subagent`) | `subagent-unattributed` |

- Measured `query_source` values: `main`, `auxiliary`, `sdk`. The docs also list `subagent`; it did not appear in a no-subagent probe.
- `auxiliary` gets its own bucket rather than defaulting to `team-lead` because it is cheap-model overhead (observed: `claude-haiku-4-5`, `effort: high`), not lead work — attributing it to the lead inflates one role's share of the chart PT-79 exists to draw.
- **`subagent-unattributed` is a loud guard, not a bucket we expect to see.** If it ever appears in the data, role attribution is broken and the chart's per-role split is wrong; a silent `team-lead` default would hide exactly that.

**Blocking AC:** with the receiver running, spawn one real teammate, do work, and assert a line appears whose `role` is that teammate and whose `records`/counts are non-zero. Per C3, `agent.name` is *not* known to be emitted for teammates — if this test fails, the per-role split does not work and PT-79's stacked-by-role requirement cannot be met from OTel. Find that out in this loop, not in PT-79.

## 6. Privacy — what the receiver must drop

**Persist exactly:** `source: "otel"`, `generated`, `window_start`, `window_end`, `issue`, `role`, `model`, `input`, `cache_write`, `cache_read`, `output`, `records`. Nothing else. Same 12 keys PT-77 writes, minus the two optional `cache_write_5m`/`cache_write_1h` fields, which OTel does not split (omitting them is not a translation — PT-77's schema ruling already allows it).

**Never written to disk, under any flag:** `user.email`, `user.id`, `user.account_id`, `user.account_uuid`, `organization.id`, `terminal.type`, `effort`, and **`session.id`** — the last is held in memory as the series key of §3 and discarded at flush. — PT-77's scope ruling recorded no session ids and no identity at all; a live collector is not a licence to lower that bar, and `user.email` in a committed file is the specific thing that must never happen.

**Implement as an allow-list, not a deny-list.** A future Claude Code version adding a new identifying attribute must be dropped by default, not persisted until someone notices.

`type` maps to the counters: `input` → `input`, `cacheCreation` → `cache_write`, `cacheRead` → `cache_read`, `output` → `output`. Measured: those four values, exactly.

## 7. Writing to `token-usage.jsonl`

- **Append-only, `source: "otel"`, under PT-77's `process/cairn/metrics/.lock`.** The receiver never rewrites another source's lines; it takes the lock because PT-77's regenerating rewrite would otherwise lose an append landing between its read and its `os.replace`.
- **Flush triggers:** when the attributed issue changes, on clean shutdown, and otherwise at most every 30 minutes. — a line per export interval would add hundreds of lines a day to a committed file; these triggers give a handful per feature loop while keeping the issue boundary sharp.
- **`window_start`/`window_end`** are the UTC dates of the earliest and latest datapoint in that flush, contribution-wide, exactly as amended for PT-77. `generated` is the flush moment.
- **Compaction:** the receiver may rewrite **its own** `source: "otel"` lines to coalesce same-key lines by summing — permitted by PT-77 §2's regenerating-source rule, and safe because these lines are additive. It must still take the lock, and must not touch `transcript-backfill` lines.
- **Serialisation:** `json.dumps` defaults, one object per line — the canonical form pinned in PT-77's review addendum, so a later backfill regeneration produces no diff churn.

## 8. The non-overlap invariant

**No `otel` line may carry data timestamped before the `generated` of the latest `transcript-backfill` line in the file.** There is no cross-source dedupe; overlap is a silent double count. The receiver asserts this at flush and refuses to write a line that violates it, naming both timestamps. — the backfill *scanned* up to its `generated`, which is why that is the sound boundary rather than its `window_end`.

## 9. Dollars

**Do not persist `claude_code.cost.usage`. Recompute dollars from tokens, for both sources, using PT-79's dated price table.**

- Measured: `cost.usage` exists and carries plausible USD values (`0.000942`, `0.203258`) with the same attribute set.
- But PT-77's backfilled history has **no** cost signal at all, so it must be computed from tokens regardless. Persisting Anthropic's estimate for live data and computing it for history means one chart mixing two methods, with a step discontinuity at the boundary that looks like a real cost change and is not.
- **Cost of this call:** we lose Claude Code's own estimate, which may model pricing details our table does not. **Reversal:** add an optional `cost_usd` field later and let PT-79 prefer it — the schema tolerates optional fields by construction.
- The chart labels dollars "estimated" and tokens not, per PT-79 AC3.

`.claude/settings.json` ships the `env` block **commented in the docs and absent from the file** until `/setup-tracker` opts in, per AC2:

1. A synthetic OTLP-JSON payload (capture a real one to `/tmp` and hand-edit — do **not** check a real one in; it contains the user's email) produces the expected file delta.

## Addendum — C3 resolved far enough to unblock PT-79 (2026-09-03, second probe)

**Teammates are separate OS processes, each launched with its own agent name in argv.** Observed on the three live teammates in this session:

```
.../versions/2.1.259 --agent-id architect@session-9464c7f5 --agent-name architect \
  --team-name session-9464c7f5 --agent-color blue --parent-session-id <uuid> \
  --agent-type architect --permission-mode auto --model opus
```

…and the same shape for `qa-engineer` (`--model sonnet`) and `implementation-lead` (`--model sonnet`). Consequences for the receiver:

- Each teammate runs its **own** Claude Code process with its **own** OTel SDK, its **own** `session.id`, and its own metric stream. §3's in-memory series keying already handles that — nothing changes.
- The agent name reaches the process by **argv, not environment**. There is no `CLAUDE_CODE_AGENT_NAME` env var: the env keys a teammate's shell inherits are `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_BRIDGE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDECODE`, `AI_AGENT`, plus whatever `settings.json` sets. So a receiver cannot read the role from the environment — the OTel attribute is the only channel.
- This also **confirms C1's inheritance claim from the other direction**: teammates are spawned from the lead and inherit its environment, so telemetry env set in `settings.json` reaches every teammate, while anything the lead "sets" after its own start reaches none of them.

**`agent.name` is emitted conditionally, and that explains its absence in the first probes.** In the 2.1.259 binary the metric attribute builder reads:

```js
{...r && {"agent.name": r}, ...o && {"skill.name": o}, ...f && {"plugin.name": f}, ...}
```

with `r = attributionAgent`. The key is **omitted entirely** when there is no attribution agent — which is exactly what a plain `claude -p` run is. So the earlier absence is explained and is **not** evidence that teammates omit it. (Method note: the first `grep` over the 200 MB binary reported `0` because it bailed on binary content; `grep -a` reports 2 occurrences of `agent.name`, the same count as `claude_code.token.usage`. An absence from an aborted search is not an absence.)

**Still unproven, so §5's guard and its blocking AC stand:** that a teammate's *own* turns populate `attributionAgent` with its `--agent-name`. The surrounding code is a general attribution block covering `agent` / `skill` / `plugin` / `mcp_server` / `mcp_tool`, so `attributionAgent` may track the agent invoked *for a request* rather than the identity of the emitting process. The one-real-teammate end-to-end check is what settles it.

**Revised risk to PT-79: low, was high.** The per-role split is very likely available from live data — the name exists per process and the attribute exists in the exporter. `subagent-unattributed` remains the guard so that a failure is loud rather than silently folded into `team-lead`.

**Addendum — the concrete implementation surface.** The ruling above is the *what and why*; this is the exact set of names, flags and commands implementation-lead and qa build against, so neither has to infer them. Nothing here changes a decision above.

### Files

| Path | Role |
|---|---|
| `scripts/cairn/otel_receiver.py` | the receiver — CLI, HTTP shell, folding, flushing |
| `scripts/cairn/tests/test_otel_receiver.py` | tests |
| `scripts/cairn/tests/fixtures/otlp/*.json` | hand-edited OTLP payloads (see §11 test 1 — never a real capture) |
| `process/cairn/metrics/token-usage.jsonl` | output, shared with PT-77 |
| `process/cairn/metrics/.lock` | PT-77's lock, taken by both writers |
| `process/cairn/metrics/.receiver.pid` | pidfile |

### Module seams — tests must not need a socket

Split so the whole data path is testable as pure functions; the HTTP server is a thin shell over them:

```python
parse_export(payload: dict) -> List[Datapoint]   # OTLP-JSON -> flat records; applies the §6 allow-list
fold(datapoints, state) -> state                 # the §3 (series, startTimeUnixNano) grouping
flush(state, out_path, issue, generated) -> List[dict]   # emits the lines, takes the lock
```

`parse_export` and `fold` are where every counting and privacy assertion belongs. Only the `--once` test touches a port. — a receiver whose logic is only reachable through a bound socket makes its own tests flaky and slow, and this project has enough socket-bound tests already.

### CLI

```
python3 scripts/cairn/otel_receiver.py [--port N] [--out-file PATH] [--flush-interval SECONDS]
                                       [--pidfile PATH] [--ingest PATH|-] [--once]
                                       [--ensure-running] [--flush-now] [--stop]
```

- `--port N` — default from `config.yml` key `otel_port`, falling back to `4318`.
- `--out-file PATH` — default `process/cairn/metrics/token-usage.jsonl`. **Resolve it from the repo root, never from `Path.cwd()`** — PT-77's blocking defect and PT-80 exist because of exactly that; `cairn.load_config` now raises rather than defaulting, so use it.
- `--flush-interval SECONDS` — default 1800 (§7's 30 minutes).
- `--ingest PATH|-` — read one OTLP-JSON payload from a file or stdin, fold it, flush, exit. **Binds no port.** The main test seam.
- `--once` — bind, accept exactly one request, flush, exit. The single integration test.
- `--ensure-running` — start detached if the pidfile is stale or absent and nothing is listening; exit 0 either way, never an error. What the hook calls.
- `--flush-now` — signal the running receiver (SIGUSR1) to flush immediately and return. Needed by the §5 check, which must not wait 30 minutes.
- `--stop` — signal it to flush and exit cleanly.

### SessionStart hook (one new entry in the existing `hooks.SessionStart[0].hooks` array)

```
[ -f scripts/cairn/otel_receiver.py ] || exit 0; python3 scripts/cairn/otel_receiver.py --ensure-running >/dev/null 2>&1; exit 0
```

All the pidfile and listen-probe logic lives in `--ensure-running`, not in shell. — the existing hooks show how quickly shell-side conditionals become unreadable, and this one must never fail a session start: it ends in `exit 0` unconditionally.

### The 12-key allow-list, verbatim

Each emitted line has exactly these keys, in this order:

```
source, generated, window_start, window_end, issue, role, model, input, cache_write, cache_read, output, records
```

`source` is always `"otel"`. Implement as a literal tuple the writer iterates — **not** as "the incoming dict minus a deny-list". Anything not on this list is dropped, including every attribute in §C2 and any attribute a future Claude Code version adds.

### Counting, restated as the implementable rule

```
key   = (all persisted-and-dropped attributes together, i.e. the full attribute set incl. session.id)
group = (key, startTimeUnixNano)
value(group) = max(observed values in that group)
bucket total = sum over all groups with that (issue, role, model, type)
```

`session.id` participates in the key and is discarded at flush; it is never written. `type` maps `input→input`, `cacheCreation→cache_write`, `cacheRead→cache_read`, `output→output`.

### §5's one-real-teammate check — exact procedure and pass predicate

**Precondition that will otherwise waste the run:** per C1 the env block only takes effect for a session started *after* it is written. Running this in the current session produces zero datapoints and looks like a failure of `agent.name` when it is really a failure to enable telemetry.

```bash
# 1. env block present in .claude/settings.json, then START A FRESH SESSION.
# 2. receiver up, writing somewhere scratch:
python3 scripts/cairn/otel_receiver.py --ensure-running --out-file /tmp/pt78-check.jsonl
# 3. in the fresh session: spawn ONE real teammate (e.g. qa-engineer) and have it
#    complete one turn that makes at least one model call.
# 4. force a flush rather than waiting out --flush-interval:
python3 scripts/cairn/otel_receiver.py --flush-now
# 5. pass predicate:
python3 -c "
import json,sys
L=[json.loads(l) for l in open('/tmp/pt78-check.jsonl')]
roles={x['role'] for x in L if x['source']=='otel'}
print('roles seen:', sorted(roles))
ok = bool(roles - {'team-lead','auxiliary'}) and 'subagent-unattributed' not in roles
print('PASS' if ok else 'FAIL'); sys.exit(0 if ok else 1)"
```

**PASS** = at least one role that is neither `team-lead` nor `auxiliary`, and no `subagent-unattributed`. **FAIL** in either direction is a real finding, not a flaky test: `subagent-unattributed` means `agent.name` is absent for teammate turns, and only `team-lead`/`auxiliary` means teammate traffic is being misattributed. Either outcome must be reported before PT-79 is scoped — it decides whether the per-role split exists for live data at all.
