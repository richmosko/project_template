## Problem

PT-77 backfills history once. Going forward, token usage should come from Claude Code's own
telemetry, not from scraping transcripts.

## What the export provides (verified against the Claude Code monitoring docs, 2026-09-03)

- Enabled per process by `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus `OTEL_METRICS_EXPORTER` and
  `OTEL_LOGS_EXPORTER` (`otlp`, `console`, `none`; metrics also `prometheus`). OTLP endpoint and
  protocol via the standard `OTEL_EXPORTER_OTLP_*` vars. There is no file exporter.
- Metric `claude_code.token.usage` with attributes `type` (`input`, `output`, `cacheRead`,
  `cacheCreation`), `model`, `query_source` (`main`, `subagent`, `auxiliary`), `agent.name`,
  and `session.id` (on by default).
- Metric `claude_code.cost.usage` in USD, same attributes. Event `claude_code.api_request` with
  `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `cost_usd`.
- **Cost is labelled "estimated" by the docs.** It is Claude Code's client-side computation, not
  Anthropic billing. Token counts are the API's own usage numbers and are exact. The ongoing
  process is authoritative for tokens and an estimate for dollars; the chart must say so.
- **There is no git-branch attribute.** Issue attribution needs `OTEL_RESOURCE_ATTRIBUTES`
  (e.g. `cairn.issue=PT-78`), which is read at process start and attaches to every datapoint.
  Teammates spawned during a feature inherit the environment, so `/start-feature` setting it
  before the team is spawned covers the lead and every teammate for that loop.

## Acceptance criteria

1. A local receiver owned by cairn accepts OTLP (protocol is the architect's call) and appends
   token and cost datapoints to the **same committed data file PT-77 writes**, keyed by issue
   (`cairn.issue` resource attribute, `main` when absent), role (`agent.name`, default
   `team-lead`), and model, split by `type`. It records counts and estimated cost only. No
   prompts, no message bodies, no tool output; `OTEL_LOG_RAW_API_BODIES` stays unset.
2. `.claude/settings.json` ships the `env` block that turns the export on and points it at the
   receiver. Documented, and off by default in the template until `/setup-tracker` opts in.
3. `/start-feature` sets `cairn.issue` for the loop; `/merge-pr` clears it. The mechanism must
   survive teammate spawn and be verified end to end with one real teammate, not assumed.
4. Losing the receiver loses nothing already written; datapoints while it is down are dropped
   and the file says so. No retry queue.
5. Tests: a synthetic OTLP payload through the receiver produces the expected file delta; a
   payload with no `cairn.issue` lands in `main`.
6. `process/TRACKER.md` documents the env vars, the receiver, the schema (shared with PT-77),
   and the "tokens exact, dollars estimated" caveat.

## Open for the architect

- Receiver placement: inside `cairn serve`, or a separate always-on process (the board server
  dies on `/exit`; teammates outlive it in tmux mode).
- Whether `cost.usage` is used at all, or dollars are recomputed from tokens with the same
  dated price table PT-79 needs, so backfill and live numbers agree.
