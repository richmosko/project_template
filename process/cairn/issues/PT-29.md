## Problem

Three board-UX gaps, all in the swimlane rendering (`scripts/cairn/board/`), requested by Mosko 2026-08-22:

1. **No default roll-up.** Every milestone lane loads expanded; a populated board opens as a wall of issue cards. The lanes should load **collapsed** (issues hidden), letting the user disclose the milestones they care about. Collapse state stays view-local/in-memory per the PT-16 contract — only the *default* flips.
2. **The disclosure toggle reads as a dot.** PT-16's toggle already uses `▾`/`▸` glyphs (`board.js` ~L444/487), but `.swimlane-toggle` has `font: inherit` at lane-header size — the glyph renders too small to read as a triangle. Replace with **filled, legibly-sized triangles: down `▼` = shown, right `▶` = hidden** (size via CSS, not just a bigger glyph in inherited font).
3. **No containment boundary.** Majors/milestones are flat header rows above loose issue-card grids. Render each shown major/milestone as a **larger containing card** — a bordered/surfaced card the issue cards sit *inside* — so the hierarchy is visible as nesting, not just headings. Applies to both grouping modes (milestone lanes, and repo→milestone nesting from PT-3 multi-root).

## Acceptance criteria

- [ ] On load, all milestone lanes are collapsed by default (issues hidden); expanding is one click and stays view-local (no disk write, no network call on toggle — PT-16 contract preserved). Absence from the state map means **collapsed**, so a lane key first appearing after a refresh or filter change is collapsed too, not expanded
- [ ] Disclosure token is a filled down triangle (▼) when expanded and filled right triangle (▶) when collapsed, sized to be legible at a glance, in a **fixed-size box** so the label does not shift on toggle; aria-labels preserved and `aria-expanded` added
- [ ] Each shown major/milestone renders as a containing card with the issue cards visually embedded inside its boundary, in both single-root and multi-root (repo-grouped) modes — achieved by **promoting the existing group elements, with no new wrapper elements**, and with each nesting level on a distinguishable surface
- [ ] Repo-scoped keys preserved (bare-id-across-roots defect class — zero regressions), including a test that two same-id milestones under different repos toggle independently; drag-and-drop and the drawer still work inside the new containment structure
- [ ] Pure-logic changes covered by the board-logic.js node:test suite (red-first), with `BOARD_COLUMNS` relocated from board.js into board-logic.js as the single copy; DOM/visual behavior verified via team-lead Chrome pass against a QA-authored checklist

## Notes

- QA has no browser tools — checklist + suite is QA's lane; the Chrome pass is team-lead's (established SC2/PT-16 split).
- Collapse default interacts with the drawer's deep-link (if any) — expanding a lane to show a targeted issue is in scope if such a path exists; verify.

### 1. Containment-card DOM/CSS structure

**No new wrapper elements.** Containment is a CSS promotion of the two
existing group elements — `.swimlane` and `.repo-group` become the cards.
Adding a wrapper div would re-parent the drop targets and the drawer's click
surface for zero visual gain, and PT-3's "single-root DOM is byte-identical"
criterion survives only if the single-root branch keeps its current shape.

DOM stays exactly as today:

```
main
  .swimlane[.is-collapsed]          <- the containing card (single-root)
    .swimlane-header                <- the card's title bar; ALWAYS present
    .board                          <- the card body; present only when expanded
      .column x5
        .card x n
```

```
main
  .repo-group[.is-collapsed]        <- outer containing card (multi-root)
    .repo-group-header
    .swimlane x n                   <- inner containing cards, nested
      ...as above
```

**Surface alternation.** Three nested levels need three distinguishable
surfaces, and `.column` is already white-on-grey. Alternate by depth:

| Context | Element | Background |
|---|---|---|
| single-root | `main > .swimlane` | `--panel` (white card, border + radius + shadow) |
| single-root | `main > .swimlane .column` | `--bg` (grey well), `border-color: transparent` |
| multi-root | `.repo-group` | `--panel` (white outer card) |
| multi-root | `.repo-group .swimlane` | `--bg` (grey inset card, 1px border) |
| multi-root | `.repo-group .column` | `--panel` (unchanged — the default already alternates correctly) |

The standalone `.board` (Swimlanes checkbox **off**) is untouched: no
containment card exists in that mode, so `.column`'s base style must not be
edited globally — every column restyle is a descendant selector under a
containing card. Add `--shadow: 0 1px 2px rgba(9,30,66,0.12)` next to the
existing custom properties rather than inlining the value twice.

`.repo-group`'s current `border-left: 3px solid var(--border)` +
`padding-left` was a substitute for a card; once it is a card, keep the left
accent (recolour to `--accent`) as the repo marker and fold the padding into
the card's own padding.

**Where the collapse boundary sits:** unchanged from today — the header is
always in the DOM, only `.board` is conditionally appended. Add an
`is-collapsed` class on the group element so CSS can tighten the collapsed
card's padding; do not use it to drive any JS branch.

**What a collapsed card shows.** Today: the total count only. Ruling: a
collapsed lane must carry enough to decide whether to open it, so render a
compact status breakdown — one chip per **non-empty** status in board-column
order (`backlog, todo, in-progress, in-review, done`), each `label · n`, with
the existing `.swimlane-count` total retained. Shown **only when collapsed**;
when expanded the columns already carry those numbers and a second copy is
noise.

> **Judgment call.** The issue text asks only that lanes load collapsed; a
> status breakdown is additive. Cost: one new pure function + tests, one
> extra span per collapsed lane. Reversal: delete the summary element and
> leave `.swimlane-count`.

### 2. Default-collapsed state model

**Invert the map: `state.collapsedLanes` → `state.expandedLanes`, where
absence means collapsed.** Presence with a truthy value is the *only*
representation of "open".

Rejected alternatives, and why:

- *Eagerly initialise `collapsedLanes` to true for every lane key at first
  render.* A key that first appears **later** — a filter change reveals a
  milestone, the poll picks up a new issue — would be absent, therefore
  expanded, therefore pops open on refresh. It also mutates state during a
  render pass, which is the freshness hazard board-logic.js's header
  convention exists to prevent.
- *Keep `collapsedLanes` and default a missing key to `true` on read.* That
  is this ruling with inverted polarity and a name that now lies about what
  the map stores. Same behaviour, worse readability.

The inversion gives one invariant a reader can hold: **a key in
`expandedLanes` ⇒ that lane is open; everything else is closed.** New keys
are collapsed for free, which is the desired default.

**Collapsing must `delete` the key, not set `false`.** Two encodings of
"closed" in one map is how the next reader gets it wrong.

**Repo sections keep their current polarity — `collapsedRepos` is
unchanged.** Collapsing repos by default would hide the milestone headers as
well, leaving the board as a list of repo names; the roll-up the issue asks
for is one level in from that.

> **Judgment call.** This leaves the two maps with *opposite* polarity
> (`expandedLanes` opt-in-open, `collapsedRepos` opt-in-closed). That
> asymmetry is a genuine defect source and must be spelled out in a comment
> at the `state` declaration, not left to be inferred from the names. Cost:
> the comment, and a reader's one-time surprise. Reversal: flip
> `repoSectionEl`'s read/write and rename to `expandedRepos`.

**Both maps become `Object.create(null)`.** For `collapsedRepos` this is a
real fix — its keys are bare `root.id` values, so a root named `constructor`
collides on a bare `{}` (the PT-23 class). For `expandedLanes` it is
insurance only: the keys are `"<repo>::<milestone>"` composites and no
`Object.prototype` member contains `"::"`. Say so in the comment so a future
reader does not cite a hazard that cannot fire.

**Key composition is non-negotiable and unchanged.** Every read and every
write goes through `laneStateKey(repoId, milestoneKey)`, with an explicit
repo id at every call site including single-root. Bare-id-across-roots is a
four-time repeat defect in this codebase; a lane key that omits the repo
makes two repos' identically-named milestones toggle as one.

**No "expand all / collapse all" control in PT-29.** Out of scope per the
issue text. Flagging for team-lead: with everything closed on load, restoring
the old whole-board view costs N clicks — worth a follow-up issue, not a
scope-creep here.

### 3. Disclosure-token spec

Glyphs: **`▼` U+25BC** (expanded / issues shown) and **`▶` U+25B6**
(collapsed / issues hidden). The token reports *state*, not the action; the
aria-label keeps reporting the action.

The current control is not merely small — `font: inherit` pins it to the
13px lane-header font and the thin `▾`/`▸` variants have almost no mass at
that size. Fix in CSS on a shared class used by **both** toggles:

```css
.swimlane-toggle, .repo-group-toggle {
  font-family: inherit;
  font-size: 12px;          /* the FILLED glyphs carry far more mass than ▾ at the same px */
  font-weight: 400;
  line-height: 1;
  width: 18px;              /* fixed box: ▼ and ▶ have different advance widths */
  height: 18px;
  display: inline-flex;
  align-items: center;
  justify-content: center;
  background: none;
  border: none;
  padding: 0;
  color: var(--text-dim);
  cursor: pointer;
}
```

Two things that are easy to miss:

- **The fixed box is the point, not the font-size bump.** Without it the
  label shifts horizontally every time you toggle, because the two glyphs
  are not the same width.
- **Drop the `font: inherit` shorthand** — it resets family, size and weight
  together, so a bare `font-size` override alongside it is order-dependent.
  Set the three properties explicitly.

Add `aria-expanded="true"|"false"` to both buttons alongside the existing
aria-labels.

> **Judgment call, two of them.** (a) The issue names only the milestone
> toggle; applying the same token to the repo toggle touches PT-3 code it
> did not name — but leaving `▾`/`▸` beside `▼`/`▶` reads as two different
> controls. Cost: two glyph strings in `repoSectionEl`. Reversal: revert
> those two strings. (b) `aria-expanded` is additive to "aria-labels
> preserved". Cost: one line each. Reversal: delete the line.

### 4. What must live in board-logic.js

Everything below is pure, synchronous-render-pass only (the module header's
standing convention applies), and exported so QA's `node:test` suite can bite
without a DOM:

| Function | Contract |
|---|---|
| `laneExpanded(expandedMap, stateKey)` → bool | The **single** read path. Encodes "absence ⇒ collapsed". |
| `nextExpandedLanes(expandedMap, stateKey)` → new map | The **single** write path. Returns a fresh `Object.create(null)` map: adds the key when absent, **deletes** it when present. Non-mutating, so the "never store `false`" invariant is assertable via `Object.keys`. board.js does `state.expandedLanes = nextExpandedLanes(...)`. |
| `disclosureToken(expanded)` → `"▼"` / `"▶"` | Exact codepoints, asserted by test — this is what stops the glyph silently regressing to the thin variants. |
| `laneSummary(issues)` → `{ total, byStatus: [{status, count}] }` | Board-column order, zero-count statuses omitted. Drives the collapsed card's chips. |
| `laneStateKey(repoId, milestoneKey)` | **Unchanged.** Reasserted, not touched. |

**Move `BOARD_COLUMNS` from board.js into board-logic.js and export it.**
`laneSummary` needs the canonical status order; a second copy is the exact
drift class PT-22 closed. board.js reads it off `CairnLogic` like every other
import at the top of its IIFE.

Not in board-logic.js: anything touching `document`, the CSS class names, the
`is-collapsed` decision, or the collapse rendering itself.

**Red-first test surface** (QA's lane — this is the list I expect to see
failing before any implementation lands):

1. absence ⇒ collapsed, for an empty map and for a map holding other keys
2. toggle → expanded; toggle again → key **absent** again (`Object.keys().length`
   back to 0, not 1-holding-`false`)
3. `nextExpandedLanes` does not mutate its input
4. **two lanes with the same milestone id under different repos toggle
   independently** — the bare-id regression guard; this one is mandatory
5. `disclosureToken` returns the exact `▼` / `▶` codepoints
6. `laneSummary`: column ordering, zero-count omission, empty input, and a
   status value not in `BOARD_COLUMNS`
7. prototype-shaped keys (`"constructor"`, `"__proto__"`) on both maps

### RECORDED findings — none block the merge

**1. Multi-root + Swimlanes OFF renders white columns on the white repo card.
This is a gap in my ruling, not a deviation from it.** With the checkbox off,
`repoSectionEl` appends `columnsFor(issues)` directly, so the DOM is
`.repo-group > .board > .column` with no grey lane in between. My surface
table only covered `.repo-group .column` on the assumption a `.swimlane`
always intervenes; it doesn't in that mode. Pre-PT-29 the repo group had no
background, so white columns popped against the page grey — now they sit on a
white card, separated only by their 1px border. One line closes it, matching
the treatment already given to the equivalent single-root case:

```css
.repo-group > .board .column { background: var(--bg); border-color: transparent; }
```

Recommend taking it inside PT-29 rather than as a follow-up — it is one line,
the Chrome pass will surface it anyway, and shipping the ruling's surface
model with a hole in one of its four cells is worse than the diff cost.

**2. Collapsed-lane chips can sum to less than the lane total.** With "Show
cancelled" on, a cancelled issue passes `filteredIssues`, joins the lane's
`issues`, and counts toward both `.swimlane-count` and `laneSummary.total` —
but `cancelled` is not in `BOARD_COLUMNS`, so it renders in no column and
produces no chip. Header then reads e.g. `5` beside chips summing to 4. The
over-count is **pre-existing** (`.swimlane-count` has always been
`issues.length` while the columns have never rendered cancelled); PT-29 only
makes the discrepancy visible by putting the parts next to the whole. Not a
regression, and `total = issues.length` is QA's pinned contract, so leaving it
is defensible — but it is now a visible inconsistency where before it was an
invisible one. Follow-up candidate.

**3. `.swimlane-header` has no `flex-wrap`.** `.swimlane-label` is
`flex: 1 1 0%`, so it shrinks to nothing before `.swimlane-summary` gives up
any width. A lane collapsed with all five statuses populated, at a narrow
viewport, will crush the milestone name rather than wrap the chips.
Chrome-pass item: check one fully-populated collapsed lane below ~900px.

**4. `aria-expanded` without `aria-controls`.** Correct as far as it goes, but
the disclosed region (`.board`) carries no id, so a screen reader is told a
control is expanded without being told what it controls. Optional polish;
needs a stable per-lane id, which the lane key can supply.

**5. `▼` now means two things in one app.** Disclosure-expanded in the kanban
toggles, sort-descending in the list-view header (`board.js:727`, the
pre-existing `▲`/`▼` pair). Different views, different controls, and the
`▲`/`▼` pairing reads unambiguously as sort — noting it once so it is on the
record, not proposing a change.

**6. `BOARD_COLUMNS` is exported as a live mutable array.** Any consumer can
`push` into the canonical column order. Nothing does, and freezing it would
be the only guard; ignoring it is fine. Recorded for completeness.

# PT-29 browser-verification checklist (team-lead's Chrome pass)

Acted against sha `7cc03da` (red tests) on `feature/pt-29-board-rollup`, on top of the
architect's ruling at `9a6f749`. Run this AFTER implementation-lead's task #4 lands and
the JS suite (`node --test scripts/cairn/tests/js/*.test.js`) is green — this checklist
covers what only a real browser/DOM can confirm: visual sizing, CSS surface alternation,
and interaction survival (drag-and-drop, drawer) inside the new containment structure.

## Setup

1. Start `cairn serve` (or however the board is normally served) against a board with:
   - At least 2 milestones with issues in the primary repo, one of which is empty (0 issues)
     of some status, to exercise zero-count chip omission.
   - If a multi-root/repo-grouped board is available, use one — otherwise note "single-root
     only, multi-root not covered" in your report.
   - Ideally a milestone id that appears under two different repos (to exercise the
     independent-toggle case visually, not just at the unit level).

## 1. Default roll-up on load

1. Load the board fresh (hard refresh, not cached).
2. Assert: every milestone lane is collapsed — no issue cards visible anywhere, only lane
   headers.
3. Assert: each collapsed lane header shows a compact status-breakdown (chips like
   "todo · 3", "done · 1") plus the existing total count — NOT just the bare total.
4. Assert: a status with zero issues in that lane has no chip for it (no "backlog · 0").
5. Click a lane's disclosure toggle. Assert: the lane expands, issue cards appear, the
   status-breakdown chips disappear (columns already show the counts — no duplicate).
6. Reload the page. Assert: the lane you expanded is collapsed again (view-local state,
   not persisted across a real navigation/reload — this is expected, not a bug, per the
   "in-memory only" contract. Flag if it survives reload, since that would mean state
   leaked into storage somewhere it shouldn't.)
7. **Must NOT happen:** open devtools Network tab, click a toggle. Assert zero new
   network requests fire (no POST/PUT/GET beyond whatever polling already runs
   independently of the click). This is the PT-16 contract restated by the ruling —
   toggling writes to `state.expandedLanes` only, never disk, never network.

## 2. Disclosure triangles

1. With a lane collapsed, inspect the toggle glyph. Assert: it reads clearly as a
   **filled right triangle (▶)** at a glance — not a dot, not a thin/hollow arrow.
2. Expand the lane. Assert: the glyph becomes a **filled down triangle (▼)**, same
   visual weight/size as the collapsed one.
3. Toggle back and forth several times rapidly. Assert: the **label text next to the
   toggle does not shift horizontally** — the fixed-size box is the point (ruling
   section 3); a shifting label means the box isn't actually fixed-width.
4. Inspect the toggle button's `aria-expanded` attribute in devtools. Assert: it flips
   `"true"`/`"false"` in sync with the visual state, and `aria-label` still reads
   "Expand <name>" / "Collapse <name>" as before.
5. Repeat steps 1-4 for the **repo-group toggle** if a multi-root board is available —
   same glyphs, same fixed-box sizing, per the ruling's judgment call 3(a) unifying both
   toggle classes.

## 3. Containment cards

1. In single-root view with Swimlanes on: assert each expanded milestone lane renders
   as a visually bordered/surfaced card (`.swimlane`) with the issue columns sitting
   **inside** its boundary — not a flat header row above a loose grid of cards.
2. Assert the column background inside a lane card reads as a distinct, slightly
   recessed "well" relative to the card's own surface (grey column on white card, per
   the ruling's surface-alternation table) — a visible, not just technical, nesting cue.
3. If a multi-root board is available: assert the **outer** repo section also renders as
   a containing card, and the **milestone lanes nest visibly inside it** — three
   distinguishable surface levels (repo card → milestone card → column well), not two.
4. Turn Swimlanes **off** (flat column board, no lane grouping). Assert: **no**
   containment-card styling appears here — this mode is explicitly untouched by the
   ruling (no `.swimlane`/`.repo-group` elements exist in this mode at all). Flag if
   columns pick up card/shadow styling they shouldn't.
5. Inspect the DOM (Elements panel) around a lane. Assert: **no new wrapper `<div>`**
   was introduced around `.swimlane` or `.repo-group` — the ruling is explicit that
   containment is a CSS promotion of the existing elements, not a new wrapper. If you
   see e.g. `.swimlane-card > .swimlane`, that's a deviation from the ruling worth
   flagging back to implementation-lead before merge.

## 4. Interactions still work inside containment cards

1. Expand a lane. Drag an issue card from one status column to another **within** the
   same lane. Assert: the drop succeeds, the card moves, no visual glitch from the new
   card/well nesting.
2. If a multi-root board is available, repeat the drag inside a nested lane under a
   repo-group card. Assert: same result — nesting doesn't break the drop target
   hit-testing.
3. Click an issue card to open the drawer. Assert: the drawer opens normally, shows the
   right issue, and closes normally — containment card doesn't intercept or alter the
   click.
4. Attempt to drag a card belonging to a non-primary repo (if multi-root available).
   Assert: unchanged prior behavior (not draggable / refused drop, per `isDraggable`) —
   this is a pure regression check, containment should not have changed drag
   eligibility.

## 5. Independent toggle (bare-id-across-roots) — visual confirmation

Only if a multi-root board with a same-id milestone under two repos is available:

1. Expand the milestone lane under repo A only.
2. Assert: the same-id milestone lane under repo B remains collapsed.
3. Reload, then expand repo B's lane only. Assert: repo A's lane is collapsed. This is
   the DOM-level twin of the mandatory unit test (`lane-expanded.test.js`, case 4) —
   confirms the composite key discipline actually reaches the rendered page, not just
   the pure function.

## What must NOT happen (regression watch, whole session)

- No JS console errors on load, toggle, drag, or drawer open (`read_console_messages`).
- No network request fires on any disclosure toggle (section 1, step 7).
- No visual change to the flat (Swimlanes-off) column board.
- No new wrapper element around `.swimlane`/`.repo-group` in the DOM.
- Drag-and-drop and the drawer both still function inside every nesting level touched.
