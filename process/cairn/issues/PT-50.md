Scope per PT-28 precedent: named `cairn migrate` (idempotent, --dry-run), update every archive/ glob (payload build, check_repo scans, find_record_path order, cairn archive write target, _WATCHED_SUBDIRS), is_archived_path already parts-based (PT-42 extraction — correct at any depth, deliberately), lint accepts both layouts during transition or errors with migrate hint (architect rules which). ### @architect — 2026-08-24

**Ruling — `archive/issues/` migration.** Sites verified by reading `scripts/cairn/cairn.py` (89d817e plus the in-flight PT-47 edits, so **cited by symbol** — line numbers are moving under us).

**§1 Migration contract — `cairn migrate archive-issues [--dry-run]`.** Named sub-subcommand under `migrate` (PT-28 precedent: an invocation in a shell history means one specific thing forever). Moves every `archive/*.md` → `archive/issues/<name>` via `_git_mv_or_rename`, so git records renames. **Touches zero bytes inside any file** — filesystem-only, unlike `prefix-ids`. Never touches `archive/milestones/` or `archive/majors/` (already correct, and invisible to the non-recursive `_dir_glob` anyway). Does **not** gate on `check_repo` — same reasoning as the other two migrations: it must run on the repo whose lint it is fixing. Report `{"issues": [{"old", "new", "resumed"}]}` rendered by one formatter for dry and real runs — the plan IS the report. Exit 0 for any completed run; surviving lint errors printed as warnings, not this command's failure.

**Idempotency + interruption:** keyed on presence of the **source** file (prefix-ids' filename-keyed precedent). Nothing at `archive/*.md` → "nothing to do". Destination already exists → **validate the whole set before moving anything** (archive_major's two-phase precedent): byte-identical → report `resumed: true` and unlink the source; **differing** → refuse the entire run, naming the file, moving nothing. A rename cannot produce differing content, so differing content means a human put it there and this command has no basis to pick a winner.

**§2 Every site that globs `archive/` — eleven, not five.** Three of the six the brief did not list are correctness-critical.

*READ (must see both layouts):*
1. `find_issue_path` — the `archive/<id>.md` candidate.
2. `_RECORD_SEARCH_SUBDIRS` — its `"archive"` entry.
3. `_next_id_candidate` — `for sub in ("issues", "archive")`. **Not on the brief's list and the worst one:** miss it and `cairn new` re-allocates an id an archived issue already holds, breaking the one invariant the ID scheme exists to protect.
4. `check_repo`'s issue scan — `_dir_glob(data_dir / "archive")`. Miss it and archived issues stop being resolution targets: `parent`/`blocked_by`/`milestone` refs to them go dangling, and the archived-issue-milestone-status rule stops firing.
5. `migrate_prefix_ids` phase 2's ref scan — same expression, different function. **Not on the brief's list.** A repo needing both migrations must not have the older one silently skip its archived issues.
6. `build_board_payload` — `issue_paths += _dir_glob(data_dir / "archive")`.
7. `compute_etag` — its `subdirs += ("archive", …)` tuple. **Not on the brief's list.** Miss it and an archived-issue edit doesn't bust the etag; Show-archived serves a 304 over changed data.
8. `_WATCHED_SUBDIRS` — its `"archive"` entry (SSE).

*WRITE (target the new layout only):*
9. `cmd_archive`'s `--done-before` path — `archive_dir = data_dir / "archive"`, its `mkdir`, and its `_git_mv_or_rename(p, archive_dir / p.name)`.
10. `archive_milestone` — its **own** `archive_dir = data_dir / "archive"` for the issue moves. A second write target, not the same one as #9. (`archive_major` delegates to it; `archive_major_dir` is `archive/majors/`, unchanged.)

*UNCHANGED — verified, do not touch:* `is_archived_path` (parts-based since PT-42, correct at any depth); `_record_schema_for_path` (parts-based — `archive/issues/PT-1.md` classifies as `issue` with no change); `build_issue_payload`'s `path` (inherits `find_issue_path`).

*Non-code:* `.claude/skills/setup-tracker/SKILL.md`'s `mkdir -p process/cairn/{issues,archive,milestones,majors}` → `archive/issues` (a fresh repo must never be created in the legacy layout); `process/TRACKER.md`'s Archive layout block **and** the paragraph justifying the flat layout — that reasoning is now reversed, replace it rather than leaving it contradicting the diagram; the CLI table's new `migrate archive-issues` row; `tests/INTERFACE.md` wherever it names archive paths.

**§3 One helper, not eleven unions.** Add `archived_issue_paths(data_dir) -> List[Path]` = `_dir_glob(archive/issues) + _dir_glob(archive)`, and route read sites 1–8 through it. The dual-read then has exactly one deletion point. `find_issue_path` and `_RECORD_SEARCH_SUBDIRS` order the **new** location first: in a half-migrated tree the destination is authoritative.

**§4 Transition posture: read both, write one, lint one.** Reads accept both layouts; writes only ever produce `archive/issues/`; `cairn check` **errors** on any `archive/*.md`, one error carrying the count and the literal command `scripts/cairn/cairn migrate archive-issues --dry-run`.
*Justification, one sentence:* reading both is what keeps the break **lint-only** — the posture `prefix-ids` and `lifecycle-status` set — because a read-new-only engine would not merely fail an unmigrated repo's lint, it would re-allocate its ids and dangle its references, which is data breakage, not a lint break.
Not a warning: `check_repo` returns errors only and has no warning tier; inventing one for this is a larger change than the migration itself. The dual-read is **scheduled, not permanent** — file a follow-up against the next MINOR to delete the legacy leg of the helper; do not delete it in 0.7.1.

**§5 Release-note posture.** BREAKING (lint-only), stated with the exact command, in the 0.7.1 notes. A break in a PATCH release is legitimate on the 0.6.1/PT-28 precedent (a patch milestone that carried a lint-only break) and because 0.x is semver's reserved no-compatibility-promise zone. Say plainly: your board and CLI keep working; only `cairn check` fails until you run the command.

**§6 Tests to pin.** Migration: moves, idempotent re-run, differing-destination refusal, `--dry-run` writes nothing. Legacy-layout fixture still (a) allocates a non-colliding id, (b) resolves refs in `check_repo`, (c) renders under `?archived=1`, (d) produces a changed etag when an archived file changes. `cairn check` errors on the legacy layout with the command in the message. Both write targets (`--done-before` and `--milestone`) land in `archive/issues/`.

Grepped `scripts/cairn/tests/js` and `scripts/cairn/board` for hardcoded archive paths first — none found (JS never constructs the on-disk path; the server sends it) — JS suite untouched.

**Real-repo migration:** ran `cairn migrate archive-issues --dry-run` then for real against this repo's own `process/cairn` (44 legacy issues under `archive/`) — moved cleanly, `cairn check` clean afterward, byte-identical content confirmed by diff. **Bubble-up finding, not a PT-50 defect:** `_git_mv_or_rename` (pre-existing, PT-8-era) passes `subprocess.run(["git", "mv", str(src), str(dest)], cwd=str(src.parent), ...)` — when `--data-dir` is a *relative* path, the args stay relative to the ORIGINAL cwd while `cwd=` points somewhere else, so `git mv` fails silently (only checks `returncode == 0`, no logged stderr) and falls back to a plain filesystem move that leaves git status showing an untracked add + unstaged delete instead of a staged rename. Every existing test that exercises this path uses an *absolute* `--data-dir` (tempfile-based), so it was never caught. Worked around here by passing an absolute `--data-dir` for the real migration; the latent bug affects `archive_milestone`/`archive_major`/`cmd_archive`'s `--done-before` path too, predates PT-50, and is out of this issue's scope — flagging for a follow-up (not filed as an issue by me; team-lead's call on priority since none of this repo's tooling/docs currently recommend a relative `--data-dir` for real use).
