## Problem

PT-86's self-stop (session registry drains non-empty → empty, grace window elapses, final flush,
pidfile removed, exit) writes nothing to `process/cairn/metrics/otel_receiver.log`. On 2026-09-04
an unexpected receiver exit looked like a new defect and cost a diagnosis round (PT-84 comments
6304afd, e1e9cd4): the log held only an earlier refused-flush line, and the self-stop left no trace.

## Ask

One log line at the point of no return, naming the trigger: `self-stop: registry drained at
<ts>, grace <n>s elapsed, flushed <k> lines, exiting`. Also one line when a registration cancels an
armed grace window. Nothing else changes.

## Acceptance criteria

1. Test: the existing self-stop test asserts the log line is present with the trigger named.
2. Test: the cancel-inside-grace test asserts the cancel line.
3. Full suite green; `cairn check` ok; data file and real registry untouched by tests.

### @architect — 2026-09-07

**Gate 1 ruling.** All line numbers at 7e3c438, `scripts/cairn/otel_receiver.py`.

**Measured baseline — the "nothing else changes" number is 0, not "a few".** Driving both scenarios through the test module's own helpers against a throwaway fake engine root: `<fake_root>/process/cairn/metrics/otel_receiver.log` is **created and empty — 0 lines — in both** the self-stop case (receiver gone) and the cancel case (receiver still up). The real checkout's `otel_receiver.log` and `token-usage.jsonl` were byte-identical (sha256) before and after. So the after-state is exactly **1 line each**, assertable as equality, not as "contains".

**The log is the daemon's own stderr.** There is no logging framework and no `_log` helper: `--ensure-running` detaches with `stdout=log, stderr=log` onto `LOGFILE_REL` (line 1418), so a `print(..., file=sys.stderr)` in the watchdog *is* a log line. Measured: `sys.stderr.line_buffering` is `True` even when redirected to a file, and a child's line reaches the file while the child still lives — **no `flush=True` needed**; do not add one as insurance.

**The two decision points.**
- **Point of no return** — the fall-through after line 1829's re-read. Nothing past it aborts. The line goes ~~after `_do_flush()` (1851) and before `_compare_and_delete_pidfile` (1852)~~ **after `_compare_and_delete_pidfile` (1852)** — still after the flush, because `<k>` is only known once it returns. *(Amended at gate 4: the original placement put a buffered file write inside the window `test_one_session_start_end_exits_after_grace_period_with_a_flush` races between `server_close()` and the pidfile removal. Everything the line reports is equally true after the pidfile is gone.)*
- **Cancel of an armed window** — three sites reset `shutdown_deadline` to `None`: **1802** (registry non-empty at the top of a tick), **1819** (the pre-exit re-probe found life), **1834** (a session registered inside the `.closing` race). All three log, and **only when `shutdown_deadline is not None`** — site 1802 runs on every ordinary tick, so an unconditional print there would flood the log once per `WATCHDOG_TICK_SECONDS` forever. That condition is the whole design of this line.

**Seam.**
- `_do_flush()` (1644) currently returns `None` and discards `flush()`'s return, which is `List[Dict]` — the lines written. Change it to return `len(lines)`, and `0` on the refused-flush path (a refused flush wrote nothing, so `flushed 0 lines` is true, not a guess).
- Two formats, exactly:

      self-stop: registry drained at <iso>, grace <n>s elapsed, flushed <k> lines, exiting
      grace-window cancelled: registry non-empty at <iso>, <reason>, staying up

  `<iso>` is `_now_iso()`; `<n>` is `grace_period_seconds` as given (`0.4`, `10.0`); `<k>` is `_do_flush()`'s count. `<reason>` is one of `session registered`, `session proved alive at the pre-exit probe`, `session registered during the closing race`, for 1802 / 1819 / 1834 respectively — so a future diagnosis can tell an ordinary cancel from a race.

**Assertion tokens** — match the shape, not the values, so a timestamp or a grace value can never make the test brittle:

    ^self-stop: registry drained at \S+, grace [\d.]+s elapsed, flushed \d+ lines, exiting$
    ^grace-window cancelled: registry non-empty at \S+, [^,]+, staying up$

Assert `len(log_lines) == 1` in each scenario as well — that is the measured baseline of 0 doing real work, and it is what catches an accidental second line better than any review.

**Tests qa extends** in `tests/test_otel_receiver_self_stop.py` — extend in place, add no new module:

- AC2 → `LastSessionSelfStopTests::test_a_start_during_the_grace_window_cancels_the_exit` (678). That test exercises site **1802** only; 1819 and 1834 are race paths with no deterministic trigger — log them, do not try to test them, and say so in the test's docstring rather than leaving a silent gap.
- **Do not touch this file's `setUpModule`/`tearDownModule` (275/303)** — they are the PT-91 real-data-file guard and are themselves under test elsewhere in the module.

**Red mutations.** AC1: delete the `print` after 1851 → the self-stop assertion fails. AC2: delete the `print` at 1802 → the cancel assertion fails. The claim is that 1800–1803 is "the routine still-alive reset (not a cancel)" and that only 1818–1820 and 1829–1835 cancel an armed deadline. Measured by patching a **copy** of the receiver inside a throwaway fake engine root — never the real file, which was byte-identical either side — marking all three sites with `armed={shutdown_deadline is not None}` and running the AC2 scenario (start, end, re-register at 0.6 × grace):

    SITE-1800 armed=False        <- 1 of these
    SITE-1800 armed=True         <- the cancel, exactly one
    SITE-1800 armed=False   x9
    (SITE-1818 and SITE-1829: never fired)

**1800 is the cancel site**, and in this scenario it is the *only* site that fires at all. 1818 and 1829 sit after the deadline has already **expired**; a session that registers *during* the window is seen at the top of the next tick, at 1800, long before the deadline passes. Placing the line only at 1818/1834 would leave `test_a_start_during_the_grace_window_cancels_the_exit` asserting on a line that never appears — the AC2 test would be unwritable and the common case unlogged.

The builder is right that 1800 also does a routine reset: **10 of the 11 firings have `armed=False`**. That is precisely what the ruling's `shutdown_deadline is not None` condition is for — it turns 11 lines per scenario, forever, into 1. The condition is not a nicety; without it this site is a log flood, and with it this site is the feature.

1818 and 1834 stay in the ruling as loggers: they are genuine cancels when they fire, they have no deterministic trigger, and their distinct reason tokens are what will tell a future diagnosis that a race happened rather than an ordinary cancel.

**`_do_flush()` returning a count: agreed**, that half of the builder's prep is correct and already in the ruling — it discards `flush()`'s `List[Dict]` today, and `<k>` cannot be written without it.
