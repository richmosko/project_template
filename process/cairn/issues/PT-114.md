### @team-lead — 2026-09-08

From PT-110's verdict delta 2 (architect, 2026-09-08): every bits-ui floating overlay (popover, dropdown, select, tooltip, sheet) had been at layer 0 since PT-54 — shadcn's `z-50` sits on a static content node inside bits-ui's absolute-positioned wrapper, whose z-index is auto (bits-ui copies the content's z inside a requestAnimationFrame, a race by construction). PT-110 added the declarative floor `[data-bits-floating-content-wrapper] { z-index: 50; }` in `src/app.css`, which covers all of them by selector, and set the header at `z-40`. Ask: (1) browser-verify each overlay type over the sticky header (elementFromPoint in the overlay's top strip while it overlaps the header), on the live board; (2) record the tier ladder — content `z-auto` < sidebar rail `z-10` < header `z-40` < portal'd overlays `z-50` — in `docs/DESIGN/design-system-spec.md` with the PT-110 reason, so the next positive z anyone adds has a ladder to argue with; (3) a scan that no component in `src/` declares a z-index class above 50 without a comment naming the ladder. Backlog, not PT-0.12.2 (Mosko routes new follow-ups).

### @team-lead — 2026-09-08

Addendum to the ask (from PT-117's verdict @bae4d88, 2026-09-09): the header's z-40 only stays above content because every non-header direct child of the page root carries `isolate` (PT-117) — a library overlay at z-50 inside a content block that lacks it escapes above the header again. Fold into the ladder entry and the guard: (4) every non-header direct child of the page root is `isolate`, scanned structurally (count the children, not a fixed list of three), so a future fourth section cannot silently reopen PT-117.
