Reported by Mosko (2026-08-27) on the merged PT-55 state: the dashboard
constrains its content column, and the embedded kanban — six columns with
Show-cancelled on — doesn't fit. Layout ruling (team-lead, from the spec):
the Dashboard scale defines 28px page MARGINS, not a max-width, and the
preset's own preview is full-bleed — the cap is an implementation artifact.

**Acceptance criteria**
- [x] Dashboard content area is full-width (28px page margins retained, no
      max-width cap); the embedded board gets the viewport
- [x] Six-column kanban (Show-cancelled on) fits without inner horizontal
      cramping at common desktop widths; board's own overflow-x scroll
      remains the fallback below that
- [x] Status cards / roster / other sections remain visually sane at full
      width (grid columns may cap or stretch — implementation judgment,
      spec's card scale holds)
- [x] dist rebuilt and committed in the same PR (dashboard src changes)

## Comments

### @implementation-lead — 2026-08-27

Fixed in `3af5249`: dropped `max-w-6xl` from the root container (now full-bleed,
28px margins only via `px-7`/`py-7`), and moved header/status-cards/tracker-table/
agent-roster into their own `max-w-6xl` wrapper so those sections don't stretch
across an ultrawide monitor — only the Board section is outside any cap.

Full suite 357 JS / 706 py, `cairn check` clean. Verified via curl against a live
`cairn serve` (`/dashboard`, `/?embed=1`, `/api/dashboard` all 200) and confirmed
in the built `dist/assets/index.js` that the root container carries no
max-width class and `max-w-6xl` only applies to the new inner wrapper.

On AC2 specifically (six columns fitting at common desktop widths): I don't have
browser automation available this session to screenshot-verify the actual
rendered width, so this is arithmetic, not observation — board.css's `.column`
is `flex: 1 1 0; min-width: 220px` inside a `12px`-gap flex row, so six columns
need roughly 1380px at their floor plus ~136px of margin/padding/iframe-card
chrome (≈1516px total) before overflow-x kicks in. The *previous* max-w-6xl cap
(1152px minus that same ~136px ≈ 1016px available) was below that floor at
every viewport, i.e. always cramped; removing the cap entirely means only
viewports narrower than ~1516px fall back to the board's own horizontal scroll,
which the AC explicitly allows. Flagging so team-lead's browser pass is the
thing that confirms this, not my math.
