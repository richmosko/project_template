## Problem

Measured 2026-09-05 at the PT-85 loop (user's question: "how many tests get run every time?"):

| Suite | Tests | Files | Wall time |
|---|---|---|---|
| Python (`unittest discover`, serial) | 1327 | 77 | ~155 s |
| JavaScript (`node --test`) | 458 | 47 | <1 s |

Every teammate runs the full Python suite repeatedly inside a loop (qa after each commit,
implementation-lead before each report, the architect on a clean control, the lead at
pre-flight) — 15–20 full runs per feature, each blocking that agent for 2.5 min. Per-file wall
time (top of 77): test_server 22.4 s, test_otel_receiver_self_stop 19.0, test_dashboard 13.5,
test_backfill_tokens 12.9, test_show_archived 12.2, test_record_mutation 9.5, test_root_redirect
8.0, test_cli 6.3, test_otel_receiver 6.1, test_otel_receiver_hardening 5.1. The top seven files
are ~97 s of the 155: they spawn real servers/daemons (with grace-window waits) or build a fresh
git repo per test. 30 of 77 files use subprocess or temp-dir repos.

## Ask (in payoff order)

1. **Tiered gating** (WORKFLOW → Implement inner loop): during a loop a teammate runs the modules
   touched plus the guard modules (`discover -p "test_<area>*.py"`); the full suite runs at two
   points only — qa's final pass and the /finish-feature gate. Write the rule and the command.
2. **Parallel runner**: a small script (`scripts/cairn/run_tests.py`) that runs the 77 files
   across N workers (files are independent; unittest has no parallelism) and aggregates
   pass/fail/skip counts and exit code; wire /finish-feature's gate and the WORKFLOW commands to
   it. Target: ≤45 s on 4 workers, same counts.
3. ~~**Fixture reuse**~~ — **split to PT-96** (ruling 2026-09-06: not required for AC1; the
   runner alone takes 171 s → 26 s).
4. ~~**Consolidation**~~ — **split to PT-96**. The `cairn test --full --gate` hook from the
   team-lead's 2026-09-05 comment below is **split to PT-97**.

## Acceptance criteria

_Amended by the gate-1 ruling, 2026-09-06._

1. Full Python suite wall time ≤ 45 s via `scripts/cairn/run_tests.py` at its **default** job
   count on this machine, with pass/skip counts identical to serial `discover` (1379 / skipped=1
   at 5fd6db1); serial `discover` still works and agrees, and `run_tests.py --serial` agrees with
   both. The default is 8, not 4: 4 workers measured 47.73 s (size-desc) / 44.34–46.00 s (oracle
   order) and does not reliably clear 45 s — see `process/reviews/PT-93/timings.md`.
2. WORKFLOW → Implement → Inner loop and `.claude/skills/finish-feature/SKILL.md` name the tiered
   rule and the runner command; the finish-feature pre-flight gate invokes the runner.
3. Per-file timing recorded before/after for **all** files (not just the top seven), from
   `run_tests.py --json`, in `process/reviews/PT-93/timings.md`.
4. No test deleted in this loop (consolidation is PT-96); `cairn check` ok; the real data file,
   the registry, and `process/cairn/metrics/` untouched.

**Seam** — `scripts/cairn/run_tests.py`, paths resolved from `__file__`, runnable from any cwd:
- Child command is exactly `[sys.executable, "-m", "unittest", "discover", "-s", "tests", "-p", <file>]`, cwd `scripts/cairn`, **no `-t`**. Measured trap: `-t .` drops `tests/` off `sys.path`, every module dies on `import helpers`, and each file still prints `Ran 1 test … FAILED (errors=1)` — a plausible-looking wrong answer, not a crash.
- Discovery `sorted(TESTS.glob(p))` over `--pattern/-p` (repeatable, default `test_*.py`) — same flag is the tiered-run entry point.
- Scheduling `ThreadPoolExecutor(max_workers=jobs)`, files submitted **largest source file first**. No cached timings file: size is r = 0.474 against duration and captures ~75 % of the oracle's gain with nothing to go stale.
- `--jobs/-j N` default `min(8, os.cpu_count() or 4)`; `--serial` ≡ `-j 1`; `--list` prints names, exit 0; `--json PATH` writes `{wall, jobs, files, tests, failures, errors, skipped, failed_files, times}` (`times` = file → seconds; this is AC3's instrument).
- stdout ends with unittest's own two lines so existing greps survive: `Ran <N> tests in <W>s (<F> files, <J> workers)` then `OK (skipped=<N>)` or `FAILED (failures=<N>, errors=<M>, files=<K>)`. Each failing file prints `FAIL <name> (<s>s)` and its captured stderr above that block; passing files print nothing. Exit 0 iff every child exited 0.
- Tiered rule text (WORKFLOW → Implement → Inner loop, and finish-feature pre-flight): a teammate runs `python3 run_tests.py -p "test_<area>*.py"`; the full `python3 run_tests.py` runs at the four gates only, by the gate owner (PT-94 C9).

**Guard thresholds** — qa's red tests in `tests/test_run_tests.py`; none of them may run the real suite (D11: this feature pays back the seconds it adds). Assert:
1. discovery == `sorted(glob("test_*.py"))`, ≥ 80 files; `-p` narrows it; `--list` prints exactly that, exit 0.
2. the child argv equals the list above, element for element, and `"-t" not in argv`.
3. parsing real `unittest` stderr yields `(ran, failures, errors, skipped)`; a `Ran 0 tests` child contributes 0 rather than being dropped, and an unparseable child is an error, not a silent 0.
4. one child exiting non-zero ⇒ process exit 1 and that name in `failed_files`; all zero ⇒ exit 0, `failed_files == []`.
5. default jobs == `min(8, os.cpu_count() or 4)`; `--serial` ⇒ jobs 1.
6. for files of known sizes the submission order is size-descending.
7. `--json` writes every key above; `times` has one entry per discovered file.

AC1/AC3 are a one-off measurement at gate 4 (`run_tests.py --json` vs `discover`), not unit tests. Proceeding on this unless the file says otherwise.

**Why it blocks.** This loop's headline deliverable is a rule telling every teammate to run `run_tests.py -p "test_<area>*.py"` mid-loop. A mistyped or wrong-prefix area name is the single most likely operator error against that rule, and today it returns a green with nothing executed — the silent-pass class the runner exists to remove. `tests/test_run_tests.py` has no guard for empty discovery (grep for `empty|no files|zero`: only the `Ran 0 tests` parse test, which is a different subject).

**Deltas — one batch, all in `scripts/cairn/run_tests.py` + `tests/test_run_tests.py`:**
1. **Blocking.** `discover_files` returning `[]` is an error: print `no test files matched: <patterns>` to stderr and exit **2** (distinct from 1 = red suite, so a caller can tell a typo from a failure). Applies to `--list` as well as a run. Red test: a pattern matching nothing exits 2 and names the pattern; the mutation that turns it red is restoring the `return 0`. Second test pins that a matching pattern still exits 0, so the guard can't pass by rejecting everything.
2. **Take with 1** (you are in the file anyway). `parse_summary` currently raises `ParseError("unparseable unittest stderr: …")` for a module unittest reports as `NO TESTS RAN` — measured on `-p "palette_check.py"`, which errors with a message blaming the parser for a file that simply has no tests. Keep the failure, fix the reason: detect `NO TESTS RAN` and raise/report it as "no tests ran in `<file>`". This is the ruling's guard threshold 3 read correctly — never a silent 0, but the message must name what actually happened.

**Note, no action this loop.** `main()` re-implements `run_all()`'s timer-plus-`_aggregate` sequence instead of calling it, so `run_all`'s guard tests do not cover the CLI path they describe. Three lines, and the WORKFLOW → Validate duplicated-inline-expression criterion points at exactly this shape. Fold it into PT-96 rather than reopening here.
