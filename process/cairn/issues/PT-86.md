## Problem

The receiver (`scripts/cairn/otel_receiver.py`) is started detached by the SessionStart hook and
never stops on its own: only `--stop`, a kill, or a reboot ends it. That was a deliberate PT-78
choice — sessions overlap (every teammate is its own process), the exporter sends its final batch
at process exit, and an idle localhost process costs nothing — but "never stops" is a choice, not
a necessity, and it leaves a daemon running on every machine that ever opted in.

## Ruling (team-lead with the user, 2026-09-04)

Stop the receiver when the **last** session on the repo ends, not when any session ends, and only
after the exporter's final flush has had time to land.

1. A `SessionEnd` hook calls `otel_receiver.py --session-ended`. The receiver keeps a count of live
   sessions: `--ensure-running` (SessionStart) increments; `--session-ended` decrements. Counting
   is by session id passed from the hook input, not a bare integer, so a crashed session that
   never sent its end does not pin the receiver forever: a liveness probe of the recorded session
   ids (their processes) is run on every decrement and at each flush.
2. On the last decrement the receiver waits a grace period (default 10 s, ≥ the exporter's export
   interval tail) for the final batch, flushes to `token-usage.jsonl`, releases the lock, removes
   its pidfile, and exits. A new session starting inside the grace window cancels the shutdown.
3. Teammate processes count as sessions: they run SessionStart too, so the count is per process.
   Verify that a teammate's SessionEnd fires on shutdown_request; if it does not, the liveness
   probe is the backstop.
4. `--status` reports the live-session count and ids' liveness. `--stop` remains for manual use.
5. TRACKER.md → Ongoing collection documents the lifecycle: starts with the first session, stops
   with the last, survives `/exit` of one session while others run.

## Acceptance criteria

1. Tests with two fake project roots and fake session ids: one session start/end → receiver exits
   after the grace period with a flush; two starts, one end → still running; a session id whose
   process is gone is reaped by the liveness probe; a start during the grace window cancels exit.
2. The final flush provably contains a datapoint received during the grace window.
3. SessionEnd hook line in `.claude/settings.json`, same shape and exit-0 discipline as the
   SessionStart line; no stderr redirect.
4. Full suite green; `cairn check` ok; data file untouched by tests.

Gating ruling — the how-questions the 2026-09-04 ruling leaves open. Read §0 first; every
other section is derived from it. Measured this turn on this machine: a hook-spawned
subprocess' ancestor chain is `python3` ← `zsh -c …` ← `…/.local/share/claude/versions/2.1.260
--agent-id architect@session-… --agent-name architect`, i.e. the session process is an
identifiable, non-shell ancestor.

**§0 Governing asymmetry.** A false *pin* costs one idle localhost process — today's status
quo, the thing PT-78 deliberately accepted. A false *reap* costs every subsequent datapoint of
a live session, silently, with no second SessionStart to recover it. The two errors are not
comparable, so every sub-decision below breaks toward not-stopping. If an implementation choice
here looks over-cautious, that is the reason.

**§1 Registry transport: an HTTP control endpoint, not a state file.**
`POST /control/session` with body `{"event": "start"|"end", "session_id": "...", "repo_root":
"<absolute, resolved>", "pid": <int|null>}`. Unknown paths keep returning 404.
*Why not a file:* the daemon becomes the **single writer** of the registry, mutating it under
the existing `state.lock` — which is what turns the grace-window cancel race (§4) into a
two-line check instead of a multi-writer file protocol with its own lock, its own format, a
gitignore entry, and either polling or a second signal. Teammate SessionStarts arrive in a
burst; multi-writer file state is the defect class this repo keeps re-learning.
*Cost accepted:* the registry does not survive a receiver crash. §6 makes that a pin, not a
reap.
*Cross-repo guard (mandatory).* The daemon compares the request's `repo_root` against its own
resolved repo root and answers **409, no state change**, on mismatch. Without it a
`--session-ended` fired in repo B stops repo A's receiver whenever the two share `otel_port` —
PT-79's real contamination incident, in the opposite direction. This is what AC 1's "two fake
project roots" must exercise: a control POST from root B against root A's receiver changes
nothing.

**§2 Session id and pid capture (client side).**
- `--session-id <id>` explicit flag for tests and manual use; otherwise read the hook's JSON
  from stdin **only when stdin is not a TTY**, and take `session_id`. Never block on stdin.
- `--ensure-running` with no session id still starts the receiver and registers nothing; §6
  says why that cannot cause a spurious stop.
- **pid** = the nearest ancestor that is not a shell (`sh`/`zsh`/`bash`/`dash`) *and* whose
  command line matches the claude binary. If no ancestor matches, send `pid: null` — do not
  guess. Picking a wrapper process that exits immediately would manufacture exactly the false
  reap §0 forbids.
- **No start-time / pid-recycle guard.** A recycled pid can only ever produce a pin. Not worth
  the portability surface.

**§3 Liveness probe** = `os.kill(pid, 0)`, run on every `end` event, at each flush, and once
more immediately before the point of no return (§4). Dead → drop the entry. `pid: null` → never
dropped by the probe; it leaves the registry via its own `--session-ended` or not at all, and
`--status` shows it as `live=unknown`. **No transcript-mtime probe**: an idle-but-live session
(user stepped away) writes nothing, and mtime would reap it.

**§4 Grace window and the cancel race — one lock, one point of no return.**
- `--grace SECONDS`, float, default `10.0`. No config.yml key; tests use ~1 s.
- When an `end` or a probe empties a registry **that was non-empty**, record
  `shutdown_deadline = monotonic() + grace` under `state.lock`. **Do not flush at this moment** —
  flushing on the decrement is what would make AC 2 unprovable.
- A watchdog daemon thread ticks ≤ 0.25 s. Per tick, under `state.lock`: registry non-empty →
  clear the deadline; deadline set and passed and the registry still empty after a fresh probe →
  set `closing = True` (**the point of no return**) and proceed to §5.
- A `start` request under the same lock: `closing` False → register **and clear the deadline
  unconditionally** (this is the cancel); `closing` True → **503 `{"closing": true}`**, no
  registration.
- **Client handling of 503 is mandatory, not best-effort:** `ensure_running` waits for the port
  to stop listening (bounded ≤ 1.0 s, 0.1 s ticks) and then falls through to its existing spawn
  path, registering with the new receiver. Skip this and a session started in the instant
  between the point of no return and the socket closing gets neither a receiver nor a second
  SessionStart — its entire run goes unrecorded, and nothing anywhere reports it.

**§5 Shutdown ordering.** A wrong order here still passes a naive test and loses data:
1. **close the listening socket first** (`httpd.shutdown()` from the watchdog, `server_close()`
   in `serve`'s `finally`) — after this no export can arrive, so the final flush is complete *by
   construction* rather than by hope;
2. **final flush** — it takes and releases `process/cairn/metrics/.lock` itself; never hold that
   lock across the socket close or the pidfile unlink;
3. **unlink the pidfile compare-and-delete**: read it back, delete only if it still holds our own
   pid;
4. return from `serve`, exit 0.
*Why socket-before-pidfile:* unlinking while still listening drives a racing `--ensure-running`
into PT-81's H2 "port held by another process" branch — it refuses to start, and that session
gets no receiver plus an alarming message about a stranger's process.
*Compare-and-delete applies to the existing paths too.* As written today, `_on_shutdown` and
`serve`'s `finally` both call `pidfile.unlink()` unconditionally, so an exiting receiver can
delete a **successor's** pidfile. Fix it in this loop; the 503 handoff widens that window.

**§6 What may and may not trigger a stop.** Only a **non-empty → empty** transition stops the
receiver. A registry that has *never* been non-empty never stops it — that covers a receiver
started by a session whose id could not be read, and a receiver respawned after a crash while
other sessions are still live (their ids are gone with the old process; their eventual `end`
events are unknown ids). Both are pins. An `end` for an unknown session id → 200
`{"known": false}`, no state change.

**§7 `--status`** gains `sessions: <n>` and one line per id: `<session_id> pid=<pid|none>
live=<true|false|unknown>`. Exit code stays 0 running / 1 not — do not overload it with
liveness.

**§8 PT-87 non-foreclosure.** Role stays resolved **at flush time** from the transcript; do not
pre-resolve or cache a role when a session registers. At registration the transcript may not
exist yet, and TRACKER already pins "a miss is deliberately not cached". Transcripts outlive
their session, so the post-grace final flush resolves roles exactly as a periodic flush does,
and PT-87 changes one function with both paths following.

**§9 Hook line.** SessionEnd mirrors SessionStart's shape: guard on the script's existence,
exit 0, no stderr redirect (AC 3), stdin left connected so the JSON reaches the script. Verify
empirically and record as a comment: SessionEnd fires (a) for the main session on `/exit`, and
(b) for a teammate on `shutdown_request`. If (b) does not fire, the §3 probe is the backstop and
that fact goes into TRACKER → Ongoing collection rather than being left as folklore.

**§10 Cost budget.** `--ensure-running` for a second session stays in the ~0.1 s class: pidfile
read + `kill(pid,0)` + port probe + one control POST with a **1.0 s timeout**. Every
control-path failure — refused, timeout, 409, malformed — is non-fatal: one stderr line, exit 0.
Telemetry never fails a session.

Tests: non-default `--port` and an `--out-file` under a temp dir, always (AC 4 — the committed
data file stays untouched). Anything this ruling does not name is the implementer's call; bring
it back here only if it collides with §0.

### @architect — 2026-09-04

Addendum — §1 amended. **qa's committed seam governs; my control-endpoint ruling is withdrawn.**
It is the better design and I'd rather say so than make 634 lines of tests satisfy a rationale
that no longer holds. §0's asymmetry (a false pin is free, a false reap silently costs a live
session's remaining telemetry) is unchanged and still decides everything below.

**A. Why the file registry wins.** My §1 rested on one claim: single-writer state under the
daemon's existing lock. A **file per session id** is per-key single-writer — no shared mutable
file, no lock, no contention — which dissolves that claim entirely. Three axes then favour it
outright:
1. **Crash survival.** `.sessions/` outlives the receiver, so a respawned daemon inherits a
   correct registry instead of §6's permanent pin.
2. **No cross-repo channel exists.** The directory is derived from the pidfile path inside the
   repo, so a `--session-ended` in repo B cannot reach repo A even when both share `otel_port`.
   **§1's `repo_root` check and the 409 response are withdrawn — there is nothing left to
   guard.** AC 1's two fake roots keep the purpose the committed suite already gives them:
   driving the real spawn/pidfile/signal path against an isolated tracker.
3. **Testable without sockets**, via the pure functions the test file already declares.
The one thing the endpoint did better — a synchronous `503 closing` — is replaced by B.

**B. The point of no return, without a synchronous channel.** A two-flag protocol; both sides
write first, then check.
- **Daemon:** (1) exclusive-create `.sessions/.closing`; (2) re-read the directory. Non-empty →
  remove `.closing`, cancel, keep serving. Empty → close the socket → final flush →
  compare-and-delete the pidfile → remove `.closing` → exit 0. **The daemon never re-binds**:
  the abort happens strictly before the socket closes, so there is no TIME_WAIT question.
  A new daemon removes a stale `.closing` at startup — a crash can leave one.
- **Client (`--ensure-running`):** (1) write its own `.sessions/<id>`; (2) check `.closing`.
  Present → wait ≤ 1.0 s (0.1 s ticks) for the port to free, then take the normal spawn path.
  If that wait times out while `.closing` has vanished and the port is still listening, the
  daemon aborted: return quietly, already registered — **do not** print PT-81 H2's "port held by
  another process", which would be a false alarm about a healthy receiver.
- The interleaved case is the point: both sides see each other, so the daemon aborts *and* the
  client attempts a spawn that H2 refuses — leaving the session registered and the receiver
  alive. A pin, never a lost session.

**C. pid capture — `$PPID` accepted, §2's ancestor walk withdrawn.**
Measured today: a hook subprocess' chain is `python3` ← `zsh -c …` ← the claude process, so the
hook shell's `$PPID` **is** the session process. Confirmed against the hooks reference: stdin
JSON carries `session_id`, `transcript_path`, `cwd`, `hook_event_name` (plus `agent_id`/
`agent_type` inside a subagent, plus `reason` on SessionEnd) and **no pid field of any kind**.
`$PPID` is therefore the only cheap source and it is the right one — simpler than the walk and
equally correct, with no `ps` fork on a path that has ~20 ms of headroom (§10).
- **Residual risk, and how it is closed without a fork.** If a future version interposes a
  wrapper between claude and the hook shell, `$PPID` names a process that exits immediately —
  a false reap, exactly what §0 forbids. So the probe requires **two independent signals of
  death**: reap only when `not is_alive(pid)` **and** the session's own transcript
  (`<transcripts_dir>/<session_id>.jsonl` — the file role resolution already reads) has an mtime
  older than **30 minutes**. A live, working session survives a mis-detected pid; the cost is one
  `stat`, consulted only once the pid already looks dead.
- No usable pid (`--session-pid` absent or 0) → record `pid: null`, **never** reaped, shown as
  `unknown`.

**D. The seam, pinned.** Where qa's committed names differ from my ruling's, **mine yield** —
these are the names to build and test against:
- CLI: `--ensure-running --session-id ID --session-pid PID`; `--session-ended [ID]`;
  `--grace-period-seconds N` (default 10). §4's `--grace` is withdrawn.
- **Both ids are optional**: absent → read `session_id` from the hook's stdin JSON, and only when
  stdin is not a TTY. Never block on stdin.
- Pure functions exactly as the test module declares — `_sessions_dir(pidfile)` =
  `pidfile.parent / ".sessions"`, `register_session`, `deregister_session`,
  `reap_dead_sessions(sessions_dir, is_alive=_pid_is_alive)`, `live_session_ids`.
- **No clock seam.** Tests pass a short `--grace-period-seconds`; the real timer stays real.
- `--status`: `sessions: N`, then one sorted line per recorded id,
  `session <id>: alive|dead|unknown`. `unknown` is the third state §7 requires for a null pid.
  Exit code unchanged (0 running / 1 not).
- Hook lines: SessionStart gains `--session-pid "$PPID"`, stdin left connected for the id;
  SessionEnd mirrors SessionStart's shape — guard on the script existing, exit 0, no stderr
  redirect.
- **`.gitignore` must gain `process/cairn/metrics/.sessions/`**, beside the existing `.lock`
  entry. The registry is runtime state; committing a session file is a defect. No acceptance
  criterion covers this — it will not fail a test, so it has to be remembered.

**Everything else stands:** §3's probe cadence, §5's shutdown ordering (socket → flush →
compare-and-delete pidfile, plus the fix to today's unconditional `pidfile.unlink()` in
`_on_shutdown` and `serve`'s `finally`), §8's PT-87 non-foreclosure (role resolved at flush time,
never at registration), §9's SessionEnd measurement, §10's cost budget. **§6 relaxes in one
direction:** because the directory survives a receiver crash, an **inherited non-empty registry
is authoritative** and may legitimately drain to empty and stop; the "never been non-empty" rule
now protects only a receiver started with no session id at all.

### @architect — 2026-09-04

**Delta 6 (new, found from team-lead's §9 aside — an upgrade hazard, not a code defect).**
Team-lead noticed while setting up §9 that the receiver running from before this change had to be
restarted, because a nudge would have killed it. That generalises past their machine and is worth
closing before merge.

Verified by construction: the pre-PT-86 `serve()` (743ae87) installs handlers for **SIGUSR1,
SIGTERM and SIGINT only** — no SIGUSR2 — and a Python process with no SIGUSR2 handler is
terminated by it (measured: exit `-31`). So **any receiver started before this change and still
running when it lands is killed by the first `--session-ended`**, with no handler, therefore no
final flush: every token count accrued since its last flush is lost. Flushes are export-driven,
so "since its last flush" can exceed the 30-minute interval.

Blast radius is one-time per machine, but it is not confined to this repo — every downstream
project that adopted PT-78/PT-81 and later pulls PT-86 hits the same window, and none of them
will read this PR.

Three options, in ascending cost:
1. **Release note only.** After pulling, run `python3 scripts/cairn/otel_receiver.py --stop` once
   before the next SessionEnd — SIGTERM still reaches the old handler, which flushes cleanly.
   Cheapest, and invisible to anyone who doesn't read it.
2. **A capability marker (~6 lines, permanent).** The new daemon writes a marker beside its
   pidfile at startup; `_nudge_daemon` sends SIGUSR2 only when the marker is present, and
   otherwise stays silent (the watchdog's own tick still does the work, at up to 0.25 s latency).
   This makes the nudge self-gating for every future signal-protocol change, not just this one.
3. Nudge with SIGUSR1 instead — an old daemon would merely flush. Rejected: it turns every
   SessionEnd into a full flush, changing write cadence and adding a data-file line per session
   end. Worse than the problem.

**Recommendation: 2, plus 1 in the PR body.** The marker is small and it closes the class rather
than this instance; the note covers receivers already running right now, which no code change can
reach. Team-lead's call — this is a judgment about how much we owe downstream adopters, not a
correctness question.
