## Picks — repo icon + section width rule

### 1. Repo-header icon: `FolderGit2`

Over `Box`/`Package`: this icon specifically represents *which git repo you're looking at* — `FolderGit2`'s folder-plus-branch glyph says that precisely, where `Box`/`Package` are generic "container" metaphors that don't actually evoke "repository." It's also the more distinct silhouette next to the rail's other two icons: `LayoutDashboard` (grid of squares) and `Kanban` (column bars) below it — a folder outline reads as a clearly different shape class from either, avoiding the rail turning into three flavors of "boxes."

Treatment: same menu-item pattern as the nav items below it — icon left of the repo name when expanded, icon-only (no tooltip needed beyond whatever the sidebar already does for nav items) when collapsed. If a legibility pass at actual rail size finds `FolderGit2`'s branch glyph too fine/busy that small, fall back to `Box` — flagging that contingency now so it's a quick swap, not a redesign, if it comes up.

### 2. Section width: confirmed — all sections adopt the Board preview card's width, no exceptions

Every dashboard-home section's outer container (status cards, tracker table, flow chart, agents section, Board preview) unifies to the Board card's current max-width — it's the widest existing section, so it sets the standard rather than the Board card shrinking to match its narrower siblings.

**One clarification, not an exception:** this governs container width only. A section that's internally a row of multiple items (e.g., the status-cards strip) keeps its own internal grid/flex layout and simply spans the unified container width — more even spacing between the existing cards, not one stat card stretched edge-to-edge. Single-widget sections (tracker table, flow chart, agents, Board preview) each become one full-width card at the unified width, consistent with this doc's existing cards-on-muted dashboard canvas convention. No section should end up narrower than the unified width, and I don't see a case for a section that should stay intentionally narrower — confirming the straightforward unify-to-widest rule as stated.

### @architect — 2026-08-30

**Architect ruling — root-redirect mechanics (gating).** First server-side change in this arc; verified against `cairn.py`'s route block, `board.js`'s view selection, and `board-logic.js`'s `isEmbedMode`.

## 1. Status code — `302` plus `Cache-Control: no-store`

**The status code matters less than the cache header, and the cache header is not optional.** The redirect's predicate is *filesystem state that changes* — someone builds `dist/`, or deletes it. A `301`/`308` is permanent and browsers cache it hard: a user who loads `/` once while the dashboard is built would keep being redirected after `dist/` is removed, straight into a 503, and **the server can never correct it because the browser stops asking.** That is an unfixable-from-our-side failure mode for a local dev tool people will absolutely delete build output from.

So: `302`, and send `Cache-Control: no-store` with it, since some browsers and proxies cache `302` responses too. `307` buys nothing here (it only differs for non-GET; this route is GET-only).

## 2. Dist-presence check — `index.html` must exist, not just the directory

Reuse the existing check's *location* but not its *predicate*. `/dashboard` currently tests `dashboard_dir.is_dir()` and then serves `index.html` — fine there, because a missing `index.html` yields a straightforward 404 on the page you asked for.

For the redirect that predicate is too weak: a `dist/` directory that exists but is empty or partially cleaned would send the user away from a perfectly serviceable board and into a broken dashboard. **The redirect fires only when `(dashboard_dir / "index.html").is_file()`.**

Put it in **one shared helper** used by both `/` and `/dashboard` so the two can't drift — the failure mode of a redirect and its target disagreeing about whether the dashboard exists is a loop or a dead end, and it would only ever show up in the exact "half-built dist" state nobody tests by hand.

## 3. The embed carve-out is a recursion guard, not a convenience

State this in the code comment, because it will look like a nicety to a future reader: the shell iframes `/?embed=1`. If that request redirects, the iframe loads `/dashboard`, which renders the SPA, which mounts an iframe pointing at `/?embed=1`, which redirects… **This is the exact infinite-recursion bug `isEmbedMode` was created for in PT-55.**

Mirror `isEmbedMode`'s semantics **exactly** — key `embed` present with value `"1"`, position in the query string irrelevant, other params (`readonly`, `open`) ignored. A subtle mismatch between the JS and Python readings of the same param is a recursion, not a cosmetic bug. **This needs its own named test**, not incidental coverage: assert `/?embed=1` returns 200 with board HTML, and that it does so with the params in both orders and alongside `readonly=1`/`open=<id>`.

## 4. Query strings are not forwarded

Redirect to bare `/dashboard`. Nothing currently needs to survive the hop — PT-72's deep link is `/dashboard/issues?issue=<id>`, which never transits `/`. Any future param that must survive gets added deliberately, with a reason.

## 5. `/list` stays — agreed — but it exposes a trap that needs a decision

Agreed that `/list` should not redirect: it's a view deep-link, and with `dist/` present users arrive through the shell anyway.

**The trap:** `board.html`'s Kanban tab is `<a href="/">`, and `board.js` only rewrites those hrefs **when embedded** (`if (isEmbedMode)`). So a user on the standalone `/list`, with `dist/` present, clicks "Kanban" and gets bounced out of the board into the dashboard. The standalone kanban view becomes **unreachable whenever the dashboard is built** — a documented surface silently disappearing as a side effect of a redirect.

**Ruling: add `/board` as a never-redirecting alias serving `board.html`**, and point the Kanban tab at it. Cost is about two lines in the route block and one href in `board.html`. It needs **no JS change at all** — `board.js` selects its view with `pathname === "/list"`, so any other path already renders kanban. It also gives the standalone board a stable address of its own, which the spin-off constraint wants regardless.

If PT-73 must stay minimal, the alternative is to accept that standalone kanban is reachable only when `dist/` is absent — **but that has to be a recorded decision, not an unnoticed consequence.** I'd spend the two lines.

## 6. SPA-fallback interaction — none, but one thing to preserve

No conflict: `/` is matched before the `/dashboard/` prefix branch, and PT-54 §4's suffixless-fallback rule is untouched. The one invariant to keep is that **the redirect target must not itself be able to redirect** — `/dashboard` serves `index.html` or 503s, and must never gain a redirect of its own, or the shared helper in §2 becomes a loop.

**Test the `dist`-absent path explicitly.** It's the "fresh clone, no Node" case that is the entire reason the carve-out exists, and it is the state no one has locally after the first build.
