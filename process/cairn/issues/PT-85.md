## Problem

The PT-61 "Issue flow over time" chart plots the count of issues in each status per day,
including archived issues while they were live. Its meaning is inconsistent across series: `done`
only ever grows (closed issues never leave it), while `backlog`, `todo`, `in-progress` and
`in-review` drain as issues move on. So the top of the stack reads as "79 done" on a day when four
issues closed, and nothing on the chart says how much work moved that day. The user read it as a
count of today's work and it is not; the caption that explains it is small print.

## Ruling (team-lead with the user, 2026-09-04)

Replace the status-stack with a **throughput view**. Cumulative status counts are not a
consistent measure; flow is.

1. Primary chart: per period (day by default, week toggle), bars for **issues closed** (done) and
   **issues opened** (created), on the same axis, so a day reads "4 closed, 4 opened".
2. A **WIP line** on the same chart: issues in `in-progress` + `in-review` at the end of each
   period. Point-in-time, and labelled as such.
3. **Milestone scope**: a control to scope the chart to one milestone (default: the milestone
   with the most recent activity) or all. Archived milestones selectable.
4. The status-stack area chart is **retired** (ruled 2026-09-05, architect §7 + team-lead): not
   kept behind a toggle — it is the artifact that produced the misreading, and a toggle preserves
   it for exactly the reader most likely to misread it again. Its PT-61 ordinal `--chart-flow-*`
   tokens are reused for the two bar series and the WIP line where they fit, else retired with the
   token guard adjusted (AC 5).
5. Same data source as today (`/api/flow`, git-reconstructed daily states); the server computes
   opened/closed deltas per period so the client stays pure. `cancelled` counts as neither
   opened nor closed for throughput; shown in the tooltip only.

## Acceptance criteria

1. `/api/flow` (or a sibling endpoint, architect's call) returns per-period opened, closed, WIP,
   and cancelled, per milestone and overall; memoized like the current payload. Derivation per the
   ruling (409d310): both series from the git walk's per-issue status map, never frontmatter
   `created:`; opened = first-ever appearance of a stem (a `seen_stems` set — an archive move is a
   delete-plus-add of the same stem and must not count); closed = a transition into `done`;
   cancelled = a transition into `cancelled`, tooltip only; WIP = `in-progress` + `in-review` at
   period end; milestone scope from the milestone recorded in the blob at that event; period
   boundaries on today's derivation — each event bucketed by its UTC calendar day
   (`astimezone(utc).date()`), deliberately unchanged so no history is re-dated — stated in TRACKER. The fixture history must
   include a bulk-archive commit, because an append-only fixture passes the broken version.
2. The dashboard block renders bars + WIP line with the day/week and milestone controls; caption
   names the period, the scope, and that WIP is end-of-period.
3. Drawer unaffected. Sidebar status cards unaffected.
4. Tests at the Python endpoint level (fixture history with opens, closes, cancels, a milestone
   boundary) and structural tests for the block; browser-visibility leg per the standing protocol.
5. `process/TRACKER.md` and the dashboard section of the design-system spec updated. PT-61's
   ordinal `--chart-flow-*` ramp is retired in BOTH `app.css` and `variants.css` (all ~23 theme
   variants × light/dark; ruled 586af1f + team-lead 2026-09-05 on the architect's measurement at
   0243718) — a deletion, not a rewrite; the ordinal-ramp guard `test_chart_variant_ramps.py`
   retires with it. The opened/closed/WIP series use base categorical palette entries (or local
   names aliasing them), never ramp steps; qa decides the categorical-distinguishability check
   that replaces the ramp guard.

### @architect — 2026-09-05

Gating ruling. **§1 and §2 are measured against `_compute_flow_payload`; §2 is the one that would
silently corrupt the numbers.**

**§1 The data is already there — no new git work, and opened/closed are exact, not inferred.**
Measured: the existing walk (`git log --reverse -M --raw` over `issues/` and `archive/issues/`)
maintains **`live: {stem -> status}`**, a real per-issue state map, and then discards it into
`{date, counts}` at each day boundary. So per-period throughput is derivable from the *same* walk:
- **opened** — the stem's **first-ever appearance** in the chronological walk;
- **closed** — a transition **into** `done` (previous status ≠ `done`, new status = `done`);
- **cancelled** — a transition into `cancelled`; counted as neither opened nor closed, tooltip only;
- **WIP** — count of stems whose **end-of-period** status is `in-progress` or `in-review`.

Derive **both series from the git walk**, never mixing in frontmatter `created:` for "opened". A
backdated `created:` would make opened and closed incomparable — and *that inconsistency of measure
is the entire defect PT-85 exists to remove.* Do not reintroduce it in the fix.

**§2 The archive-move trap — this is where a naive implementation inflates "opened".** The walk
keys on `Path(event["path"]).stem`, so `issues/PT-86.md` and `archive/issues/PT-86.md` are the
**same** stem. An archive move can surface as a delete plus an add, and "opened = appears in `live`
after being absent" would count that as a **new issue**. PT-84 measured a real bulk-archive commit
touching **seven** milestone files at once; the issue equivalent would spike "opened" by seven on a
day when nothing was opened at all.
**Required:** track a `seen_stems` set across the whole walk and count an open **only on a stem's
first-ever appearance**. Likewise `closed` must key on a *transition*, so an archived-and-re-added
stem that was already `done` is not re-counted. A deletion (`status_letter == "D"`) removes from
`live` but **must not** clear `seen_stems`.

**§3 Period boundaries: half-open `[start, next)`, and the day derivation is unchanged.** Today's
`day` comes from `%cI`, the committer date **with its local offset** — so days are local, not UTC.
Leave it. Re-dating existing history to UTC is invisible scope creep that would shift points on a
chart nobody asked us to change; **state the convention** in TRACKER instead. Week buckets group
those same local days, week start pinned explicitly (ISO Monday).

**§4 WIP is `in-progress` + `in-review` only**, measured at the **end** of each period, labelled
point-in-time in the caption. Not `todo`, not `backlog` — those are queue depth, not work in flight,
and folding them in would rebuild the same "cumulative counts read as activity" confusion in a new
shape.

**§5 Milestone scope comes from the same blobs.** The walk already parses each blob's frontmatter
for `status`; take `milestone` from that same parse — no extra git, no second pass. Scope by the
milestone **recorded in the blob at that event**, not the issue's current milestone: this is a
historical reconstruction, and using today's value would retroactively move past work between
milestones. Default scope: the milestone with the most recent activity, as ruled.

**§6 Extend `/api/flow`; do not add a sibling endpoint.** Same walk, same memoization keyed on HEAD,
one payload carrying per-period `opened`/`closed`/`wip`/`cancelled` **per milestone and overall**.
A second endpoint would double the git work and give two caches to invalidate on one commit.

**§7 The cumulative view is removed from the default, and I'd retire it rather than toggle it.**
Ruling §4 permits a toggle; if it stays, its caption must open with "cumulative counts, not
activity". My recommendation is removal: it is the artifact that produced the misreading, and a
toggle preserves it for the reader most likely to misread it again. Team-lead's call — say which in
the file.

**§8 Fixtures must be shaped like real tracker history** (the PT-84 lesson): a synthetic repo whose
issue files are **created, edited, moved to `archive/issues/`, and in one case deleted** — with at
least one **bulk archive commit touching several issues at once**, which is the §2 trap's natural
habitat. A fixture that only ever appends new files will pass a broken implementation.

**§9 Tokens (AC 5):** reuse PT-61's ordinal `--chart-flow-*` for the two bar series and the WIP
line if the count matches; if any are left unused, **retire them and adjust the token guard in the
same commit** — an unused ordinal token with a guard still asserting it is exactly the drift that
guard exists to catch.

### @architect — 2026-09-05

**Addendum — `/api/flow` payload shape, pinned. The proposal is accepted with three changes; one of
them prevents PT-85's own defect reappearing in the schema.**

```
{
  "period": "day",
  "series": [
    {"date": "YYYY-MM-DD",            # UTC day, half-open
     "opened": n, "closed": n, "cancelled": n, "wip": n,      # overall
     "by_milestone": {"<id>": {"opened": n, "closed": n, "cancelled": n, "wip": n}, ...}}
  ],
  "milestones": [{"id": "...", "name": "..."|null, "status": "..."|null}],
  "default_milestone": "<id>"|null,
  "as_of": "<head sha>", "scope": "...", "warning": "..."|absent
}
```

**Change 1 — `by_milestone` is DENSE once a milestone has first appeared**, not only on days it had
events. This is the important one. The record mixes **two different gap semantics**: `opened`/
`closed`/`cancelled` are deltas (a missing day means **zero**) while `wip` is point-in-time (a
missing day means **unchanged**). Leaving a sparse dict for the client to interpret would put two
incompatible meanings in one structure and make the reader carry the difference — **which is
precisely the defect PT-85 exists to remove, reproduced in the payload.** Emit every
already-seen milestone on every point, zeros for the deltas and the carried value for `wip`. Cost is
~14 ids × the existing point count; trivial. The **`series` itself stays sparse** (points only on
days with committed activity), unchanged from today.

**Change 2 — `by_milestone`, not `milestone`.** A singular key holding a map of ids reads as "the
milestone of this record", and sits one line from the top-level `milestones` list meaning something
else. Two adjacent fields differing by an `s` is a naming trap.

**Change 3 — define "activity" for `default_milestone` as a transition, never standing WIP:** the
milestone whose latest day carries a non-zero `opened`, `closed` or `cancelled`. Ties break toward
the later-created milestone. If WIP counted, a milestone abandoned with stale `in-progress` issues
would remain the default forever — the chart would open on the wrong scope indefinitely and look
correct.

**Accepted as proposed:** top-level four numbers are **overall**, counting every stem *including
those with no milestone at all*; `as_of`/`scope`/`warning` keep today's shape with `scope`'s text
rewritten for throughput; **`counts`/`STATUS_ORDER` dropped entirely** — verified, the only
consumers of `/api/flow` are `IssueFlowChart.svelte` (the component this ticket replaces) and its
tests, so nothing else reads them, and the reasoning is right: keeping dead cumulative fields is
§7's retirement undone in schema form.

**`period` and the week toggle.** The server emits **day granularity only**, with `period: "day"`
naming what it sent. The client aggregates for the week view: **sum `opened`/`closed`/`cancelled`,
and take the LAST `wip` of the week — never a sum or a mean.** Summing a point-in-time series is the
exact category error this ticket exists to fix; state it in the component so the next editor cannot
reach for `reduce` by reflex. Weeks start **ISO Monday** over UTC days.

**`milestones` list:** ids come from the **walk**, so archived and historical milestones appear and
the control can select them; `name`/`status` come from the current milestone records. **An id seen
in the walk with no current milestone file still appears, with `name: null`** — dropping it would
erase history from the control, which is the one thing this list exists to expose.

**Memoization key stays the HEAD sha.** The added inputs (milestone files for `name`/`status`) are
themselves in git, so HEAD already invalidates them by construction; no second key, no second cache.
