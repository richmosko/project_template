Mosko, 2026-09-02: *"The issues Card on the main dashboard page still has a line to add
new issues. This should be removed, with only the ability to add issues on the dedicated
cairn page."*

The user-visible symptom is one half of a wider defect. The new-issue form has **never been
closable on any surface** — `+ New` has been a no-op since it shipped — and the read-only
dashboard card inherits that permanently-open form because nothing in the read-only rule set
covers it.

## Defect record — measured 2026-09-02

**Browser (team-lead, `claude-in-chrome`):**

| Surface | `body.readonly` | `#new-issue-btn` computed | `#new-issue-form` `hidden` attr | `#new-issue-form` computed `display` | bounding height |
|---|---|---|---|---|---|
| `/dashboard` read-only card (`/?embed=1&readonly=1` iframe, PT-72) | `true` | `none` ✅ | `true` | **`flex`** ❌ | **27px** |
| `/board` standalone | `false` | rendered (`+ New`) | `true` | **`flex`** ❌ | **27px** |

**Source (architect, verified against `daaa074`):**

- `scripts/cairn/board/board.html:176` — `<div class="new-issue-form" id="new-issue-form" hidden>`
- `scripts/cairn/board/board.css:346` — `.new-issue-form { display: flex; … }`, with **no** `[hidden]` counter-rule anywhere in the file
- `scripts/cairn/board/board.js:2910-2925` — `+ New` does `form.hidden = !form.hidden`; the JS state has been toggling correctly the whole time and nothing has ever obeyed it
- `scripts/cairn/board/board.css:181-187` — the `body.readonly` hide list is `.filters, .view-tabs, #new-issue-btn, #expand-all-btn, #collapse-all-btn, .swimlane-toggle, .repo-group-toggle`. **`#new-issue-form` is absent.**

**Age:** the `.new-issue-form { display: flex }` rule and the markup's `hidden` attribute are both present at v0.6.0, v0.7.1, v0.8.0 and v0.9.0 with no `[hidden]` counter-rule until PT-69 added two element-specific ones for the theme menu. Shipped broken in at least four releases.

## Root cause — and a correction to the mechanism recorded in PT-69

`board.css:1110-1119` (PT-69) explains the same bug for `.theme-settings-menu` as a
**specificity tie** broken by source order: *"the `hidden` attribute and this class's own
`display: flex` above are the SAME specificity … so without this rule the browser's
UA-stylesheet `[hidden] { display: none }` LOSES the cascade tie to whichever rule loads later."*

**That model is wrong, and the corrected one matters for the fix.** Specificity and source
order are never consulted here. **Cascade origin is compared first**, and author-origin
declarations unconditionally outrank UA-origin declarations (CSS Cascade §6.1 — Origin and
Importance precedes Specificity and Order of Appearance). So an author `display: flex` beats
the UA `[hidden] { display: none }` **always** — regardless of specificity, and regardless of
which loads later. That is why this reproduces 100% of the time rather than intermittently, and
why "just put your rule after theirs" would not have helped.

The consequence for the fix: **raising specificity is not a general remedy.** A
`[hidden][hidden]` rule (0-2-0) would still lose to any future `#some-id { display: block }`
(1-0-0). Only an author-origin `!important` declaration is both origin- and
specificity-independent.

## Architect ruling — one generic reset, retiring the per-element fixes

**(a) Fix:** add a single rule near the top of `board.css`:

```css
[hidden] { display: none !important; }
```

and **delete** the two element-specific counter-rules it subsumes — `.theme-settings-menu[hidden]`
(`board.css:1120`) and `.theme-settings-row-flyout[hidden]` (`board.css:1171`) — **moving PT-69's
explanatory comment to the generic rule, corrected per the section above.** Do not delete the
explanation; it is the reason the rule exists.

**Why generic, over three more per-element rules:**

1. **It makes the bug class unrepresentable rather than fixing one instance.** The per-element
   approach requires every future author who adds a `display:` declaration to remember to pair it
   with a `[hidden]` rule. That invariant has already been forgotten once out of three
   opportunities, silently, for four releases.
2. **`!important` is warranted and its blast radius is provably nil.** The generic rule can only
   change rendering for an element that *currently* has an author `display` beating the UA rule —
   i.e. exactly the buggy ones. Every element carrying `hidden` today with no author `display`
   declaration (`#pull-indicator`, `#engine-stale-banner`, `#filter-repo`, the
   `.view-state-btn` pair) already resolves to `display: none`, and the two PT-69 elements already
   resolve to `display: none`. **The rule is behaviour-preserving everywhere except where it is
   the fix.** Verify this claim during implementation rather than taking it from here.
3. **There is no legitimate override.** `hidden` is HTML's "not relevant" semantic. Present-but-
   invisible is expressed in this codebase with `transform` / `visibility` (`.pull-indicator` does
   exactly that), never by keeping `display` alive under `hidden`.
4. **This overrides PT-69's stated `!important`-free preference, deliberately.** That preference
   was correct for PT-69's scope — one element, where specificity-raising was sufficient and
   local. It does not generalise: specificity-raising is neither sufficient (an id rule defeats
   it) nor self-maintaining (it must be re-remembered per element). Record the override in the
   comment so it doesn't read as drift.

**(b) Read-only surface carries no create affordance.** Add `#new-issue-form` to the
`body.readonly` hide list at `board.css:181-187`, alongside `#new-issue-btn`. Keep it even
though (a) makes it redundant while the attribute is set: the read-only rule is the *policy*
statement ("this surface has no create affordance"), and it must hold even if the toggle is
reached some other way.

**This is a gap in my own PT-72 ruling, not an implementation deviation.** That ruling's
"hidden in read-only" list was presented as complete and named the "create-issue button" without
naming the form the button toggles. The implementation matched the ruling; the ruling was short.

## Acceptance criteria

**Fix**

- [ ] `board.css` contains a single generic `[hidden] { display: none !important; }` rule.
- [ ] `.theme-settings-menu[hidden]` and `.theme-settings-row-flyout[hidden]` are removed, and
      PT-69's explanatory comment survives on the generic rule with the cascade-origin correction
      (not the "specificity tie broken by source order" model).

- [ ] No behaviour change to the theme settings menu or the row flyout: both still open on
      trigger and close on outside-click / Escape / re-trigger.

**Browser verification — the acceptance leg, not ceremony**

A property or attribute read is **not** evidence here: `hidden` was `true` on both surfaces the
entire time the user was looking at the form. Every check below is `getComputedStyle` +
`getBoundingClientRect` + `document.elementFromPoint` at the element's centre.

- [ ] `/board` standalone, before clicking `+ New`: `#new-issue-form` computed `display` is
      `none` and its bounding height is `0`.
- [ ] `/board` standalone, after clicking `+ New`: form is visible (`display` not `none`,
      height > 0, `elementFromPoint` at its centre resolves inside it).
- [ ] `/board` standalone, after clicking `+ New` twice: back to `display: none`, height `0`.
      **This is the assertion that has never passed.**
- [ ] `/dashboard` read-only card (inside the `/?embed=1&readonly=1` iframe): `#new-issue-form`
      computed `display` is `none` and height `0`, and no create affordance is reachable —
      `#new-issue-btn` also `none`.
- [ ] `/dashboard/issues` (the full board inside the shell, PT-72): behaves as the standalone
      `/board` — form closed on load, `+ New` toggles it. **Check this placement explicitly**;
      one sampled surface does not generalise across DOM placements.
- [ ] **Census, not sample:** for every element in `board.html` carrying the `hidden` attribute
      (`#pull-indicator`, `#engine-stale-banner`, `#theme-settings-menu`, `#filter-repo`,
      `#expand-all-btn`, `#collapse-all-btn`, `#new-issue-form`) plus any JS-created
      `.theme-settings-row-flyout`, assert computed `display === "none"` while `hidden` is set.
      This is the proof of ruling claim (2) — behaviour-preserving everywhere except the fix.

**Automated regression — what the harness can and cannot do**

The JS harness has **no jsdom and no `document`**, so the "assert the form is not *rendered*
before `+ New` is clicked" test cannot be written as computed style. This is a documented,
re-confirmed limit, not an omission — see `scripts/cairn/tests/js/embed-visibility-scope.test.js`
lines 3-9 ("impossible — no jsdom, no document, confirmed against 8 existing test files that
already document the same limit"). The browser leg above is therefore **load-bearing acceptance,
not ceremony.** What the harness *can* assert, and must:

- [ ] New test `scripts/cairn/tests/js/hidden-attribute-reset.test.js`, source-text guard in the
      same shape as `embed-visibility-scope.test.js`:
      (i) `board.css` declares a generic `[hidden]` rule whose `display` is `none` **and carries
      `!important`** — assert the `!important`, since dropping it silently reintroduces the bug
      for any id-based `display` rule;
      (ii) the `body.readonly` hide-list selector set is extracted and asserted to contain
      `#new-issue-form` **and** `#new-issue-btn`;
      (iii) no element-specific `X[hidden] { display: none }` rules remain (they are now dead
      weight and their return would signal the generic rule was lost);
      (iv) every extractor raises a **named `ExtractionError`** when its pattern matches nothing —
      never a silent empty list, never a vacuously-green pass. Same contract as PT-36 / PT-45.
- [ ] `scripts/cairn/tests/test_css_parse_sanity.py` stays green. **Do not re-invent it** — the
      PT-57 parse-level gate (stray comment-closer, brace balance, top-level rule-count floor)
      already covers `board.css`. Net rule count moves by −1 (two removed, one added), well clear
      of the `min_rules=50` floor.
- [ ] Full gate green: `( cd scripts/cairn && python3 -m unittest discover -s tests )` and
      `node --test scripts/cairn/tests/js/*.test.js`.
