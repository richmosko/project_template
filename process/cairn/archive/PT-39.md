## Problem

Three related gaps (Mosko, 2026-08-23):
1. No first-class way to mark a Milestone or Major "Done" — today the lead hand-edits `status: completed` in the file on a branch.
2. Status vocabulary is split: issues use `done`, milestones/majors use `completed`. Should unify on the issue cycle's `done`.
3. No archive mechanism for done Milestones/Majors — `cairn archive` covers issues only; completed milestone/major files accumulate in the live directories forever.

## Acceptance criteria

- [ ] Architect design ruling first: status-value migration (completed→done — a named `cairn migrate` per the PT-28 precedent, incl. check_repo lint update and downstream-repo posture), CLI surface (`cairn set` on milestones/majors? a dedicated command?), archive semantics (what happens to issues referencing an archived milestone — dangling-ref lint interaction)
- [ ] Marking done is one command; lint accepts only the unified vocabulary
- [ ] `cairn archive` (or sibling) moves done milestones/majors with referential integrity preserved
- [ ] This repo's own live data migrated in the same PR (`cairn migrate lifecycle-status` run against process/cairn/ — 1 major + 8 milestones carry old vocabulary); `cairn check` green at HEAD when the PR merges
- [ ] Skill write-paths emit the new vocabulary (setup-tracker:57, merge-pr:45, merge-pr:61 — temp/2026-08-23-architect-skill-write-path-drift.md §B)

# PT-39 ruling — milestone/major lifecycle

## 1. Unified status vocabulary

**One enum for milestones AND majors:**

```
planned | in-progress | paused | done | cancelled
```

- `completed` → `done`, `active` → `in-progress`. `in-progress` (not `active`) because PT-39's
  ask is to unify on the *issue* cycle's vocabulary, and the issue cycle's working state is
  `in-progress`. Two records that mean "being worked on" must not spell it two ways.
- `paused` is kept (documented for milestones today, unused in data) and extended to majors —
  one enum for both, not two that overlap by four values out of five.
- Issue `STATUSES` is untouched. Milestones have no `in-review`; majors have no `backlog`.
  Constants: `RECORD_STATUSES` (new, cairn.py), separate from `STATUSES`.

**Data reality check (measured, this repo @ HEAD):** 7 milestones `completed`, 1 milestone
`active`, 1 major `active`. `active` on a milestone is not even in TRACKER.md's documented
milestone enum today — nothing lints milestone/major `status:` at all, which is how it drifted.

## 2. Named migration

`cairn migrate lifecycle-status [--dry-run]` — PT-28 precedent verbatim:

- Rewrites `status:` in `majors/*.md` and `milestones/*.md` only. `completed`→`done`,
  `active`→`in-progress`. Any other value untouched (lint reports it).
- Value-keyed ⇒ idempotent by construction; no filename/id work, so no crash-recovery phase.
- Frontmatter-only rewrite via the existing `dump_frontmatter` + byte-identical body path.
  `apply_patch`/`dump_frontmatter` are already schema-aware (PT-13: non-issue-shaped dicts keep
  their own key order and never get `updated` injected) — **do not add a second writer.**
- Does **not** gate on `cairn check` (same reason as `prefix-ids`: it exists to fix a failing lint).
- Exit 0 for any completed run; residual unrelated lint errors are reported, not this command's failure.

## 3. Lint (`check_repo`)

New errors:

1. Milestone/major `status:` missing or not in `RECORD_STATUSES`. When the value is `completed`
   or `active`, append the migration hint (`_migrate_hint_if_bare`'s pattern — a named helper,
   not a re-typed string at each site).
2. An issue in `archive/` whose `milestone:` is non-null and resolves to a milestone that is not
   `done`/`cancelled`. See §5 — this is what makes PT-43's counting invariant structural.
3. `known_milestones` / `known_majors` resolve against the archive subdirs too (§4), or archiving
   a milestone would dangle every issue that references it.

**Downstream posture: BREAKING, lint-only** — identical to PT-28. An unmigrated repo's board and
CLI keep working; only `cairn check` fails, with the one-command fix in the error string. Board
renders an unknown status via a label fallback (PT-37's pattern), never `undefined`. Needs a
**BREAKING** note in the STATE.md release row.

## 4. Archive layout for milestones/majors

```
archive/PT-14.md              issues        (unchanged — do NOT move these)
archive/milestones/PT-0.4.md  NEW
archive/majors/PT-V0.md       NEW
```

Subdirectories, not a flat archive: `check_repo` and `build_board_payload` iterate
`issues/` + `archive/` expecting the *issue* schema, and `_dir_glob` is non-recursive
(`d.glob("*.md")`) — so the two new dirs are invisible to every existing glob. Additive, zero
migration for existing archived issues. Judgment call: the asymmetry (loose issue files beside
two typed subdirs) is accepted over a rename migration that buys only tidiness.

Also add `"archive/milestones"`, `"archive/majors"` to `_WATCHED_SUBDIRS` (else SSE misses them).

## 5. `cairn archive` — new preconditions and selectors

Exactly one selector, required, mutually exclusive. All three accept `--dry-run` (new; `archive`
moves files in bulk and had no preview).

| Invocation | Moves | Refuses / skips |
|---|---|---|
| `--done-before YYYY-MM-DD` (existing) | done/cancelled issues older than the date | **NEW:** skips (prints reason, does not error) any issue whose milestone is not `done`/`cancelled` |
| `--milestone <id>` (new) | that milestone's done/cancelled issues (no date filter) **then** the milestone file | refuses if the milestone's own status isn't `done`/`cancelled`, or any of its issues is neither |
| `--major <id>` (new) | that major's milestones (each per the row above) **then** the major file | refuses if the major isn't `done`/`cancelled`, or any milestone fails its own precondition |

**The precondition is the load-bearing part.** "Archive never sweeps issues out from under a
live milestone" is what lets the board compute an honest `n/m` from `issues/` alone with zero
archive reads (see the PT-40/43/44 ruling §3). It converts PT-43's mixed case from a number to
compute into a state that cannot arise — and lint rule §3.2 catches the hand-`git mv` bypass.

Verified against this repo @ HEAD: every archived issue belongs to a `completed` milestone
(PT-0.4/0.5/0.5.1/0.6/0.6.1), so the new lint passes here on day one — no grandfathering needed.

## 6. Mark-done CLI surface

**Extend `cairn set`. No new verb.**

```
cairn set PT-0.7.0 status=done
cairn set PT-V1 status=done target_ship=2026-12-01
```

- New `find_record_path(data_dir, id)` resolving `issues/` → `archive/` → `milestones/` →
  `archive/milestones/` → `majors/` → `archive/majors/`. `find_issue_path` stays exactly as it is
  and stays the only thing the HTTP write path can reach (the PT-3 read-only guarantee is
  structural — do not widen it).
- Field-name validation becomes per-schema: `ISSUE_FIELD_ORDER` / `MILESTONE_FIELD_ORDER` /
  `MAJOR_FIELD_ORDER`, selected by which directory the id resolved in.
- `status=` validates against `STATUSES` for issues, `RECORD_STATUSES` for milestones/majors.
- `cairn ls` / `cairn show` on a milestone or major id: **out of scope for PT-39.** File the
  follow-up rather than growing this issue.

Rejected: a dedicated `cairn done <id>` — a second write path for a strict subset of what `set`
already does, and the frontmatter rewriter being subtly different in two places is the exact
hazard the single-writer rule exists to prevent.

**Not editable from the board in 0.7.0** — see the PT-40/43/44 ruling §5.

## 7. Spec edit: drop the MINOR-only milestone-id preference (team-lead ruling, 2026-08-23)

TRACKER.md currently says *"Prefer version-named ids for anything that tags… that is what keeps
milestone ↔ `MAJOR.MINOR` 1:1"*, while shipped reality has `PT-0.5.1`, `PT-0.6.1`, `PT-0.6.2` and
`PT-0.7.0` — patch-granularity milestones that each tagged a real release. **Ruled: the preference
goes; a development milestone's id may sit at any release granularity, and its `target_tag` names
the tag it cuts.**

**Doc-only; no regex change and no migration** — the lint already accepts both shapes
(`^<P>-(?:M\d+[a-z]?|\d+\.\d+(?:\.\d+)?)$`).

**⚠ Blast radius is larger than one sentence — read this before editing.** Grepping `MINOR`
across both files turns up a connected doctrine, not a stray claim (`TRACKER.md:177,288`;
`WORKFLOW.md:568,582,587,589`). Two of those sites are load-bearing:

- **`WORKFLOW.md:582` binds PATCH to *Hotfix* — "`issues/<ID>.md` on the milestone it patches."**
  That says a patch release is issues on the *existing* milestone, **not** a new milestone file.
  Shipped reality is the opposite: `PT-0.5.1`, `PT-0.6.1`, `PT-0.6.2` are standalone milestone
  files with their own `target_tag`. **This row is what actually has to change**, and it is the
  substance of the lead's ruling — not the id shape, which was only the symptom.
- **`WORKFLOW.md:589` "One milestone per MINOR (Model A)"** is a *named* decision. It survives:
  Model A forbids splitting the **run-up** to `N.0.0` across several milestones (use pre-release
  tags instead), and a *post-release patch* milestone doesn't do that. Only its closing clause
  ("keeps the 1:1 milestone↔version mapping intact") is falsified.

**The reformulation that keeps everything Model A protects:**

> **milestone ↔ `target_tag` is 1:1** — not milestone ↔ `MAJOR.MINOR`. A feature milestone moves
> the MINOR digit; a patch milestone moves PATCH. No two milestones claim one tag, and a single
> release's run-up is still a single milestone.
