### @architect — 2026-08-30

**Architect ruling — unified shell: routing, embed variant, read-only semantics (gating).** Verified against `App.svelte`, `board.js`, `board-logic.js`, `board.css`, `board.html`, and `cairn.py`'s dashboard routes. Drafted with ux-designer, whose shell UX spec is the paired artifact.

## 1. Routing — path-based `/dashboard/issues`, minimal soft nav, no router dependency

**No server change is required.** PT-54 §4 already built the SPA fallback: `/dashboard/<rel>` serves a real file when one exists, falls back to `index.html` for any **suffixless** path, and 404s a suffixed miss. `/dashboard/issues` therefore serves the SPA today, unmodified. Reject hash routing — its only advantage is avoiding a server change we don't need, and it makes the path logic worse.

**Navigation is soft, via ~15 lines, not a router library:** intercept sidebar anchor clicks, `history.pushState`, hold the route in a `$state` variable, listen for `popstate`. The anchors remain real `<a href>` values, so a hard load of `/dashboard/issues` still works through the fallback above — deep links, bookmarks and no-JS all function, with soft nav as pure enhancement.

**This revises my own first draft**, which specified full-page-load navigation on the strength of PT-61's no-router convention. ux-designer's spec requires shell chrome to persist across route changes with no remount or flash, and a full load cannot deliver that: it repaints, re-fetches `/api/dashboard`, and re-renders the sidebar every time. PT-61 chose no-router for *two links with no shared-chrome persistence requirement*; PT-72 introduces that requirement, so the conclusion changes with the premise. Recorded plainly rather than defended.

Resulting behaviour: chrome mounts once and never remounts; the board iframe mounts on navigating **to** Issue Tracking and unmounts on leaving, so its content loads on arrival while the chrome around it does not.

## 2. Embed variant — `readonly=1` as a flag orthogonal to `embed=1`

`?embed=1` keeps its exact current meaning (chrome suppressed, full edit). Add **`&readonly=1`** as an independent flag. *Is the chrome suppressed* and *is mutation allowed* are orthogonal questions; collapsing them into one param's value space permanently forecloses chromeless+editable and chrome+read-only, and would disturb the existing `embed=1` tests and the `withEmbedParam` recursion guard for no gain.

- Issue Tracking page (`/dashboard/issues`) → iframes `/?embed=1` — existing behaviour, full edit, **full height** (not the home card's `h-[70vh]`).
- Dashboard home preview → `/?embed=1&readonly=1`.

Note `isEmbedMode` is `CairnLogic.isEmbedMode(search) || window.self !== window.top` — iframe-ness is detected independently of the param, so embed suppression holds even if a src ever loses `embed=1`.

## 3. Read-only — suppression at a single point, never a second code path

**PT-55 explicitly rejected a read-only mode**, on the grounds that it "would mean forking new state into board.js to deliver LESS." That reasoning was correct and its *premise* has changed: there was one board surface, so weakening it was pure loss; there are now two, so the split is division of labour. **The objection still binds the implementation.** One flag read once in `init()` → adds a `body.readonly` class and skips handler attachment. No branching inside render functions, no parallel state machine. If it starts growing conditionals in rendering, that is the failure PT-55 predicted and the design is wrong.

**Hidden in read-only** (ux-designer's enumeration, complete): wordmark/masthead and the board's own Dashboard tab (already via `embed=1`); filter row; Kanban/List view tabs; create-issue button; drag affordances (do not attach `dragstart`/`drop`, and set `draggable=false`); per-column add buttons; `#expand-all-btn` / `#collapse-all-btn`; per-lane `.swimlane-toggle` and `.repo-group-toggle`.

**Kept:** column headers with titles and counts; cards (click-through only); the connection-state indicator (informational, not a control).

**Lane state:** read-only **ignores `cairn.board.expandedLanes` entirely and always renders fully expanded.** No new storage key. Rationale: that key is persisted and origin-shared, so without this a user who collapses lanes on the workspace page returns to a near-empty preview with no affordance to fix it and no visible cause — a bug that only ever presents as "confusing", never as an error. Ignoring an existing read is another suppression, in the same class as the rest of this list; a second key would be new state to maintain. The preview sits in a fixed-height panel that scrolls internally, which it needed as an ordinary dashboard widget regardless.

Because the toggles are hidden and their handlers unattached, no write path to that key exists in read-only.

## 4. Card click — navigate the shell, deep-linked, via two distinct params

Clicking a card in the read-only preview navigates the **shell** to the full Issue Tracking page with that issue's drawer already open. Not an inline edit, not a read-only modal — the latter is precisely the second detail-view implementation PT-55 rejected read-only over.

**Mechanism: `window.top.location`, not postMessage.** Same-origin (the board already depends on that for shared `localStorage`), so a message protocol and listener buy nothing. Free property: standalone, `window.top === window`, so the same code path navigates the current window correctly with no branching.

**Two params in two layers — do not conflate them.** The shell URL is `/dashboard/issues?issue=PT-42` (user-visible, bookmarkable). The iframe `src` is separately `/?embed=1&open=PT-42`, derived by the shell from its own query. The board can only read its own URL, so the shell must pass it down. Implemented as a single param, the bookmark case breaks.

**This is real `board.js` work, not shell wiring** — reading `open=<id>` on load and opening that drawer is a new board capability. Small and clean, but it must be costed, not assumed free.

A plain "View full board" link (no specific issue) stays as the non-card escape hatch, per ux-designer's spec: discovery should not depend on users guessing that cards are click-through.

## 5. Standalone board survives — mandatory

`/` and `/list` keep working exactly as today, no params, each retaining its own theme-settings trigger. Three independent reasons, any one sufficient: the spin-off constraint (the board must not depend on the dashboard — the direction PT-63 ruled on for fonts); the dashboard is a **build artifact** while the board is zero-build, so a fresh clone with no `dist/` would otherwise have no working UI at all (the server already 503s that case); and `/list` has no proposed shell equivalent.

**Consequence:** the embed-conditional trigger suppression in `wireThemeSettings()` must stay **conditional**. It cannot simplify to "the board never renders its own trigger", which would break the standalone surface.

## 6. Nav rename

Sidebar "Board" (`/`, which currently navigates *out* of the shell — Mosko's actual complaint) becomes **"Issue Tracking"** (`/dashboard/issues`). Label confirmed by ux-designer; the collapsed rail is icon-only with a hover tooltip, so label length is constrained only by the expanded sidebar's single-line width, which 14 characters clears.

## 7. Noted, not ruled

- **Pre-JS trigger flash (minor, PT-70-adjacent).** The trigger is static markup in `board.html` removed by JS in `wireThemeSettings()`, and `board.js` loads at the end of `<body>`, so it can paint before removal. A `body.embed` CSS rule **cannot** close this — `body.embed` is itself applied by JS at the same moment as the removal. The only mechanism that works is head-time class assignment, for which `board.html` already has an inline `<head>` script (PT-69's theme bootstrap); the CSS would key on `:root.embed`. Sub-100ms, one button, local-only tool — not worth a standalone issue. The cheap moment is while PT-70 is already restructuring that early-return path, or never.
- **PT-30's view state and PT-69's theme key are both origin-shared**, so the iframe inherits the shell's theme with no plumbing. That is PT-69's origin-global scoping decision paying off as intended.

### @ux-designer — 2026-08-30

## UX spec — unified shell, Issue Tracking page, read-only home preview (consolidated)

Paired with architect's ruling above; this is the settled UX spec, not a chronological record — full back-and-forth is in the message thread if provenance is ever needed.

### Persistent chrome
Sidebar + Header (page title, Refresh, theme-settings trigger top-right) mount once and persist across navigation between Dashboard and Issue Tracking — soft nav swaps only the content area. The board iframe mounts on arrival at `/dashboard/issues` and unmounts on leaving; the chrome around it never remounts or flashes.

### Issue Tracking page (`/dashboard/issues`) — full board
- Iframes `/?embed=1`, **full height** (not the home card's capped height).
- Full board functionality, unchanged: drag/drop, create/filter bar, Kanban/List tabs, card click opens the real editable drawer, connection-state indicator.
- No own theme-settings trigger on this route — the shell header's trigger is the only one (existing embed-conditional suppression in `wireThemeSettings()` already covers it, confirmed working).
- No wordmark/masthead to retire — `board.html`'s "cairn" wordmark is already suppressed under `embed=1`, and the board never carried a repo-name display in the first place (PT-68 touched only the dashboard sidebar). Nothing further needed here.

### Dashboard-home preview (`/?embed=1&readonly=1`)
**Hidden:** filter row; Kanban/List view tabs (fixed to Kanban — a glance surface is one fixed presentation, not a switchable workspace); create-issue button; drag affordances (no `dragstart`/`drop` handlers, `draggable=false`); per-column add buttons; `#expand-all-btn`/`#collapse-all-btn`; per-lane `.swimlane-toggle`/`.repo-group-toggle`; wordmark/masthead + the board's own Dashboard tab (already covered by `embed=1`).

**Kept:** column headers with titles + counts; cards (click-through only); the connection-state indicator (informational, not a control).

**Lane state:** ignores `cairn.board.expandedLanes` entirely — always renders fully expanded. A glance surface should look identical on every visit regardless of what got collapsed on the workspace page; the alternative (reading the shared, origin-persisted collapse state) creates a stuck-looking-empty preview with no visible cause and no on-screen affordance to fix it, since the toggles that would fix it are hidden here. No new storage key — this is one more suppression, same class as the rest of the list. The panel is fixed-height with internal scroll regardless of lane count — ordinary containment for one section among several on a busy dashboard home, not new complexity this decision forced.

**Card click:** navigates the shell (`window.top.location`, same-origin) to `/dashboard/issues?issue=<id>`, which derives `/?embed=1&open=<id>` for the iframe `src` — that issue's drawer opens automatically on arrival at the full page. Not an inline edit, not a read-only modal in place — avoids a second detail-view implementation, the exact thing PT-55 rejected read-only over.

**Discovery:** an explicit "View full board" link/button at the top of the section, independent of card-click — the standing lesson from the Sidebar.Footer placement miss is not to rely on users guessing that cards are click-through.

### Nav rename
**"Issue Tracking"** at `/dashboard/issues`, confirmed as Mosko proposed. Label length is bound only by the expanded sidebar's single-line width (14 characters, comfortably next to "Dashboard"'s 9) — the collapsed rail is icon-only with a hover tooltip, so rail width was never actually the constraint the original ask named. Icons (PT-71, ruled separately): Dashboard = `LayoutDashboard`, Issue Tracking = `Kanban`.

### Standalone board — unaffected
`/` and `/list` are unchanged: no params, full chrome, own theme-settings trigger. This is the zero-build fallback and must not depend on the dashboard shell existing.
