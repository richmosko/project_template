# PT-38 ruling — `board.columns`

## 1. Config shape: ordered subset of the known statuses. Not new statuses.

```yaml
board:
  columns: [todo, in-progress, in-review, done]   # order + subset, nothing else
```

- Every entry must be a member of `STATUSES` **minus `cancelled`**. A custom vocabulary is
  explicitly out: TRACKER.md rules status vocabulary non-configurable in v1 because the skills
  hard-code the transitions, and `board.js:1182` uses `Object.keys(STATUS_LABELS)` as the issue
  drawer's status `<select>` options — a project-defined status would be renderable but not
  settable. PT-38's promise is *column customization*, and that is what this delivers.
- `cancelled` is **rejected** with a pointed error: it is owned by the Show-cancelled toggle
  (PT-35). Two mechanisms producing one column is the drift class, not a feature.
- Duplicates rejected. Empty list rejected. Non-list / non-string entries rejected.
- An issue whose status is not a configured column renders in no column and is not counted —
  no new rule needed, PT-31's "total is the sum of `byStatus`" already makes that honest. Say so
  in TRACKER.md: dropping `backlog` from `columns` *hides* backlog issues on the Kanban.

**`cairn snapshot` ignores `board.columns` entirely** — it always renders `STATUS_ORDER`. A
snapshot silently missing a project's hidden statuses is data loss in the artifact that exists
for offline reading. Board view ≠ canonical rendering.

## 2. Validation, and what happens when it fails

- **`cairn check`** errors on every violation above (same posture as `prefix:` — a lint that
  quietly stops linting is worse than no lint).
- **The server does not crash and does not refuse to start.** Invalid `board.columns` ⇒ fall back
  to `DEFAULT_COLUMNS` **and** print one line to stderr naming the offending value. The client
  renders no warning banner: `/api/board`'s `warnings` key exists but nothing in board.js consumes
  it today (verified), and wiring a first consumer is a separate piece of work, not a rider here.

## 3. Server → client plumbing

- `/api/board` gains one top-level key, `columns`: the **resolved** list (config or default,
  `cancelled` never present).
- **Multi-root: the primary root's config governs.** Secondary roots are read-only lenses; their
  `board.columns` is ignored. Stated in TRACKER.md → Multi-root.
- No conditional payload shape: `columns` is always present, single-root included (the PT-3
  precedent).

## 4. Client

`board-logic.js`:

```js
var BOARD_COLUMNS = ["backlog", "todo", "in-progress", "in-review", "done"];  // stays a LITERAL

function resolveColumns(configured)          // payload columns -> the active base list
function boardColumns(columns, showCancelled)  // columns.concat(["cancelled"]) or columns itself
```

- **`BOARD_COLUMNS` must stay a literal array declaration.** The PT-36 drift guard
  (`tests/test_column_parity.py`) extracts it from board-logic.js *as source text*; a dynamic
  construction silently defeats it.
- **Reference identity carries the byte-identical guarantee (PT-35 precedent, AC3).**
  `resolveColumns` returns `BOARD_COLUMNS` **itself** — the same array object — when `configured`
  is absent/null or element-wise equal to it; otherwise a fresh validated array. Pin with
  `strictEqual`, never `deepEqual` (a `deepEqual` passes for a well-meaning `.slice()` and
  degrades the guarantee from *identical* to *equal today*).
  Two cases must both return the identical object: (a) payload omits `columns` (older server —
  forward/backward compat, same posture as the SSE→poll fallback), (b) payload carries the default.
- `boardColumns` gains `columns` as a **required first argument, no default** — a missing argument
  throws (PT-35's JC1: loud-and-total over quiet-and-wrong; an undercount is exactly the defect
  PT-31 shipped a fix for). `activeColumns()` in board.js becomes
  `boardColumns(resolveColumns(state.board && state.board.columns), state.showCancelled)` and
  stays a **function**, never a render-scoped cached variable (PT-35 JC4).
- The client does **not** re-validate the list. The server is the one validator; the client renders
  what it is given, with PT-37's `STATUS_LABELS` fallback covering an unlabeled slug. One
  validator, not two that must agree.

## 5. Drift guards to add (PT-36 pattern)

1. Existing parity test extended: assert the JS `BOARD_COLUMNS` literal still equals
   `cairn.DEFAULT_COLUMNS` (unchanged), **and** that `cairn.DEFAULT_COLUMNS` is what
   `load_config` falls back to.
2. **New:** assert board.js's `STATUS_LABELS` key set ⊇ `cairn.STATUS_ORDER`. That is the
   cross-language contract PT-37 is currently patching around with a runtime fallback; with
   configurable columns it becomes load-bearing. Source-text extraction, Python suite, same
   fail-loudly extractor contract as PT-36 §3.3.

## 6. `board.swimlane` — in scope for PT-38 (team-lead ruling, 2026-08-23)

`board.swimlane: milestone | none` is documented in TRACKER.md, set by `load_config`, and **read
by nothing** — the identical defect that produced PT-38. Folded in here rather than left behind
as a second documented-but-unread key.

- Valid values: `milestone` | `none`. Anything else is a `cairn check` error; the server falls
  back to `milestone` + one stderr line — **the same posture as `board.columns` §2**, not a
  second convention.
- `/api/board` gains a top-level `swimlane` key, always present, primary root's config governs
  (§3's rules apply unchanged — one plumbing pattern for both keys).
- Client: `state.swimlanesOn` initialises to `payload.swimlane !== "none"` instead of the
  hardcoded `true` at board.js:118. Absent key (older server) ⇒ `true`, preserving today's default.
- **No localStorage precedence problem to resolve:** verified — PT-30 persists `expandedLanes`
  only; `swimlanesOn` has never been persisted. Config sets the initial value, the checkbox
  overrides it for the session, nothing is written to storage. Do not add persistence here.
- The Swimlanes checkbox stays fully functional under `swimlane: none` — this is a *default*, not
  a lock. A config key that disabled a visible control would need a disabled-state UI story that
  nothing here asks for.
- List view is unaffected (`swimlanesOn` is Kanban-only today; `expandAllBtn.hidden` etc. already
  branch on `isListView`).
