## Problem

Two board gaps (Mosko, 2026-08-23):
1. Milestone and Major records are non-viewable from the dashboard — lane headers and the progress strip name them, but nothing opens their card/body (no drawer equivalent; the DoD text, target_tag, ga flag are file-only).
2. No Milestone/Major STATUS indicator on the Kanban view — a lane header doesn't show whether its milestone is active or done.

- [ ] Clicking a milestone lane header (and a major tab) opens a viewable card with the file's body + fields
- [ ] Kanban lane headers carry a status indicator for their milestone; majors' indicator surfaced on their tabs
- [ ] Depends on/aligns with PT-39's unified status vocabulary if both land in one release

# PT-40 + PT-43 + PT-44 ruling — the milestone surface

The three issues describe one thing: **the milestone's own lane header is its identity strip, and
its card is its record.** The top progress strip goes away.

## 1. Record data reaches the client on `/api/board`. No new endpoint.

`build_board_payload` switches milestones and majors from `_read_frontmatter_dict` to
`parse_frontmatter`, adding **`body`** (the markdown after the closing fence) to each record.

- Cost: one paragraph per record; ~8 records here, ~30 KB even at 100 milestones. Nothing
  measurable.
- Buys: no second fetch, no second read path, and the card is live via the existing ETag/SSE
  machinery (the watcher already watches `majors/` and `milestones/`).
- Rejected: `GET /api/milestone/<id>` — a second read endpoint for data already in the payload.

## 2. Lane header = the retired strip's content, in its own place

Today's strip renders, per milestone: `id · name · [GA] · [target_tag] · n/m done`.
The lane header gains, left to right:

```
▼  PT-0.6.2 · board follow-ups   [Done]   3/3   [v0.6.2 released]   (count)  (collapsed chips)
   └ disclosure   └ label(existing)  └ status  └ progress  └ release state
```

- **Status indicator** (PT-40): a pill using a **new `RECORD_STATUS_LABELS` map**, with a raw-slug
  fallback. **Do not fold these into `STATUS_LABELS`** — `Object.keys(STATUS_LABELS)` is
  load-bearing as the issue drawer's status `<select>` option list (board.js:1182); adding
  `planned`/`paused` would offer invalid issue statuses. Say so in the code comment.
- **GA** moves from the `· GA` suffix to a chip.
- **Clicking the label opens the milestone card** (§5).

### Zero information loss requires lanes for milestones with no live issues

Lanes are built from `groupByMilestone(issues)` — a milestone with no live issues has **no lane**
(PT-0.3 and PT-0.4 today, entirely archived). Retiring the strip without fixing this loses them
outright, which fails AC2.

**Ruling: render a lane for every milestone in the payload** (filtered by the active major tab),
not only those with issues. Empty lanes render collapsed, carrying their status / GA / release
chips and `0` — which is *correct* for a live empty milestone and never shown for a done one (§3).

Ordering: keep `groupByMilestone`'s existing first-seen order for lanes that have issues, then
**append** milestone-only lanes in payload order, `(none)` last. Judgment call: append-only is a
minimal diff and in practice puts live milestones above finished ones; a new sort comparator over
version-shaped ids is maintenance for a marginal gain. Revisit if it reads wrong.

**List view** loses the strip too. Compensate: the milestone cell in a list row becomes a link
that opens the same milestone card. Otherwise milestone status/release state is Kanban-only.

## 3. PT-43 — progress that survives archival, with zero archive reads

The count rule is decided **by the milestone's own status**, not by counting `archive/`:

| Milestone status | Lane header + card shows |
|---|---|
| `done` / `cancelled` | **`✓ Done · v0.4.0 released`** — completion + release state. **No ratio at all.** |
| anything else | `n/m done` over the issues in the payload |

- The `0/0` bug disappears because a shipped milestone never displays a ratio (AC2).
- The mixed case (AC3) is correct **by construction, not by computation**: PT-39 §5 makes
  `cairn archive` refuse to sweep issues out from under a non-done milestone, and PT-39 §3.2 lints
  the hand-`git mv` bypass. A non-done milestone's live issues therefore *are* all its issues.
- ⇒ the default board never opens `archive/`. That is what keeps PT-42's 83 ms off the default path.
- With Show-archived **on**, archived issues are ordinary members of `issues` (PT-42 §1/§4), so the
  ratio of a non-done milestone simply includes them. One counting path, three issues.

## 4. Release state — source of truth: **git tags, read by the server**

`released` is a new field on each milestone record: `true` / `false` / `null`.

- `null` when `target_tag` is null (definition milestones make no claim), or when git is
  unavailable / this isn't a repo. Client renders **no chip** for `null`.
- `false` → chip `unreleased`. `true` → chip `v0.6.2 released`.
- Server reads the tag set **once per payload build** via
  `git -C <root data dir> for-each-ref --format=%(refname:short) refs/tags` — measured **8 ms**.
  The engine already shells out to git (`_git_mv_or_rename`) and this reads **no file outside
  `process/cairn/`**, so the spin-off constraint holds.
- Failure posture: git missing / not a repo ⇒ all `released: null` + one stderr line. Never crash
  (the `_git_mv_or_rename` precedent).
- **One producer:** the server ships the predicate, not the tag list. Shipping the tag list and
  re-deriving per milestone in JS would be the duplicated-expression class.

**Rejected:**
- **`STATE.md` Releases table** — disqualified outright: `process/STATE.md` is outside
  `process/cairn/`, and "the engine touches no project file outside `process/cairn/`" is the
  constraint that makes `git subtree split` work.
- **GitHub API** — network, auth, and it breaks the offline board. Out, as PT-44 assumed.
- **A `released:` field on the milestone file** — duplicates a fact git already holds; drifts.

**Two states only, not three.** A local tag cannot distinguish "published" from "draft release",
and a local tag may not be pushed. That nuance stays in STATE.md's Releases table, which is where
a human writes it. Do not fake a third state.

**Staleness, stated:** tags are **not** folded into the ETag (that would add 8 ms to every 304
poll). A bare `git tag` with no file change leaves the chip stale until the next file change — in
practice `/merge-pr` writes issue files in the same operation it tags. Mitigation:
**pull-to-refresh clears `state.etag`** so an explicit user refresh is a real refetch (also
required by PT-42 §2, so it is one rule, not a special case).

## 5. The card: drawer reuse, read-only

- **Reuse the existing drawer + overlay**, new render function `renderRecordDrawer(record)`.
  A second panel would duplicate overlay/close/escape/markdown plumbing for no gain.
- **Generalize `state.openIssueId` → `state.openRecord = {kind, id}`** (`kind`:
  `issue` | `milestone` | `major`), and the render-race guard compares **both**. Do **not** add a
  parallel `state.openMilestoneId` — two encodings of "what is open" is the PT-29 polarity trap.
- Card contents: id, name, kind, major, status pill, `target_tag` + release state, GA chip,
  progress per §3, `body` via the existing `renderMarkdown` (marked + DOMPurify, unchanged), and
  the file path line (same as the issue drawer's `path`).
- **Read-only in 0.7.0.** Editing would need a mutation endpoint for a second schema, `seen`
  tokens for records that have none, and an interaction with archive semantics — all for a field a
  human changes a handful of times per release. The card names the command instead:
  `cairn set PT-0.7.0 status=done` (PT-39 §6). Reversible later; not free now.

## 6. Majors on the tab bar

- Each major tab gets a **status dot** (PT-40 AC3), colour from the same `RECORD_STATUS_LABELS`
  vocabulary, with the label in `title`/`aria-label` (no room for text).
- Opening the major card: a **sibling** `▸` button appended after the tab inside `.majors-tabs`,
  `aria-label="Open PT-V1"`. Sibling, not nested — a `<button>` inside a `<button>` is invalid
  HTML. Clicking the tab itself keeps meaning "filter", unchanged.
- Multi-root: tabs dedupe majors by bare id across repos (PT-3). When >1 record shares an id, the
  card renders one repo-qualified section per record. Rare; do not special-case further.

## 7. Removals (AC1 — the strip is gone)

`#milestone-progress` out of `board.html`, its block out of `renderHeader()`, its CSS out of
`board.css`. The strip's filter `progress.total === 0 && ms.kind !== "product"` goes with it — §2's
"a lane for every milestone" replaces it. `milestoneProgress` (board-logic.js) **stays** and gains
the §3 status branch; it is now the lane header's and the card's single producer.
