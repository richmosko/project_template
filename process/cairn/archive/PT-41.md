# PT-41 — major naming semantics: options

**Mosko decides.** My recommendation is at the bottom; the options are laid out so it can be
overridden on its merits.

## The situation

`majors/PT-V1.md` is the sole major; every milestone under it tags `0.x`. Lint shape today is
`^<P>-V\d+$`. Nothing in this repo carries `ga: true` — the GA milestone for `PT-V1` is
**undesignated**, and nothing lints that (see "Findings" below).

## Option A — keep `PT-V1`, make the meaning explicit

*"`V<n>` names the line by the major version it culminates in. A line is `V1` from its first 0.x
commit."*

| | |
|---|---|
| Migration | **None.** |
| Lint change | **None** — `^<P>-V\d+$` already correct. |
| N.0.0-GA convention | **Unchanged and coherent** — `V1` is *defined* as the line whose GA milestone tags `1.0.0`; the 0.x milestones are its pre-GA scope chunks. |
| Doc work | One paragraph in TRACKER.md → Major file + WORKFLOW.md → Versioning scheme. |
| Cost | A newcomer reads "V1" as "we're at version 1". The disambiguation is one sentence deep — and PT-40 gives it a *visible* home: the major card can state "GA target: v1.0.0 · GA milestone: PT-1.0 (undesignated)". |
| Id stability | Preserved. Ids never change; git history of the file stays intact. |

## Option B — `PT-V0` now, rename to `PT-V1` at GA

*The major id tracks the current MAJOR digit.*

| | |
|---|---|
| Migration | **Now** (`PT-V1`→`PT-V0` + retarget every milestone's `major:`), **and again at GA** (`PT-V0`→`PT-V1`). |
| Lint change | None for `PT-V0` (matches the existing regex). The dotted variant `PT-V0.x` does **not** match and would need one — see Option C. |
| N.0.0-GA convention | **Actively contradicted**: the GA milestone of a major named `V0` tags `1.0.0`. |
| Cost | A rename at the moment of the biggest release in a line's life, on every downstream repo. Destroys the "ids are stable" property. Makes concurrent majors incoherent (`V0` is a *phase*, `V2` is a *line*). |
| Upside | "V0" is honestly pre-1.0 with no explanatory sentence. |

## Option C — `PT-V1.x`

| | |
|---|---|
| Migration | Rename + retarget every `major:` ref. Named migration required (`cairn migrate major-ids`). |
| Lint change | Regex becomes `^<P>-V\d+(\.x)?$`. A literal `x` inside an id shape is a wildcard-in-a-name; `PT-V1.x` also reads adjacent to development-milestone ids (`PT-1.0`), weakening the "shapes are separable at a glance" property PT-28's prefixing was for. |
| N.0.0-GA convention | Survives, but "V1.x" implies the line contains only 1.x releases — it also contains every 0.x release. Arguably *less* accurate than `PT-V1`. |
| Upside | Reads as a version *range* rather than a version. |

## Recommendation: **Option A**

Zero migration, zero lint change, and it fixes the confusion where it actually bites — the spec
and the board — rather than by renaming an id whose stability is a feature. Option B pays a
migration twice to buy honesty that Option A buys with one sentence, and it breaks the N.0.0-GA
convention at the same time. Option C pays a migration once for a name that is arguably less
accurate.

**If A is chosen, ship these two riders with it** (they are the real fix, and both are cheap):

1. **Designate the GA milestone.** Create `milestones/PT-1.0.md`, `kind: product`,
   `target_tag: v1.0.0`, `ga: true`. Today no milestone in this repo carries `ga: true`, so the
   documented "exactly one per major" convention has no instance to point at.
2. **Lint the convention** (`check_repo`): error on **more than one** `ga: true` milestone per
   major; error when a `ga: true` milestone's `target_tag` is not `v<N>.0.0` for its major's `N`.
   Do **not** error on zero — a young major legitimately hasn't designated GA yet. This binds
   "V1 means the line that culminates in v1.0.0" to the data instead of to prose, which is the
   only durable answer to "the name is misleading".

**Named migration needed?** A: no. B and C: yes — `cairn migrate major-ids`, phase-1 keyed on
filename stem, phase-2 rewriting `major:` on every milestone (including `archive/milestones/`),
per PT-28's idempotency/crash-recovery shape. B needs it a second time at GA.

## Findings surfaced while ruling (independent of the option chosen)

- No `ga: true` milestone exists in this repo. The convention is currently unlinted and
  uninstantiated.
- `milestones/PT-0.7.0.md` is named with three version digits while TRACKER.md maps a milestone to
  the `MINOR` digit (`PT-0.6`, `PT-0.5`). The lint accepts both shapes; the convention prefers
  two. Cosmetic, but the roadmap now reads with one odd entry. Worth a one-line ruling from
  Mosko: normalise going forward, or drop the preference from TRACKER.md.
