2. Design System

The single source of truth for the visual language. The written spec lives alongside this doc; the machine-readable system lives in the two CSS files that frontend-lead consumes directly.

  • design-system-spec.md — the written spec (token rationale, component inventory, usage rules)
  • tokens.css — design tokens as CSS custom properties
  • screen.css — component & screen styles built on the tokens

Figma stays the high-fidelity design tool (via the ux-designer's Figma skills); docs/DESIGN/ is the in-repo, code-level home that ships with the project and is the contract for implementation.

10.1 FAQs

Q: How do I add review comments to this design doc?
A: Same as the other docs. Hand-edit docs/DESIGN/comments.md with ## §<section-id> blocks pointing at a section's id (e.g. tokens, flows), or run /serve-docs DESIGN and use the inline + Comment widget. Then run /refine-doc DESIGN to have the changes applied and the addressed comments removed. The sidecar is gitignored; resolutions land via PR. See process/WORKFLOW.md → Doc review loop.
Q: Why is the design system in docs/DESIGN/ and not in the app's source?
A: It's the design deliverable — the contract. During Implement, frontend-lead imports or derives the app's real stylesheets from tokens.css / screen.css. Keeping the canonical system here keeps it reviewable as a doc and decoupled from any one app's build layout.
